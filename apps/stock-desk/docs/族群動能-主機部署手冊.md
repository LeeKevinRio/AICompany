# 族群動能功能：主機部署手冊

適用對象：CEO（Windows PowerShell）。適用範圍：僅 `product/stock-desk` 分支的
族群動能功能（ADR-0012）。本手冊只補充 ADR-0012 C-52 裁定之後，「判定程序與
API 程序在主機上從同一個 git checkout 直接執行」這個部署形態需要的操作步驟；
既有的 Docker Compose 快速啟動（前端、一般資料層）仍照 `apps/stock-desk/README.md`
的說明，本手冊不重複。

> 為什麼不能沿用 `docker compose up` 來跑判定：見文末「為什麼不能用 compose
> image 做判定」一節，先讀過再往下操作，會比較清楚每一步在防什麼。

## 0. 前置需求

### 0.1 git、uv 版本

**本項未在 CEO 本機實測，以下為裝機前必查證項目**（devops-sre 職責，見公司章程
§「查證依賴的當下 stable 版本」）：

- 本次撰寫手冊時，devops-sre 只能在本沙盒環境確認到 `git 2.43.0`、`uv 0.8.17`
  可正常運作（`uv sync --frozen` 對本專案 `uv.lock` 成功）；**本沙盒沒有對外
  網路，無法查到 git-scm.com / astral.sh 當下真正的最新穩定版**，上面兩個版號
  只能當作「已知可用的下限」，不是「當下 stable」。
- CEO 部署前請在自己機器上查證並安裝當下穩定版：
  - git：<https://git-scm.com/download/win>，或 `winget install --id Git.Git -e`。
  - uv：<https://docs.astral.sh/uv/getting-started/installation/>，或
    `winget install --id=astral-sh.uv -e`（`uv` 本身可以再用
    `uv python install 3.12` 幫忙裝好 Python 3.12，不需要另外手動裝 Python）。
  - 裝完後執行 `git --version`、`uv --version`，把實際版號記回本檔案這一節
    （比照 `apps/stock-desk/README.md`「已查證版本」表的作法）。
- Python 版本需求：`>=3.12`（`apps/stock-desk/backend/pyproject.toml`
  `requires-python`）；`uv sync` 會依 `uv.lock` 鎖定所有 Python 套件版本，
  不吃系統既有的套件版本。

### 0.2 `.env`：放哪、有哪些變數（只列名稱，不寫真值）

本部署形態下，程式**不會**自動讀取 `.env` 檔（`app/` 底下沒有 `dotenv` /
`load_dotenv`；`.env` 的自動載入只存在於 `docker compose` 的 `env_file:`
設定，主機直跑不吃這個檔）。因此請把祕密與設定值放進：

- `apps/stock-desk/backend/.env`（沿用既有 `.gitignore` 規則，此檔案本來就不
  會被追蹤進版控），只當作「你自己記值的地方」；
- 實際生效要靠 PowerShell 設環境變數。可以每次開機用下面這段小片段把
  `.env` 的內容載入成當前 session 的環境變數（`.env` 格式維持既有慣例的
  `KEY=VALUE`，一行一個，`#` 開頭當註解）：

  ```powershell
  cd C:\stock-desk\apps\stock-desk\backend
  Get-Content .env | Where-Object { $_ -match '=' -and $_ -notmatch '^\s*#' } | ForEach-Object {
      $name, $value = $_ -split '=', 2
      [System.Environment]::SetEnvironmentVariable($name.Trim(), $value.Trim(), 'Process')
  }
  ```

  這只影響目前這個 PowerShell process；API 與 scheduler 各自的視窗都要各跑
  一次（或改用 `'User'`／`'Machine'` scope 永久設定，兩個 service 就不用每次
  重覆做，但務必記得 `.env` 內容一有變動要重新設一次）。

**只列變數名稱、不得填真值**（真值只存在 CEO 自己的 `.env`，絕不進 repo、絕不
寫進 commit）：

| 變數 | 用途 | 是否必要 |
| --- | --- | --- |
| `FINMIND_API_TOKEN` | FinMind 備援來源；暖身回補（見下）一定要有效 token 才跑得動 | 暖身回補時必要；一般營運時可選（未設定則 FinMind 明確回 `unavailable`） |
| `STOCK_DESK_DB_PATH` | 主 DB（board、`sector_rank_stats`、`sector_gate_checks`、`sector_gate_approvals`、`sector_method_registry`，加上既有持倉／設定／警示） | 選用，建議顯式指定，見 0.3 |
| `STOCK_DESK_MARKET_DB_PATH` | 市場 DB（`pit_snapshot_runs`、`market_daily_bars`、`pit_*_rows`、`market_backfill_progress`，ADR-0012 D-2） | 選用，建議顯式指定 |
| `STOCK_DESK_RESEARCH_DB_PATH` | 研究 DB（偏誤研究，ADR-0012 D-14；API 永不開啟） | 選用 |
| `ALERT_DISCORD_WEBHOOK_URL` / `ALERT_TELEGRAM_BOT_TOKEN` / `ALERT_TELEGRAM_CHAT_ID` | 既有警示推播（與族群動能無關，沿用 `backend/README.md`） | 選用 |
| `SCHEDULER_DATA_INTERVAL_MINUTES` / `SCHEDULER_ALERT_INTERVAL_MINUTES` | 既有排程間隔（與族群動能無關） | 選用 |

**絕不使用環境變數提供的欄位**（ADR-0012 C-52 明文禁止，`sector_attestation.py`／
`sector_runtime.py` 也用 AST 測試 T-36 擋住）：`running_commit`、
`ci_passed_commit`、`suite_hash` 一律只能來自 `git rev-parse HEAD`、
`app/_build/ci_attestation.json`、磁碟上的測試檔，**不要**試圖用環境變數或
設定檔覆寫這三個值——這麼做不會被系統擋下（唯讀邊界目前只靠自律與審查），
但一旦做了就是違反 C-52 的規範性要求。

### 0.3 三個 DB 檔路徑

建議顯式指定三個路徑（不吃預設值），這樣 API、scheduler 兩個 process 保證看
到同一組檔案，也方便備份腳本知道要備份哪裡：

```powershell
$env:STOCK_DESK_DB_PATH          = "C:\stock-desk\data\stock-desk.db"
$env:STOCK_DESK_MARKET_DB_PATH   = "C:\stock-desk\data\stock-desk-market.db"
$env:STOCK_DESK_RESEARCH_DB_PATH = "C:\stock-desk\data\stock-desk-research.db"
```

三者預設值分別是 `./data/stock-desk.db`、`./data/stock-desk-market.db`、
`./data/stock-desk-research.db`（相對於執行時的工作目錄）；用相對路徑時務必
確保 API 與 scheduler 兩個視窗的工作目錄一致，否則會出現「排程寫的資料 API
讀不到」的既有已知坑（`backend/README.md`「資料持久化」一節同樣的教訓，只是
這次是路徑而不是 volume）。

## 1. 首次部署

以下全部在 `git bash` 或 PowerShell 皆可；標了 PowerShell 語法者以 CEO 慣用
的 PowerShell 為準。

```powershell
# 1) clone 並切到 product/stock-desk（若已經 clone 過，改用 git fetch + checkout）
cd C:\stock-desk
git clone <repo-url> .
git checkout product/stock-desk

# 2) 安裝依賴（--frozen：完全依 uv.lock，不重新解析版本，見 ADR-0012 C-52
#    "依賴不受 commit 綁定，部署時要 uv sync --frozen"）
cd apps\stock-desk\backend
uv sync --frozen

# 3) 載入環境變數（見 0.2、0.3）
Get-Content .env | Where-Object { $_ -match '=' -and $_ -notmatch '^\s*#' } | ForEach-Object {
    $name, $value = $_ -split '=', 2
    [System.Environment]::SetEnvironmentVariable($name.Trim(), $value.Trim(), 'Process')
}

# 4) 產生 NE-7 build attestation ——工作樹必須乾淨（git status --porcelain 為空）
#    才會成功；這是 C-36/C-52 機制的第一步，見下方「為什麼不能用 compose
#    image 做判定」。首次 clone 剛切出來的分支通常就是乾淨的。
git status --porcelain   # 確認輸出為空；不是空的話，判定會恆為 NE-7
uv run python scripts\attest_sector_gate.py
```

第 4 步成功會印出 `attested ci_passed_commit=<commit> suite_hash=<hash>`，並在
`apps\stock-desk\backend\app\_build\ci_attestation.json` 寫入一個檔案（此檔
已列入 `.gitignore`，不會被追蹤，也不需要備份——它只對「當下這個 commit、
當下這個工作樹」有意義，換 commit 就要重跑）。失敗（exit code 1 或 2）時**不會**
留下舊檔，此時所有判定都會是 NE-7，屬 fail-closed，先照印出的訊息排除問題
（通常是工作樹不乾淨，或 NE-7 測試集合本身沒過）再重跑。

```powershell
# 5) 啟動 API（開一個 PowerShell 視窗，或用 Start-Process 背景執行）
cd apps\stock-desk\backend
# First deployment only: *>> does not create missing folders
New-Item -ItemType Directory -Force -Path ..\..\..\logs | Out-Null
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 *>> ..\..\..\logs\api.log

# 6) 啟動 scheduler（另開一個 PowerShell 視窗；務必也載入同一份環境變數）
cd apps\stock-desk\backend
uv run python -m app.scheduler *>> ..\..\..\logs\scheduler.log
```

兩個 process 都要從**同一個 git checkout**（同一個 `apps/stock-desk/backend`
目錄）啟動——這正是 C-52 K1 的字面要求，不是巧合。`*>> logs\...` 把
stdout/stderr 一起導向檔案，方便後面「監控與告警」一節做持續檢查；也可以用
`Start-Transcript`或既有的 process 監督工具（NSSM、工作排程器）包起來讓它們
開機自動啟動，本手冊不強制指定作法，只要求「同一個 checkout、環境變數一致、
啟動後兩者都在跑」。

啟動後 `scheduler.py` 會照 D-5 的設計，兩個 cron job（`pit_snapshot_capture`、
`sector_board_refresh`）**啟動時各補跑一次**，所以第一次啟動幾秒內日誌就會
看到一次 capture 與一次 refresh 的結果，不用等到下一個排程時間點。

健康檢查：`GET http://localhost:8000/health` 應回 200；
`GET http://localhost:8000/api/sectors/momentum?market=TW` 在累積樣本數不足
150 之前會合理地回 `gate_status: "not_evaluated"`（`accumulating` 或
`pit_history_missing`，視有沒有先做暖身回補而定），這是預期行為，不是故障。

## 2. 暖身回補（D0 前，只能執行一次性）

**只能在 D0 之前做**：D0 是「四種快照第一次全部 `ok` 的交易日」，一旦過了
D0，`--warmup` 會直接拒絕執行（`WarmupAfterD0Error`，exit code 1）。如果還
沒開始每日常態擷取（`pit_snapshot_capture` 排程），現在就是做暖身的時機。

```powershell
cd apps\stock-desk\backend
uv run python -m app.services.pit_snapshot --warmup --since 2026-06-01
```

- `--since` 是 ISO 日期，且暖身要求至少 D0 前 80 個交易日（60 天上市天數 +
  20 天流動性窗，ADR-0012 D-3），日期抓太晚可能導致覆蓋不足，抓太早只是多
  花一點時間、不影響正確性。
- 需要有效的 `FINMIND_API_TOKEN`（見 0.2）；沒有 token 該檔會逐一失敗並在
  終端列出。
- **以 symbol 為最小重試單位**，checkpoint 記在市場 DB 的
  `market_backfill_progress`：中途中斷（斷線、Ctrl-C）重跑同一條指令，已完成
  的 symbol 會顯示 `already done`，不會重複打 API、也不會重複寫入。
- 這是**一次性**操作：正常情況下只在建置這台主機的當下跑一次。D0 之後漏抓
  的日子依 D-2「不回填」原則，就是沿用前一份，**不要**事後再跑 `--warmup`
  想要補洞——程式本身就會拒絕，這是刻意設計，不是限制不足。
- 節流沿用 FinMind 0.3 秒／請求；1,000＋檔股票跑完抓取本身需要一段時間
  （抓取本身，不含限流等待，約數十分鐘到數小時視標的數與網路狀況），請預留
  時間、不要在跑到一半時關閉終端機。

暖身完成後，正常交易日的排程擷取（`pit_snapshot_capture`）與判定
（`sector_board_refresh`）會自然接續下去，不需要額外操作。

## 3. 每次更新（部署新版本 commit）

```powershell
cd apps\stock-desk\backend

# 1) 拉新版本
git pull

# 2) 依新的 uv.lock 重新鎖定依賴（C-52："依賴不受 commit 綁定，部署時要
#    uv sync --frozen"）
uv sync --frozen

# 3) 確認工作樹乾淨、重新產生 attestation（新 commit 一定要重新跑這步，
#    舊 commit 的 attestation 對新 commit 無效——ci_passed_commit 綁定的就是
#    當時的 git rev-parse HEAD）
git status --porcelain
uv run python scripts\attest_sector_gate.py

# 4) 同時重啟兩個 process（先後順序不重要，重點是儘快讓兩邊都切到新 commit）
#    停掉舊的 uvicorn / scheduler 視窗（Ctrl-C，或依你自己的程序監督工具），
#    再依「首次部署」步驟 5、6 重新啟動。
```

**部署窗口內的 `commit_mismatch` 屬預期行為，不必驚慌、也不用告警**：API
process 讀到的 `ci_passed_commit` 與 scheduler 尚未用新 commit 重新判定前的
`stats.running_commit` 短暫不一致時，讀取端會判 NE-7，直到 scheduler 用新
commit 重新跑過一次判定為止（ADR-0012 D-8「部署期間的預期行為」）。因為
scheduler 啟動時會自動補跑一次 `sector_board_refresh`（D-5），這個窗口通常
只有「重啟 scheduler 到它跑完第一次補跑」這幾秒到幾分鐘，**同時重啟兩個
process**（而不是隔很久才重啟另一個）是縮短這個窗口的關鍵動作。

## 4. 備份

三個 DB 的重要性並不對等，備份策略也不同：

### 4.1 市場 DB（`STOCK_DESK_MARKET_DB_PATH`）—— 最高等級，務必備份

只增不刪（D-2）、**完全無法重建**：`recorded_at`、每日上市名單、分類快照、
除權息公告都是「當下才寫得下去」的前瞻紀錄，遺失等於前瞻累積歸零，之前累積
的樣本數全部作廢，要重新等 3 年以上才能再次判定。備份頻率至少比照每日擷取
節奏（例如每天收盤擷取完成後備份一次），並保留多個歷史版本（不要只覆蓋同一
份備份檔——還原時若不小心用到損毀的最新一份，還有前一份可退）。

**還原時不得重編 `run_id`**（D-2 規範性要求；來源指紋 C-50 依賴這個性質）：
還原之後若對 `market_daily_bars` / `pit_snapshot_runs` 之類的表重新整理、
重建、或用非官方工具「壓縮」過，只要 `run_id` 的相對順序或數值被改動，所有
既有 `sector_rank_stats` 的來源指紋（`source_run_min`／`source_run_max`／
`source_digest`）就會全部核對失敗，讀取端會整批拒收（NE-6, fail-closed）。
用 `.backup`（見下）或直接複製檔案是安全的；**不要**用會重建 rowid／重新
`VACUUM` 成新檔後再手動搬資料的方式還原。

### 4.2 主 DB（`STOCK_DESK_DB_PATH`）—— 也要備份，重要程度僅次於市場 DB

這裡的措辭需要比「可重建可不備份」更精確一點：主 DB 裡的
`sector_rank_stats`／`sector_gate_checks` 理論上**可以**在市場 DB 還在的前提
下，靠重放 `sector_eval` 的純函式重新算出來；但同一顆檔案還裝著：

- 使用者真實持倉、風險設定、警示規則（族群動能之外，既有功能就已經在用，
  完全不可重建）；
- `sector_gate_approvals`（人工書面核准紀錄：CEO／dev-lead 的 `--operator`、
  `--reviewer`、`--review-doc` 與 git blob hash）——這是「人做過的判斷」，
  不是程式可以重算出來的東西，遺失了核准紀錄，即使統計數字能重算，也拿不
  回「當初是誰、依據哪份書面文件核准轉態」這件事；
- `sector_method_registry`（`accumulation_start`＝D0、`m` 計數的持久化）——
  雖然 D0 理論上可從市場 DB 反推，但 `counts_toward_m` 的歷史軌跡是逐次寫入
  累積的，重建成本高且容易出錯。

因此主 DB **建議一併備份**，優先度僅次於市場 DB；真的因故沒有主 DB 備份、
只剩市場 DB 時，至少統計數字可以重算，但持倉資料與核准紀錄回不來。

### 4.3 研究 DB（`STOCK_DESK_RESEARCH_DB_PATH`）—— 可不備份

內容全部可由 `app/research/sector_biased/` 對市場 DB 重新執行分析重新產生
（只要市場 DB 還在），且明文標示「含已知偏誤，不得上畫面」，不影響任何正式
判定或 API 回應（D-14：API 永不開啟此檔）。遺失時重新跑一次研究分析即可，
可以不備份，或用最低優先度、有空再備份即可。

### 4.4 WAL 模式下的安全備份做法

三顆 DB 都是 SQLite WAL 模式，直接複製 `.db` 檔案**不安全**（可能漏掉還在
WAL 檔裡、尚未 checkpoint 的資料）。用下列任一種線上備份方式，兩者都不需要
停機、不需要先停掉 API／scheduler：

**方式一：`sqlite3` CLI 的 `.backup`**（若 CEO 機器上有裝 `sqlite3.exe`）：

```powershell
# First backup only: create the target folder
New-Item -ItemType Directory -Force -Path C:\stock-desk\backups | Out-Null
sqlite3 C:\stock-desk\data\stock-desk-market.db ".backup 'C:\stock-desk\backups\stock-desk-market-$(Get-Date -Format yyyyMMdd-HHmmss).db'"
```

**方式二：Python 的線上備份 API（`VACUUM INTO` 或 `sqlite3.Connection.backup`）**——
專案已經依賴 Python，不需要額外安裝 `sqlite3.exe`，推薦用這個：

```powershell
# First backup only: create the target folder
New-Item -ItemType Directory -Force -Path C:\stock-desk\backups | Out-Null
cd apps\stock-desk\backend
$stamp = Get-Date -Format yyyyMMdd-HHmmss
uv run python -c "import sqlite3,sys; src=sqlite3.connect(sys.argv[1]); src.execute('VACUUM INTO ?', (sys.argv[2],)); src.close()" `
  "C:\stock-desk\data\stock-desk-market.db" `
  "C:\stock-desk\backups\stock-desk-market-$stamp.db"
```

對三個 DB 各跑一次（依 4.1～4.3 的優先度決定頻率）。`VACUUM INTO` 對來源
資料庫是唯讀操作，即使另一個 process 正在寫入也能拿到一致的快照
（SQLite WAL 的既有保證）；備份出來的檔案本身不是 WAL 模式的一部分、不含
`-wal`／`-shm` 邊車檔，可以直接當一般檔案搬動、封存。

## 5. 監控與告警

`scheduler.py` 對每次 `sector_board_refresh` 都會印一行 INFO log（見
`app/scheduler.py::refresh_sector_board`）：

```
sector board refresh: session=<日期> board=<id或None> stats=<run_id或None> notes=<逗號分隔>
```

`notes` 出現 `attestation:<problem1>,<problem2>,...` 時，`<problemN>` 只會是
以下五種之一（`app/services/sector_attestation.py`）：

| 問題碼 | 意思 | 告警規則 |
| --- | --- | --- |
| `commit_mismatch` | API 與 scheduler 切換到新 commit 的時間點不同 | **部署窗口內出現屬預期，不告警**；同一個 commit 已經穩定運作一段時間（例如超過一次排程週期，約 2 小時）後仍持續出現才要當異常處理 |
| `git_unreadable` | 讀不到 `git rev-parse HEAD` 或 `git status`（可能是這台主機根本不是 git checkout，或 `git` 不在 PATH） | **持續出現即告警**——這代表整個 C-52 部署形態已經失效 |
| `attestation_missing` | 讀不到 `app/_build/ci_attestation.json` | **持續出現即告警**——通常代表忘記在部署時跑 `attest_sector_gate.py`，或跑了但失敗 |
| `dirty_worktree` | 工作樹不乾淨 | **持續出現即告警**——正常部署流程裡工作樹應該一路乾淨；若有人手動在主機上改了檔案，要先查清楚改了什麼 |
| `suite_hash_mismatch` | NE-7 測試檔內容與 attestation 記錄的不符 | **持續出現即告警**——通常代表 `git pull` 之後忘記重跑 `attest_sector_gate.py`，或測試檔案被部署流程之外的方式改動過 |

**建議的檢查方式**（無需額外安裝監控系統，先用最土的方式盯住）：定期（例如
每小時）掃描 `logs\scheduler.log` 最近幾行，若同一個問題碼連續出現超過一次
排程週期（兩個 job 都是平日約每 2 小時一次：`pit_snapshot_capture` 17:30／19:30／21:30，
`sector_board_refresh` 17:45／19:45／21:45，見 `app/scheduler.py`），就視為持續發生：

```powershell
Select-String -Path C:\stock-desk\logs\scheduler.log -Pattern 'attestation:' | Select-Object -Last 10
```

出現 `attestation:` 但**不含** `commit_mismatch` 以外的任何問題碼、且只出現
一次，先觀察；出現 `git_unreadable`／`attestation_missing`／`dirty_worktree`／
`suite_hash_mismatch` 中任何一個，或 `commit_mismatch` 持續超過一次排程週期
未消失，就要介入排查（依上表「意思」欄位的線索去查）。

**scheduler 常駐檢查**（D-2 缺日沿用規則的營運面提醒）：

- 漏抓的日子**不回填**——這是設計，不是 bug。若某天 `pit_snapshot_capture`
  三個時段都失敗（例如主機當天沒開機、或整天斷網），當天就是沒有 `ok` run，
  後續讀取端會沿用最近一份可見的 run（`carried_forward=true`）。
- **任一種快照連續超過 5 個交易日沒有新的 `ok` run，受影響的樣本視為無效
  （不計入 N）**——這代表主機若計畫性離線（例如維護、搬遷），務必控制在 5
  個交易日以內恢復，否則會實質拉長「累積滿 150 個樣本」需要的時間，且已經
  累積的部分樣本可能因此作廢。
- 沒有自動告警機制會替你算「連續缺幾天」——目前只能靠人工檢查
  `logs\scheduler.log` 是否每個交易日都有 `pit_snapshot_capture` 的
  成功紀錄；若要自動化，可以另外寫一支掃描腳本比對 `pit_snapshot_runs` 表
  最近一筆 `ok` 的 `session_date` 與今天的交易日曆差距，此項目本次未實作
  （超出本次任務範圍，日後有需要可另行派工）。

## 6. 為什麼不能用 `docker compose` 的 image 做判定

`ci_passed_commit` 機制（ADR-0012 D-8、C-36）證明「現在跑的程式碼」就是
「NE-7 測試集合跑過並且全綠」的那個 commit，作法是在**同一份磁碟**上比對
三件事：`git rev-parse HEAD`（現在的 commit）、`app/_build/ci_attestation.json`
（build 時寫下的 attestation）、`tests/` 目錄下 NE-7 測試檔案的雜湊值。

`docker build` 出來的 image 裡面：

- **沒有 `.git`**：`Dockerfile` 只 `COPY pyproject.toml uv.lock ./` 和
  `COPY app ./app`，從來沒有把 `.git` 目錄放進 image（也不應該放——`.git`
  可能長達數百 MB，而且放進去也無法回答「這個 image 建置時的工作樹乾不
  乾淨」這件事，因為 image 建置完成後工作樹狀態已經與 image 內容脫鉤）。
- **沒有 `tests/`**：Dockerfile 沒有把測試檔複製進去（本次新增的
  `.dockerignore` 就算不排除也一樣，因為 Dockerfile 本來就沒有 `COPY tests`）。

所以只要是從這個 image 啟動的 container 去跑 `sector_board_refresh`，
`app/services/sector_attestation.py::verify()` 一定會同時回報
`git_unreadable` 與 `suite_hash_mismatch`（讀不到 git，也算不出 NE-7 測試檔
的雜湊），`selfcheck_passed=false`，該次判定的 `not_evaluated_reason` 恆為
`lookahead_tests_failed`（NE-7）。**這是刻意設計的 fail-closed 結果，不是
故障，也不可以透過放寬 C-36（例如允許 image 內建的 commit 字串，或改用
環境變數塞值）來「修好」**——ADR-0012 Options K2（image 內烘入 commit 與
attestation）明文列為未採用，要採用必須另立修訂並經 CEO 核可。

換句話說：**Docker Compose 的 `backend`／`scheduler` 兩個 service 還是可以
繼續照 `apps/stock-desk/README.md` 的說明跑其他既有功能**（持倉、訊號、
建議、警示等，這些都不受 C-52 影響）；但只要牽涉族群動能的判定
（`sector_board_refresh` 這個 job），就必須改成本手冊「首次部署」／
「每次更新」描述的主機直跑形態，兩者目前無法二選一混用同一份判定結果——
在 N 達到 150 之前，用 image 部署對外看到的原因是 NE-2（正在累積），跟主機
直跑沒有明顯差異；N 達到 150 之後，用 image 部署會讓卡片永遠停在
`not_evaluated`（ADR-0012 Consequences 明文提醒的陷阱）。

## 7. P95 量測（T-34，非合併門）

`GET /api/sectors/momentum` 的效能目標是 PRD FR-8「P95 ≤ 2 秒」，且 ADR-0012
C-51 要求這個延遲不隨市場 DB 的 run 數成長（1,000 筆與 100,000 筆 run 應該
測出幾乎一樣的延遲）。這個時間目標**刻意不放進 CI**（T-34：「CI 不做計時
斷言」），因為 CI 的沙盒機器與磁碟不能代表真實部署主機。改用
`apps/stock-desk/scripts/measure_sector_momentum_latency.py`，由 CEO 在正式
部署的主機上、API 已經在跑的狀態下手動執行：

```powershell
cd apps\stock-desk\backend
uv run python ..\scripts\measure_sector_momentum_latency.py `
    --base-url http://127.0.0.1:8000 --requests 50
```

（不需要任何 token——`/api/sectors/momentum` 是無驗證的唯讀端點，D-10。）

輸出範例（數字為示意，非實測）：

```
samples: 50
status codes: {200: 50}
errors: 0
min:    12.3 ms
mean:   18.7 ms
p50:    17.1 ms
p95:    31.4 ms  (budget: 2000 ms, PRD FR-8 / ADR-0012 D-10)
p99:    45.0 ms
max:    52.1 ms
over budget: 0 / 50
RESULT: PASS
```

腳本以 `--budget-seconds`（預設 2.0）為門檻，P95 超過門檻或任何請求出錯時
結束碼為 1（`RESULT: FAIL`），可以接進日後想做的排程健檢或 CEO 手動判讀，但
**不要**把它接進 `pytest` 或 CI workflow——這樣會違反 T-34「非合併門」的
設計，CI 機器的磁碟／CPU 條件無法代表真實部署主機，接進去只會得到一個時好
時壞、與正式環境無關的假訊號。

**本次任務未做的事**：devops-sre 沒有一份真的長到 100,000 個 run 的市場 DB
可以在此環境實測（沙盒內只對空白資料庫跑過腳本，確認腳本本身可用）；C-51「run 數
從 1,000 長到 100,000，API 取回資料量不變」這件事已由 ADR-0012 v9 實作時新增的
T-34 pytest 測試在 CI 涵蓋（`tests/test_sector_source_scale.py`：合成 100,000 個
run 建庫，斷言 SQL 條數、來源驗證恰一條，以及自主 DB 取回的字元數不隨 run 數改變），本腳本量到的
是**真實世界的 wall-clock 秒數**，兩者互補、缺一不可。CEO 本機累積出真實
規模的市場 DB 之後，請照上面指令跑一次，把實測數字回填進本節，取代示意
數字。
