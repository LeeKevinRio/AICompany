# ADR-0013：唯讀邊界執行層的完整性周界與審查分級

- 狀態：accepted（CEO 2026-09-29 核可）。**延伸 ADR-0007，不取代**：ADR-0007 的決策與落地狀態全部維持有效，本 ADR 只補上「執行層本身被改動時，由誰、用什麼流程發現」這一層。
- 日期：2026-09-29
- 決策者：tech-architect（草案）、CEO（2026-09-29 核可）

> 來源標註：本 ADR 的決策內容（D1–D7、Options、Consequences）轉錄自 tech-architect 草案，經 CEO 2026-09-29 核可，由 CEO 辦公室以任務單轉交 tech-writer 落檔。
> 「Context」中標示 `檔案:行號` 的敘述是 tech-writer 另行讀 code 所得，行號為撰寫當下工作目錄的快照（分支 `chore/agent-readonly-hook`，尚未 commit），會隨後續修改漂移，抽驗時請以原文定位。

## Context（背景）

ADR-0007 於 2026-09-28 讓 PreToolUse hook 落地：`.claude/settings.json` 登記 matcher `Write|Edit|Bash`（`.claude/settings.json:28-32`），hook 與 validator 都從 `.claude/lib/agent_policy.py` 取得政策（`READONLY_AGENTS` 在 `.claude/lib/agent_policy.py:102`、`READONLY_BASH_SCOPED_AGENTS` 在 `:117`、`BASH_RULES` 在 `:237`）。
這讓「唯讀角色能做什麼」有了執行層的強制力，但同時產生一個新問題：**執行層本身的檔案沒有任何完整性檢查**。政策檔、hook、設定、validator、CI 設定，以及規範審查流程的文件，都可以被具寫入權的角色修改；一旦被改弱，hook 照新規則放行、CI 照新規則判綠，兩層都不會攔。

qa-reviewer 對 ADR-0007 落地批次的審查中，指出下列缺口：

1. **原本的審查檢查在 hook 生效後失效。** 原檢查是兩道以管線接 `grep` 的指令，只看兩個符號名稱。
   - hook 會依 `|` 等運算子拆成子命令，每個子命令都必須符合 `BASH_RULES` 才放行（拆分運算子見 `.claude/hooks/readonly_guard.py:142-143`，逐一比對見 `:269-279`）；`BASH_RULES` 只有 `git diff` 與兩種 `codex` 形狀（`.claude/lib/agent_policy.py:237-274`），`grep` 不在其中，所以接管線的指令必然被擋。
   - 第二道檢查的 pattern 另含 `(`、`)`，而這兩個字元在 `_DANGEROUS_CHARS` 內，含有即整條阻擋（`.claude/hooks/readonly_guard.py:137`、`:255-259`）。
   - 即使能執行，符號比對也抓不到「集合內新增成員」（見 Options 方案 A）。
2. **周界不只一個檔案。** 只盯 `agent_policy.py` 不夠：
   - hook 以 `sys.path.insert(0, …/lib)` 匯入政策（`.claude/hooks/readonly_guard.py:305`）；依 tech-architect 草案，在 `.claude/lib/` 新增同名 package（`agent_policy/__init__.py`）可以不動原檔就換掉政策。
   - hook 腳本本身 `import json`（`.claude/hooks/readonly_guard.py:111`）；依草案，在 hooks 目錄新增 `json.py` 之類的檔案可以劫持 import。
   - `.github/workflows/validate.yml` 是 hook 測試在 CI 的執行點（`.github/workflows/validate.yml:18-19`，依草案為唯一執行點）。
   - 審查規則本身（skill 與 qa-reviewer 定義檔）若被刪弱，檢查也會悄悄消失。
   - `.claude/settings.local.json` 不進版控（`.gitignore:16`），但一旦被強制加入就會現形。
3. **唯讀角色改名可逃出邊界。** hook 靠 `agent_type` 判斷角色（`.claude/hooks/readonly_guard.py:318`）；validator 逐個 agent 檔檢查，並要求 `name` 與檔名一致（`scripts/validate_agents.py:142`），以檔名判斷是否唯讀（`:170`）。當時沒有任何檢查要求 `READONLY_AGENTS` 的每個成員都有對應檔案，所以把唯讀 agent 改名或刪除後，原名稱不再對應任何被檢查的檔案（此為依上述行為所作的推論；D5 的懸空檢查即為封住此路徑）。
4. **主執行緒死結。** hook 在 `_decide` 內才匯入政策（`.claude/hooks/readonly_guard.py:305-310`），匯入失敗會被 `main()` 的 catch-all 以 exit 2 阻擋（`:370-375`）；而 matcher 對主執行緒同樣生效。修正前的行為是：政策檔損壞時，主執行緒的 Write / Edit / Bash 也被擋，連修復政策檔的動作都做不了（`.claude/lib/agent_policy.py:18-19` 的說明文字亦載明 hook「fails closed」並對「everyone」阻擋；D6 落地後此段說明已與行為不符，待 devops-sre 修正該註解）。

## Options（選項比較）

草案原本只給出「內容」與「結論」兩欄，未逐項拆出優點、缺點、風險；以下依草案原文轉錄，不另行補充。

| 方案 | 內容 | 結論與理由 |
| --- | --- | --- |
| A | 維持符號 grep | **否決**：抓不到集合內新增成員；需要管線，而管線會被 hook 擋 |
| B | 4 條路徑加 `--stat` | 留下 3 個缺口（tech-architect 2026-09-28 評估）：① 未涵蓋整個 `.claude/lib/`，新增同名 package 可不動原檔換掉政策；② 唯讀 agent 改名可完全不碰清單路徑逃出邊界；③ 審查規則本身與 CI（`validate.yml`）被刪弱時無人察覺 |
| C | 9 條路徑、`--name-status`、懸空檢查、canary、三級嚴重度 | **採用** |
| D | C 加 CODEOWNERS 與 branch protection | **採用，CEO 核可**（即本案的最終形態） |
| E | hook 擋所有角色寫入周界 | **否決**：會擋掉正當維護、誤擋面大，且主執行緒仍能繞過 |

## Decision（決策）

採方案 D（含 C 的全部內容）。共七項：

### D1 執行層周界：9 條路徑

1. `.claude/lib/`
2. `.claude/hooks/`
3. `.claude/settings.json`
4. `.claude/settings.local.json`
5. `scripts/validate_agents.py`
6. `.github/workflows/validate.yml`
7. `.claude/skills/code-review-checklist/SKILL.md`
8. `.claude/agents/qa-reviewer.md`
9. `CODEOWNERS`（CEO 辦公室 2026-09-29 補列：D7 的平台層控制以此檔為準，刪弱它等於撤掉 D7；屬收緊性補充）

理由（見 Context 第 2 點）：只列 `agent_policy.py` 不夠，新增同名 package 或劫持 import 都能不動原檔就換掉政策；`validate.yml` 是 hook 測試的 CI 執行點；審查規則被刪弱時檢查會悄悄消失；`settings.local.json` 不進版控，但一旦被強制加入就會現形。

### D2 審查指令

取代原本的兩道管線檢查。hook 生效後 qa-reviewer 不能接管線，原指令必然被擋，所以必須改寫；**公司文件中不得再出現任何接管線的審查指令**。

審查 staged 時：

```bash
git --no-pager diff --staged --name-status -- .claude/lib/ .claude/hooks/ .claude/settings.json .claude/settings.local.json scripts/validate_agents.py .github/workflows/validate.yml .claude/skills/code-review-checklist/SKILL.md .claude/agents/qa-reviewer.md CODEOWNERS
```

審查分支範圍時，把 `--staged` 換成 `<base>...<head>`，放在 `--name-status` 之後、`--` 之前。`<base>`、`<head>` 是佔位符，實際執行要換成真實 ref（指令中出現 `<`、`>` 會被 hook 阻擋，見 `.claude/hooks/readonly_guard.py:137`）。

**只要有輸出，就視為命中周界。** 用 `--name-status` 是因為 `D`（刪除）、`R`（改名）、`A`（新增）可以直接對應嚴重度。

此指令使用的旗標 `--staged`、`--name-status`、`--stat` 都在 git diff 旗標白名單內（`.claude/lib/agent_policy.py:124-141`），`--no-pager` 放在 `git` 與 `diff` 之間是被允許的形狀（`.claude/lib/agent_policy.py:172-179`），`--` 之後的 pathspec 不再檢查旗標（同檔 `:180-186`）。

### D3 liveness canary（每次審查都要先跑）

```bash
git --no-pager diff --stat -- 'readonly-guard-canary()'
```

- **預期**：被 hook 擋下，stderr 以「readonly_guard: 阻擋」開頭。被擋的原因是指令含 `(`、`)`（`.claude/hooks/readonly_guard.py:137`、`:255-259`）；`.claude/hooks/test_readonly_guard.py` 的 `CanaryTests`（`:885-905`）鎖定此行為，若有人從 `_DANGEROUS_CHARS` 移除這兩個字元，該測試會在 CI 轉紅。
- **若正常跑完、沒被擋**：代表本 session 的 hook 沒有生效。可能原因：本機設定、缺 `python3`、該分支沒有 `settings.json`。報告要寫明「hook 未生效」並升級 devops-sre。這屬於環境問題，**不擋受審的 diff，除非該 diff 同時命中周界**。
- canary 本身無害：沒有 hook 時，它只是對一個不存在的 pathspec 做唯讀 diff。此指令在本 ADR 明文列為核准用法，不算越界。
- 補充（tech-writer 讀 code 所得）：若 hook 自身出錯，訊息會以「readonly_guard: fail-closed 阻擋」開頭（`.claude/hooks/readonly_guard.py:372`），與正常阻擋的開頭不同；這種情況指令同樣被擋，表示 hook 有作用但腳本內部有錯誤，建議一併回報 devops-sre。此補充不在草案內，如需納入判準請由 tech-architect 確認。

### D4 嚴重度三級

命中任一級，都要求實作者回答四問：**改了什麼、為何改、有無對應 ADR、屬哪一級以及判定依據**。

**T1：直接升級 tech-architect／CEO，不進退回迴圈；沒有 accepted ADR 不得放行。**

- `READONLY_AGENTS` 或 `READONLY_BASH_SCOPED_AGENTS` 成員異動（加入或移出）。
- 新增 `BashRule` 或新的 declared token。
- hook 被停用、刪除或取消登記。
- `settings.json` 的 hook command 或 matcher 被修改。
- `settings.json` 的 env 新增影響 Python 的變數（`PYTHON*`）。
- `validate.yml` 移除驗證步驟，或讓步驟失敗時不影響結果。
- 唯讀 agent 檔被刪除或改名。

**T2：high → `BLOCKING_ISSUES=true`，退回補依據。** 放行條件：security-engineer 簽核，且 CEO 裁定已記入 ADR 落地狀態。

- 既有規則內的放寬：flag allowlist 新增項目、matcher 形狀放寬。
- `_DANGEROUS_CHARS` 刪減項目。
- 解析邏輯變寬鬆。
- fail-closed 路徑有任何改動。
- 刪除或弱化 deny 類測試。
- `.claude/lib/` 或 `.claude/hooks/` 新增 `.py` 檔或 package。
- 審查檢查本身被刪除或弱化。

**T3：一般規則。** 收緊性異動、純註解或文字修改、新增測試都屬此級。**例外**：收緊後會擋掉公司文件規定的審查指令，至少算 medium，且必須同步修正文件。

**兜底規則：**

- 無法判定屬哪一級 → 以 T2 計。
- 同一個 diff 同時有放寬與收緊 → 依放寬的那一級計。
- 路徑檢查指令本身被擋 → 視同命中 T2。

### D5 validator 新增懸空檢查

`READONLY_AGENTS` 的每個成員都必須有對應的 `.claude/agents/<name>.md`，用來封住「唯讀 agent 改名就能逃出邊界」的路徑。由 devops-sre 實作。

### D6 hook 的主執行緒死結修正

hook 在匯入政策之前，先對「沒有 `agent_type`」的情況（也就是主執行緒）直接放行。這樣政策檔損壞時，**主執行緒仍然能修復政策檔**；subagent 維持 fail-closed。由 devops-sre 實作，屬 T2，需要 security-engineer 簽核。

### D7 平台層控制

CEO 核可 CODEOWNERS 加上 branch protection（周界路徑必須經 code owner 核准）。

**落地狀態：待 devops-sre 查證可行性與設定步驟，並由 CEO 在 GitHub 設定。在 GitHub 端設定完成之前，此項不構成任何控制。**

## Consequences（後果）

**好處**

- qa-reviewer 的審查指令在 hook 生效下可以執行（D2 使用的旗標皆在白名單內，見 D2）。
- 周界異動可以被機械偵測，並依嚴重度分流；T1 不進退回迴圈，避免空轉一輪。
- 唯讀 agent 改名或刪除會被 validator 的懸空檢查擋下（D5）。
- 政策檔損壞時主執行緒不再被卡死（D6）。

**代價**

- 每次審查多兩道指令（canary 與周界檢查）。
- 路徑清單要跟著目錄結構維護。
- **白名單過窄，會誤擋 qa-reviewer 的合法指令**，例如 `git log`、`git -C`。hook 的 docstring 已揭露這一點（`.claude/hooks/readonly_guard.py` 模組說明的最後一段）；要放寬必須另出 ADR，而 `git -C` 建議維持阻擋。

**殘餘風險（不因本決策而淡化）**

- 審查者本身也是 agent。
- 未進版控的本機設定只能被偵測，無法被審查。
- canary 只能證明「本 session、該角色」的 hook 有生效。
- 「新設一個不列入 `READONLY_AGENTS`、實質上卻在做審查的角色」這類角色歸類問題，不在機械檢查範圍內。
- git diff 旗標白名單只和審查它的人一樣完整。
- codex 的形狀比對依賴對 Codex CLI 行為的理解，未來版本可能改變。
- D6 只修正「匯入政策失敗」這條路徑；hook 收到無法解析的 stdin 時，`main()` 仍一律以 exit 2 阻擋（`.claude/hooks/readonly_guard.py:361-375`），此路徑不在 D6 範圍內（tech-writer 讀 code 所得，非草案內容）。

**被此決策約束的事**

- 修改周界內任何檔案，都要走 D4 的分級與四問。
- 放寬 hook 白名單（例如 `git log`）須另出 ADR。
- 周界路徑清單有變更，須以新 ADR 更新本 ADR 的 D1，並同步 `code-review-checklist` skill 與 qa-reviewer 定義檔中的指令。
