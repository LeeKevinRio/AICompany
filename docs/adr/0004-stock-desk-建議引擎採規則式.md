# ADR-0004：stock-desk 建議引擎採規則式，非 ML 黑箱

- 狀態：proposed
- 日期：2026-07-26
- 決策者：tech-architect（草案撰寫中）；尚未經 CEO 核可，故狀態為 proposed
- 適用範圍：僅 `product/stock-desk` 產品線（本 ADR 不存在於 main）
- 相依：ADR-0002（技術棧 + 「建議引擎必須是 YAML 規則式」約束）、ADR-0003（資料源降級鏈、`as_of`/`source` 欄位約定）

---

## Context（背景）

建議引擎是 stock-desk 的決策核心：給定一支標的的市場訊號、持倉狀況、風險預算，輸出可解釋的行動建議（add / hold / reduce / stop_loss / take_profit）。

兩大類技術方案在競爭：

1. **規則式引擎**：規則以 YAML 檔定義，條件由「欄位 + 運算子 + 閾值」組成，逐條求值，規則權重決定結果。
   - 優點：完全可解釋、可 git 版本控制、可 code review、容易稽核。
   - 缺點：規則編寫需手工；規則參數優化成本高；無法學習複雜非線性模式。

2. **機器學習（ML）/ 黑箱模型**：如梯度提升樹、類神經網路，從歷史標籤數據學習。
   - 優點：特徵工程省力；可學習複雜模式；可能性能更高。
   - 缺點：無法解釋為何建議；難以稽核；金融監管紅線；版本管理困難；過擬合風險。

本決策文檔定位架構選擇的理由、替代方案比較、約束條件與後果。

---

## Options（選項比較）

| 方案 | 優點 | 缺點 | 風險 | 適用場景 |
| --- | --- | --- | --- | --- |
| **規則式（YAML）** | 完全可解釋、可追蹤、易於稽核、支援 git 版本控制 | 規則編寫手工、參數調整高成本 | 規則過於保守或過於激進導致低效；規則遺漏導致盲點 | 需要風控審查、內部研究、可解釋性要求高 |
| **梯度提升樹（XGBoost / LightGBM）** | 性能強、無須手工特徵工程、支援特徵重要度 | 無法解釋為何建議；難以稽核；金融紅線 | 「演算法決策」風險；過擬合樣本內；監管不適；用戶信賴度低 | 內部風險評分或預測（不直接推送給用戶） |
| **類神經網路** | 理論上可學最複雜模式 | 完全黑箱、計算成本高、監管最嚴厲 | 同上，加劇 | 完全不適用於直面用戶的決策 |
| **規則式 + ML 混合** | 規則提供基礎框架、ML 微調參數 | 複雜度翻倍、維護成本高 | 兩方面風險共存 | 對規則式不滿意但無預留時間完全遷移時才考慮 |

---

## Decision（決策）

採用**規則式（YAML）引擎**，完全拒絕黑箱模型直接生成建議動作。理由如下：

### 1. 可解釋性（Interpretability）
- 每筆建議卡都列舉「哪些規則命中、各自的權重、反駁點、失效條件」。
- 使用者（特別是投資專業人士）能重現並質疑決策過程。
- 金融產業監管對「自動化決策」要求透明度；黑箱無法滿足。

### 2. 可審查性（Auditability）
- 規則檔案（`app/advice/rules/default.yaml`）進入 git，支援 diff、歷史追蹤、code review。
- 每條規則的文案（名稱、解釋、反駁、失效條件）都被 compliance 掃描（禁用詞檢查）。
- 若發現誤導、過度自信，或違反風控紅線的規則，可快速定位與修正。
- 與梯度提升樹「我們也不知道為什麼會這樣輸出」的局面天壤之別。

### 3. 版本控制與演進
- 規則是文本檔案，每次改進都可 commit 帶說明，記錄「為何加這條規則」。
- 舊規則可備註原因、被標記為 deprecated（而非悄悄刪除）；但當前實作尚未支援此標籤。
- 使用者若不信任新版本，可 checkout 舊版本。
- ML 模型的「版本」是權重二進位檔；改進的來源曖昧不明。

### 4. 法規與風控友善
- 如前述，金融監管對「演算法決策」要求極高。
- 規則式引擎向監管單位解釋時：「這條規則就是當 RSI < 30 且 close > MA60 時發出 add 建議，權重 0.4」。
- ML 模型：「有 2048 個隱藏單元…… 我們也不知道為什麼會這樣」→ 監管拒絕。

### 5. 本產品的實際需求
- Stock Desk 定位「研究與教育工具」，非日內高頻交易。
- 規則在 day-end 或日內固定時間評估，不需極高精度或毫秒級反應。
- 使用者能接受「規則式有時會較保守」，因為他們明白規則的邏輯。
- 黑箱模型「有時準、有時不準」，使用者會掉頭。

## Consequences（後果）

### 好處
1. **完全可解釋**：每筆建議都能追蹤規則源頭。
2. **可版本控制**：規則歷史清晰，支援快速回滾。
3. **風控可讀**：監管審查一眼就懂邏輯。
4. **使用者信賴**：透明度高，理解規則邏輯後更信賴系統。
5. **快速迭代**：新增規則不需重訓練模型；編輯 YAML + code review 即可。
6. **低成本**：規則編寫是領域知識工作，無需大規模標籤數據。

### 代價
1. **規則編寫人力**：需量化策略團隊或領域專家編寫初始規則集。
2. **參數調整成本**：規則中的閾值、權重不能自動最佳化；每次調整需人工測試 + 回測。
3. **性能上限**：規則難以捕捉複雜非線性模式；性能上限可能低於 ML。
4. **覆蓋率風險**：遺漏的交易場景無人設計對應規則時，系統無法自動學習。

### 架構約束
1. **規則 ≠ 建議動作的直接輸出**
   - 規則輸出的是 `action` 欄位：`add` / `hold` / `reduce` / `stop_loss` / `take_profit`。
   - 引擎用 `ACTION_DIRECTION` 對照表推導建議方向（constructive / neutral / defensive），規則作者無法也不需指定。
   - 規則集的多條規則通過投票機制（按方向分組，方向內再按權重排序）得出最終建議。
   - 風險上限與防禦型規則可降級 `add` 為 `hold`（但不能升級 `hold` 為 `add`）。

2. **規則文案必須通過 compliance 掃描**
   - 禁用詞檢查（`app/advice/loader.py` 的 `BANNED_PHRASES`）。
   - 禁用詞（共 10 個）：保證、必漲、必賺、必跌、穩賺、穩賠、一定會、包賺、零風險、無風險。
   - 任何嘗試直接輸出這些詞的規則在 load-time 拒絕。

3. **每條規則必須帶「反駁點」與「失效條件」**
   - 反駁點：該規則的潛在對方（例如「但若 VIX > 30」）。
   - 失效條件：該規則停止適用的場景（例如「若未來三天有重大公告」）。
   - 目的是提醒使用者：這條規則不是萬能；有邊界條件。

4. **無目標價**
   - 規則只輸出「加碼 / 觀望 / 減碼 / 停損 / 獲利」，不輸出「目標價 2,500 元」。
   - 目標價涉及預測，而規則層面無法提供有信心的預測（也就是為什麼禁用「必漲」）。
   - 價格目標由分析師或投資決策留給用戶自行評判。

5. **規則版本化與文案稽核流程**
   - 規則檔案整體有 `version` 字段（semver），每次改進遞增。
   - 新增或修改規則需 pull request；至少經過 qa-reviewer（邏輯檢查） + risk-compliance-officer（文案審查）。
   - 建議卡返回 `rules_version` 欄位讓前端與使用者知曉當前規則版本。

## 棄卻的替代方案及其理由

### 1. 完全 ML 模型
**為何棄卻**：
- 無法解釋決策邏輯 → 監管風險極高。
- 黑箱 → 無法稽核、無法版本控制、使用者不信任。
- 金融界對「演算法決策」有嚴格監管；直接用黑箱輸出買賣建議違反多國規範。

**若堅持 ML 的折衷**：ML 只用於風險度量或概率估計（不直接輸出建議）；規則層仍需人工設計。

### 2. 混合方案（規則 + ML）
**為何棄卻**：
- 複雜度翻倍；維護成本在「規則維護」與「模型迭代」間不斷切換。
- ML 部分仍無法解釋 → 稽核風險未消除，反而更難診斷問題源於規則還是模型。
- 適合長期願景，但眼下沒必要搶先複雜化。

**未來考慮**：若規則式性能持續不滿意，可考慮「規則決定大方向，ML fine-tune 權重」的混合；但需先完整落地規則式。

### 3. 規則 + 機率校準（輸出置信度而非決策）
**為何不選**：
- 本決策堅持「規則直接輸出決策」；機率校準屬工程優化，非架構層的替代方案。
- 但可作為後續優化：在既有規則式基礎上，加入「置信度計算」（confidence = 規則一致性 + 資料完整度）。
- 這正是 stock-desk 當前的做法：卡片上有 confidence 欄，但它反映的是規則證據質量，不是機率。

## 實施指導（逐條，可被 qa-reviewer 與 code review 檢查）

### 規則定義與加載
1. 規則檔案：`app/advice/rules/default.yaml`（YAML 格式）。
2. Schema 驗證：`app/advice/loader.py` 嚴格 validation（`extra="forbid"`），每個欄位檢查。
3. Load-time 檢查：
   - 規則 id 全域唯一。
   - 每條規則的文案通過 `BANNED_PHRASES` 掃描（合規紅線）。
   - condition 中的所有欄位必須在 `KNOWN_FIELDS` 中；不認識的欄位是 load-time 錯誤。
   - 規則檔案帶 `version` 字段（semver）。

### 規則結構
```yaml
version: "1.0.0"
rules:
  - id: "rsi_oversold_with_trend"
    name: "中期趨勢向上時的 RSI 低檔"
    explanation: "14 日 RSI 低於 30 但收盤價仍在 60 日均線之上，屬上升結構中的短期回檔。"
    counterargument: "RSI 低檔可延續數週，若中期趨勢同時轉弱，低檔訊號會連續失效。"
    invalidation: "收盤價跌破 60 日均線，或 RSI 續創新低並伴隨成交量放大的下跌。"
    action: "add"  # add / hold / reduce / stop_loss / take_profit
    weight: 0.4    # 相對優先序
    condition:
      all:
        - field: "rsi14.last"
          op: "lt"
          value: 30.0
        - field: "close"
          op: "gt"
          ref: "ma60.last"  # close > MA(60)
```

### 規則評估流程
1. 展平訊號/風險輸出為「規則詞彙」（`app/advice/context.build_context`）。
   - 例如：`{"rsi14.last": 25.3, "ma20.last": 2500.5, "atr14.last": 50.0, ...}`
2. 逐規則求值（`app/advice/engine.evaluate_rule`）。
   - 若任何輸入欄位缺失（None），規則被 skip；記錄缺失的欄位。
   - 若欄位都存在，evaluate condition tree（支援 and / or 嵌套）。
3. 統計匹配規則的權重、方向（由引擎推導）。
4. 按方向分組聚合權重；**方向間先比累計權重，`DIRECTION_PRECEDENCE` 只在權重相等時作 tie-break**；方向內按權重排序。
5. 決出最終建議（aggregated_action）。
6. 應用保守門檻（conservative gates）：
   - 資料不足（evaluable 規則 < 50%）→ insufficient_data（但防禦型建議即使資料不足仍會輸出）。
   - 建議為 add 但有任何防禦型規則命中 → 降為 hold。
   - add 被風險上限擋下 → hold 且標記擋下的上限編號。

### 卡片內容
返回的 advice card 包含：
- `action`：最終建議（add / hold / reduce / stop_loss / take_profit / insufficient_data）。
- `confidence`：low / medium / high（反映規則一致性 + 資料完整度）。
- `matched_rules`：觸發的規則清單（id、name、action、weight、weight_meaning、explanation）。
- `counterarguments`：獨立去重清單（卡片層級，非規則層級）。
- `invalidation_conditions`：獨立去重清單（卡片層級，非規則層級）。
- `action_weights`：每項建議的累計權重（含未被選中的）。
- `direction_weights`：三個方向的累計權重。
- `has_conflict`：本次是否有反向規則同時命中。
- `limits_check`：五項風險上限的檢查結果。
- `quantity_range`：基於風險上限的可選股數範圍。
- `blocked_action` / `blocked_notices`：若 add 被上限擋下，記錄擋下的上限。
- `downgrade_notices`：若 add 因防禦型規則降為 hold，記錄降級原因。
- `disclaimer`：「本工具為研究與教育用途，非投資建議」。

### 版本與迭代
- 規則檔案版本每次修改遞增（e.g., 1.0.0 → 1.0.1 → 1.1.0）。
- Changelog 記錄每版改動（新增規則、移除、調整權重、調整閾值）。
- 廢棄規則：當前實作尚未支援 deprecated 標籤，刪除時應完整移除或在 changelog 記錄遷移指引。
- 卡片返回的 `rules_version` 欄位讓前端與使用者知曉當前規則版本。

## 規則品質管理

### 規則發展與審查（規劃中）

未來計畫實作以下品質監測機制（目前尚未上線）：

1. **回溯統計**：定期選取 1-2 週歷史，檢查各規則的假陽性率與假陰性率。
2. **使用者反饋**（預留）：首頁與設定頁預留「報告異常」按鈕；使用者標記「此建議不合理」時匯總。
3. **定期審查**（季度）：
   - Risk-compliance-officer 逐條規則審查文案（有無新的風控紅線衝突）。
   - Tech-writer 檢查說明文案是否準確。
   - Qa-reviewer 抽查規則的邏輯完整性。

這些機制的正式落地需待後續專案週期。

## 尚缺的設計決策（不阻擋本 ADR，實作時必須補齊）

1. **規則優先序算法的正式名稱與論文**：
   - 當前為自創「方向分組 + 權重排序」；需檢查是否已有標準名稱（e.g., majority vote、weighted voting）。
   - 供未來新成員理解與質疑。

2. **規則參數的自動掃描範圍**：
   - 若決定對某些規則（如 RSI 閾值）做自動掃描優化，需定義搜索空間、優化目標、約束（e.g., 不得改變規則邏輯方向）。
   - 當前決策中無自動掃描；規則參數手工。

3. **新規則的提案與審批流程**：
   - 誰可提案新規則（任何開發者 vs. 只有策略團隊）。
   - 審批路徑（qa-reviewer → risk-compliance-officer → tech-architect 還是其他順序）。
   - SLA（多久內必須審批）。

4. **使用者自定義規則的可行性**：
   - 本決策未涉及；棄卻了長期支持用戶修改規則檔案。
   - 若日後要求使用者自訂規則，需新增沙箱 + 審核層。

## 驗收標準

本 ADR 被視為「實施成功」當且僅當：

1. `app/advice/rules/default.yaml` 完備，當前含 12 條規則，涵蓋常見交易場景。
2. 規則 loader (`app/advice/loader.py`) 通過所有測試；合規掃描正常工作。
3. 建議卡返回的 matched_rules 與 action_weights 與實測規則求值邏輯一致。
4. Confidence 計算與文案說明相符（反映規則一致性與資料完整度，非勝率）。
5. 所有規則文案通過 risk-compliance-officer 審查；無禁用詞。
6. 前端卡片完整展示規則、反駁、失效條件；使用者能讀懂邏輯。
7. Code review 已驗收；Codex（若環境就位）提供第二意見。
