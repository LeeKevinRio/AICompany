# ADR-0007:唯讀驗收職能的權限邊界與 E2E 降級路徑(執行/判斷分離)

- 狀態:proposed
- 日期:2026-08-23
- 決策者:tech-architect(裁定)、CEO(待核可)

## Context(背景)

2026-08-23 C8-10 實際發生:遠端容器未掛載 Claude_Preview MCP,`qa-e2e` 依其 frontmatter
(`.claude/agents/qa-e2e.md:4`)只剩 `Read, Grep, Glob` 與一整組 `mcp__Claude_Preview__*` 工具,
MCP 缺席時等於只剩唯讀檔案工具,UI 實機驗收整條卡死。

同時發現章程 §4「唯讀職能不得有 Write/Edit/Bash」的**字面規則與實作有落差**:
`scripts/validate_agents.py:52` 定義 `READONLY_FORBIDDEN = {"Write", "Edit", "Bash"}`,
`scripts/validate_agents.py:144-147` 的檢查邏輯是 `READONLY_FORBIDDEN & set(tools)`,屬**精確字串比對**,
只擋未限定範圍的 `"Bash"`,不擋 `"Bash(codex:*)"` 這類帶括號的 scoped 字串。
實證:`qa-reviewer` 就在 `scripts/validate_agents.py:51` 的 `READONLY_AGENTS` 名單內,其
`.claude/agents/qa-reviewer.md:4` 的 `tools` 卻帶有 `Bash(codex:*), Bash(git diff:*)`,CI 綠燈通過。
這個不一致本身需要一併裁定,不能只解 MCP 缺席這一個症狀。

待解問題:MCP 缺席時,如何在不侵蝕唯讀不變式的前提下完成 UI 實機驗收。

## Options(選項比較)

| 方案 | 優點 | 缺點 | 風險 |
| --- | --- | --- | --- |
| **A. 執行/判斷分離(採用)**:qa-e2e 維持唯讀,MCP 缺席時由具 Bash 者代跑,只交未經改寫的事實,Verdict 仍由 qa-e2e 出具 | 唯讀不變式零侵蝕;`validate_agents.py` 不用改判準邏輯;今天就可用(C8-10 已實證);MCP 恢復後自動回主路徑,無權限回滾債 | 每次 UI 驗收多一個 session 交接;證據經一手轉述有失真風險 | **探索性驗收能力下降**——qa-e2e 看到異常無法即時再點一下追查,只能請代跑者重跑 |
| **B. 給 qa-e2e scoped Bash(否決)** | 表面上看起來仍是「有限縮」的 Bash | `Bash(node:*)` 一句 `node -e "require('fs').writeFileSync(...)"` 即取得完整寫入與任意程式碼執行權,技術上等同未限定 `Bash`;`Bash(npx playwright:*)` 會執行專案 `playwright.config` / `globalSetup`,同樣是任意程式碼執行;且仍需 `Write` 才能落腳本與截圖 | Guardrail 侵蝕**不可逆**:先例一開,往後每個「工具不夠」的請求都會援引此例要求放寬 |
| **C. 自建能力受限執行介面(本案不採)**:受限 CLI 包裝或自架 preview MCP | 長期可能是正解,能提供更完整的窄化執行環境 | 為一個**環境暫時性問題**新建基礎設施,成本與本案急迫度不成比例 | 啟動指令屬產品線細節,員工線若包裝會引入產品耦合,違反 CLAUDE.md §1「main 保持零產品耦合」 |

## Decision(決策)

1. **採方案 A**。`qa-e2e` 維持唯讀、工具白名單不變(`.claude/agents/qa-e2e.md` 的 `tools` 不動);
   MCP 缺席時,由具 Bash 者(預設 `qa-automation`)依 `.claude/skills/e2e-fallback/SKILL.md` 代跑,
   **只交事實**:截圖、逐字文字、`getComputedStyle` 量測值、**未經改寫的** console / network 原始輸出。
   Verdict(PASS / NEEDS_CHANGES)一律由 `qa-e2e` 出具,代跑者不得代下 Verdict。
2. **明定唯讀不變式的真正判準**:唯讀職能不得有 `Write` / `Edit` / **未限定範圍的 Bash**;
   僅可持有明列於 `READONLY_ALLOWED_BASH` 的**非變更性且可窮舉**指令。
   `Bash(node:*)`、`Bash(npx *:*)` 等可執行任意程式碼者**不符合此判準**,明文禁止收錄。
   判準務必寫成「非變更性且可窮舉」,而非「有沒有括號」。
3. 新增項目進 `READONLY_ALLOWED_BASH` 須經 `tech-architect` 出 ADR 並由 CEO 核可,`dev-lead` 不得自行加入。
4. 章程 §4 依此修訂(修訂文字見本 ADR 附錄,需 CEO 核可後才由 `tech-writer` 落入 `CLAUDE.md`)。

## Consequences(後果)

**好處**

- 唯讀不變式首次被**實作**(機械判準)而非僅被宣告。
- UI 驗收在無 MCP 環境有明確路徑,不再臨場發明。
- MCP 恢復後自動回到主路徑,沒有權限回滾債。

**代價**

- UI 驗收固定多一次交接(延遲與 token 成本)。
- **探索性驗收能力下降**——這是本案最實質的品質損失,不淡化:qa-e2e 無法臨場再點一下追查異常,只能請代跑者重跑一輪。
- 證據轉述失真風險——「未經改寫的 stdout」是本方案命脈而非格式潔癖,代跑者若改寫或摘要證據,整條路徑的可信度會崩掉。
  落地實例:代跑實測時,受測站未宣告 `charset=utf-8`,runner 忠實回報亂碼字串;
  這正是「未經改寫」的價值——代跑者若「好心還原」猜測原文,就會蓋掉一個真 bug。
  因此 skill 明文要求:亂碼照實回報、屬 finding、不得自行還原。

**殘餘風險(不假裝不存在)**

代跑者 runtime 越界、自行下 Verdict,**本架構無法機械攔截**——`scripts/validate_agents.py`
是對 agent 定義檔的靜態 linter,看不到 session 內實際發生了什麼。
替代做法是把偽造成本壓到判讀端的**可稽核痕跡**:

1. qa-e2e 降級時,驗收摘要必須含固定字樣「以 e2e-fallback 代跑,代跑者:&lt;who&gt;」。
2. 交件必附未經改寫的 stdout 與截圖絕對路徑。
3. 任務單交接紀錄必須留下 `qa-automation → qa-e2e` 這一筆。
4. **判準:缺任一痕跡的 UI 驗收 PASS,CEO 一律視為未完成。**

**約束**

往後任何 agent 因「環境缺工具」而請求放寬唯讀權限,一律援引本 ADR 駁回,
改走執行/判斷分離(方案 A)或方案 C。

## 落地狀態(供日後追溯)

- **M1**(在 `scripts/validate_agents.py` 新增 `READONLY_ALLOWED_BASH`,對唯讀角色檢查凡 `Bash` 開頭
  且不在清單內即報錯)= 進 main 硬性前提。**已於 `d4e9f39` 落地**,並經兩情境紅燈實測:
  ①僅把 `Bash(node:*)` 加進 `qa-e2e.md` → exit=1;
  ②**同時**把 `Bash(node:*)` 加進 `SCOPED_BASH`(舊版會綠燈)→ 仍 exit=1。
  還原後 15 個 agents 全過,`qa-reviewer` 既有兩個 scoped Bash 未被誤殺。
  **技術債**:`READONLY_ALLOWED_BASH` 目前無自動化測試(validator 自身無 test suite),本次為手動驗證。
- **M2**(`qa-automation` 的「代跑時不下 Verdict」升到 `## 紅線` 小節)= 硬性前提,**已於 `d4e9f39` 落地**。
- **M3**(Verdict 署名權靜態允許清單 `VERDICT_AGENTS`)= 另開 chore 分支處理;
  **注意此清單不能從 `READONLY_AGENTS` 推導**——`security-engineer`(`.claude/agents/security-engineer.md:4`)
  非唯讀(持有 `Write, Edit, Bash`),但同檔 `:38-41` 有完整 `## Verdict` 區塊,
  直覺寫法(以唯讀清單為 Verdict 清單)會誤殺它。
- runtime 層機械強制 = **明確不做**,理由與替代做法見「Consequences / 殘餘風險」。

## 附註:本 ADR 的編號

員工線 `main` 與本分支的 `docs/adr/` 僅有 `0001`,但 `product/stock-desk` 已存在 `0002`–`0006`
(stock-desk 系列)。產品線會定期 `merge origin/main`——若員工線出一份 `0002`,合併後同一 repo 會有
兩份 ADR-0002,**檔名不同不會產生 git 衝突,會靜默撞號**,牴觸 ADR-0001「編號從 0001 遞增、不重用」。
故本案取 **0007**(落檔前已以 `git ls-tree` 對 `origin/main`、`origin/product/stock-desk`、
本分支三邊查證,確認 0007 未被占用)。
**「多分支下的 ADR 編號策略」(建議員工線與各產品線分號段)另案處理,不夾帶進本 ADR。**
