# N-152 檢測指令：舊 DB 裡是否殘留「未收盤 K 棒」（給 CEO 本機執行）

- 日期：2026-10-26
- 對應：後續追蹤清單 N-152；風控裁定 `work/reviews/2026-10-26-信任缺陷結案確認-風控.md` 第 3 點 (c)
- 腳本：`apps/stock-desk/backend/scripts/unfinished_bar_probe.py`（分支 `feat/stock-desk-unfinished-bar-probe`）
- 性質：**唯讀**離線檢測。本雲端環境沒有真實的價格 DB，**必須在存有 `stock-desk.db` 的機器上跑**。不需網路、不涉祕密、不需付費。

## 一、這支腳本唯讀，不會改資料

- DB 以 SQLite `mode=ro` 開啟，並下 `PRAGMA query_only=ON`；檔案不存在就拒絕（exit 2），**不會新建**。
- 全程只送一條 `SELECT`（讀 `price_bars_cache` 的 symbol、market、trade_date、source、fetched_at）；不讀價格欄位，不寫任何檔，輸出只到 stdout。
- 沒有 INSERT / UPDATE / DELETE / DDL。測試有逐項驗證：對該連線下寫入語句會失敗，跑完後 DB 檔的 SHA-256 與資料列不變。
- 唯一副作用來自 SQLite 本身：讀 WAL 模式資料庫時，旁邊可能出現空的 `-wal`／`-shm` 輔助檔，資料庫檔本身位元組不變。想更保守，可先把 `stock-desk.db`、`stock-desk.db-wal`、`stock-desk.db-shm` 三個檔一起複製到別處，對複本執行。
- 只用標準函式庫，不 import `app.*`。
- 不做清理。就算有輸出列，腳本也不會動任何資料；清理屬於寫入動作，須另案經您明確同意。

## 二、判定規則

一列被列出，當且僅當：

```
fetched_at  <  該列 trade_date 在該市場收盤時刻（換算成 UTC）
```

| 市場 | 收盤時刻 | 時區 |
| --- | --- | --- |
| TW | 13:30 | Asia/Taipei（無日光節約） |
| US | 16:00 | America/New_York（換算 UTC 隨 DST 變動：夏令 20:00Z、冬令 21:00Z） |

- 收盤時刻逐列用 `zoneinfo` 依該列自己的 `trade_date` 換算，不寫死 UTC 偏移。
- `fetched_at` 剛好等於收盤時刻：**不列出**（與資料服務判斷一致，`freshness.py` 以 `local.time() >= session_close` 視為已收盤）。
- 腳本沒有交易日曆，只依日期判定。
- `fetched_at` 在 upsert 時會被更新（`cache.py:228`），所以列出的是「最後一次寫入發生在收盤前」的列。

## 三、停哪些程序、跑哪條指令

### 1. 停程序（建議，非必要）

腳本只讀，後端不停也能跑。但為了讓輸出是**單一時間點的靜止快照**（避免跑的當下剛好有 upsert 改了 `fetched_at`），建議先停下面兩個：

- 後端 API：`uvicorn app.main:app`
- 排程：`python -m app.scheduler`

用 `dev-up.sh` / `dev-up.bat` 啟動的，直接在該視窗 Ctrl+C 即可（會一併收掉子程序）。用 docker compose 的，執行 `docker compose stop`（在 `apps/stock-desk` 目錄）。**跑完再照平常方式啟動。**

前端不碰 DB，不用停。

### 2. 取得腳本

用獨立 worktree，避免動到您目前所在的分支：

```bash
REPO=<您的 AICompany checkout 路徑>
cd "$REPO"
git fetch origin feat/stock-desk-unfinished-bar-probe
git worktree add ../AICompany-n152 origin/feat/stock-desk-unfinished-bar-probe
```

### 3. 執行

```bash
# 路徑用變數，請依您的機器調整；DB 通常在後端目錄下的 data/stock-desk.db
export STOCK_DESK_DB_PATH="$REPO/apps/stock-desk/backend/data/stock-desk.db"

cd ../AICompany-n152/apps/stock-desk/backend
uv run python scripts/unfinished_bar_probe.py
# 等價寫法：uv run python scripts/unfinished_bar_probe.py --db-path "$STOCK_DESK_DB_PATH"
```

- `--db-path` 省略時依序用環境變數 `STOCK_DESK_DB_PATH`，再退回 `./data/stock-desk.db`（相對於目前目錄，所以在新 worktree 裡跑時務必設環境變數或給 `--db-path`，否則會指到不存在的檔而 exit 2）。
- docker compose 部署的 DB 在具名 volume 內（容器內路徑 `/app/data/stock-desk.db`），請先把該檔連同 `-wal`、`-shm` 複製出來，再對複本執行。
- 退出碼：0 成功（含「0 筆」）；2 表示讀不到 DB 或沒有 `price_bars_cache` 表。

### 4. 跑完收尾

```bash
git rev-parse HEAD        # 在 ../AICompany-n152 內執行
cd "$REPO" && git worktree remove ../AICompany-n152
```

（`worktree remove` 只刪腳本的 checkout，不碰 DB。）

## 四、輸出各段的意思

| 段落 | 內容 |
| --- | --- |
| 檔頭 | 腳本名、實際讀取的 DB 路徑、執行時間（UTC） |
| Rule | 判定規則與兩個市場的收盤時刻、時區 |
| Counts | 掃描總列數；每個市場的總列數、`fetched_before_close`（符合規則的筆數）、其中 `is_latest_bar` 與 `not_latest_bar` 各幾筆；無法判定的列數與原因分項 |
| Rows with fetched_at before close | 逐列：market、symbol、trade_date、`fetched_at`（DB 內原值）、該日收盤時刻（UTC）、`is_latest_bar`（yes／no）、該 symbol 在表內最新的 trade_date、source |
| Rows that could not be judged | 規則套不上的列，原值照列：`unknown_market`、`unparseable_trade_date`、`unparseable_fetched_at`、`timezone_naive_fetched_at`。這些列不會被略過，也不會被猜測 |

`is_latest_bar = yes` 的意思：該列的 `trade_date` 等於同一 `(symbol, market)` 在表內最新的 `trade_date`。

輸出只有事實：計數、列、規則。腳本不印結論，也不印任何建議。

## 六、這份輸出不能做什麼

- 它只能說「這一列最後一次寫入發生在該日收盤前」，**不能說明為什麼**。該列的 close 值是否與最終收盤價不同，輸出看不出來，腳本不讀價格欄位。
- 沒有交易日曆：落在週末或休市日的列，只依日期判定。
- `fetched_at` 被後續 upsert 更新過的列，會顯示最後一次寫入時間，早先的盤中寫入看不到。
- 如何處理（若有輸出列）由風控與 tech-architect 依輸出判讀；清理須 CEO 明確同意。
