## 一、這支腳本唯讀，不會改資料

- DB 以 SQLite `mode=ro` 開啟，並下 `PRAGMA query_only=ON`；檔案不存在就拒絕（exit 2），**不會新建**。
- 除了開頭那一條 `PRAGMA query_only=ON`，送出的全部是 `SELECT`。讀的表：`playbook_directives`、`playbook_batches`、`playbook_state`、`price_bars_cache`（只讀 `trade_date`），以及 `sqlite_master`（確認表在不在）。
- 腳本原始碼裡沒有 INSERT／UPDATE／DELETE／DROP／ALTER／ATTACH 等字樣，測試逐字檢查；也測過「對腳本的連線下寫入語句一定失敗」「跑完 DB 檔 SHA-256 不變」。
- 只用標準函式庫，不 import `app.*`，不連網，輸出只到主控台。
- 唯一副作用來自 SQLite 本身：讀 WAL 模式的資料庫時，可能在**同一個資料夾**新增 `-wal`／`-shm` 輔助檔。所以本文件要您**對複本執行**，正本與備份都不會被碰到。

## 二、偵測什麼（判準）

「決策身分」K1 = `(symbol, batch_no, rule_id, action, execution_date)`。同一次評估寫出的所有列共用一個 `created_at`，所以「同一個 K1、`created_at` 不只一種」就代表同一個決策被寫了好幾次。

| 類別 | 判準 | 腳本印什麼 |
| --- | --- | --- |
| D-A | 同一 K1、R1 買進、**全部 executed** | 每組的 ids、股數、成交價、批次狀態；通過全部誤判防護才印「推算多扣金額」=（列數 − 1）× 股數 × 成交開盤價 |
| D-A′ | 同一 K1、R1 買進、**全部 missed** | `missed_count` 多加的次數（列數 − 1），不印金額 |
| （R1 其他） | 同一 K1、R1 買進，但不是全部 executed 也不是全部 missed（例如還在 pending） | 逐列列出，標「需人工判讀」 |
| D-B | 同一批（symbol, batch_no）有超過 1 列 executed 的 R1 買進，且執行日不同 | 只揭露，逐列列出，不印金額 |
| D-B-pending | 同一批已有 executed 的 R1 買進，卻還有**另一個執行日**的 R1 買進在 pending | 只揭露。這就是「後補 K 線時舊單又成交、又扣一次現金」的情境 |
| D-C | 同一 K1、動作是順延（defer）或跳過（skip）：R2、R3、M1 | 只揭露，附批次的 `defer_count`、狀態 |
| D-D | 同一 K1、P1／P2（1/3 減碼）／P3 賣出 | 只揭露，逐列列出，附「第一列之外又成交幾列」 |
| D-E | 同一 K1、S1／S2／P2 移動停利出清；EMERGENCY 賣出以（symbol, batch_no）跨日分組 | 只列計數（這幾類結算時有 `min` 保護，股數與現金不會翻倍） |
| D-F | 以上任何重複組，**還有未結算（settled=0）的列** | 列出那些列的 id。這些列在下次開頁結算時會逐列結算 |
| D-G | 買／賣單已過執行日仍 pending | 該標的在 `price_bars_cache` 裡：執行日當天有沒有 K 線、之後有沒有 K 線、之後第一根是哪天、最新一根是哪天。**不判斷是休市還是資料缺漏** |
| 其他 | 重複組不屬於任何類別（例如 P2 兩種變體混在同一組） | 原樣列出，不會被略過 |
| playbook_state | `cash`、`total_deploy`、`total_deploy_set_at`、`total_deploy_source` | 原值照印；沒有這個鍵就印 `(absent)` |

P2 的兩種變體用指令列的 `rule_summary` 區分：只有移動停利出清那一列含「移動停利觸發」字樣（測試釘住與 engine 字面一致）。

**D-A 誤判防護**：以下任一條命中，該組印 `NEEDS_MANUAL_REVIEW (需人工判讀)` 與原因，**不印金額**：

1. 同一組裡出現相同的 `created_at`（單次評估不可能發生，原因不明）。
2. 股數不只一種值，或成交價不只一種值；成交價缺漏或無法解析。
3. 找不到該批的 `playbook_batches` 列，或批次 `shares` 不等於單列股數。
4. `total_deploy_set_at` 不存在、無法解析，或**晚於該組第一列的結算時間**（代表之後重新輸入過資金或跑過 REBALANCE，現金已被覆寫，再回補會變成重複更正）。
5. 結算時間缺漏或無法比較。

為了讓備份是單一時間點的靜止快照，**必須先停**後端 API 與排程：

- **用 `Start-Process` 背景啟動**：用 `Get-Process` 找出對應的 python／uvicorn 程序，以 `Stop-Process -Id <PID>` 停止。
- **用 docker compose**：在 `apps\stock-desk` 目錄執行 `docker compose stop`。DB 在具名 volume 內（容器內 `/app/data/stock-desk.db`），請先把該檔連同 `-wal`、`-shm` 複製出來，再從第 2 步的「複製到備份資料夾」開始。

### 2. 備份三個檔到帶時間戳的資料夾，記錄 SHA-256

```powershell
# DB 所在資料夾請依您的實際位置（主機部署手冊範例為 C:\stock-desk\data；
# 用 dev-up 開發時是 <AICompany>\apps\stock-desk\backend\data）
$DB_DIR = "C:\stock-desk\data"
$TS = Get-Date -Format "yyyyMMdd-HHmmss"
$BK = "C:\stock-desk\backup\n172-$TS"
New-Item -ItemType Directory -Path $BK | Out-Null

foreach ($f in "stock-desk.db", "stock-desk.db-wal", "stock-desk.db-shm") {
    $src = Join-Path $DB_DIR $f
    if (Test-Path $src) { Copy-Item $src $BK; Write-Host "copied: $f" }
    else { Write-Host "not present: $f" }
}

# 正本與備份的雜湊要一模一樣，才代表備份忠實
Get-FileHash -Algorithm SHA256 "$DB_DIR\stock-desk.db*" | Format-Table Hash, Path -AutoSize
Get-FileHash -Algorithm SHA256 "$BK\*" | Format-Table Hash, Path -AutoSize

# 再複製一份給腳本讀（腳本讀的是這份，備份資料夾保持原封不動）
$PROBE = "$BK-probe"
New-Item -ItemType Directory -Path $PROBE | Out-Null
Copy-Item "$BK\*" $PROBE
Write-Host "probe copy: $PROBE\stock-desk.db"
```

- `-wal`、`-shm` 不存在是正常的（程序正常結束時 SQLite 會把它們收掉），印 `not present` 即可；**有的話一定要三個一起複製**，否則最近的寫入會遺失。
- 請把兩張雜湊表與最後一行 `probe copy:` 的路徑記下來，第 3 步要用，也請一起回傳。
- 備份資料夾 `$BK` 請保留到 R-3（修復）結案；萬一之後需要還原，就是把這裡的三個檔覆蓋回 `$DB_DIR`。

## 四、看到什麼代表什麼（白話）

先看 `== Summary ==` 那一段，每一類都有計數。全部是 0，代表這個 DB 沒有被 N-172 影響到。

| 您看到 | 白話意思 |
| --- | --- |
| `playbook_state` 的 `cash` | 帳冊目前記的現金。D-A 有金額時，帳冊現金比實際少了大約那個金額 |
| `total_deploy_set_at`、`total_deploy_source` | 最後一次寫入資金的時間與來源（`user_confirmation` 是確認規則時輸入資金，`quarterly_rebalance` 是季末 REBALANCE） |
| `[D-A] ... estimated_overcharge = (3 - 1) x 100 x 600 = 120000` | 同一張 R1 買單被記成成交 3 次，畫面上您只看到 1 張，但帳冊現金被扣了 3 次。多扣的推算是 2 × 100 股 × 600 元 = 120,000 元 |
| `[D-A] ... NEEDS_MANUAL_REVIEW (需人工判讀)` 加 `reason:` | 也是重複成交，但有某個條件讓推算不可靠（例如之後重新輸入過資金），所以**故意不給金額**，要逐筆看 |
| `estimated_overcharge_total(computable only)` | 只加總「可以推算」的 D-A 組；需人工判讀的組不算在內 |
| `[D-A'] ... missed_count_excess = 2` | 同一張買單沒成交（MISSED）被記了好幾次，重試計數多加了 2。這可能讓該批提早被 R3 跳過，但不影響現金 |
| `[R1-mixed]` | 同一張買單的幾列狀態不一致（常見是還沒結算），要人工看 |
| `[D-B]` | 同一批在**不同天**各成交一次買單。您可能真的在券商買了兩次（例如資料缺漏那天您其實下過單），所以只揭露、不推算，要您逐案說明 |
| `[D-B-pending]` | 同一批已經成交過，卻還有另一天的買單在等結算。若那天的 K 線之後被補上，目前的程式會再成交一次、再扣一次現金 |
| `[D-C]` | 順延或跳過被記了好幾次。`defer_count` 可能被灌高，該批可能因此被 R3 提早跳過。不影響現金 |
| `[D-D]` | P1／P2／P3 減碼被記成成交好幾次：帳冊股數被多扣、現金被多加，帳冊會和券商對不上。`executed_beyond_first` 是第一列之外又成交幾列 |
| `[D-E]`、`[D-E EMERGENCY]` | 停損、移動停利或緊急出清重複。這幾類第二列只會移動 0 股，現金與股數不會翻倍；這裡只是計數 |
| `[D-F]` | 重複的列還有沒結算的。下次開排程台結算時，它們會一列一列被結算，照樣多扣 |
| `[D-G] ... fact: no bar on execution_date and later bars exist` | 這張單的執行日當天沒有 K 線，但之後的日子有。可能是休市（例如颱風假），也可能是資料缺漏，腳本不判斷 |
| `[D-G] ... bar_on_execution_date=yes` | 執行日有 K 線，只是還沒結算（通常是之後還沒開過排程台） |
| `[other]` | 重複了但不屬於上面任何一類，原樣列出給技術判讀 |

再次說明：輸出只有事實，腳本不下結論、不給建議，也不會動任何資料。要不要修、怎麼修，等輸出回來後由 tech-architect 判讀、風控把關，再請 CEO 裁示。

## 六、這份輸出不能做什麼

- 它不能分辨「使用者實際在券商下了幾次單」。D-A 的推算前提是：使用者每次只看到 1 張單、只下 1 次（qa 實測每次回應只顯示 1 行）。若您實際下過不只一次，請告知。
- 現金在 DB 裡只有一個值，沒有異動歷史；腳本只能從指令列反推，也只看得到最後一次寫入資金的時間。
- D-A 之後若跑過 REBALANCE，`total_deploy` 是用偏低的現金算出來的；回補現金不會自動修正它（這屬於修復階段的決定）。
- 過去因現金偏低而被縮量或取消的買單，是已經發出的指令，這份輸出不追溯。
- D-G 沒有交易日曆，只陳述 `price_bars_cache` 裡有沒有那天的 K 線。

## 七、單元測試

- 唯讀保證：寫入語句一定失敗、跑完 DB 位元組不變、開啟後只送 `PRAGMA query_only=ON` 與 SELECT、目錄名含空白／`#`／`%`。
