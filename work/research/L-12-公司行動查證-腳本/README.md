# L-12 公司行動查證：CEO 本機執行說明

對應風控列管 L-12（required，R2 前置，擋規則集 1.2.0 送審）：
在 CEO 本機真實快取上查證，持股中是否有標的在 540 日窗內發生分割、反分割、減資，以及資料來源的收盤欄位是否為還原價。

腳本：`work/research/L-12-公司行動查證-腳本/corporate_action_scan.py`（純讀取、只用 Python 標準庫、不連網）。

## 為什麼要查

規則集 1.1.0 的 `drawdown.current` ＝ 最新收盤 ÷ 540 日窗內至今最高收盤 - 1，用的是本機快取的日線收盤。
若收盤是**未還原**價：

- 分割（例：1 拆 4）：收盤一夕變成約四分之一，目前回撤顯示約 -75%，兩條回撤規則會一直命中到舊高點滑出窗外。
- 反分割、減資：收盤一夕變高，目前回撤變淺，規則可能**漏判**。

## 執行步驟（Windows）

1. 開 PowerShell 或命令提示字元，切到後端目錄：

   ```
   cd <你的 repo 路徑>\apps\stock-desk\backend
   ```

2. 執行腳本，由腳本自己把報告寫成 UTF-8 檔 `L-12_out.md`（`--db` 請指到你平常 App 在用的那個 SQLite 檔；
   App 預設放在後端目錄的 `data\` 底下，若你有改過 `STOCK_DESK_DB_PATH` 就用你改的路徑）：

   ```
   .venv\Scripts\python ..\..\..\work\research\L-12-公司行動查證-腳本\corporate_action_scan.py --db <DB 檔完整路徑> --out L-12_out.md
   ```

   **編碼**：請用 `--out`，不要用 `>` 導向。Windows 的 `>` 在命令提示字元會用 cp950、在 PowerShell 5.1 會轉成 UTF-16，
   中文與符號可能亂碼或報錯；`--out` 一律寫 UTF-8。（腳本也已把 stdout 設為 UTF-8，cmd.exe 導向可用，但不建議。）

   `--db` 沒有預設值，不給會報錯，這是刻意的，避免誤指到別的檔案。
   也不需要、也不要打開任何 `.env`。

3. 用記事本或編輯器打開 `L-12_out.md` 看一眼，確認第一行是「# L-12 公司行動查證輸出」、§A 有你的持股。

選用參數：

| 參數 | 說明 |
|---|---|
| `--out 檔名` | 報告寫入該檔（UTF-8，建議；不給則印到螢幕） |
| `--threshold 0.30` | 單日收盤變動幅度門檻（預設 30%）。想看更細可調小，例如 `0.15` |
| `--scope all` | 掃快取內全部商品（含非持股、常用標的）；預設只掃持股（`positions` 表） |
| `--as-of 2026-10-02` | 只用該日以前的日線（預設：每檔以自己的最後一根日線為終點）。要對齊線上窗 [今天-540, 今天]，請帶今天日期 |

結束碼：0 ＝ 正常；1 ＝ 範圍內沒有任何商品（多半是 `--db` 指錯檔）；2 ＝ 錯誤（檔案不存在、不是 stock-desk 的資料庫等，訊息在 stderr）。

### 關於「純讀取」

- 資料庫以 SQLite `mode=ro` 開啟，腳本沒有任何寫入、建表、修改資料的程式碼；也不讀 `.env`、不連網。
- 資料庫若是 WAL 模式，SQLite 在唯讀連線時可能在 DB 旁邊建立空的 `-wal`／`-shm` 附屬檔（我們自測有觀察到）。
  這不是改動資料；App 本來就會產生同名檔案。若 App 正在執行也沒關係，不需要先關閉。
- 若你想更保險，可以先複製一份 DB（連同 `-wal`、`-shm` 如果有）再對複本執行。

## 輸出怎麼讀

`L-12_out.md` 有五節：

- **§A 逐檔總表**：每檔持股一列。重點看「超過門檻筆數」與「判定」；「原始目前回撤」是用快取收盤直接算的值（公式與規則集 1.1.0 相同；窗長同為 540 日，但以各檔最後一根快取日線為終點，快取落後時與線上窗 [今天-540, 今天] 不同，需要時用 `--as-of` 帶今天日期。另外本腳本只讀 `price_bars_cache`，線上經 resolver 可能補抓到較新的日線），
  若某檔顯示 -70% 以上而你知道它其實沒跌那麼多，八成是公司行動。「無資料」代表該持股在快取裡一根日線都沒有，**不等於沒有事件**（代號大小寫或前後空白與快取不一致也會如此）。
- **§B 事件明細**：窗內單日收盤變動超過門檻的日期、前後收盤、幅度。「疑似類型」只是依幅度分類：
  跌逾 45% ＝ 疑似分割；漲逾 45% ＝ 疑似反分割／減資；其餘 ＝ 待人工判斷。**這不是結論**。
  「事件在窗內高點之後」＝是，表示這個跳動會直接進入目前回撤。「來源（前→當日）」前後不同表示該日前後的資料是不同來源，要先懷疑是來源口徑差異。
- **§C 價量同日佐證**：事件同一天成交量放大或縮小逾 3 倍者。有佐證較可信，沒有佐證不代表不是（分割後量能常是漸進放大）。
- **§D 資料缺口與品質備註**：窗內混用多個來源、快取起點晚於窗起點、事件與前一根相隔過久（可能是缺資料造成的多日累計）、無資料的持股。
- **§E 限制**：本腳本看不到什麼。

判讀順序建議：先看 §A 有沒有「需處理」的檔 → 在 §B 找該日期 → 對照交易所公告（分割、減資恢復買賣日）確認是不是公司行動 → 若是，該檔的目前回撤在窗內舊高點滑出前都是失真的。

台股一般股票有 ±10% 漲跌幅限制，所以超過 30% 的單日變動幾乎必為公司行動或資料錯誤；ETF 與美股沒有這個推論。

  持股若有美股，同樣不處理分割。

關於「兩來源互相驗證」的限制：`twse.py` L17-22 記載 TWSE 與 FinMind 三檔、七個交易日共 21 組收盤與成交量完全一致。
這**無法**證明兩者是否為還原價：還原價只會改動「事件之前」的歷史值，若那七天附近沒有公司行動，還原與未還原的最近幾天本來就相同。

**依程式碼判讀的結論**：本機快取的收盤在**本系統內**沒有被還原；至於上游給的是否已還原，要看交易所端點與 FinMind 資料集的實際行為，
**這份腳本才是真正的查證**——若快取中某檔在已知分割／減資日出現跳動，就代表該來源的歷史值並未還原。
反過來，若已知有分割的標的在 §B 沒有出現，則要懷疑上游已還原（或快取窗內沒有該日），須人工比對該標的的股價歷史。
