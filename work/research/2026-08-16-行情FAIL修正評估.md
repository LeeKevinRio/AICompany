## 1. TPEx 上櫃行情

### 1.1 現行呼叫面（讀 code 得出，未臆測）

- `apps/stock-desk/backend/app/data/providers/tpex.py`：`TpexAdapter` 實作
  `MarketDataProvider.get_daily_bars(symbol, start, end) -> ProviderResult`。
  介面契約明訂「回傳 `[start, end]` 任意區間內的日線」（`app/data/interface.py:147-158`），
  一次呼叫可能橫跨多個月（`_util.iter_month_starts` 逐月切 legacy 端點請求）。
- 接線位置：`app/api/deps.py:87-91`，`TpexAdapter` 是 TW 市場的**第一備援**
  （`primary=TwseAdapter()`, `backups=[TpexAdapter(), FinMindAdapter()]`）。TWSE 只收上市（上市）股，
  上櫃代號查 TWSE 會落空，因此 TpexAdapter 實務上是**上櫃個股唯一的即時行情鏈**。
- 消費端：訊號、回測（`app/backtest/*`）、建議卡估值都要求可回溯數十至數百個交易日的區間查詢，
  不是單日快照。
- **現行持倉全上市**（無上櫃持倉），此項 FAIL 對現有使用者無立即影響，可排入待辦而非阻斷任務。

### 1.2 legacy 端點死亡的影響範圍

`st43_result.php` 回 302，代表 legacy 路徑本身失效，不是網路被擋（OpenAPI 根同網域可達 200，
排除環境網路問題）。TpexAdapter 目前**唯一**的實作路徑就是這支死路徑，故現況是：任何上櫃代號查詢
會逐月請求全部失敗 → `ProviderResult.status=UNAVAILABLE`（`tpex.py:107-124`），不會誤植假資料，
但上櫃標的的行情鏈實質上是斷的。

### 1.3 已驗證 dataset 與現行呼叫面的落差

`tpex_mainboard_daily_close_quotes`（已在 2026-08-12 目錄同步中被 CEO 真實驗證過）**是「當日全市場快照」**：

- 無 `symbol` 查詢參數 —— 一次回傳全部上櫃證券（含 ETF／債券 ETF），要自行從結果過濾代號。
- 無日期區間參數 —— `Date` 欄位就是「今天」，**沒有「查某個過去月份」的能力**。

這與 `get_daily_bars(symbol, start, end)` 的介面契約（任意歷史區間）**不相容**。直接把這支 dataset
接進 `TpexAdapter.get_daily_bars` 只能在 `start<=today<=end` 時回一筆，其餘全空，等同上櫃標的的
訊號／回測歷史視窗仍舊拿不到資料，不是真正的修復，只是把「完全失敗」換成「絕大部分時間仍失敗」。

**結論**：`tpex_mainboard_daily_close_quotes` 是有效的**過渡素材**，但不是解方本身；需要先找 TPEx
OpenAPI 底下是否存在「個股歷史日成交／月成交」類 dataset（等同 legacy `st43_result` 的 OpenAPI 版）。
在未查證前，data-engineer 不寫死任何候選 dataset 名稱（紅線：不憑記憶寫死 API 規格）。

### 1.4 過渡策略評估：當日快照逐日累積是否足以支撐現行呼叫面

評估「比照除權息同步（`app.dividends.sync`）的逐次累積語意，每日排程抓 `tpex_mainboard_daily_close_quotes`
存入本地 DB，逐日累積出歷史」是否可行：

- **技術上可行**，模式與 `dividends/sync.py` 的逐次累積一致，不需要新的架構元件。
- **但語意本質不同，不建議直接用來覆蓋現行呼叫面契約**：
  1. **無法回補歷史**。除權息同步只需要「未來事件」，本來就沒有回補需求；但 `get_daily_bars` 的呼叫端
     （回測引擎、訊號引擎）預期 `start` 可以回溯到遠早於「今天」的日期（例如回測要 200 個交易日窗口）。
     快照累積只能從「開始排程那天」起算，上線第一天到有完整可用窗口之前，上櫃標的的回測／訊號會持續
     `insufficient_data`，且沒有時間表能保證何時補滿。
  2. 這是**呼叫面語意的降級**，不是同語意的替代實作——`MarketDataProvider` 抽象介面對所有 provider
     承諺同一份契約（「回傳 `[start,end]` 任意區間」），若 TPEx 這條線悄悄變成「只能回溯到累積開始日」，
     上層呼叫端在契約層面察覺不到差異，可能對著一段「看似合法但實際永遠拿不到」的區間空等或誤判。
  3. 是否接受這種降級語意，涉及回測／訊號功能對上櫃標的的可用性承諾，超出 data-engineer 的職權
     （skill 明訂「資料源商業取捨交 tech-architect 拍板」），需要 tech-architect／product-manager 一起定調。

**建議路徑（兩層）**：
1. **優先**：CEO 依下方探測指令，確認 TPEx OpenAPI 底下是否存在支援日期區間／逐月查詢的個股歷史
   dataset。若存在，直接替換 `ST43_RESULT_PATH` 對應的端點與欄位解析，呼叫面與語意完全不變，
   風險最小，data-engineer 可依既有 fixture-測試套件（`tests/test_providers_tpex.py`、
   `tests/fixtures/tpex_daily_trading_5483_202401.json`）直接改造，不需要動上層任何呼叫端。
2. **若探測後確認 TPEx OpenAPI 只有「當日快照」這一種形態**（沒有任何歷史查詢 dataset），才把
   「快照逐日累積」列為候選過渡方案，但必須先經 tech-architect 拍板降級語意是否可接受，且需要：
   - 呼叫端（回測／訊號）明確收到「上櫃標的僅自 `<累積起始日>` 起有資料」的訊號，不能靜默回應空區間。
   - UI／文案揭露此限制，而非隱藏。
   - 是否值得為此投入排程基建（新增每日排程任務、儲存層），也是成本問題，一併請 tech-architect／CEO
     評估優先序。

### 1.5 給 CEO 的 PowerShell 探測指令（TPEx，可直接複製執行）

原則：不臆測 dataset 名稱與 swagger 路徑，用 Swagger UI 頁面自帶的 `url` 參數自動解析定義檔位置，
再用關鍵字自動篩選候選，最後才手動確認語意、抓樣本。

```powershell
# ===== Step 0：確認 TPEx OpenAPI 根可達、看內容型態 =====
$root = Invoke-WebRequest -Uri "https://www.tpex.org.tw/openapi/" -UseBasicParsing -TimeoutSec 20
"$($root.StatusCode) / $($root.Content.Length) bytes"
$root.Content | Out-File -Encoding utf8 tpex_openapi_root.html

# ===== Step 1：從 Swagger UI 頁面內嵌的 url 參數自動解析 swagger 定義檔路徑（不臆測固定路徑）=====
$swaggerPath = $null
if ($root.Content -match 'url\s*:\s*"([^"]+)"') {
    $swaggerPath = $Matches[1]
    if ($swaggerPath -notmatch '^https?://') { $swaggerPath = "https://www.tpex.org.tw" + $swaggerPath }
    Write-Host "找到 swagger 定義: $swaggerPath"
} else {
    Write-Host "頁面沒抓到內嵌 url，改試常見候選路徑（僅供嘗試，非確定規格）"
}

# ===== Step 2：Step1 找不到才試常見候選路徑 =====
if (-not $swaggerPath) {
    $candidates = @(
        "https://www.tpex.org.tw/openapi/swagger.json",
        "https://www.tpex.org.tw/openapi/v1/swagger.json",
        "https://www.tpex.org.tw/openapi/swagger/v1/swagger.json"
    )
    foreach ($c in $candidates) {
        try {
            $null = Invoke-RestMethod -Uri $c -TimeoutSec 15
            Write-Host "OK: $c"
            $swaggerPath = $c
            break
        } catch {
            Write-Host "FAIL: $c -- $($_.Exception.Message)"
        }
    }
}

# ===== Step 3：抓 swagger 定義，列出全部 dataset path，存檔供人工複查 =====
$spec = Invoke-RestMethod -Uri $swaggerPath -TimeoutSec 20
$allPaths = $spec.paths.PSObject.Properties.Name
$allPaths | Sort-Object | Out-File -Encoding utf8 tpex_openapi_all_datasets.txt
"共 $($allPaths.Count) 個 dataset，已存到 tpex_openapi_all_datasets.txt"

# ===== Step 4：關鍵字篩選「個股日成交/歷史/月成交」類 dataset =====
$fxLikeCandidates = $allPaths | Where-Object { $_ -match '日成交|個股|歷史|月成交|history|daily|quote' }
$fxLikeCandidates

# ===== Step 5：對每個候選印出 summary/description/parameters，判斷是否支援 symbol + 日期區間查詢 =====
foreach ($p in $fxLikeCandidates) {
    $def = $spec.paths.$p.get
    Write-Host "===== $p ====="
    Write-Host "summary: $($def.summary)"
    Write-Host "description: $($def.description)"
    $def.parameters | Select-Object name, in, required, description | Format-Table
}

# ===== Step 6：挑一個看起來支援 symbol + 歷史區間查詢的 dataset，實際抓 5483 樣本 =====
# 請把下面 <實際dataset路徑>、<實際參數> 換成 Step5 找到的真實內容再執行
Invoke-RestMethod -Uri "https://www.tpex.org.tw/openapi/v1/<實際dataset路徑>?<實際參數>" `
    | ConvertTo-Json -Depth 6 | Out-File -Encoding utf8 tpex_candidate_sample.json
```

若 Step 4 篩不到任何候選（即整個 TPEx OpenAPI 只有 `tpex_mainboard_daily_close_quotes` 這種當日快照
形態），請把 `tpex_openapi_all_datasets.txt` 全文回傳給 data-engineer，改走 1.4 節「快照逐日累積」
過渡方案的拍板流程。

## 2. 台銀匯率（USD/TWD）

### 2.1 現行呼叫面

- `apps/stock-desk/backend/app/data/providers/fx.py`：`BankOfTaiwanFxAdapter` 實作
  `FxRateProvider.get_daily_rates(pair, start, end) -> FxRateResult`，抓即期買賣中點作為當日匯率
  （`fx.py:19-25`，模型值非官方收盤匯率，此點已在 `fx.py` header 與 `services/fx.py::SOURCE_NOTES`
  對使用者誠實揭露）。
- **是唯一 FX 來源，無備援、無快取層**（對照 TW/US 行情鏈都有 `MarketDataService(cache=...)` +
  多層 backups；FX 只有這一個 provider）。`app/api/deps.py:127-134` `_default_fx_provider()` 直接
  回傳單一 `BankOfTaiwanFxAdapter()`。
- 消費端：`app/services/fx.py::resolve_fx_quote`，被 `app/api/advice.py`（建議卡風控）與
  `app/api/portfolio.py`（帳本層五條風險上限，FR-8）共用同一份匯率解析，確保估值與風控口徑一致
  （`已知限制清單#7`）。
- **失敗時的既有行為已經是誠實降級**：`resolve_fx_quote` 沒有可用匯率時回傳
  `FxQuote(rate=None, status=UNAVAILABLE, source_note=...)`，不是靜默用預設匯率或內插值
  （`services/fx.py:96-111`），符合紅線「不用假資料冒充真實資料」。此次台銀 CSV 被反爬蟲擋下，
  行為上就是全數落在這條 UNAVAILABLE 路徑——**沒有資料完整性風險，只有可用性風險**。
- **現無美股持倉**，此項 FAIL 對現有使用者無立即影響，可排入待辦而非阻斷任務。

### 2.2 替代來源選項比較

| 選項 | 誠實度 | 維護成本 | 合規考量 | 備註 |
| --- | --- | --- | --- | --- |
| (a) TWSE OpenAPI 是否有匯率 dataset | 若存在則高（官方一級來源）；但先驗判斷命中機率低（TWSE 是證交所，非匯率主管機關） | 若找到，成本與現有 TWSE adapter 相同量級 | 官方來源，合規風險最低 | **任務要求必須探測**，見下方 CEO 指令；不可用記憶斷定「一定沒有」，仍需實測 |
| (b) 中央銀行（台灣）／data.gov.tw 政府開放資料平台 | **最高** —— 央行是新臺幣匯率法定主管機關，公告的是官方統計數字，非商業銀行報價 | 中 —— 需新寫 adapter，端點與欄位格式未知，需 CEO 查證後才能動工 | 最佳；用「央行公告匯率」取代「台銀商業報價中點模型值」，同時解決現行 `fx.py` header 已自陳的「非官方收盤匯率」誠實度缺口 | 需先由 CEO 在 data.gov.tw 網站以關鍵字「匯率」「央行」「新台幣」人工搜尋出候選 dataset，因為 data.gov.tw 平台本身的檢索 API 路徑同樣未查證，不宜臆測寫死 |
| (c) 第三方泛用匯率 API（如 exchangerate-api.com、Open Exchange Rates 等） | 中低 —— 多為市場中間價聚合，非台灣官方公告，方法論不透明，需在文案上老實揭露「非官方臺幣匯率」 | 低 —— 通常有現成 swagger/OpenAPI 文件，adapter 好寫 | 需 risk-compliance-officer 額外評估：這條匯率直接餵進風控上限計算（FR-8），若來源方法論不透明，可能影響上限判定的可信度；多數商用 API 免費層需 API key（合規上須走環境變數，符合紅線）且有配額／服務條款風險 | 不建議列為主來源候選，僅在 (a)(b) 皆探測落空時再評估 |
| (d) 降級為使用者手動輸入匯率（比照 FR-9「自報帳戶淨值」模式） | **最高** —— 無爬蟲、無第三方臆測，數字就是使用者自己輸入的，系統只誠實標示「使用者自報，非即時市場匯率」 | **最低** —— 沿用既有 UI／驗證／過期防呆模式（FR-9 已有前例與風控定調可直接借鏡），不需要新 adapter | 需比照 FR-9 走一輪 risk-compliance-officer 定調（有效期、防呆、揭露文案），但因為已有先例流程可套用，決策成本不高 | 不是「即時」匯率，且需要使用者主動維護，體驗較差；適合當**沒有可靠自動源時的備援層**，不建議當唯一解 |
| (e) 維持現狀（FX 保持 UNAVAILABLE，等 (a)/(b) 查證結果） | 高 —— 現有 UNAVAILABLE 路徑本身就誠實 | 零 | 無新增風險 | 短期可接受，因為現無美股持倉、無立即影響；但美股持倉一旦出現，風控上限會持續對該部位 `not_evaluable` |

### 2.3 data-engineer 推薦路徑

**短期**：維持現狀（選項 e）作為安全網，不倉促接一個未經查證的來源；同時立即執行下方兩組 CEO
探測指令，把 (a) 與 (b) 的可行性弄清楚。

**中期優先序**：(b) 中央銀行／data.gov.tw 官方源 > (a) TWSE OpenAPI（若真的存在）> (d) 使用者手動
輸入作為**並存備援層**（不是取代主來源，而是在官方自動源也不可用時的第二層降級，架構與 FR-9 一致）
> (c) 第三方泛用 API（僅在前三者都不可行時，且需先過風控合規審查）。

理由：這個產品的所有其他已驗證資料源（TWSE STOCK_DAY、TWSE 產業別、TPEx 目錄、除權息預告）全部是
官方一級來源；FX 若改用非官方第三方聚合源，會是整個資料鏈中唯一的例外，且直接餵進風控上限計算，
誠實度與合規風險不成比例地高於維護成本的節省。(d) 手動輸入因為架構上已有 FR-9 完整先例（風控定調
六項前置問題的裁決可直接參考），是全部選項裡「零新增技術風險」的一個補強層，建議與 (b) 並行推進，
而不是互斥。

最終是否採用、以及主來源／備援排序，仍需 tech-architect 依上表拍板 ADR（本檔僅供輸入）。

```powershell
        Write-Host "===== $p ====="
        Write-Host "summary: $($def.summary)"
        Write-Host "description: $($def.description)"
    }
} else {
    Write-Host "TWSE OpenAPI 目前找不到匯率相關 dataset（先驗判斷符合預期，證交所非匯率主管機關）"
}
```

#### 2.4.2 央行／data.gov.tw 官方匯率源（選項 b，需一步人工搜尋 + 一步指令抓樣本）

data.gov.tw 平台本身的檢索 API 路徑未查證，不宜臆測寫死，改用「人工搜尋定位 → 指令驗證」兩步：

**人工步驟**（瀏覽器）：開啟 `https://data.gov.tw/`，以關鍵字「匯率」「央行」「新台幣」搜尋，
找到你認為最符合「中央銀行公告新台幣匯率」的 dataset，點進 dataset 詳細頁，複製其 API 資源連結
（通常標示為「API」或有 JSON/CSV 圖示的資源連結）。

**指令驗證**（把上一步複製到的真實 URL 貼進 `<資料集API網址>`）：

```powershell
$url = "<資料集API網址>"   # 換成人工步驟複製到的真實連結
try {
    $resp = Invoke-RestMethod -Uri $url -TimeoutSec 20
    Write-Host "可連線，回傳型態: $($resp.GetType().Name)"
    $resp | ConvertTo-Json -Depth 6 | Out-File -Encoding utf8 cbc_fx_sample.json
    "已存樣本到 cbc_fx_sample.json，前 3 筆："
    $resp | Select-Object -First 3 | Format-List
} catch {
    Write-Host "FAIL: $($_.Exception.Message)"
}
```

請把 `cbc_fx_sample.json`（或找不到候選 dataset 時的搜尋結果截圖／dataset 頁面連結）交回
data-engineer，用於評估欄位格式與是否可直接支援 `USD/TWD` 逐日查詢。

## 3. 兩案共通的既有基礎（本次不需重做）

不論最終走哪條路線，以下 `data-source-integration` skill 要求的必要條件在現有 `TpexAdapter` /
`BankOfTaiwanFxAdapter` 中已具備，只是端點/欄位需要替換，架構層不需要重做：

- **快取**：`RateLimitedClient` + `MarketDataService(cache=...)`（TPEx 走這條路徑；FX 目前無此層，
  屬 2.1 節提到的既有落差，若採 (b)/(d) 並存方案時建議一併補上）。
- **Rate limit**：`RateLimitedClient(min_interval_seconds=0.5)`，兩個 adapter 皆已設定。
- **重試／逾時**：`RateLimitedClient` 內建指數退避與 timeout（`TransportError` 皆被捕捉，不會讓例外
  往上炸穿）。
- **離線 fixture**：`tests/fixtures/tpex_daily_trading_5483_202401.json`、
  `tests/fixtures/tpex_openapi_mainboard_daily_close_quotes.json`（已存在，供未來改接 OpenAPI 時
  比對用）；FX 側 `tests/test_providers_fx.py` 亦全走 fixture，不打外網。
- **as_of / source**：`PriceBar` / `FxRate` 皆為 pydantic frozen model，`as_of` 有 timezone-aware
  驗證器強制；`source` 有非空驗證器。換源後這兩個必填欄位的驗證邏輯不需要動。
- **無憑證需求**：TPEx OpenAPI 與台銀 CSV／央行公開資料皆為免金鑰公開端點，選項 (a)(b) 若採用不會
  新增憑證管理負擔；選項 (c) 第三方 API 才會引入 API key（若走到那一步，金鑰一律走環境變數，不進
  code／fixture）。
