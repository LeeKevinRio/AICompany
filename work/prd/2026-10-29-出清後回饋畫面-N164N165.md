## 背景與目標

「全部出清」是排程台唯一的不可逆操作。使用者按下後，畫面要做到三件事：

1. 讓使用者確認這個請求被受理了。
2. 讓使用者接著去看指令帳冊與結算（出清後最需要讀的內容）。
3. 揭露類文案（R 系列暫停多久、何時恢復、S/P 仍照常評估、歸屬語）照風控裁決常駐可見。

現況的問題（已實測，除非另註）：

- **N-164**：成功橫幅被放在 sticky 狀態列裡，一直釘到重新整理才消失。
  - 狀態列佔視窗高度：

    | 情境 | 1280×900 | 375×812 |
    |---|---|---|
    | 出清前基準 | 87px（9.7%） | 87px（10.7%） |
    | mock 成功後 | 405px（45%） | 531px（65.4%） |
    | 沙盒真實出清後（無持有批次，是下限） | 273px（30.3%） | 379px（46.7%） |
    | 重新整理後（橫幅消失） | 87px | 127px |

  - 375 寬時可讀區只剩約 35%～53%。
  - 高度在捲動 0／中段／底部都不變，因為整塊是 `position: sticky`。
  - 有持有批次時，message 與 warnings 較長，高度預期更高，目前沒有實測值。
- **N-165**：同一句 `mode_reason` 出現兩次，一次在橫幅，一次在狀態列自己那行。
  - 真實後端已證實：出清回應的 `mode_reason` 與之後 `/today` 的 `mode_reason` 逐字相同。
  - 另有第三層語意重疊：`message` 結尾那句與 `mode_reason` 說的是同一件事（風控已裁決接受，見 Q4）。
- **NB-6**：出清回 500 時，ErrorPanel 直接露出後端英文 `Internal Server Error`，也沒有說明請求有沒有被處理。
- **NB-7**：1280 寬時，徽章被置中在高區塊左側，橫幅在右側，版面鬆散。成因與 N-164 相同（橫幅擠進狀態列的 flex 列）。
- **v2 新增（風控讀碼發現，推論，未實測）：出清回饋的整套狀態都掛在會因 `/today` 失敗而卸載的元件底下。**
  - `page.tsx:48` 只在 `today.isSuccess` 時渲染 `ModeStatusBar`。
  - 出清 mutation、對話框 portal、現行橫幅都長在 `ModeStatusBar` 裡的 `EmergencyExitControl`。
  - 依 TanStack Query v5 語意（專案為 5.101.4），背景重新取得失敗時 `status` 變 `error`、`isSuccess` 變 false，資料還在也一樣。
  - 後果：`/today` 一失敗，狀態列卸載，橫幅、對話框、失敗面板跟著消失，受理回執不見。
  - FR-8a 要求失敗後重新取得 `/today`；斷線時這次重新取得幾乎一定也失敗。若不處理，NB-6 的定稿字面沒有機會被看到，AC-17「對話框維持、可重試」也會退化。
  - 前提需由 qa-e2e 以 mock 先行實測確認，見 AC-12 的前置驗證。
- **v3 併入（N-170，風控讀碼發現，推論，未實測；CEO #81 裁定併入本包）：`/today` 載入或重新取得失敗時，「全部出清」觸發鈕本身也不在。**
  - 觸發鈕在 `ModeStatusBar` 內，`ModeStatusBar` 只在 `today.isSuccess` 時渲染（`page.tsx:48`）。
  - 因此以下三種情境，使用者都沒有出口：
    1. `/today` 首次載入失敗（error）。
    2. `/today` 首次載入中（pending）。依風控讀碼，`usePlaybookToday` 設 `retry: 1`，所以 pending 期間包含一次重試的等待，error 畫面要等重試也失敗才出現。這段時間比單次請求長。
    3. `/today` 背景重新取得失敗（已有資料，`isSuccess` 變 false）。
  - 這與 EX-2「出口零摩擦，最高優先」，以及 `wording.py` 降級分支「缺欄位不得變成鎖住的門」的意圖衝突。出口不能依賴「排程台資料讀得到」。
  - 搬出對話框與 mutation 的工作（FR-7）已經在本包內；v3 補的是觸發鈕本身在上述三種情境的存在與可操作，以及它在狀態列掛載／卸載之間換位時的連續性。

目標：

- 出清成功後，sticky 狀態列回到接近出清前的高度。
- 受理結果與揭露文案仍然完整、常駐、不摺疊、不移到頁尾。
- 出清失敗時，不讓使用者誤判請求有沒有被處理，也不讓使用者誤以為重送是安全的。
- 出清回饋（橫幅、對話框、失敗面板）不因 `/today` 的載入狀態而消失。
- **（v3）「全部出清」的觸發鈕在 `/today` 的任何狀態（pending、error、背景重新取得失敗、success）下都存在且可操作，任一時刻 DOM 中恰好一個，且不加任何前置條件。**

## 使用者與情境

使用者是單一個人投資者，用排程台執行自己設定的規則。

- **情境 U1，成功後要看帳冊（N-164）**
  - 他在手機（375 寬）按完「全部出清」，對話框關閉。
  - 他要往下捲，確認今日指令帳冊、持倉、結算。
  - 現況：上方 47%～65% 的畫面被釘住的狀態列占掉，可讀區只剩約三分之一。
- **情境 U2，在已捲動的位置按出清（N-164 的新風險）**
  - 觸發鈕在 sticky 列裡，所以使用者可能在頁面中段就按了出清。
  - 橫幅改放內容頂部後，成功後橫幅會在視窗外，使用者看不到受理回饋。
  - 這是方案 A 必須處理的副作用，見 FR-3。快市啟動時狀態列更高，是風控列為阻擋條件的情境。
- **情境 U3，重複看到同一句（N-165）**
  - 使用者在橫幅讀到「緊急出清後凍結：R 系列暫停中……」，緊接著又在狀態列讀到一模一樣的一句。
  - 他會懷疑是不是出了兩次，或畫面壞了。
- **情境 U4，出清回 500 或斷線（NB-6）**
  - 使用者按下「確認送出全部出清」後看到「全部出清送出失敗：Internal Server Error」。
  - 他不知道持倉到底有沒有被出清，也不知道再按一次會發生什麼事。可能的反應：
    - 重複再按。在 N-166 合併前，若後端其實已產生賣出指令，再按會再產生一整組賣出指令。（v4 註：N-166 先於本包合併後，已有尚未結算之出清賣出指令的持有批次不會再重複產生；但再次送出可能延後 R 系列的預計恢復日，見風控 N-166 裁示第 3 項與 FR-8b。）
    - 以為沒事而不管，其實後端已凍結。
  - 網路中斷時同樣不確定，且 `/today` 的重新取得多半也失敗（情境 U6）。
- **情境 U5，大螢幕看橫幅（NB-7）**
  - 1280 寬時，使用者看到徽章孤零零地在左側垂直置中，橫幅在右側，讀起來像兩個互不相關的區塊。
- **情境 U6，出清當下網路不穩（v2 新增）**
  - 使用者送出出清，回應回來（成功或失敗）後，`/today` 的重新取得失敗。
  - 現況推論：狀態列卸載，對話框、橫幅、失敗面板一起消失，使用者看到「無法載入排程台資料」，不知道出清有沒有被受理。
  - 期望：橫幅（成功時）或失敗面板（失敗時）仍在，使用者仍能讀到結果、仍能重試。
- **情境 U7，打開排程台就想出清，但 `/today` 讀不到（v3 新增，N-170）**
  - 使用者一進 `/playbook` 就要出清（例如判斷市況不對，想立刻撤出），但 `/today` 正在載入（含重試等待），或已載入失敗（後端異常、網路不穩）。
  - 現況推論：頁面只有骨架或「無法載入排程台資料」，沒有觸發鈕，沒有出口。
  - 期望：觸發鈕在載入中與載入失敗時都在，按下去能走完同一套三步流程，不必等 `/today` 好了才能出清。
- **情境 U8，使用者看著頁面，`/today` 在背景失敗又恢復（v3 新增，N-170）**
  - 使用者已在 sticky 狀態列看到觸發鈕。背景重新取得失敗，狀態列卸載，觸發鈕隨之消失；隔一會兒重新取得成功，狀態列又掛載回來。
  - 若對話框正開在第 2、3 步，觸發鈕的所在位置會在期間換位。期望：對話框、步驟、焦點不被打斷；關閉後焦點回到當時還存在的那一個觸發鈕。

## 功能需求

### N-164 與 N-165：成功橫幅

**FR-1　橫幅離開 sticky 區。**
成功橫幅不得出現在 sticky 狀態列的容器內，改放在排程台主內容區頂部，處於一般文件流（非 sticky、非 fixed）。
- 位置：`<h1>` 之後（art-lead 規範 §2.1 已定），在歸屬語、§6 總覽區塊、警示、帳冊之上。
- 橫幅所在位置不得位於 `today.isSuccess` 的閘門之內（見 FR-7a）。
- `/today` 為 pending 或 error 時，橫幅相對於 `<h1>` 與「無法載入排程台資料」面板的先後順序，由 art-lead 補規範（不新增字面）。

**FR-2　sticky 狀態列的高度不受成功橫幅影響。**
- 出清成功前後，sticky 狀態列的高度差在 ±4px 內（同一寬度、同一 mode 條件下比較）。
- 絕對上限：以 art-lead 規範 V-1 為準（375×812 不超過 138px、1280×900 不超過 108px）。
  - PM 原暫定值 162px（20%）、135px（15%）是「不得放寬」的上界；art-lead 已依 v1 的授權收緊，兩者取較嚴者。
- 參考：重新整理後的實測值為 87px（1280）與 127px（375）。
- 此條在捲動 0／中段／底部三個位置都要成立。
- 快市啟動時狀態列自身會超過上限，此情境的判準只有 ±4px 與不超過 PM 暫定上界（art-lead 規範 §1.3）；其捲動偏移見 FR-3。

**FR-3　成功回饋必須進入視窗（v2：快市情境為阻擋條件；風控必改項 12）。**
- 因為觸發鈕在 sticky 列，使用者可能在已捲動的位置按出清。成功後若橫幅不在可視範圍內，頁面要讓橫幅進入視窗，並且不被 sticky 狀態列遮住。
- **只在橫幅掛載時捲一次**。`/today` 重新取得造成的重新渲染不得再捲。
- 捲動行為使用 `behavior: "auto"`（瞬間完成，不做平滑捲動）。這同時自然滿足 `prefers-reduced-motion`。
- **不搬動焦點**。焦點行為維持 N-163 已驗收的狀態：成功後焦點回到「全部出清」觸發鈕，不搬到橫幅。
- 是否需要捲動的判定與偏移量，依 art-lead 規範 §4（固定偏移 `scroll-mt-40`／`lg:scroll-mt-32`）。
- **阻擋條件**：「快市啟動 + mode = frozen + mock 長橫幅」的情境下，V-9 必須驗證通過，FR-3 才算完成。
  - 原因：狀態列現為不透明，快市啟動時狀態列會超過 138／108px，固定偏移可能不夠，橫幅第一行會被完全蓋住。
  - 若此條件下橫幅上緣被狀態列蓋住，改用「即時量測狀態列高度」計算偏移，再重驗；不得以放寬 FR-2 的上限處理。
  - 這項在 v1 屬於 art-lead 規範 §9 的 qa-automation 補測（P3）。v2 升為 FR-3 的完成條件，不再是補測。
- 橫幅應能被輔助科技宣告（live region）。這是 should，不是 must，不新增任何可見字面。
  - 常駐的 live region 容器同樣要放在 `today.isSuccess` 閘門之外（見 FR-7a），讓它在 `/today` 失敗時也存在。

**FR-4　橫幅不可關閉；生命週期只被「重新整理」或「開始新一輪出清」結束。**
- 橫幅只存在於當次工作階段，重新整理後消失（現況，已實測）。本輪不加關閉鈕。
- 橫幅離開 sticky 後隨頁面自然捲走，不再需要關閉。
- 「開始新一輪出清」的定義見 FR-12（should）。在 FR-12 採納前，沿用現行行為（打開對話框即清除）。**（v4 例外，風控 r2 核對第 9 點）`/today` 非 success 時，不得使用「打開對話框即清除」，須滿足 FR-12b 的回執地板。**
- 橫幅不得因 `/today` 的任何狀態（pending、error、重新取得）而消失，見 FR-7a。

**FR-5　橫幅不重複狀態列已顯示的同一句 `mode_reason`（v2：隱藏條件與移除方式收緊；必改項 4、5）。**

隱藏條件：橫幅內的 `mode_reason` 那一段，只在以下兩點**同時成立**時才移除：
1. 狀態列處於掛載狀態。判斷式與「狀態列掛載」的判斷完全相同（現為 `today.isSuccess`）。
2. `today.data.mode_reason` 與出清回應的 `mode_reason` **嚴格逐字相等**，不做 trim、不做任何正規化。

並且：
- 這個判斷在共同父層、同一次 render 內完成，不得由兩個元件各自讀不同來源。
- 風控法遵底線只有一條：**任何時候整頁的 R 都不能是 0 次**。「兩邊短暫都有」不算違規，只是視覺瑕疵（art-lead V-16 仍要求不出現）。
- **（v4，F-6）隱藏條件的判斷式維持綁在狀態列的掛載判斷式（現為 `today.isSuccess`），不得改綁成「觸發鈕的容器存在」。** 否則 `/today` 失敗、後備觸發鈕存在時，橫幅會把 R 藏掉，整頁 R 變成 0 次。見 AC-59。

移除方式：
- 移除就是**卸載**。
- 不得用 CSS 隱藏、`visibility: hidden`、`sr-only`、`aria-hidden` 留副本。
- 不得預留空位（`min-height`、隱形占位），不得加 transition 或動畫。
- `role="status"` 容器不得另外放一份該句文字。

正常情況（兩者相同）：整頁只出現一次，在狀態列內，與模式徽章同一區塊。

不同或狀態列未掛載的情況（出清成功但 `/today` 尚未取得、重新取得失敗而狀態列卸載、字面不同）：橫幅保留那句凍結揭露。

**FR-6　揭露文案完整性與橫幅內部結構（v2：必改項 6、7）。**
- 橫幅中的 `message`、`attribution`（非 null 時）、`warnings`（非空時）逐字不變、不摺疊、不截短，字級與對比不低於現行。
- 狀態列的 `mode_reason` 逐字不變。
- 沒有任何一段揭露文案被移到頁尾、tooltip、可展開區塊。
- **橫幅內部**：
  - `message`、`mode_reason`（有條件顯示）、`EXIT_ATTRIBUTION`、`warnings` 留在**同一個容器**裡，順序不變。
  - 橫幅的 attribution（`EXIT_ATTRIBUTION`）不得拆到橫幅之外。
  - 橫幅邊框維持 `border-neutral-600`，與頁面層歸屬語區隔。這是風控的必要條件，不能拿掉。
- **頁面其他區塊**：
  - 頁面歸屬語、§6 總覽、警示、Cap1 揭露的樣式與相對順序不變。
  - 橫幅與帳冊之間不得插入任何未經審查的新元素。

**FR-7　出清回饋的存續不依賴 `/today`（v2 新增，P2；必改項 1、2、3）。**

**FR-7a　橫幅撐過 `/today` 失敗。**
- 出清 mutation 的狀態、橫幅、常駐的 `role="status"` 容器，都放在 `today.isSuccess` 閘門之外，也不在 `ModeStatusBar` 之內。
- 橫幅的生命週期只能被「重新整理」或「開始新一輪出清」（FR-4）結束，不得因 `/today` 的狀態而消失。

**FR-7b　對話框與失敗面板撐過 `/today` 失敗。**
- 對話框（portal）、步驟狀態、失敗面板，不得掛在會因 `today.isError` 而卸載的元件底下。
- `/today` 重新取得失敗時，對話框必須維持開啟、停在第 3 步、可以重試。這是 AC-17 的前提。
- 對話框內 Step 2／Step 3 的核取句來源與換句規則，**Q8、Q11 已裁示，見 FR-14**（v4 定案，取代 v2 的「未裁決前的預設」）。要點：
  - 對話框開啟時依 Q8 決定一組，之後 `/today` 轉為失敗不換句（R-2）；不得用失敗前的舊資料去決定「新開」的對話框的那一組；核取句不得為空。
  - 「撐過 `/today` 失敗」指同一個已開啟的對話框保有它正在顯示的那一組，不是把舊資料留給下一次開啟。
- 觸發鈕在 `/today` 失敗時的存在與可操作，由 FR-13（N-170，v3 併入）負責。對話框關閉後的焦點落點，見 FR-13f（取代 v2 的 Q9）。

**FR-7c　`/today` 失敗時，不得以舊資料渲染狀態列。**
- 狀態列的渲染條件維持現行 `today.isSuccess` 閘門，不得放寬。
- 若要改為在失敗時繼續用舊資料渲染，必須附過時提示。那是新字面，須送風控審查，目前不允許。
- 原因：否則會出現「正常」徽章與「R 系列暫停」橫幅並陳卻不標示誰較新。

### NB-6：出清失敗

**FR-8a　出清請求結束後一律重新取得 `/today`（P2）。**
- 出清請求以任何方式結束（成功，或 HTTP 5xx、其他非 2xx、網路層失敗、回應解析失敗而失敗）後，頁面都要重新取得 `/today`，讓狀態列反映後端的真實模式。
- 風控指定的機制：`invalidateQueries(["playbook-today"])` 由「只在成功時」改為 `onSettled`（必改項 11）。
- 狀態列的模式徽章能顯示的事實有限：
  - 能顯示：R 系列（新倉進場）目前是否已暫停。
  - 不能顯示：這次是否已受理（是否已產生賣出指令）。若送出前 R 系列就已暫停（例如 EX-3 的再出清），徽章一定顯示暫停，判斷不了這次是否已受理。
  - （v4 註）tech-architect Q5 原指出的狀態 (ii)「只寫了凍結」，在 N-166 之後已不存在（指令與凍結同一個寫入交易，失敗時一起 ROLLBACK，依風控 N-166 裁示引用的 ADR-0033 C-1、T-5）。500 仍可能落在 (i) 尚未處理，或 (iii) 已受理，所以字面仍不得斷言任何一種。

  - 內文第 1 句：「這次送出未取得可確認結果的回應。目前可能尚未處理，也可能已受理：R 系列（新倉進場）已暫停，持有批次也都已有賣出指令。」

名詞：「正式句」指後端 `exit_confirm` 下發的核取句；「降級清單」指前端在沒有可用 `exit_confirm` 時使用的核取句（現行共 4 句，與正式句同數量）。

**FR-14a　核取句的來源：開啟時決定一次（R-1；Q8 裁示 1a；F-1 改）。**
- 對話框開啟當下，依下表決定要顯示的那一組核取句，並存在**對話框自己的狀態**；關閉或取消時丟掉，重新開啟時再依下表重新決定。

  | 情境 | TanStack v5 的狀態 | 核取句來源 |
  |---|---|---|
  | 首次載入中 | `isPending`，沒有 data | 降級清單 |
  | 首次載入失敗 | `isError`，沒有 data | 降級清單 |
  | 背景重新取得失敗 | `isError`，舊 data 還留著 | 降級清單，**舊 data 不得使用** |
  | 成功（含由失敗恢復成功） | `isSuccess` | 後端 `exit_confirm` 的核取句 |

- 風控指定的機制（F-1 改）：
  - 開啟時以 `exitConfirmChecks(today.isSuccess ? today.data.exit_confirm : null)` 決定。
  - 不得寫成 `today.data?.exit_confirm`（`isError` 時會拿到舊 data，等於選了被否決的選項）。
  - 不得在對話框之外保存最後一次成功的 `exit_confirm`（ref、state、context、storage 皆不得），供之後開啟的對話框使用。
- **被否決的選項：** 「沿用失敗前最後一次成功取得的 `exit_confirm`」，含加過時提示的版本，風控 VETO。風控不提供過時提示字面，也不接受日後送提示字面來換取該選項。理由（風控摘要）：
  1. 送出前講了可能已經錯的精確數字（預計恢復日由當天 `as_of`、交易日曆與當時參數算出，舊 data 可能是前一天的），屬於隱藏不確定性。
  2. N-166 之後核取句 2 用 S9 還是一般句由後端決定；舊 data 可能停在錯的分支。
  3. 過時提示救不回來，還會在出口流程多加一句讓人遲疑的字面，牴觸 EX-2、EX-5。
- S9 只能由後端放進 `exit_confirm` 下發。降級時一律不出現，不得由前端推算，也不得從舊 data 沿用。
- 與 FR-7b 的關係：FR-7b 的「撐過」是同一個已開啟的對話框保有它正在顯示的那一組（FR-14c 的 R-2），不是把舊資料留給下一次開啟的對話框。這是風控對 Q8 的澄清，不是推翻。

**FR-14b　降級清單第 2 句的修訂字面（風控 Q8 裁示 1b、1c；F-3；backend 與 frontend 落地）。**
- 降級清單第 2 句改為逐字（風控 APPROVE，**本包必須落地**）：
  「送出後，R 系列（新倉進場）暫停；本次未能取得暫停交易日數與預計恢復日，預計恢復日會在受理後的執行結果中顯示。」
- 降級清單其餘三句（第 1、3、4 句）不改（風控 1c：與 `/today` 無關，三種情境都為真）。
- 修訂原因（風控）：原句「兩者於送出後的執行結果中顯示」有兩處不成立：
  - 送出失敗時沒有執行結果（首次載入失敗時後端很可能本來就掛了，這句的承諾最常落空）。
  - N-166 合併後，F-c 分支的 S7 只有預計恢復日、沒有暫停交易日數，「兩者」不實。
- 這是修訂一句既有字面，不是新增。揭露沒有變少：送出前本來就兩個數字都沒有，送出後的 `message` 仍然帶天數。修訂後字面在 N-166 合併前後都為真，不必等 N-166。
- 原句不得留在任何 build。
- 單一來源在後端 `wording.py`（backend 落地，含相關註解的同步修正），前端鏡射，守門測試更新（FR-11、AC-57）。

**FR-14c　何時換句：只在已知變動時（R-2、R-3、R-4）。**
- **R-2　`/today` 轉為非 success，不換句。** 重新取得失敗，或由 success 轉為 error 時，不改變對話框正在顯示的那一組、不清勾選、不顯示 N1。理由：取不到資料不代表內容變了；每次網路抖動就換句清勾選是出口摩擦，而且使用者剛讀完數字畫面就改口說「未能取得」，看起來像自相矛盾。
- **R-3　`/today` 回到 success，且內容與正在顯示的不同，才換句。**
  - 只替換有變動的那幾句，只清掉這幾句的勾選，其他句的勾選保留。
  - 典型兩種情況：降級句換成正式句（pending 或 error 轉為 success），或正式句的數字改變（換日、參數改變、S9 分支改變）。
  - 內容相同則不換、不清、不顯示 N1。
- **R-4　跨日視為已知變動。** 對話框持有的是正式句，而它的取得時間（`dataUpdatedAt`）與現在不是同一個台北日曆日時，視為已知可能變動：換成降級清單，再照 R-3 清勾選、顯示 N1。理由：這是 R-2「保留舊句」的期限，沒有這條，對話框開過夜就等於選了被否決的選項。R-4 的評估時機與 `dataUpdatedAt` 是否可作依據，交 tech-architect 確認（Q12）。
- 「句子是否變動」以逐句比較內容判斷，不比較數量。

**FR-14d　勾選綁住句子內容（F-2 改）。**
- 勾選表示「我讀過這一句」，只能代表當時畫面上的那一句。只清掉內容變了的那幾句的勾選，其他句的勾選保留，以減少摩擦。
- 不得保留只比核取句數量的重設邏輯。風控讀碼發現（推論，未實測）：降級清單與正式句同為 4 句，互換時數量沒變，勾選會原樣保留，使用者勾的是「未能取得天數」那一句，畫面上已換成帶天數與日期的版本，勾選卻還在，等於默默更動使用者的輸入。
- 換句時除 N1 外，不得加任何「內容已更新」之類的字面。
- 步驟不重置；步驟倒退只限 FR-14e 的例外。

**FR-14e　第 3 步（R-5；F-9）。**
- 進入第 3 步時，記下使用者在第 2 步確認的是哪一組（正式句或降級清單）。第 3 步覆述的是這一組。
- 若發生 R-3 或 R-4，**而且確認過的那一組是正式句：退回第 2 步**，清掉有變動那幾句的勾選，顯示 N1；焦點照現行規則落在第 2 步標題。理由：使用者確認過的具體事實已知變了，不得帶著舊事實按下不可逆的確認。
- 若確認過的那一組是降級清單：維持不動，直到對話框關閉，不退回第 2 步。降級句仍為真，只是資訊較少；為補資訊而退一步是摩擦。
- **送出中**（送出鎖已取得，或 `isPending`）：一律不換句、不退步。事後的回執（橫幅 `message`）會列出實際值。
- **出清失敗後**（AC-17 的情境）：R-2、R-3、R-4 照樣適用。實務上同一天內重新取得，不論成功或失敗，都不會讓核取句改變，所以「停在第 3 步、可以重試」不受影響。
- 實作上須確認逐句比較的時機與送出鎖、`isPending` 的先後關係，不會讓退步在送出中觸發（交 tech-architect，Q12）。

**FR-14f　N1 提示（R-6；F-10；風控 Q11 裁示新字面，APPROVE）。**
- 字面逐字：「核取句已依最新取得的資料更新，有變動的項目已改為未勾選，請重新閱讀後再勾選。」
- **顯示條件：只在「至少一個勾選被系統清掉」時顯示。** 這是為了讓 N1 的字面恆真：變動的那一句原本就沒勾，就不顯示。開啟時、R-2、正常流程、換句但沒有任何勾選被清掉，都不顯示。
- 位置：第 2 步標題下方、核取清單上方。樣式 `text-sm`、`neutral-300`；不得用紅色或琥珀色，不加圖示、動畫或倒數。
- 放在對話框內一個 `role="status"`（polite）的容器裡，讓報讀軟體會唸出來；不搬動焦點。退回第 2 步時，焦點照現行規則落在第 2 步標題。
- 一直保留到對話框關閉；不需要關閉鈕，也不擋任何操作。
- N1 不是前置條件，不擋送出，重新勾選後照常可以繼續（EX-2）；只陳述事實，沒有勸阻、恫嚇或倒數（EX-5、H-1）；有說明系統為什麼清掉勾選；不提模式、不提「資料可能有誤」、不提過時。
- 單一來源在後端 `wording.py`（backend 新增常數，風控舉例命名 `EXIT_CONFIRM_CHECKS_UPDATED`，註解寫明：只在核取句換句、而且至少一個勾選被清掉時才由前端渲染），前端鏡射，守門測試逐字相同（FR-11、AC-57、AC-58）。

**FR-14g　出清失敗後，因 R-5 退步再回到第 3 步時，失敗面板重新出現（v4 新增，should；風控視覺規範 r2 核對，逐條意見第 15 點，info）。**
- 情境：出清失敗後，因 R-4 跨日（或 R-3）使確認過的正式句變動，對話框退回第 2 步；使用者重新勾選，再次來到第 3 步。
- 期望：在下一次送出開始之前，回到第 3 步時，失敗面板（FR-8b）要重新出現，而不是隨著離開第 3 步而消失。
- 這是 should，不是 must：風控列為 info，不列必改。若不採納，須在變更紀錄註明，並接受使用者回到第 3 步時看不到上一次的失敗結果的風險。
- 不得因此新增字面；面板字面仍是 FR-8b 的合併後版本。

1. **後端在 500 時無法分辨「已處理」與「未處理」（NB-6 的根本限制）。**
   我讀了 `app/api/playbook.py` 與 `app/playbook/service.py`、`store.py`（只讀，未執行）。`POST /emergency-exit` 的流程是：
   - 先讀取批次與行情。
   - 再呼叫 `apply_effects`，其中 `freeze_emergency` 透過 `_set_state` 寫入凍結狀態，使用自己的連線與交易。
