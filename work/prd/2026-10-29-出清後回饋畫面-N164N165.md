## 背景與目標

「全部出清」是排程台唯一的不可逆操作。使用者按下後，畫面要做到三件事：

1. 讓使用者確認這個請求被受理了。
2. 讓使用者接著去看指令帳冊與結算（出清後最需要讀的內容）。
3. 揭露類文案（R 系列暫停多久、何時恢復、S/P 仍照常評估、歸屬語）照風控裁決常駐可見。

現況的問題（已實測）：

- **N-164**：成功橫幅被放在 sticky 狀態列裡，一直釘到重新整理才消失。
  - 狀態列佔視窗高度：

    | 情境 | 1280×900 | 375×812 |
    |---|---|---|
    | 出清前基準 | 87px（9.7%） | 87px（10.7%） |
    | mock 成功後 | 405px（45%） | 531px（65.4%） |
    | 沙盒真實出清後（無持有批次，是下限） | 273px（30.3%） | 379px（46.7%） |
    | 重新整理後（橫幅消失） | 87px | 127px |

  - 375 寬時可讀區只剩約 35%～53%。
  - 高度在捲動 0／中段／底部都不變，因為整塊是 `position: sticky`。
  - 有持有批次時，message 與 warnings 較長，高度預期更高，目前沒有實測值。
- **N-165**：同一句 `mode_reason` 出現兩次，一次在橫幅，一次在狀態列自己那行。
  - 真實後端已證實：出清回應的 `mode_reason` 與之後 `/today` 的 `mode_reason` 逐字相同。
  - 另有第三層語意重疊：`message` 結尾那句與 `mode_reason` 說的是同一件事。
- **NB-6**：出清回 500 時，ErrorPanel 直接露出後端英文 `Internal Server Error`，也沒有說明請求有沒有被處理。
- **NB-7**：1280 寬時，徽章被置中在高區塊左側，橫幅在右側，版面鬆散。成因與 N-164 相同（橫幅擠進狀態列的 flex 列）。

目標：

- 出清成功後，sticky 狀態列回到接近出清前的高度。
- 受理結果與揭露文案仍然完整、常駐、不摺疊、不移到頁尾。
- 出清失敗時，不讓使用者誤判請求有沒有被處理。

## 使用者與情境

使用者是單一個人投資者，用排程台執行自己設定的規則。

- **情境 U1，成功後要看帳冊（N-164）**
  - 他在手機（375 寬）按完「全部出清」，對話框關閉。
  - 他要往下捲，確認今日指令帳冊、持倉、結算。
  - 現況：上方 47%～65% 的畫面被釘住的狀態列占掉，可讀區只剩約三分之一。他得在狹窄的視窗裡捲動，才讀得到剛剛那個不可逆動作的後果。
- **情境 U2，在已捲動的位置按出清（N-164 的新風險）**
  - 觸發鈕在 sticky 列裡，所以使用者可能在頁面中段就按了出清。
  - 若橫幅改放內容頂部，成功後橫幅會在視窗外，使用者看不到受理回饋。
  - 這是下方方案 A 必須處理的副作用，見 FR-3。
- **情境 U3，重複看到同一句（N-165）**
  - 使用者在橫幅讀到「緊急出清後凍結：R 系列暫停中……」，緊接著又在狀態列讀到一模一樣的一句。
  - 他會懷疑是不是出了兩次，或畫面壞了。
- **情境 U4，出清回 500（NB-6）**
  - 使用者按下「確認送出全部出清」後看到「全部出清送出失敗：Internal Server Error」。
  - 他不知道持倉到底有沒有被出清。可能的反應：
    - 重複再按，造成重複送出。
    - 以為沒事而不管，其實後端已凍結。
  - 網路中斷（`無法連線到後端服務`）時同樣不確定。
- **情境 U5，大螢幕看橫幅（NB-7）**
  - 1280 寬時，使用者看到徽章孤零零地在左側垂直置中，橫幅在右側，讀起來像兩個互不相關的區塊。

| N-164 | **P2** | 維持 qa-e2e 的 medium。出現在不可逆操作後的回饋畫面，且內容與控制項仍可達，所以不是 P1。 |
| N-165 | **P3**，與 N-164 同包交付 | 純冗餘，不誤導。去掉一份同時降低橫幅高度，且兩者改的是同一塊版面，拆開做會互相打架。 |
| NB-6，狀態同步部分（FR-8a） | **P2** | 不需要新文案，只靠既有的後端真相，就能消除「到底有沒有處理」的資訊缺口。對不可逆操作影響大。 |
| NB-6，文案部分（FR-8b） | **P3**，卡在風控定稿 | 屬使用者面向的新字面。定稿前維持現行文案。 |
| NB-7 | **P3** | 美感問題，預期隨 N-164 自然消失，由 art-lead 驗證。 |

## 範圍內 / 範圍外

**範圍內**

- 出清成功後橫幅的擺放位置、是否重複、是否可關閉。
- 出清成功後 sticky 狀態列的高度上限。
- 出清失敗（含 5xx 與網路層失敗）時的錯誤呈現與狀態同步。
- 1280 寬度下狀態列／橫幅的版面（交 art-lead 定視覺）。

**範圍外（non-goals）**

- **不改任何揭露類文案的字**：
  - `message`、`mode_reason`、`attribution`、`warnings`、徽章文字、4 個按鈕文字，都維持後端與風控定稿的字面。
  - 本 PRD 只動擺放與去重。
- **不拆分或截短 `message`**：結尾那句與 `mode_reason` 的語意重疊，因為 `message` 是後端一整段定稿字串，前端拆它等於改字。本輪接受這層重疊，見開放問題 Q4。
- 不處理後端冪等性（N-166，由 tech-architect 與 dev-lead 評估）。本 PRD 只列出和它的依賴。
- 不處理 N-160（modal 的 scroll chaining）、N-163（送出中焦點，已 PASS）。這兩項的既有驗收條件不得被本次改動破壞，見 AC-10。
- 不在出清流程加任何前置條件、倒數、額外確認（CEO EX-2「出口零摩擦」，`service.emergency_exit` 的 docstring 寫明「加前置條件是出口唯一不能有的東西」）。
- 不做 Safari、Firefox、觸控、螢幕閱讀器的驗收（沿用先前的驗證限制）。

## 功能需求

### N-164 與 N-165：成功橫幅

**FR-1　橫幅離開 sticky 區。**
成功橫幅不得出現在 sticky 狀態列的容器內，改放在排程台主內容區頂部，處於一般文件流（非 sticky、非 fixed）。
位置：狀態列之下、現有的歸屬語、§6 總覽區塊、警示、帳冊之上。是否在 `<h1>` 之前或之後，交 art-lead。

**FR-2　sticky 狀態列的高度不受成功橫幅影響。**
- 出清成功前後，sticky 狀態列的高度差在 ±4px 內（同一寬度、同一 mode 條件下比較）。
- 絕對上限（PM 暫定值，art-lead 可收緊，不得放寬）：
  - 375×812：不超過視窗高度 20%（162px）。
  - 1280×900：不超過視窗高度 15%（135px）。
- 參考：重新整理後的實測值為 87px（1280）與 127px（375），分別是 9.7% 與 15.6%。
- 此條在捲動 0／中段／底部三個位置都要成立。

**FR-3　成功回饋必須進入視窗。**
- 因為觸發鈕在 sticky 列，使用者可能在已捲動的位置按出清。成功後若橫幅不在可視範圍內，頁面要讓橫幅進入視窗，並且不被 sticky 狀態列遮住。
- 尊重 `prefers-reduced-motion`：減少動態時不做平滑捲動。
- **焦點行為維持 N-163 已驗收的狀態**：成功後焦點回到「全部出清」觸發鈕，不搬到橫幅。
- 橫幅應能被輔助科技宣告（live region）。這是 should，不是 must，不新增任何可見字面。

**FR-4　橫幅不可關閉，持續時間維持現行。**
- 橫幅只存在於當次工作階段，重新整理後消失（現況，已實測）。本輪不加關閉鈕。
- 理由見下方方案比較。本輪採「離開 sticky」後，橫幅隨頁面自然捲走，不再需要關閉。

**FR-5　橫幅不重複狀態列已顯示的同一句 `mode_reason`。**
- 橫幅內的 `mode_reason` 那一段只在「狀態列目前顯示的 `mode_reason` 與它不是逐字相同」時才顯示。
- 這覆蓋兩種情況：出清成功但 `/today` 尚未重新取得；以及重新取得失敗，狀態列仍停在舊模式。這兩種情況下橫幅仍保有那句凍結揭露，避免狀態列舊、橫幅又缺。
- 正常情況（兩者相同）：整頁只出現一次，出現在狀態列內，與模式徽章同一區塊。

**FR-6　揭露文案完整性。**
- 橫幅中的 `message`、`attribution`（非 null 時）、`warnings`（非空時）逐字不變、不摺疊、不截短，字級與對比不低於現行。
- 狀態列的 `mode_reason` 逐字不變。
- 沒有任何一段揭露文案被移到頁尾、tooltip、可展開區塊。

### NB-6：出清失敗

**FR-8a　失敗後自動同步後端狀態（P2，不需新文案）。**
- 出清請求以任何方式失敗（HTTP 5xx、其他非 2xx、網路層失敗）後，頁面要重新取得 `/today`，讓狀態列反映後端的真實模式。
- 理由：後端在 500 時無法分辨「已處理」與「未處理」（見「風險與依賴」）。狀態列的模式徽章是現有且唯一可信的事實來源，不需要新增任何宣稱。
- 對話框維持現行行為：保持開啟、仍在第 3 步、兩顆按鈕可再操作、焦點在「確認送出全部出清」（N-161、N-163 已驗收）。
- **不得因為失敗就封鎖重試**，原因是出口零摩擦（EX-2）。若要擋重複送出，屬後端 N-166 的範疇。

**FR-8b　500／網路失敗的文案（P3，待風控定稿）。**
- 對出清這個請求，不得再向使用者露出後端的英文原文（例如 `Internal Server Error`）。
- 新文案必須是「結果不確定」的中性語氣：
  - 不得暗示已處理，也不得暗示未處理。
  - 要指引使用者看狀態列的模式。
  - 同一句要涵蓋 5xx 與網路層失敗，因為兩者同樣無法判斷後端是否已落地。
- 現行 label「全部出清送出失敗」的「失敗」二字在不確定情境下可能被讀成「沒處理」，一併請風控判斷是否要換。
- 範圍：只限出清這個請求。共用的 `ErrorPanel` 對其他頁面的行為不得被改動。
- 文案草案，**僅供風控審閱，不是定稿，不得直接上線**：
  - label：「全部出清結果未確認」
  - 內文：「無法確認這次全部出清是否已被處理。請關閉此視窗，以頁面上方狀態列顯示的模式為準。」
- 定稿前，維持現行文案不變。

### NB-7：1280 版面

**FR-9　狀態列回到單一緊湊列。**
- 依 FR-1，橫幅離開後，1280 寬時徽章、規則版本、觸發鈕應在同一列，不再有高區塊中的垂直置中空白。
- 視覺細節（間距、橫幅在內容區的寬度與層級、是否與歸屬語區塊對齊）交 art-lead 定。

## 驗收條件

量測條件統一：headless Chromium，視窗 1280×900 與 375×812，production build。
本節「橫幅」指出清成功後出現的 `message` 區塊。
「狀態列」指 sticky 的模式列。
`R` 表示該句 `mode_reason` 的字面，取自出清回應。

### FR-1、FR-2、FR-9（N-164、NB-7）

**AC-1　橫幅不在 sticky 容器內（兩個寬度）**
- Given 排程台載入完成，狀態列為 sticky
- When 使用者完成三步確認並出清成功（mock 200 或沙盒真實出清皆可）
- Then 橫幅的任一祖先元素都不是 `position: sticky`／`fixed`
- And 橫幅位於 main 內容區，在歸屬語／總覽區塊／帳冊之上

**AC-2　狀態列高度不隨橫幅增加（375×812）**
- Given 視窗 375×812，出清前量得狀態列高度為 H0
- When 出清成功，橫幅出現
- Then 捲動位置為 0、中段、底部三處，狀態列高度與「重新整理後」的高度差皆在 ±4px 內
- And 高度不超過 162px（視窗 20%）

**AC-3　狀態列高度不隨橫幅增加（1280×900）**
- Given 視窗 1280×900
- When 出清成功，橫幅出現
- Then 狀態列高度在 0、中段、底部三個捲動位置皆不超過 135px（視窗 15%），且與重新整理後的高度差在 ±4px 內
- And 徽章、規則版本、觸發鈕位於同一列（NB-7 的視覺細節由 art-lead 驗收）

**AC-4　內容可讀區（375×812）**
- Given 視窗 375×812，出清已成功
- When 捲到任一位置
- Then 狀態列以下的可讀區不少於視窗高度的 80%
- And 沒有「第一個內容元素被狀態列遮住」的重疊（對照原量測：scrollY 781 時重疊 124px，改後應為 0）

**AC-5　有持倉的長橫幅（待測試資料）**
- Given 沙盒有持倉種子資料，出清回應的 `total_shares` 大於 0、`attribution` 非 null、`warnings` 非空
- When 出清成功
- Then AC-2、AC-3 的狀態列高度條件仍成立
- And 橫幅本身可完整讀取，不被截斷，也不產生內部捲軸
- 備註：目前沒有沙盒持倉種子流程。在這個流程存在前，此條以 mock 回應（attribution 與 warnings 皆非空）驗證，真實形狀標為「未驗」。

### FR-3（回饋可見性）

**AC-6　在已捲動位置出清，成功後橫幅進入視窗**
- Given 視窗 375×812，頁面已捲到底（橫幅的位置在視窗外）
- When 使用者從 sticky 列的觸發鈕完成出清且成功
- Then 橫幅上緣進入視窗，且不被狀態列遮住（橫幅頂端 ≥ 狀態列下緣）
- And `activeElement` 是「全部出清」觸發鈕（N-163 行為不變）
- And 在 `prefers-reduced-motion: reduce` 下，捲動是瞬間完成，沒有平滑動畫

**AC-7　在頁面頂端出清**
- Given 視窗 1280×900，scrollY 為 0
- When 出清成功
- Then 橫幅已在視窗內，頁面不發生不必要的捲動

### FR-4（持續時間）

**AC-8　重新整理後的行為**
- Given 出清已成功，橫幅顯示中（兩個寬度）
- When 使用者重新整理頁面
- Then 橫幅消失
- And 狀態列仍顯示「緊急出清後凍結」徽章與 `mode_reason` 一句（一次）
- And 橫幅內原有的 `message`、`attribution`、`warnings` 不再顯示（現況，非回歸）

**AC-9　本輪沒有關閉鈕**
- Given 橫幅顯示中
- When 檢查橫幅
- Then 沒有任何關閉或收合控制項
- And 沒有新增任何使用者面向的可見字面

### FR-5、FR-6（N-165 去重與文案完整）

**AC-10　去重，正常路徑（兩個寬度）**
- Given 出清成功，且 `/today` 已重新取得（狀態列顯示 `mode_reason` = R）
- When 檢查整頁文字
- Then R 在整頁恰好出現 1 次，且位於狀態列內、與模式徽章同一區塊
- And 這個區塊是 sticky，常駐可見，沒有摺疊
- 對照：原量測 `bodyOccurrencesOfExitResponseModeReason = 2`，改後 = 1

**AC-11　去重，狀態列尚未同步的視窗**
- Given 出清已成功，但 `/today` 尚未重新取得（可用 mock 延遲 `/today`）
- When 此時檢查畫面
- Then 橫幅仍顯示該句 R，使整頁在此期間至少有一處揭露 R
- And 待 `/today` 重新取得後，R 只剩狀態列那一處（同 AC-10）

**AC-12　去重，`/today` 重新取得失敗**
- Given 出清成功，之後 `/today` 重新取得失敗，狀態列仍顯示舊模式
- When 檢查畫面
- Then 橫幅仍顯示 R，且狀態列沒有悄悄被清空或出現與橫幅矛盾的新內容

**AC-13　逐字不變**
- Given 任一出清成功回應（mock 或真實）
- When 比對畫面文字與回應欄位
- Then 橫幅的 `message`、`attribution`（非 null 時）、`warnings`（非空時）與狀態列 `mode_reason` 的字面，和回應／`/today` 欄位逐字相同
- And 與 N-164／N-165 實作前的字面相比，一字未改
- And `attribution` 為 null 時沒有歸屬語那一行，`warnings` 為空時沒有警語清單（沿用現行 EMPTY 契約）

**AC-14　風控地板**
- Given 出清成功，任一寬度與捲動位置
- When 檢查所有揭露類文案（`message`、`mode_reason`、`attribution`、`warnings`）
- Then 每一段都處於可見、非摺疊的元素內，不在頁尾，不在 tooltip，不在需要點擊才展開的區塊
- And 至少一處揭露（狀態列的 `mode_reason`）與模式徽章在同一區塊並常駐
- And 字級不低於所在區塊內文，對比不低於現行值

### FR-8a、FR-8b（NB-6）

**AC-15　失敗後同步狀態：後端其實已處理**
- Given 對話框在第 3 步；mock 讓 `POST /emergency-exit` 回 500，並讓之後的 `/today` 回 `emergency_frozen`
- When 使用者送出，收到 500
- Then 頁面自動重新取得 `/today`，狀態列徽章在不重新整理的情況下變為「緊急出清後凍結」
- And 對話框仍開啟，錯誤面板顯示，「確認送出全部出清」仍可再按

**AC-16　失敗後同步狀態：後端確實未處理**
- Given 同上，但之後的 `/today` 仍回 `normal`
- When 使用者送出，收到 500
- Then 重新取得 `/today` 後，徽章仍為「正常」，沒有任何元素宣稱「已處理」

**AC-17　網路層失敗**
- Given 出清請求發生網路層失敗（requestfailed）
- When 使用者送出
- Then 行為與 AC-15、AC-16 相同：重新取得 `/today`、對話框維持、可重試
- And 送出鎖在失敗後釋放（補足 N-163 NB-4 未驗的項目）

**AC-18　不露出英文原文，不暗示結果（FR-8b，待風控定稿後才可驗）**
- Given 出清請求回 500，body 為 `{"detail":"Internal Server Error"}` 與純文字兩種
- When 檢查錯誤面板
- Then 面板文字不含 `Internal Server Error` 等後端英文原文
- And 面板文字不含任何暗示「已處理」或「未處理」的語句
- And 面板文字有指向狀態列的指引
- And 面板文字與風控定稿逐字相同
- 風控定稿前，此條標示為 blocked，不得以草案文字通過。

**AC-19　對話框行為不回歸（N-161、N-163）**
- Given 出清失敗後
- When 在對話框內按 Tab、Shift+Tab 各 8 次、按 Esc
- Then 焦點全程在對話框內；Esc 後焦點回到「全部出清」
- And 送出中兩顆按鈕仍是 `aria-disabled="true"`，快速重複觸發仍只送出 1 筆 POST

## 風險與依賴

1. **後端在 500 時無法分辨「已處理」與「未處理」（NB-6 的根本限制）。**
   我讀了 `app/api/playbook.py` 與 `app/playbook/service.py`、`store.py`（只讀，未執行）。`POST /emergency-exit` 的流程是：
   - 先讀取批次與行情。
   - 再呼叫 `apply_effects`，其中 `freeze_emergency` 透過 `_set_state` 寫入凍結狀態，使用自己的連線與交易。
   - 再呼叫 `record_directives`，另開一個連線與交易，寫入指令稽核日誌。
   - 回到 API 層後才組回應（`_lines`、`now_iso`）。

   所以 500 可能發生在三個不同位置，結果完全不同：
   - 凍結寫入之前：整筆未處理。
   - 兩個交易之間：凍結已生效，但稽核日誌沒有出清的指令列（半處理）。
   - 兩個交易都完成之後（組回應時出錯）：已完整處理。

   整個流程沒有包在單一交易中，沒有請求 ID 或冪等鍵，回應也沒有「已處理」標記。網路層失敗（連線中斷）同理。
   **結論：本 PRD 的任何文案都不得暗示已處理或未處理。**
2. **與 N-166（冪等性）的關聯。**
   - 因為 500 後使用者可能重試，後端對重複呼叫的行為會直接影響「重試是否安全」。
   - 我的讀 code 觀察（非驗證，請 tech-architect 確認）：
     - 凍結狀態是「設定到某個日期」，同一天重複寫入結果相同。
     - 但 `record_directives` 是 INSERT。我沒看到出清會關閉批次，所以重複呼叫可能重複寫入稽核日誌。
     - 前端 dblclick 重複送出的 2 筆 POST 已實測（修鎖前），並已由前端鎖擋下。
   - FR-8a 的狀態同步能降低盲目重試，但不能取代 N-166。
3. **FR-3 的自動捲動**可能與焦點管理互相干擾，需 qa-e2e 實機確認，見 AC-6、AC-19。
4. **FR-5 的條件式隱藏**在 `/today` 重新取得完成的瞬間會讓橫幅少一段（內容區的版面位移，不在 sticky 內）。請 art-lead 評估可接受度。
5. **有持倉時的真實形狀與高度未驗。**
   - 沙盒只拿到「無持有批次」那一支。
   - AC-5 在持倉種子流程出現前只能用 mock。
   - 這是已知的驗證缺口，不是通過的證據。
6. **狀態列背景為 `bg-black/95`**（讀 code，5% 透明）。qa-e2e 截圖中疑似看到的殘影可能與此有關，computed style 沒量。這屬 NB-3（info），不在本 PRD 範圍，但交 art-lead 決定是否改為不透明。
7. **擺放變更必須讓風控知情**：橫幅從狀態列區塊移到內容頂部，且橫幅中的 `mode_reason` 改為條件式顯示。
8. 依賴：
   - 風控：FR-8b 文案與 label 定稿；擺放變更知情。
   - art-lead：視覺規範（見「交接」）。
   - tech-architect：N-166、500 語意的確認。
   - frontend-engineer：實作（待 PRD 定稿與 art-lead 規範）。
