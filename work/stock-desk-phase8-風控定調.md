# 清單一:操作摘要/進場評估措辭原則

> 適用範圍:`/position/[symbol]` 決策中樞頁的操作摘要與進場評估、建議卡、以及任何引用 `build_advice` 輸出的畫面文字。
> **不適用**於警示推播(`app/api/alerts.py` → 事件訊息)——推播為非請求式接觸,其既有更嚴格的禁用清單(`apps/stock-desk/backend/tests/test_alerts_engine.py:252` 的 `買進/賣出/加碼/減碼/建議/保證/必漲/穩賺`)**維持不變、不得與本清單「統一」而放寬**。
> 以下所有句型皆為**判準示例,非定稿文案**;定稿由 creative-lead/tech-writer 撰寫後回風控複審。

## 1. 動詞與詞彙裁定

### 1.1 核心原則(一句話判準)

- **句子的主詞永遠是引擎,不是使用者。** 「規則評估傾向減碼」可用;「你應該減碼」不可用——同一個動詞,責任歸屬不同,這才是紅線所在。
- **動詞可以直白,框架必須完整。** 不要求把「減碼」改寫成「傾向降低部位」;把動詞繞遠只會犧牲可讀性而不增加誠實度,誠實度來自歸屬語+反方論點+失效條件,不是來自動詞的迂迴。

### 1.2 白名單(可用,須以名詞化/描述性形式出現,且句中帶歸屬語)

| 引擎 action | 允許的中文標籤 | 理由 |
| --- | --- | --- |
| `add` | 加碼參考、可再買進的參考區間 | 名詞化後無法被讀成指令;「參考」是既有 `quantity_range` 的語意,非新承諾 |
| `hold` | 續抱、觀望、維持現狀 | 三者皆為「不動作」,本身不含承諾風險 |
| `reduce` | 減碼參考、降低部位的參考區間 | 同上;`basis` 既有文字已用同一框架 |
| `take_profit` | 分批獲利了結參考 | 「分批」是既有規則集語意(`bollinger_upper_breach`),保留可降低一次性出清的暗示 |
| `stop_loss` | 停損評估、規則評估傾向停損 | 保留「評估」二字,避免讀成執行指令 |
| `insufficient_data` | 資料不足,本次不提供操作評估 | 既有語意,不得美化為「暫無明顯訊號」 |

- 通用可用詞:**規則評估、傾向、參考區間、依據、反方論點、失效條件、觀察、換算、推導、命中規則**——皆為既有引擎欄位的自然中文,讀者可回溯到具體欄位。
- 強制歸屬語:每個動作標籤在摘要中**首次出現時**必須帶「規則評估」或「本規則集(版本 X)」作為主詞來源,理由:`rules_version` 已在卡片上,摘要不得把有版本的規則輸出講成無主的結論。

### 1.3 禁用清單(required,須同步擴充自動化測試)

| 類別 | 禁用詞 | 理由 |
| --- | --- | --- |
| 保證性 | 保證、必漲、必跌、必賺、穩賺、包賺、零風險、無風險、一定會 | 既有紅線,`BANNED_PHRASES`(`app/advice/loader.py:45`)已列,本次擴及前端文案 |
| 價格目標 | 目標價、合理價、上看、看到 N 元、target_price、price_target、fair_value | 既有紅線(`test_advice_wording.py:29`),無例外 |
| 技術位置擬人化 | 支撐位、壓力位、防守價、停利價、出場價、進場價、buy point、sell point | 「支撐/壓力」是對未來買賣盤行為的推斷,不是事實陳述——見 §4 的 VETO 理由 |
| 祈使/急迫 | 快買、快賣、立即、馬上、趕快、進場時機、最佳買點、逢低買進、抄底、追高、攤平 | 祈使句把責任從引擎轉嫁給使用者的行動;「攤平」另含策略指示,超出引擎能力 |
| 部位規模指令 | all-in、全押、梭哈、重壓、押身家 | 與 `MAX_POSITION_WEIGHT_CEILING = 0.50`(`app/advice/limits.py:78`)直接牴觸,出現即自相矛盾 |
| 預測/確定性 | 將會、即將、預計上漲、突破在即、有望、可期、潛力股、飆股、強勢股 | 引擎不預測;這類詞把統計描述改寫成對未來的陳述 |
| 機率洗白 | 勝率、成功率、命中率、準確率、高機率 | 直接稀釋 `CONFIDENCE_MEANING`(`engine.py:65`)與 `WEIGHT_MEANING`(`engine.py:68`),這是本次改版最容易破防的一點 |
| 即時性 | 即時、real-time、盤中、最新報價、現價(單獨使用時) | 見 §5;「現價」只有在「現價 −」的換算式中、且緊鄰資料基準日時可用 |
| 行銷語氣 | 穩健獲利、輕鬆賺、躺著賺、專業級判斷、精準 | 建議類產品的行銷語氣本身即誘導 |

- **required|測試義務**:上表須落為單一常數來源,由後端與前端共用掃描(前端文案模板亦須被掃到),並擴充 `tests/test_advice_wording.py` 的 `FORBIDDEN_TERMS` / `FORBIDDEN_ADVICE_TERMS`。理由:既有紅線只掃後端 dict,本次文案主體在前端,不擴充等同無防護。

## 2. 每一則建議輸出的必附元素(八項,缺一即 VETO)

1. **固定免責聲明**(`DISCLAIMER`,`engine.py:60`):與主結論**同一視覺區塊內常駐**,不得摺疊、不得移至頁尾、字級不得小於區塊內文。理由:摘要置頂後若免責聲明留在原建議卡位置,等同視覺弱化。
2. **`confidence` 與 `CONFIDENCE_MEANING` 同框**:只要出現信心等級徽章,「非勝率或機率」那句必須在同一視線範圍內,不得改寫、不得縮寫為「非機率」。理由:`confidence` 是本次改版中最可能被單獨截取的元素。
3. **資料基準日**:「本評估基於 YYYY-MM-DD 收盤資料」(AC-C8.2),逐字常駐於摘要內,不得只靠區塊角落的徽章代替。
4. **非即時揭露**:系統級常駐一句(AC-C8.3),且用語受 §5 約束。
5. **至少一條反方論點全文 + 一條失效條件全文**:有命中規則時,`counterarguments` 與 `invalidation_conditions` 各至少一條**以全文顯示於摘要區塊內**,不得僅以「展開查看」連結代替。理由:把散落欄位重組為摘要,最大的風控風險就是重組時只帶走正面證據;引擎已強制每條命中規則附反方論點(`test_advice_wording.py:158`),呈現層不得把它丟掉。
6. **規則式聲明 + `rules_version`**:一句「本評估由固定規則集(版本 X)計算,非預測模型」。理由:CEO 的需求描述容易讓人期待這是「判斷」,必須先說清楚它是規則。
7. **`quantity_range` 缺席時的成因**(FR-2):不得留白、不得沿用概略舊文案。**required 且維持 Phase 6 放行條件 (b)**:在風控逐條核准成因文案前,既有概略文案不得改寫為指稱特定成因。
8. **候選模式的證據限制語**(見 §3):僅候選模式適用,但為常駐必附。

- **required**:以上八項須有一條契約測試斷言「摘要 payload 同時含這八項」,而非靠 code review 把關。理由:呈現層重構會反覆發生,人工把關會漏。

## 3. 持倉建議 vs 未持有進場評估:保守度差異的五個具體體現

1. **不得出現正面結論句。** 候選模式禁止任何「可以進場/適合進場/進場條件成立」形式的句子。`add` 在候選模式只能表述為事實組合:「規則評估未命中防禦型規則,建設性規則命中 N 條」+「這不構成進場理由」。理由:CEO 的問句是「是否可以進場」,而引擎沒有能力回答是非題;回答是非題就是承諾。
2. **動詞白名單縮減。** 候選模式禁用「續抱」(無倉可抱)、「加碼」(無倉可加)、「減碼/停損/停利」(無倉可減)。僅允許「進場評估」「規則評估傾向」「可建倉股數參考區間」。理由:持倉語彙套在零部位上,本身即不實陳述。
3. **證據密度常駐揭露 + 量化。** 除 AC-C7.2 的定性句外,**required**:同時顯示 `evaluation.data_completeness` 與被跳過的規則條數(`skipped_rules` 已有)。理由:定性句讀者會略過,數字不會;且這兩個欄位引擎已產出,零成本。
4. **信心等級不可跨模式比較。** 候選模式的 `confidence` 旁必須加一句「候選評估的規則覆蓋率低於持倉評估,本等級不可與持倉評估的等級直接比較」。理由:`_confidence()`(`engine.py:239`)以完整度為輸入,候選模式的完整度天然較低,同一個「medium」在兩種模式下意義不同。
5. **候選模式不輸出任何價位形式欄位。** 見 §4 條件 C6。

- **`hold` 或防禦型輸出時(AC-C7.3)**:措辭定調為「本次規則評估未支持進場」,**禁止**軟化為「可再觀察」「時機未到」「可留意」。理由:「時機未到」隱含「時機會到」,是對未來的承諾;「可留意」是誘導保留。

## 4. 停損「參考位」裁定:條件式核准

**裁定:可以輸出,但它不是「參考位」,而是「你自己的風險預算換算出來的距離」。**

裁定依據(紅線的真正位置):`atr_stop_multiple × ATR(14)`(`limits.py:427`)的兩個輸入——使用者在設定頁自訂的停損倍數、以及過去 14 日已實現的波動統計——**都不含任何對未來價格的看法**。它與目標價的差別不在「有沒有數字」,而在於**這個數字是從你的風險預算算出來的,還是從對市場的看法算出來的**。前者可以,後者不行。且此數字的比率形式(第 4 條上限「單筆最大可承受虧損」)使用者早已在看,只是沒看到價位形式。

須全數滿足的八項條件(缺一即不得輸出,且不得以任何其他名義變相輸出——AC-C6.3 失敗路徑照舊適用):

- **C1|命名固定。** 後端欄位名 `risk_budget_stop_reference`;UI 標籤「風險預算換算的停損距離」。**禁用**「停損參考位」「防守價」「參考價」「支撐位」。理由:「位」字暗示技術位置,會把風險預算的產物讀成市場觀點。
- **C2|距離在前、價位在後。** 呈現順序固定為「距離 NN.N 元 → 對應價位約 NNN 元」,不得只顯示價位。理由:讀者第一眼讀到的必須是風險預算的產物。
- **C3|公式與輸入來源逐字可見。** 必須寫出「以你在設定頁設定的停損倍數 N.N × ATR(14) NN.N 元換算」。理由:公式可見 = 讀者能自行驗證這不是預測,這是本欄位得以存在的唯一基礎。
- **C4|固定限定語。** 必附「這是你自己的風險預算換算結果,不是價格預測、不是目標價,也不是『跌破就該賣』的指令;ATR 為過去 14 日的波動統計,波動改變時此數字隨之改變。」
- **C5|向上的價位一律否決,無條件。** 不得輸出停利參考位、目標區間、上檔壓力位或任何上方價位。理由:向下的數字用途是限制損失(保守方向),向上的數字用途只能是預期報酬(預測方向)——這是不對稱的,明確以不對稱處理。
- **C6|僅持倉模式。** 候選模式不輸出。理由:尚無部位時,此數字只能被讀成「進場後的防守價」,即最接近目標價的滑坡。
- **C7|缺輸入即誠實缺席。** ATR 不可算、缺價格或缺 FX 換算時顯示「無法換算(缺 ATR(14))」,**不得**回退到近期低點、固定百分比或任何替代估法。理由:替代估法會悄悄變成技術位置。
- **C8|測試護欄。** 除 §1.3 的禁用詞擴充外,**required** 新增一條測試斷言:卡片 payload 中「價位形式的欄位」以 allowlist 白名單管理,且白名單長度為 1。理由:防止未來第二個價位欄位以其他名義長出來——這是本裁定最主要的長期風險。

> **附註(VETO)**:PM 所提「僅呈現技術位置事實如『近期支撐 X』」**予以否決**。「支撐」不是事實,而是對未來買盤行為的推斷;改成「近期低點 X 元」雖是事實,但把它放進操作摘要,其唯一用途就是被讀成防守位,且它缺少風險預算的錨——比 ATR 換算更差。此路不通,無替代版本。

## 5. 誠實邊界執行細則(沿用 CEO 裁示,補上可執行條款)

1. **「即時」「real-time」全站禁用於描述本產品能力**,掃描範圍含前端文案模板、`work/stock-desk-產品說明.md`、README 與任何發布說明;納入 CI。理由:既有掃描只涵蓋後端輸出,文案主體不在那裡。
2. **「及時」亦不得作為產品文案。** CEO 原話中的「及時」是需求描述,不是可上線的措辭。允許表述僅有一種:「打開頁面當下,以系統手上最新的一份資料計算」。
3. **「最新」只能修飾「系統手上的資料」,不能修飾市場。** 「系統最新一份資料」可用;「最新股價」「最新行情」不可用。
4. **排程未啟動時不得承諾更新頻率**(AC-C8.4):文案一律加「排程啟用時」限定,或只陳述資料實際 `as_of`。理由:主動承諾在排程未跑時即為不實陳述。
5. **摘要必標「本評估基於 X 月 X 日收盤資料」**,且超過一個交易日時額外顯著提示(AC-C8.2);此提示不得與一般徽章同級呈現。

# 清單二:FR-9(總曝險)六問定案

## a. 分母定義 → **定案:選項 B**(新增獨立 `gross_exposure` 路徑,`total_equity_twd` 定義不變)

- **理由**:選項 A 會把第 1、4 條上限的分母從「已估值部位市值」換成通常更大的自報淨值(含現金),分母變大→比率變小→**原本 `violated` 的會靜默翻成 `passed`**。這是全面且無聲地放寬既有風控閘門,不得夾帶在一個新功能裡上線。
- 選項 B 保留既有保守誤差方向(分母偏小→比率偏高→更早擋下加碼),與 `book.py` 的 `EQUITY_BASIS_NOTE` 慣例一致。
- **連動裁定**:FR-3 走 AC-3.1,文案維持「總資產(已估值部位市值)」;FR-8 的 AC-8.2 只有第 3 條會翻轉,第 1、4 條觀測值不變。
- **標記「需 CEO」**:若 CEO 明確要選項 A,屬**放寬既有風控上限**,須 CEO 書面同意+發布說明明標行為變更+第 1、4 條文案同步改寫,並回風控複審。**預設建議:B,不阻塞開工。**

### a-附加(此問未列但必須一併定案,否則 B 會有一個不保守的破口)

- **公式**:分子=已估值部位市值合計,分母=使用者自報淨值。
- **required|任一部位估值失敗時,第 3 條一律回 `not_evaluable`。** 理由:分子漏掉估值失敗的部位會讓曝險比率**偏低**——這是選項 B 唯一往樂觀方向偏的誤差,必須堵死而非揭露了事。此規則與 `book.py` 既有的「部分帳本不冒充完整帳本」原則同源。
- **required|第 3 條 `detail` 必附三句**:(1) 分子由系統計算、分母由使用者自報,兩者來源不同;(2) 本比率假設持倉清單完整,未登錄的部位不計入分子,會讓曝險看起來偏低;(3) 自報淨值的輸入時間。

## b. 新鮮度降級 → **定案:30 天失效,7 天起提示**

- 7 天起顯示「已 N 天未更新」但仍可評估;**滿 30 天自動退回 `not_evaluable`**,原因逐字說明「淨值輸入已超過 30 天未更新」並提示更新(AC-9.4)。
- **理由**:淨值同時受市值波動與現金進出影響,30 天約為一個對帳週期,再長即不足以代表當下;7 天的軟提示讓使用者在硬失效前有機會補上,避免「上限突然消失」的體驗斷崖。
- 天數由風控核定(風控參數,非商業決策);**放寬至 30 天以上須 CEO 書面同意**,比照 `limits.py` 兩個硬上界的治理慣例。

## c. 防呆 → **定案:三檔,拒絕與警示分明,一律不得靜默 clamp**

| 輸入 | 處置 | 理由 |
| --- | --- | --- |
| ≤ 0 | **422 拒絕** | 分母數學上無效 |
| < 已估值部位市值 × 0.95 | **422 拒絕**,附繁中理由「自報淨值小於系統已估值的部位市值」 | 此輸入會讓曝險恆 >100% 恆違反,實務上幾乎必然是填錯欄位(例如填了現金餘額);0.95 容差涵蓋收盤價與券商 App 查看時點的正常落差 |
| > 已估值部位市值 × 10 | **接受但顯著警示**,警示文字須寫明「若此數字有誤,第 3 條上限將失去意義」 | 大量持有現金是合法情境不可拒絕;但灌水淨值會讓曝險恆合規,屬靜默放寬風險,必須讓使用者看見 |

- **required|不得靜默 clamp**:沿用 `limits.py` 既有立場——被無聲修正的數值是使用者日後會誤以為自己設定過的數值。

## d. 歷史序列 → **定案:只留最新一筆 + `updated_at`,不做歷史 UI**

- **理由**:單人本機工具,稽核價值低於維護成本;AC-9.1 已要求顯示上次數值與更新時間,足以支撐 (b) 的新鮮度判斷。
- **suggested**:淨值變更寫入既有應用層 log 即可(非 UI 功能)。若日後要做「曝險趨勢圖」屬新需求,須另立 FR 並重新過風控。

## e. 硬性上下界 → **定案:不新增絕對金額界;不需新的 CEO 核可**

- **下界**由 (c) 的 0.95× 相對規則承擔,**上界**由 (c) 的 10× 相對警示承擔。**理由**:絕對金額界會隨資產成長失效,相對界則永遠有意義。
- 本問與 `MAX_POSITION_WEIGHT_CEILING` / `MAX_GROSS_EXPOSURE_CEILING` 性質不同——那兩者是「風控上限值的上界」(防止閘門被開太大),此處是「輸入資料的合理域」,不需同級治理。
- **`max_gross_exposure` 預設 1.00、硬上界 1.50 維持不變,不需新的 CEO 核可**(僅啟用、未放寬),故需求書開放問題 8 的答案是「不需要」。
- **required|發布說明必須明標行為變更**:第 3 條上限將由長期的 `not_evaluable` 轉為**實際生效並可能開始擋下加碼建議**。使用者有權事先知道一條沉睡的閘門要醒來。
- **suggested|標記「需 CEO」(低優先,不阻塞)**:第 3 條啟用後若持續 `violated`,使用者把 `max_gross_exposure` 由 1.00 上調(1.50 硬上界內)是否需額外閘門。**預設建議:允許**(該區間本就是 CEO 已核可的可調範圍),但調高時 UI 須顯示一次性確認文字「你正在放寬風控上限」。CEO 無異議即依預設執行。

## f. 幣別 → **定案:只收 TWD,單一欄位,不支援外幣輸入**

- **理由一**:報告幣別已固定為 TWD(`book.py` 全模組慣例),多一種輸入幣別即多一個換算時點問題。
- **理由二**:外幣輸入需引入匯率換算,而現行 FX adapter 自述端點未查證且採即期買賣中點模型值(見 `work/stock-desk-已知限制與後續.md` 第 7 項)。把一個未查證的匯率放進**風控上限的分母**,會讓整條上限的誤差不可控——這是不能接受的位置。
- **理由三**:CEO 持倉台股為主、美股少量,自行換算成本極低,且他自己用的匯率至少是他自己知道的。
- **required|欄位標籤與提示**:標籤須寫「帳戶總淨值(新台幣)」,並附「若你有外幣資產,請自行換算為台幣後填入;系統不會為此欄位做匯率換算」。理由:若使用者誤填 USD 數字,會產生約 30 倍誤差——(c) 的 10× 警示是第二道防線,這句提示是第一道。
