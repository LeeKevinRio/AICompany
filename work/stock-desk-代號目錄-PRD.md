## 背景與目標

CEO 提出三個環環相扣的體驗問題，共同指向同一個缺口：產品裡沒有「代號 ↔ 公司名稱 ↔
所屬市場」這份目錄（以下稱**證券目錄**），導致：

1. 個股頁只顯示代號（如 `2330`），使用者要自己記得代號對應的公司名稱。
2. 使用者得自己知道、自己選「這是台股還是美股」——但代號本身理論上就決定了市場，讓
   使用者手選等於叫使用者做系統該做的事，選錯了還可能查到別的市場、算出錯的建議。
3. 搜尋只能打完整代號直達，打公司名稱或打代號前幾碼都找不到候選。

**目標**：建立證券目錄作為單一事實來源，讓「代號 → 市場」與「代號 → 公司名稱」都由系統
自動解析，使用者不必手動選市場，也能用公司名稱或代號片段找到標的。

**非目標（見範圍外）**：模糊搜尋容錯、注音／簡稱別名、美股公司名稱（第一期，理由見開放問題）。

## 使用者與情境

- **主要使用者**：CEO 本人（stock-desk 目前唯一使用者，單機、無多租戶）。
- **情境 A**：使用者在 NavBar 搜尋框打「2330」或「台積電」，想直達個股頁，過程中不想被
  問「這是哪個市場」。
- **情境 B**：使用者忘記完整代號，只記得「30」開頭，想看有哪些候選（如 3037）。
- **情境 C**：使用者已經在個股頁或持倉列表，只看到代號，想知道這支股票叫什麼名字。
- **情境 D**（離線降級）：CEO 本機尚未執行過目錄同步（或雲端開發環境驗收時，目錄本來就是
  空的），此時搜尋與個股頁不能報錯或空白卡死，要退化到「純代號直達」這個产品從第一天
  就有的能力。

## 範圍內 / 範圍外

### 範圍內
1. 證券目錄資料表：代號、公司名稱、市場、資料版本時間（`as_of`）、來源（`source`）。
2. CEO 本機一鍵同步工具：比照 `verify_market_data.py` 先例，抓 TWSE OpenAPI 上市公司清單
   與 TPEx OpenAPI 上櫃清單，寫入本機 SQLite，供離線查詢。
3. 後端搜尋 API：輸入片段，回傳「代號前綴比對」+「公司名稱子字串比對」的合併候選清單
   （代號、名稱、市場），筆數上限由 API 定一個保守預設值，前端可覆寫。
4. 後端市場判定：查目錄，代號存在則帶出對應市場；查無則維持既有輸入型態的容錯（見
   FR-2 與開放問題）。
5. 前端 NavBar 搜尋框改 combobox：輸入即查候選、鍵盤可上下選取與 Enter 確認、防抖由前端
   控制（不寫死秒數在本 PRD，由 tech-architect / frontend-engineer 訂）。
6. 前端移除 NavBar 與個股頁的手動市場 `<select>`；市場改為系統判定後的**唯讀顯示徽章**。
7. 個股頁標題與持倉列表（`PositionsTable.tsx`）補上公司名稱顯示；查無對應目錄資料時
   fallback 為只顯示代號，不自行拼湊或臆測名稱。
8. 目錄未同步（本機從未跑過同步工具、或雲端開發環境無目錄資料）時的誠實降級路徑。

### 範圍外（本期不做）
- **名稱模糊搜尋容錯**：錯字、拼音、注音、簡稱別名（如打「台積」以外的暱稱、英文縮寫）
  不在本期範圍，僅做前綴（代號）與子字串（名稱）比對。
- **美股公司名稱**：第一期只做台股目錄；美股代號維持只顯示代號（理由與後續規劃見開放
  問題）。
- **市場自動判定用於「新增持倉」表單**：`ManualAddForm.tsx` 的手動新增部位流程是否也要
  拿掉市場 `<select>`，本 PRD 不代下決定，因為手動新增可能包含目錄未收錄的標的（如興櫃、
  尚未上市），列為開放問題。
- **目錄的即時性 / 自動排程同步**：本期是 CEO 手動觸發同步（比照 `verify_market_data.py`），
  不做背景排程、不做上線後自動每日更新。
- **興櫃 / 未上市代號**：TWSE 上市清單與 TPEx 上櫃清單以外的代號（如興櫃）不在本期目錄
  收錄範圍，查無時走「查無目錄資料」的誠實 fallback，不當成錯誤。

## 功能需求（逐條編號）

### FR-1　證券目錄資料建置（後端 + CEO 本機同步工具）
系統維護一份「代號 → 公司名稱 → 市場」目錄，來源為 TWSE OpenAPI 上市公司清單、TPEx
OpenAPI 上櫃清單，比照 `verify_market_data.py` 的「CEO 本機執行、結果落地」模式：因雲端
開發環境對財經網域 egress 封鎖，本目錄**不能**假設可在雲端環境即時抓取，同步動作必須是
CEO（或任何有網路的機器）手動觸發一支腳本，結果寫入本機 SQLite 快取，之後離線可查。

### FR-2　後端市場自動判定
給定一個代號，後端查證券目錄：
- 目錄中查得到 → 回傳目錄記載的市場，個股頁、搜尋結果都用這個市場，使用者不必手選。
- 目錄中查不到（目錄未同步、或代號不在收錄範圍，如興櫃/美股尚未收錄） → 不得憑代號格式
  「猜」市場（例如「純數字＝台股」這種規則本身就可能因未來上市代號規則變化而誤判，且
  美股也存在少數純數字場外代號）；此時維持「使用者最後一次操作留下的市場、或明確的『市場
  未知，請選擇』狀態」，兩者取何種降級行為列為開放問題，需 tech-architect 與 CEO 一起定。

### FR-3　搜尋 API：代號前綴比對 + 公司名稱子字串比對
新增後端搜尋端點，輸入一段文字，回傳候選清單，每筆含代號、公司名稱（若目錄有）、市場。
比對規則：
- 輸入視為代號時：前綴比對（打「30」比對出以 30 開頭的代號，如 3037）。
- 輸入視為公司名稱片段時：子字串比對（打「積」比對出名稱中含「積」的公司）。
- 兩種比對同時執行，結果去重合併回傳。
- 回傳筆數上限由後端訂一個保守預設值（如 20 筆），可由前端帶參數覆寫（防抖動作在前端做，
  不在本 PRD 訂死毫秒數，交 frontend-engineer 依既有防抖慣例實作）。

### FR-4　NavBar 搜尋框改為 combobox
`NavBar.tsx` 的 `SymbolSearch` 元件改造：
- 輸入時即時呼叫 FR-3 搜尋 API（前端防抖），下拉顯示候選（代號＋公司名稱＋市場）。
- 支援鍵盤上下選取、Enter 確認、Esc 關閉候選。
- 選定候選後直接導向 `/position/[symbol]`，**不再帶 `?market=` 由使用者手選**——市場由
  FR-2 的後端判定決定，或沿用候選項目本身回傳的市場值。
- 保留現有「直接打完整代號按查詢／Enter」的直達路徑（FR-2 的離線降級要靠這條路徑撐住）。

### FR-5　移除手動市場選擇，改為唯讀顯示徽章
- `NavBar.tsx` 的 `<select id="nav-market-search">` 移除。
- `position/[symbol]/page.tsx` 的市場 `<select>`（可切換市場重查）移除，改為顯示 FR-2
  判定出的市場徽章（唯讀，沿用既有 `marketLabel()` 文案）。
- 個股頁網址是否保留 `?market=` query param（供分享連結、瀏覽器上一頁等場景），或改由
  後端純代號判定，列為開放問題（影響既有連結相容性）。

### FR-6　個股頁與持倉列表補公司名稱
- 個股頁標題由「僅代號」改為「代號＋公司名稱」（目錄查無時只顯示代號，不顯示任何佔位
  猜測文字如「未知公司」以外的中性字樣）。
- `PositionsTable.tsx` 的持倉明細比照辦理，逐列補公司名稱欄位。

### FR-7　目錄未同步的誠實降級
任何用到目錄的功能（搜尋候選、市場自動判定、公司名稱顯示），在目錄完全未同步（本機
SQLite 無此表或表為空）時：
- 搜尋退化為「純代號直達」——使用者仍可打完整代號 Enter 直接進個股頁，不得報錯、不得
  卡住整個搜尋框。
- 候選下拉不顯示（不假裝有候選），可選擇性顯示一行提示「尚未同步證券目錄，僅支援代號
  直接查詢」（文案細節由 frontend-engineer / tech-writer 定）。
- 公司名稱顯示 fallback 為只顯示代號。
- 市場判定 fallback 依 FR-2 開放問題的裁示執行，但無論裁示為何都不得阻斷既有「輸入代號
  查個股」的核心路徑。

## 驗收條件

### AC-1（對應 FR-1）目錄同步落地可離線查
- **Given** CEO 在有網路的本機執行同步工具
- **When** 工具成功呼叫 TWSE OpenAPI 上市清單與 TPEx OpenAPI 上櫃清單
- **Then** 本機 SQLite 寫入代號、公司名稱、市場、`as_of`、`source` 欄位，且之後在**斷網**
  環境下啟動後端，查詢目錄仍能讀到剛才寫入的資料（驗證「落地快取、離線可用」）。

### AC-2（對應 FR-1）同步失敗誠實回報，不留半套資料
- **Given** CEO 執行同步工具時 TWSE 或 TPEx 其中一個來源請求失敗（逾時／格式錯誤／連線被拒）
- **When** 工具收尾
- **Then** 終端輸出與報告明確標示該來源 FAIL/UNREACHABLE 及原因，已成功的另一來源資料仍
  正常寫入，不因單一來源失敗而整批放棄，也不用另一來源的資料去猜失敗來源的內容。

### AC-3（對應 FR-2）目錄命中時自動判定市場
- **Given** 證券目錄已同步，內含代號 `2330` → 市場 `TW`
- **When** 使用者透過搜尋或直接輸入 `2330` 進入個股頁
- **Then** 系統自動以 `TW` 市場查價與訊號，個股頁不出現任何可切換市場的下拉選單，僅顯示
  市場徽章「台股（TW）」。

### AC-4（對應 FR-2）目錄未命中時不瞎猜市場
- **Given** 證券目錄已同步但代號 `9999X`（範例，非目錄收錄代號）查無
- **When** 使用者輸入 `9999X` 進入個股頁
- **Then** 系統不得依代號格式（如是否純數字）自行猜測市場；依開放問題 Q1 裁示的降級規則
  執行，且該降級行為不阻斷頁面渲染、不拋出未處理錯誤。

### AC-5（對應 FR-3）代號前綴比對
- **Given** 證券目錄已同步，內含代號 `3037`（以及其他以 `30` 開頭的代號）
- **When** 使用者在搜尋框輸入 `30`
- **Then** 搜尋 API 回傳的候選清單中包含 `3037`，且清單只含代號以 `30` 開頭的項目（不含
  代號中間或結尾出現 `30` 但開頭不是 `30` 的項目）。

### AC-6（對應 FR-3）公司名稱子字串比對
- **Given** 證券目錄已同步，內含公司名稱「台灣積體電路製造股份有限公司」對應代號 `2330`
- **When** 使用者在搜尋框輸入「台積電」或名稱中確實存在的子字串（如「積體電路」）
- **Then** 搜尋 API 回傳候選中包含 `2330`，且候選項目附帶完整公司名稱與市場。

### AC-7（對應 FR-3）候選筆數有上限
- **Given** 輸入的片段命中目錄中超過上限筆數的候選（如輸入「電」命中上百檔含「電」字的公司）
- **When** 呼叫搜尋 API 且未帶自訂上限參數
- **Then** 回傳筆數不超過後端預設上限，且回傳結果本身不謊稱「僅此上限筆」等於「全部只有
  這些」（如附帶是否有更多結果被截斷的旗標，供前端視需要顯示「還有更多結果，請輸入更精確
  關鍵字」）。

### AC-8（對應 FR-4）combobox 鍵盤操作
- **Given** 使用者在 NavBar 搜尋框輸入後出現候選下拉
- **When** 使用者以方向鍵上下移動選取項目、按 Enter
- **Then** 頁面導向 Enter 當下反白的候選項目對應個股頁，且不需要滑鼠點擊即可完成整個查詢
  流程。

### AC-9（對應 FR-4）選定候選後不再手動選市場
- **Given** 使用者從候選下拉選定一筆代號為 `2330`、市場為 `TW` 的候選
- **When** 頁面導向個股頁
- **Then** 個股頁以 `TW` 市場載入資料，過程中使用者未被要求輸入或確認市場。

### AC-10（對應 FR-4）保留純代號直達路徑
- **Given** 使用者不理會候選下拉，直接輸入完整代號後按 Enter 或點查詢按鈕
- **When** 表單送出
- **Then** 沿用既有 `SYMBOL_PATTERN` 驗證邏輯導向個股頁，此路徑不強制依賴搜尋 API 或證券
  目錄是否可用（呼應 AC-13 的離線降級）。

### AC-11（對應 FR-5）NavBar 與個股頁不再有手動市場下拉
- **Given** 完成本期改版
- **When** 檢視 `NavBar.tsx` 與 `position/[symbol]/page.tsx` 的渲染輸出
- **Then** 兩處皆不存在可供使用者手動切換市場、藉此改變查詢結果的 `<select>` 或等效互動
  元件；市場只以唯讀徽章呈現。

### AC-12（對應 FR-6）個股頁標題含公司名稱
- **Given** 證券目錄已同步，代號 `2330` 對應「台灣積體電路製造股份有限公司」（或目錄實際
  記載的簡稱／全名，依 FR-1 同步資料為準）
- **When** 使用者進入 `/position/2330`
- **Then** 頁面標題同時顯示代號與公司名稱。

### AC-13（對應 FR-6/FR-7）目錄查無時公司名稱誠實 fallback
- **Given** 目錄中查無代號 `9999X` 對應的公司名稱
- **When** 使用者進入該代號的個股頁或持倉列表看到該代號
- **Then** 畫面只顯示代號本身，不顯示任何猜測、佔位或錯誤字樣冒充公司名稱。

### AC-14（對應 FR-6）持倉列表補公司名稱
- **Given** 使用者持有代號 `2330` 的部位，且目錄已同步
- **When** 使用者檢視持倉列表（`PositionsTable.tsx`）
- **Then** 該列同時顯示代號與公司名稱，其餘欄位（數量、市值等）不受影響。

### AC-15（對應 FR-7）目錄完全未同步時搜尋不報錯
- **Given** 本機從未執行過同步工具（目錄資料表為空或不存在）
- **When** 使用者在搜尋框輸入任意文字（如「2330」或「台積電」）
- **Then** 搜尋 API 不拋出 500 等未預期錯誤，回傳空候選清單（或明確的「目錄未同步」狀態），
  前端據此不顯示候選下拉但**仍允許**使用者按 Enter 用純代號直達（呼應 AC-10）。

### AC-16（對應 FR-7）目錄未同步時個股頁仍可用
- **Given** 目錄未同步
- **When** 使用者以純代號直達方式進入個股頁
- **Then** 頁面正常渲染既有的價格／訊號／建議卡等既有功能，僅公司名稱欄位 fallback 為
  只顯示代號，市場判定依 FR-2 開放問題裁示的降級規則運作，整體不出現空白頁或未捕捉例外。

## 風險與依賴

- **依賴**：雲端開發環境對財經網域 egress 封鎖（既有已知限制，見
  `work/stock-desk-已知限制與後續.md` 教訓段落）——本 PRD 的目錄同步機制**必須**設計成
  CEO 本機執行，開發／CI 環境不得假設能即時連線 TWSE/TPEx OpenAPI，測試需用離線 fixture。
- **依賴**：TWSE OpenAPI、TPEx OpenAPI 兩個端點目前僅被 `verify_market_data.py` 做過根網域
  可連線探測（`work/research/驗證結果-2026-08-09.md` 提及，未驗證具體資料集 schema）；
  正式 adapter 落地前 tech-architect / data-engineer 仍需依官方文件查證欄位格式，比照
  `data-source-integration` skill 的「調查與比較」步驟，不得憑記憶假設欄位名稱。
- **風險**：目錄資料若與實際發行公司名稱有出入（如更名、下市），可能誤導使用者；本期靠
  `as_of` 標示同步時間、CEO 手動重新同步來緩解，不做自動每日更新（範圍外已載明）。
- **風險**：FR-2 市場自動判定若裁示為「目錄未命中就完全不能查」，可能讓尚未收錄進目錄的
  合法標的（如剛上市、興櫃）查不到；反之若裁示為「未命中就退回上次市場」，可能查到錯誤
  市場的資料。兩種裁示各有取捨，需 CEO 明確選一個（開放問題 Q1）。
- **依賴**：本 PRD 假設既有 `SYMBOL_PATTERN`（`NavBar.tsx:16`）與後端既有的 symbol 驗證
  邏輯不變；若證券目錄上線後要收緊代號格式驗證（如目錄命中才允許查詢），屬於範圍外的
  後續變更，需另開需求討論。

## 開放問題（待 CEO 或其他部門回答）

**Q1（待 CEO 裁示）**：FR-2／AC-4 目錄未命中時的降級行為，二選一（或 CEO 提第三案）：
  - (a) 維持「使用者最後一次查詢的市場」繼續查（可能查到錯誤市場但至少有結果）；
  - (b) 明確要求使用者對「目錄未收錄的代號」補選一次市場（等於保留一個縮小範圍的手動
    選擇，只在目錄未命中時出現，不影響 AC-11 對「命中時不再有手動選單」的要求）。
  影響 FR-2、FR-5、AC-4、AC-16 的實作細節。

**Q2（待 CEO 裁示）**：美股公司名稱是否列入第一期範圍？本 PRD 目前裁定「第一期台股
  only，美股顯示代號」，理由：(1) TWSE/TPEx OpenAPI 為官方免費、無額度限制的公司清單，
  台股適配成本低；(2) 美股公司名稱需另一個資料源（如 Alpha Vantage 的 `SYMBOL_SEARCH` 或
  等效端點），而 `work/stock-desk-已知限制與後續.md` 已記載 Alpha Vantage 額度緊張
  （25 req/day）與美股 adapter 本身仍在補強中，本期若硬塞美股名稱查詢會排擠既有額度且
  增加一個新的未驗證資料源；(3) CEO 原話聚焦台股（「我這個股是台股」），美股需求非本次
  急迫項。若 CEO 認為美股名稱同樣急迫，需另評估資料源與額度，列為下一期。

**Q3（待 tech-architect + CEO）**：個股頁網址是否保留 `?market=` query param？拿掉手動
  市場切換後，這個 query param 的角色從「使用者可改的輸入」變成「後端判定結果的顯示」，
  是否仍需要出現在網址列（影響分享連結、瀏覽器上一頁行為、既有帶 `?market=` 的外部連結
  相容性），本 PRD 不代為決定，列為 tech-architect 技術評估時一併定案的項目。

**Q4（待 CEO + product-manager 後續）**：`positions/import/ManualAddForm.tsx`（手動新增
  部位）的市場 `<select>` 是否也要拿掉、改自動判定？本 PRD 範圍外，因手動新增很可能就是
  在處理目錄尚未收錄的標的（如剛上市、興櫃），拿掉手選反而可能卡住合法情境；若 CEO 想
  一併處理，需另開一輪需求釐清（是否要有「目錄未收錄，允許手動輸入公司名稱與市場」的
  另一條路徑）。

**Q5（待 tech-architect）**：FR-3 搜尋 API 的候選筆數預設上限、前端防抖毫秒數，本 PRD
  刻意不訂死（CEO 交辦時也明說「上限筆數與防抖由前端定」），實作前由 tech-architect /
  frontend-engineer 依既有效能慣例訂一個值，寫回本 PRD 或技術設計文件存查。
