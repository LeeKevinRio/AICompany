- 版本：v0.1（spec）
- 發起人：CEO
- 撰寫：product-manager

- 產品分支：`product/flight-deals`
- 前置文件：`work/flight-deals-PRD.md`（FD-1，本 PRD 修訂其 FR-A1 與 FR-A4 的出發地／目的地部分）、`docs/adr/0002-flight-deals-技術棧與資料源.md`（accepted；D-1 不加前端框架、C-14 不從 CDN 載入、C-17 禁用字）

## 背景與目標

CEO 原話：「可以的話補上我打上什麼中文，你會有個提示下拉，我可以快速選。例如我找『東』，下拉選單就會有東京之類的。不一定要用代碼來找機場。」

FD-1 的出發地／目的地是 3 碼 IATA 代碼輸入，使用者必須先知道代碼。目標：

1. 出發地與目的地欄位改為「輸入即建議」，可用中文、英文或代碼片段快速找到並選取。
2. 全站（列表、詳情、Telegram 推播）路線改以「中文名＋代碼」呈現，不必在腦中對照代碼。
3. 後端只接受內建對照表內的代碼，避免打錯字造成靜默查不到價。

成功指標（以可驗證行為為準）：
- 輸入「東」可在下拉看到東京（城市）、成田、羽田，選取後完成建立監看，全程不需手打代碼。
- 輸入「nrt」「NRT」「tok」皆能找到對應項目。
- 不在表內的代碼無法儲存，且錯誤訊息指引使用者從下拉選取。
- FD-1 既有監看照常運作，不需重建。

## 使用者與情境

- 使用者：CEO 本人，單一使用者，桌機與手機瀏覽器皆會用。
- 情境 A：新增監看時在目的地打「東」，從下拉選「東京 TYO（所有機場）」，儲存。
- 情境 B：只想看成田，打「成田」或「nrt」，選「東京成田 NRT」。
- 情境 C：開啟列表或收到 Telegram 推播時，直接看到「台北 TPE → 東京成田 NRT」，不用查代碼。
- 情境 D：用手機操作表單，下拉在窄螢幕可點選。

## 範圍內 / 範圍外

範圍內：
- 內建精選對照表（機場與城市兩種層級）及其出處紀錄。
- 出發地、目的地欄位的輸入即建議下拉（含鍵盤與手機寬度）。
- 列表、詳情、Telegram 推播的路線顯示改為中文＋代碼。
- 後端只接受表內代碼的驗證。

範圍外（non-goals）：
- 多語系介面（僅繁體中文，搜尋可吃英文與代碼）。
- 模糊拼字修正（打錯字猜你要什麼）。
- 全球所有機場；對照表僅涵蓋台灣常飛的亞洲、北美、歐洲、大洋洲主要機場與城市。
- 機場群組自訂（使用者自行組合機場）。
- 新增外部 API 查詢機場、新增執行期依賴。
- 變更查價資料源、排程、通知條件等 FD-1 既有行為。

## 功能需求（逐條編號）

### 資料

- FR-D1 對照表內容：內建一份精選對照表，涵蓋台灣常飛的亞洲、北美、歐洲、大洋洲主要機場與城市，規模約 200 至 400 筆。每筆至少含：IATA 代碼、層級（機場或城市）、中文名稱、英文名稱、補充資訊（所屬城市或國家）。
- FR-D2 兩種層級：機場（例：NRT 成田、HND 羽田）與城市（例：TYO 東京＝其下所有機場、OSA 大阪）。機場須能標示所屬城市，城市須能列出其下機場。
- FR-D3 城市代碼「已驗證可查」標記：每個城市代碼須逐筆標記是否已實測可被查價資料源查詢。僅「已驗證可查」的城市代碼開放為可選項；未驗證的城市不開放，只列其底下的機場。已知事實（2026-10-26 實測）：TPE→TYO 成功（結果含 HND、NRT）、TPE→OSA 成功（含 ITM、KIX）、TPE→LON 失敗（原因未明）。每筆標記須註明驗證日期。
- FR-D4 資料出處：對照表須註明代碼來源與查證日期（實作者查證代碼對得上 IATA），讓日後維護者可追溯。
- FR-D5 離線可用：對照表內建於產品，不依賴外部服務；使用輸入建議時不得對外發出請求。
- FR-D6 可出發地範圍：出發地與目的地使用同一份對照表（台灣機場須涵蓋，例：TPE 桃園、TSA 松山、KHH 高雄、RMQ 台中）。

### 查詢與排序

- FR-Q1 可搜尋欄位：使用者輸入可比對中文名稱、英文名稱、IATA 代碼；英文與代碼比對不分大小寫。
- FR-Q2 比對方式：支援前綴與包含（輸入片段出現在名稱任何位置）兩種。
- FR-Q3 排序規則（由高到低）：(1) 代碼完全命中；(2) 中文名稱前綴命中；(3) 英文名稱前綴命中；(4) 其餘包含命中。同一順位內的次序（例：城市在其機場之前、依字母或常用度）由 tech-architect 與實作者決定，但須固定、可預期。
- FR-Q4 結果數量：下拉顯示筆數須有上限（上限值由架構決定），避免一次列出過多項目；輸入越完整結果越少。
- FR-Q5 無結果：無任何符合項目時，下拉顯示「找不到符合的機場或城市」，不得空白或報錯。
- FR-Q6 空輸入：欄位為空時不強制顯示完整清單（可顯示常用項目，是否顯示見開放問題）。

### 表單下拉

- FR-F1 輸入即建議：出發地與目的地兩個欄位，使用者每輸入一個字元即時更新下拉。
- FR-F2 項目呈現：每個項目顯示「中文名 代碼（補充：城市／國家）」；城市層級須可與機場層級一眼區分（例：標示「所有機場」）。
- FR-F3 選取後的值：選取後欄位實際送出的值是 IATA 代碼，並在欄位旁顯示已選的中文名稱，讓使用者確認。
- FR-F4 直接輸入代碼：使用者仍可直接打完整代碼（如 NRT）；若該代碼在表內，視同選取成功並顯示中文名。
- FR-F5 預設值：出發地預設 TPE，載入即顯示「台北桃園 TPE」類的中文名。
- FR-F6 鍵盤操作：下拉須可用鍵盤操作——上下鍵移動、Enter 選取、Esc 關閉；Tab 離開欄位時行為須可預期（不得卡住使用者）。
- FR-F7 手機寬度：在 375px 寬度下下拉不超出螢幕、不造成橫向捲動，項目點擊區域足以用手指點選。
- FR-F8 無障礙語意：下拉須提供螢幕閱讀器可辨識的選單語意（目前選取項目、結果數量等），具體做法由實作者決定。
- FR-F9 無 JavaScript 或建議載入失敗時的退路：不得讓表單完全無法送出；仍可手打代碼送出並由後端驗證（FR-V1）。
- FR-F10 修改監看：編輯既有監看時，欄位預先帶入既有代碼與中文名。

### 顯示

- FR-S1 路線顯示格式：列表、詳情頁、其他出現路線之處，一律顯示為「台北 TPE → 東京成田 NRT」格式（中文名＋代碼）；單程與來回用語沿用 FD-1。
- FR-S2 Telegram 推播：推播中的路線改為中文＋代碼，字數須克制（例：城市層級用簡稱「東京 TYO」，機場層級用「東京成田 NRT」；不放補充資訊），不得因此讓單則訊息明顯變長或超出通道上限。
- FR-S3 中文名查無時的後備：若資料庫內存有不在對照表的舊代碼（見 FR-C1），顯示時退回只顯示代碼，不得報錯。
- FR-S4 文案維持事實陳述：新增或變更的文案遵守 FD-1 FR-C5 與 ADR-0002 C-17 禁用字規則。

### 驗證

- FR-V1 後端白名單：建立與修改監看時，出發地與目的地只接受對照表內（且城市須為已驗證可查）的代碼；不分大小寫，儲存時正規化為大寫。
- FR-V2 拒絕訊息：不在表內，回應 422 並提示「請從下拉選取」（欄位旁錯誤訊息）。
- FR-V3 既有規則維持：必填、出發地不等於目的地等 FD-1 FR-A4 規則照舊；此外「出發地城市與目的地機場屬同一城市」（例：TYO → NRT）是否拒絕見開放問題。
- FR-V4 未驗證城市拒絕：直接打未驗證城市代碼（如 LON）送出，須被拒絕，提示改選該城市的機場。
- FR-C1 既有監看相容：FD-1 已建立的監看（其代碼為 3 碼英文）不受影響——仍可排程查價、顯示、停用、刪除。若其代碼不在對照表內，保留原樣、顯示退回只顯示代碼；僅當使用者「修改」該監看時才套用新驗證（修改時須先選到表內項目才能儲存）。

### 驗證

- AC-V1 Given 建立表單；When 透過 API 或表單送出目的地「ZZZ」；Then 回應 422，欄位旁顯示「請從下拉選取」，不產生資料。

- AC-V3 Given 建立表單；When 直接送出未驗證城市代碼「LON」；Then 被拒絕，提示改選機場；When 改選 LHR；Then 可儲存。
- AC-V4 Given 建立表單；When 出發地與目的地同為 TPE；Then 沿用 FD-1 規則被拒絕。
- AC-V5 Given FD-1 已建立的 TPE→NRT 監看與其價格歷史；When 升級到 FD-2 後啟動；Then 監看仍啟用、可排程查價、歷史完整、列表顯示不報錯（AC-C1 的核心）。

## 風險與依賴

- 資料正確性風險（中）：200 至 400 筆代碼若有誤，使用者選到錯的機場且不易察覺。因應：實作者逐筆查證並註明出處與日期（FR-D4），qa-reviewer 抽查。
- 城市代碼可查性風險（中）：城市代碼是否可被查價資料源查詢是逐筆實測事實（TYO、OSA 成功，LON 失敗）。因應：FR-D3 逐筆標記，未驗證者不開放；驗證須實測，不能由推測得出。實測有查詢額度與被擋風險，批次驗證方式由 tech-architect 決定。
- 驗證成本風險（低）：若要驗證許多城市代碼，需對外發出真實查詢，須控制頻率以免觸發資料源封鎖。
- 相容性風險（中）：既有監看相容（FR-C1），避免新白名單讓舊監看壞掉。
- 前端約束：ADR-0002 D-1 不加前端框架、C-14 不從 CDN 載入，下拉須以不引入框架、不依賴外部資源的方式實現；具體做法由 tech-architect 與實作者決定。
- UI 驗收：涉及網頁互動，完成前須 qa-e2e 實機驗收（含鍵盤與 375px）；無人值守環境依 e2e-fallback。
- 風控閘門：機場名稱與路線顯示為事實資訊，不屬建議類文案，原則上不適用；仍須遵守 C-17 禁用字。

## 開放問題（待 CEO 或其他部門回答）

1. 【CEO】空欄位聚焦時，要不要先列出一小批常用項目（例：東京、大阪、曼谷、首爾）？預設：不列，打字才出。
2. 【CEO】出發地與目的地是同一城市的組合（例：TYO → NRT）要不要拒絕？預設：拒絕並提示。
3. 【CEO】舊監看（FD-1 建立、代碼不在表內）修改時，路線欄位是否必須重選到表內項目才能儲存？預設：是。
4. 【CEO】哪些城市代碼是你特別想要的（除 TYO、OSA 外，例如首爾 SEL、曼谷 BKK 其實是機場）？此將決定逐筆驗證的優先順序；未驗證者只列機場。
5. 【tech-architect】對照表存放形式、載入方式、下拉的實作手法（不加框架、不走 CDN）、結果筆數上限、同順位內排序，以及城市驗證標記的批次實測方式與頻率控制。
