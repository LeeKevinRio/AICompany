## 背景與目標

FD-1 到 FD-6 完成後，Telegram 只是單向的「系統推給 CEO」。CEO 在手機上想問一句「現在最低多少」「幫我現在查一下」「先暫停這個監看」，仍得打開電腦網頁。另一方面，系統已累積大量掃描紀錄：FD-6 實測 5 萬筆 scan_run 時列表頁 200 ms，且 scan_run 沒有任何清除策略，資料庫只會越長越大。FD-7 補兩件事：

1. Telegram 雙向指令：在手機上以固定指令查詢與操作既有監看（唯讀查詢、立即查價、摘要、暫停／啟用），不做自由對話，不能修改條件。
2. 資料保留與效能：掃描紀錄、價格觀測、通知紀錄有保留期與每日自動清除（清除前備份、保護目前最低價所需資料），健康頁可見資料庫規模，列表查詢補索引。

成功指標（以可驗證行為為準）：
- 只有設定的 chat id 能下指令；其他來源的訊息不被執行、不被回覆、內容不被記錄。
- 八個指令的回覆內容要素齊全、無建議語氣、長度不超過既有推播上限；`/scan` 完成後主動再回一則結果。
- 關閉指令功能後不再向 Telegram 拉取訊息；健康頁如實顯示輪詢狀態。
- 清除後超過保留期的資料消失，但各監看的「已查到最低價」與摘要數字清除前後不變；清除前當天第一次必有備份。
- 5 萬筆掃描紀錄下列表頁 < 100 ms。
- bot token 不出現在任何回覆、log、通知紀錄、健康頁。

產品前提（沿用）：價格為查到當下的參考值，實際以訂票網站為準；所有回覆只做事實陳述；服務只綁 127.0.0.1、無登入（指令入口的授權完全靠 chat id）。

## 使用者與情境

- 使用者：CEO 本人，單一使用者，Windows 本機服務，常在手機上用 Telegram 與自己的 bot 一對一對話。
- 情境 A：出門前傳 `/list`，一眼看各監看最低價與漲跌。
- 情境 B：看到某航線價格有趣，傳 `/watch 3` 看前 3 組日期與查票連結，再傳 `/scan 3` 立即查價，過一會兒 bot 主動回結果。
- 情境 C：旅行計畫改變，傳 `/pause 3` 先停掉該監看；回家後在網頁修改條件，再傳 `/resume 3`。
- 情境 D：沒收到任何通知，傳 `/status` 確認資料源、斷路器、額度與下次掃描時間。
- 情境 E：半年後打開健康頁，看到資料庫大小、各表筆數、上次清除與壓縮結果；舊資料已自動清掉，列表依然很快。
- 情境 F：有陌生人找到 bot 並傳訊息；系統不理會也不回覆，健康頁只顯示被忽略的次數。

## 範圍內 / 範圍外

範圍內：
- 指令輪詢（長輪詢）、chat id 授權、離線積壓訊息處理、重複執行防護。
- 八個指令：`/help`、`/list`、`/watch`、`/scan`、`/digest`、`/status`、`/pause`、`/resume`。
- 指令紀錄（通知紀錄新類型「指令」、「手動摘要」）、設定頁開關、健康頁輪詢狀態。
- 價格觀測、掃描紀錄、通知紀錄的保留期與每日清除；清除前備份；最近 N 輪保護；VACUUM 週期。
- 列表查詢索引與效能目標；健康頁資料庫規模資訊。

範圍外（non-goals）：

- 自由文字對話、自然語言解析。
- bot 主動推送新種類通知（價格通知、告警、每日摘要沿用 FD-1／FD-4，本批只新增「對指令的回覆」與 `/scan` 完成回覆）。
- 網頁上的「立即清除」「立即壓縮」按鈕、手動還原備份介面（見開放問題 10）。
- 探索結果與其 7 天清除規則的任何變更（沿用 FD-6）。
- 技術選型與實作細節（由 tech-architect 與實作者決定）。

## 功能需求（逐條編號）

### 一、指令輪詢與授權（FR-P）

- FR-P1 啟動條件：Telegram 已設定（token 與 chat id 皆有）且「指令功能」開關為開啟時，服務在背景持續向 Telegram 拉取新訊息（長輪詢）。Telegram 未設定或開關關閉時不發出任何拉取請求。
- FR-P2 授權：只處理「來自設定的 chat id」的訊息。其他來源（其他使用者、其他 chat、群組）的訊息一律忽略：不執行、不回覆、不寫入通知紀錄、不記錄訊息內容（含 log），只累計「已忽略未授權訊息數」。
- FR-P3 只收文字指令：非文字訊息（貼圖、圖片、語音、檔案）來自授權 chat 時視為格式錯誤，回簡短說明（同 FR-K10）；來自未授權 chat 時依 FR-P2 忽略。
- FR-P4 不重複執行：同一則訊息只會被處理一次；服務重啟、輪詢連線中斷重連後，已處理過的訊息不得再次執行（`/scan`、`/digest`、`/pause`、`/resume` 皆不得重複生效）。
- FR-P5 離線積壓：服務停機期間堆積的舊訊息，於重新啟動後「超過 10 分鐘的一律不執行」，僅回覆授權 chat 一則「服務停機期間有 N 則指令未處理，請重新傳送」（N 為授權 chat 的舊訊息數，N 為 0 不回覆）；10 分鐘內的照常處理（預設值，見開放問題 3）。
- FR-P6 失敗不影響主服務：Telegram 連線失敗、逾時、被限流時，輪詢以退避方式重試，不拋出到排程與網頁，不阻塞掃描、探索與摘要；連續失敗不產生 Telegram 告警，只反映在健康頁（FR-L5）。
- FR-P7 單一輪詢者：同一個資料庫只能有一個輪詢者（沿用 FD-3 單一排程鎖，持有排程鎖的服務才輪詢）；第二份服務不輪詢。
- FR-P8 與設定精靈共存：`flight-deals telegram-setup` 使用同一個 bot 的 `getUpdates`，與服務輪詢互斥（Telegram 對同一 bot 同時兩個 `getUpdates` 會回衝突錯誤）。精靈遇到衝突時須以人話說明「指令輪詢運作中，請先在設定頁關閉指令功能或停止服務再執行」；精靈不得吞掉服務尚未處理的授權指令（見開放問題 2）。
- FR-P9 安全：bot token 不得出現在任何回覆、通知紀錄、log、錯誤訊息、健康頁、例外追蹤（沿用 D-5 `redact()`，輪詢的所有錯誤路徑須先遮蔽，含含 token 的 URL）。
- FR-P10 寫入型限制：bot 指令只能執行本 PRD 列出的八個指令；任何會建立、修改、刪除監看或改全域設定的動作均不得經由 bot 達成（`/pause`、`/resume` 僅改啟用狀態）。

### 二、指令集（FR-K）

通則：所有回覆為純文字、事實陳述，不含建議語氣，不含 ADR C-17 禁用字與「建議」「最佳時機」「現在買」「划算」。監看「編號」為網頁監看列表上顯示的編號（見開放問題 4）。價格一律標示幣別與總價口徑（人數＋「總價」，沿用 FD-5 FR-V3），並帶「價格為查到當下的參考值，實際以訂票網站為準」免責句（`/help` 除外，長清單可共用一句於結尾）。

- FR-K1 `/help`：列出八個指令、一行用途與參數格式（例：`/watch <編號>`）；並註明「新增與修改監看請至網頁」。
- FR-K2 `/list`：列出啟用中監看，一行一個，每行含：編號、路線（中文短名＋代碼）、人數與艙等、已查到最低價與日期（來回含回程日）、較前一輪漲跌（沿用 FD-4 列表趨勢口徑：↓／↑ 金額、＝、「—」）、上次查價時間（Asia/Taipei）。目前無價格者顯示「尚未查到價格」，不得出現 0 元。結尾附「停用中：編號…」（若有），無啟用中監看時回「目前沒有啟用中的監看」。
- FR-K3 `/watch <編號>`：回該監看詳情：條件（路線、行程型態、日期模式與範圍、人數、艙等、航空、時段、預算／門檻）、目前啟用或停用狀態、最便宜前 3 組日期（各含總價、航空、直飛／轉機、查票連結，連結沿用 FD-5 tfs 連結）、上次掃描結果（時間、完成／失敗、查詢組數）與略過說明（略過筆數與原因，沿用既有「略過」口徑）。停用中的監看也可查詢。有價格不足 3 組時只列實際筆數；完全無價格時說明「尚未查到價格」。
- FR-K4 `/scan <編號>`：觸發該監看的立即查價，受既有規則約束（全域每小時額度、單一 worker 序列、探索進行中順延、已有該監看掃描進行中不重複排入）。成功排入立即回「已排入查價」（探索進行中或需順延時註明原因，例「探索進行中，將於探索結束後執行」）；額度已用盡或被拒時立即回明確原因而不排入；監看停用中時回「該監看已停用，不會查價」。查價完成後，bot 另外主動回一則結果：最低價（含日期組合、人數總價標示）、較前一輪變化、查詢組數與略過說明；查價失敗或無價格時回事實性原因（例「未查到價格：資料源被擋」），不得靜默。此主動結果訊息與立即查價帶出的價格通知（若符合條件）互相獨立。
- FR-K5 `/digest`：立即送出一則每日摘要，內容與格式同 FD-4 每日摘要（含固定結尾兩句、資料源狀態、24 小時失敗次數）。不受「同一個台北日曆日最多一則」限制，也不佔用、不影響當日排程摘要的去重額度（排程摘要當日仍會照常送一次）。通知紀錄類型記為「手動摘要」，不是「每日摘要」。可重複觸發。
- FR-K6 `/status`：回資料源狀態（正常／異常／未知）與斷路器狀態、本小時已用查詢額度與全域上限（已用／上限）、下次預計掃描時間（Asia/Taipei；探索進行中時說明順延，不顯示成已逾期）、進行中的探索（條件摘要與進度「已查 N／共 M」，無則「目前沒有進行中的探索」）。不得含 `last_error` 原文以外未遮蔽內容；資料源錯誤只顯示狀態標籤與時間。
- FR-K7 `/pause <編號>`：將該監看設為停用並回覆確認（含編號、路線、新狀態）。已停用者回「該監看已是停用」，不重複操作。
- FR-K8 `/resume <編號>`：將該監看設為啟用並回覆確認。已啟用者回「該監看已是啟用」。已過期（日期已過）的監看不可啟用，回明確原因。啟用後的首次掃描沿用既有規則（不因 bot 啟用而繞過額度）。
- FR-K9 編號錯誤：編號缺少、非整數、不存在，一律回簡短說明與正確格式（例「找不到編號 99 的監看，可用 /list 查看編號」），不執行任何動作。
- FR-K10 未知指令與自由文字：回「無法辨識的指令」與 `/help` 提示（短訊，不超過 3 行）。不解析自由文字、不做模糊比對。指令大小寫不分，允許私訊中常見的 `/指令@bot名稱` 後綴（見開放問題 5）。
- FR-K11 回覆長度：每則回覆不得超過既有單則推播長度上限；內容過多（例如 `/list` 監看很多）時截斷並明確註明「另有 N 個未列出」，不得靜默截斷；截斷時優先保留免責句。
- FR-K12 執行順序與延遲：同一批多則指令依傳送順序處理；單一指令處理失敗（例外、資料庫忙）不影響後續指令，並對授權 chat 回「指令執行失敗」（原因已遮蔽，不含內部細節）。

### 三、指令紀錄與設定（FR-L）

- FR-L1 通知紀錄：授權 chat 的每則指令與其回覆結果各記入通知紀錄，類型「指令」：含時間、指令文字（截斷至合理長度、已遮蔽）、回覆摘要或全文、成功／失敗狀態。`/digest` 另有一筆「手動摘要」紀錄；`/scan` 的主動結果訊息記為「指令」並可看出與哪個指令相關。網頁通知紀錄頁可看到、可與價格通知／告警／每日摘要／測試區分。
- FR-L2 未授權不入紀錄：FR-P2 忽略的訊息不得出現在通知紀錄。
- FR-L3 回覆發送失敗：回覆因 Telegram 錯誤發送失敗時，在紀錄中標記失敗與已遮蔽原因；回覆不進入價格通知的重送機制（不重送、不佔用價格通知的去重額度）。指令本身的效果（例如 `/pause`）不因回覆失敗而回滾。
- FR-L4 設定頁開關：設定頁新增「Telegram 指令功能」開關，預設開啟。關閉後輪詢在目前這次拉取結束後停止（最多等一個拉取逾時），不再發出新的拉取請求；重新開啟後恢復。Telegram 未設定時開關顯示但註明「未設定 Telegram，功能無作用」。
- FR-L5 健康頁狀態：健康頁新增「指令輪詢」一列，狀態為「運作中」「已關閉」「未設定 Telegram」三者之一；另顯示最近一次收到（授權）指令的時間（無則「—」）、已忽略未授權訊息數、輪詢最近一次連線失敗的時間與已遮蔽原因（若目前處於失敗重試中，狀態仍為「運作中」但附註「最近連線失敗」）。
- FR-L6 設定即時生效：開關變更不需重啟服務；同時寫入走既有設定頁驗證與 client header（D-5）。

### 四、資料保留（FR-R）

- FR-R1 掃描與觀測保留期：價格觀測與掃描紀錄（掃描輪 scan_run 及其觀測值、略過事件等隨掃描輪產生的紀錄）預設保留 180 天；設定頁可調，下限 30 天（不合法值後端 422，原設定不變）。保留期起算點為該掃描輪的結束時間（進行中的掃描輪不清除）。
- FR-R2 通知保留期：通知紀錄（含指令、手動摘要、每日摘要、價格通知、告警、測試，及其明細）預設保留 365 天；設定頁可調，下限 30 天。
- FR-R3 探索保留：探索沿用 FD-6 的 7 天，本批不改。
- FR-R4 每日自動清除：每日自動執行一次清除作業，刪除超過保留期的資料（FR-R1、R2）。服務未在預定時間執行時，啟動後補跑一次（每日最多一次）。清除不在掃描輪、探索進行中執行（順延到結束後），清除分批進行，不使網頁請求長時間卡住。
- FR-R5 最近 N 輪保護：每個監看無論日期，至少保留其最近 N 輪已完成的掃描輪及其觀測值（預設 N=10，設定頁可調，下限 3）。不論保留期是否已到，這些資料不得被清除。
- FR-R6 數字不變原則（PM 補充）：清除前後，每個監看在列表上的「已查到最低價」、其日期組合、「較前一輪」漲跌，以及每日摘要與 `/list` 所用的最低價與漲跌，必須相同。若僅保留最近 N 輪無法滿足此原則（例如彈性窗輪換取樣下，某日期組合最新一筆觀測落在 N 輪之前），清除須額外保留「目前快照所依賴的觀測」，由 tech-architect 決定方式。
- FR-R7 歷史縮短如實揭露：詳情頁價格歷史與趨勢圖只涵蓋保留期內資料，頁面註明「價格紀錄保留最近 N 天」（N 為目前設定值）。
- FR-R8 刪監看的資料：刪除監看時其資料的處理沿用既有行為，本批不變。
- FR-R9 保留期調降提示：設定頁調降保留期時，提示「下次清除將刪除超過 X 天的資料」；調降本身不立即刪除任何資料。

### 五、清除安全與壓縮（FR-S）

- FR-S1 清除前備份：每日清除作業中，若當日（Asia/Taipei）尚未備份，且本次將實際刪除至少 1 筆資料，先建立資料庫備份（沿用 migration 前備份機制或獨立備份檔，由架構決定），備份成功後才開始刪除；備份失敗則本次不刪除、記錄已遮蔽原因並顯示於健康頁。當日沒有可刪資料時不產生備份。
- FR-S2 備份檔管理：備份檔放在資料庫同目錄、符合 `.gitignore`（`*.db`）、不含祕密以外的額外外洩風險；清除用備份只保留最近 7 份（預設，見開放問題 9），超過者自動刪除；不得刪除 migration 的 `pre-v<N>` 備份。
- FR-S3 清除原子性：每個批次在同一交易內完成，任何中途失敗（含服務被強制關閉）都不得留下「掃描輪被刪但觀測仍在」或反之的不一致資料；下次清除可安全續跑。
- FR-S4 清除範圍限定：清除只刪除 FR-R1、R2 的資料；不得刪除監看、設定、alert_state、探索、仍被保留資料引用的紀錄；不得因清除讓通知去重失效而導致已通知的價格再次推播（去重鍵須與清除範圍相容，由架構確認）。
- FR-S5 清除結果紀錄：每次清除記錄時間、各類別刪除筆數（掃描輪、觀測、通知、其他）、是否產生備份、耗時；清除失敗記錄已遮蔽原因。供健康頁顯示（FR-H4）。
- FR-S6 壓縮（VACUUM）：預設每週一次，於當日每日摘要推送時間之後、清除作業完成後執行；設定頁可關閉（預設開啟）。壓縮僅在無掃描、無探索進行時執行，否則順延；磁碟可用空間不足以壓縮時略過並記錄原因，不得因此損壞資料庫。
- FR-S7 壓縮結果紀錄：記錄壓縮時間與壓縮前後檔案大小，供健康頁顯示。
- FR-S8 備份可還原說明：README 載明清除備份的檔名規則、位置，以及還原步驟（停止服務、以備份覆蓋資料庫、重啟）。

### 六、效能與健康頁（FR-H）

- FR-H1 列表索引：為列表頁查詢補上必要索引（FD-6 待辦：以 `scan_run` 的 `(watch_id, id)` 為代表，實際由架構決定），以遷移套用，沿用備份與回復慣例（migration 前備份）。
- FR-H2 列表效能目標：量測條件與 FD-6 基準相同（20 個監看、5 萬筆已完成 scan_run、每筆 12 組查詢結果、`ViewService.list_page()` 暖機 1 次後取 10 次中位數）：中位數 < 100 ms（FD-6 為 200 ms）。SQL 次數不得比 FD-6 多（沿用 C-34：1 次加每監看 1 次）。
- FR-H3 其他頁面不退步：補索引不得使新增或更新掃描資料的寫入明顯變慢（同基準下一輪掃描寫入耗時不超過改前 120%，預設，架構可調整）；健康頁含新增統計後載入時間在同資料量下 < 300 ms（預設）。
- FR-H4 健康頁資料維護區塊：顯示資料庫檔案大小（含 WAL 的合計說明）、主要資料表筆數（至少：監看、掃描輪、價格觀測、通知、探索）、上次清除時間與各類別刪除筆數、上次備份時間與檔名、上次壓縮時間與前後大小、目前保留期設定；從未清除或壓縮者顯示「尚未執行」。
- FR-H5 健康頁指令輪詢列：見 FR-L5。
- FR-H6 統計不得拖垮頁面：筆數統計不得使健康頁在 5 萬筆掃描紀錄、數十萬筆觀測下明顯變慢（見 FR-H3）；可採近似或快取，但須註明統計時間。
- FR-H7 文案：新增的健康頁與設定頁文案無建議語氣、不含禁用字。

## 驗收條件（每條需求至少一組 Given/When/Then）

測試通則：全部自動化測試使用假 Telegram 回應與假時鐘，不連外網；真實 Telegram 收發為 CEO 或總經理手動驗收項。

### 一、指令輪詢與授權

- AC-P1 Given Telegram 已設定（token＋chat id）且指令功能開啟；When 服務啟動；Then 開始向 Telegram 拉取訊息。Given Telegram 未設定；Then 不發出任何拉取請求，健康頁為「未設定 Telegram」。
- AC-P2 Given 設定的 chat id 為 A；When chat B 傳 `/list`、`/pause 1`、任意文字；Then 不執行任何動作、不傳出任何回覆（以假 Telegram 斷言 `sendMessage` 呼叫數為 0）、通知紀錄無新增、log 與資料庫中找不到該訊息內容，健康頁「已忽略未授權訊息數」增加對應則數。
- AC-P3 Given 授權 chat 傳貼圖或圖片；Then 回簡短說明（格式錯誤），不執行動作；Given 未授權 chat 傳同樣內容；Then 完全忽略。
- AC-P4 Given 已處理一則 `/scan 1`；When 服務重啟或輪詢中斷後重連；Then 同一則訊息不再被處理，不產生第二次掃描、不再回覆。
- AC-P5 Given 服務停機期間授權 chat 累積 3 則指令（其中 2 則超過 10 分鐘）；When 重啟；Then 超過 10 分鐘者不執行，bot 回一則「服務停機期間有 2 則指令未處理，請重新傳送」；10 分鐘內的 1 則照常執行。Given 無逾時舊訊息；Then 不回覆該說明。
- AC-P6 Given Telegram 連線逾時、5xx、回傳限流；When 輪詢進行；Then 服務以退避重試，排程掃描、摘要、網頁不受影響，無 Telegram 告警，健康頁顯示最近連線失敗時間與已遮蔽原因，狀態仍為「運作中」。
- AC-P7 Given 兩份服務同時啟動；Then 只有持有排程鎖者輪詢，第二份不輪詢也不拉取。
- AC-P8 Given 服務指令輪詢運作中；When 執行 `flight-deals telegram-setup`；Then 若遇衝突，印出「指令輪詢運作中，請先在設定頁關閉指令功能或停止服務再執行」類說明並以非零代碼結束，輸出不含 token；服務未被破壞，且未處理的授權指令未因此遺失（具體機制見開放問題 2 結論）。
- AC-P9 Given 以假 token（如 `123456:FAKE-TOKEN`）觸發輪詢中的 401、409、網路例外、逾時各情境，並觸發各指令回覆與錯誤路徑；When 檢查 stdout、stderr、log、通知紀錄、健康頁、所有回覆內容、例外追蹤；Then 皆不含 token 原文，也不含 `bot<digits>:` 型態的 URL（有自動化測試）。
- AC-P10 Given 授權 chat 傳入嘗試修改條件的文字（如 `/add TPE NRT`、`/edit 1`、`/delete 1`、`/set interval 5`）；Then 視為未知指令，回 FR-K10 說明，資料庫無任何變動。

### 二、指令集

- AC-K1 Given 授權 chat 傳 `/help`；Then 回覆列出八個指令與參數格式，並註明新增與修改請至網頁。
- AC-K2 Given 2 個啟用中、1 個停用中監看，其中一個監看目前無價格；When `/list`；Then 回覆一行一個啟用中監看，每行含編號、中文路線短名與代碼、人數與艙等、最低價與日期（來回含回程日）、漲跌（↓／↑／＝／—）、上次查價時間；無價格者顯示「尚未查到價格」且無 0 元；結尾列出停用中的編號。Given 全部停用；Then 回「目前沒有啟用中的監看」。
- AC-K3 Given 監看 3 有 5 組日期有價格；When `/watch 3`；Then 回覆含條件、啟用狀態、最便宜的 3 組日期（各含總價與人數標示、航空、直飛／轉機、tfs 查票連結）、上次掃描結果與略過說明。Given 只有 2 組有價格；Then 列 2 組。Given 完全無價格；Then 說明「尚未查到價格」。Given 停用中的監看；Then 仍可查詢並標示停用。
- AC-K4 Given 監看 3 啟用中、額度充足、無探索；When `/scan 3`；Then 立即回「已排入查價」，掃描完成後 bot 主動再回一則結果：最低價（含日期組合與總價標示）、較前一輪變化、查詢組數與略過說明；對外查詢遵守既有額度與節流。
- AC-K5 Given `/scan 3` 的掃描結果為被擋或無資料；Then 主動結果訊息說明事實性原因，不靜默、不顯示 0 元。
- AC-K6 Given 探索進行中；When `/scan 3`；Then 回覆註明「探索進行中，將於探索結束後執行」，探索結束後執行該掃描並主動回結果；不丟件、不重複。
- AC-K7 Given 全域每小時額度已用盡；When `/scan 3`；Then 立即回明確拒絕原因，不排入、不產生對外查詢。Given 監看 3 已停用；Then 回「該監看已停用，不會查價」。Given 該監看已有掃描進行中；Then 回已在查價中，不重複排入。
- AC-K8 Given 今天已推過排程摘要；When `/digest`；Then 仍送出一則摘要（內容同每日摘要含固定結尾），通知紀錄新增一筆類型「手動摘要」；排程摘要的去重額度不受影響（明天排程摘要照常送）。When 連傳 `/digest` 兩次；Then 送出兩則。Given Telegram 側無法送出；Then 紀錄為失敗並含已遮蔽原因。
- AC-K9 Given 尚未到今天的排程時間；When `/digest`；Then 送出手動摘要，且今天到時間時排程摘要仍會送出一則（不被手動摘要吃掉）。
- AC-K10 Given 資料源異常、斷路器開啟、本小時已用 40／上限 60、下次掃描 14:30、探索進行中已查 12／共 31；When `/status`；Then 回覆含資料源狀態與斷路器狀態、「已用 40／上限 60」、下次掃描時間（Asia/Taipei）、探索條件摘要與「已查 12／共 31」。Given 無探索；Then 回「目前沒有進行中的探索」。Given 探索進行中；Then 下次掃描不顯示成已逾期時間，而是說明順延。
- AC-K11 Given 監看 3 啟用中；When `/pause 3`；Then 監看變停用，回覆確認含編號、路線、新狀態；網頁列表同步顯示停用；排程不再查價。When 再傳一次；Then 回「該監看已是停用」，無其他變動。
- AC-K12 Given 監看 3 停用中；When `/resume 3`；Then 監看變啟用並回覆確認；When 監看已過期；Then 回明確原因，狀態不變；When 已啟用；Then 回「該監看已是啟用」。
- AC-K13 Given 傳 `/watch`（缺編號）、`/watch abc`、`/watch 999`、`/pause 0`；Then 各回簡短說明與正確格式，資料庫無變動。
- AC-K14 Given 傳 `/foo`、`你好`、`/LIST`、`/list@mybot`；Then `/foo` 與 `你好` 回「無法辨識的指令」並提示 `/help`（不超過 3 行）；`/LIST` 與 `/list@mybot` 視同 `/list`。
- AC-K15 Given 30 個啟用中監看；When `/list`；Then 回覆不超過既有單則推播長度上限，若有未列出者明確載明「另有 N 個未列出」，且保留免責句。
- AC-K16 Given 一次收到 `/pause 1`、`/foo`、`/list` 三則；Then 依序處理，中間未知指令不影響後續。Given 某指令處理拋出例外；Then 回「指令執行失敗」（不含內部細節或祕密），後續指令照常。
- AC-K17 Given 全部指令回覆、`/help` 文案與錯誤訊息（樣板與程式內字串）；When 檢查禁用字；Then 不含 ADR C-17 禁用字，也不含「建議」「最佳時機」「現在買」「划算」（有測試，字串納入既有 BANNED_PHRASES 清單）。
- AC-K18 Given `/list`、`/watch`、`/scan` 結果訊息中的價格；Then 皆標示幣別與「N 人總價」口徑，並含「價格為查到當下的參考值，實際以訂票網站為準」。

### 三、指令紀錄與設定

- AC-L1 Given 授權 chat 傳 `/list` 並成功回覆；When 開啟通知紀錄頁；Then 有一筆類型「指令」，含時間、指令文字、回覆摘要、成功狀態。Given `/digest`；Then 另有「手動摘要」一筆。Given `/scan 3` 完成後的主動結果；Then 另有一筆「指令」紀錄且可看出關聯到該 `/scan`。
- AC-L2 Given 未授權 chat 傳訊息；Then 通知紀錄無新增（見 AC-P2）。
- AC-L3 Given 回覆因 Telegram 錯誤發送失敗；Then 紀錄為失敗＋已遮蔽原因，不進價格通知重送，也不佔用價格通知去重額度；Given `/pause 3` 的回覆失敗；Then 監看仍為停用。
- AC-L4 Given 設定頁；When 檢視；Then 有「Telegram 指令功能」開關，預設開啟。When 關閉並儲存；Then 目前這次拉取結束後不再發出新的拉取請求（以假 Telegram 斷言最多再多一次進行中的請求完成），之後授權 chat 傳 `/list` 不被處理也不回覆；健康頁顯示「已關閉」。When 重新開啟；Then 不需重啟即恢復輪詢，健康頁顯示「運作中」。
- AC-L5 Given 開關關閉期間授權 chat 傳了指令；When 重新開啟；Then 依 FR-P5 處理積壓（超過 10 分鐘者不執行並回一則未處理說明）。
- AC-L6 Given 健康頁；When 分別在「Telegram 已設定且開啟」「已設定但關閉」「未設定」下檢視；Then 指令輪詢列分別顯示「運作中」「已關閉」「未設定 Telegram」，並顯示最近一次收到指令時間（無則「—」）與已忽略未授權訊息數。
- AC-L7 Given 設定頁開關寫入請求缺少 `X-Flight-Deals-Client` header；Then 回 403（沿用 D-5）。

### 四、資料保留

- AC-R1 Given 保留期 180 天，掃描輪 A 結束於 181 天前、B 結束於 179 天前，且每個監看已有超過 N 輪較新資料；When 每日清除執行；Then A 及其觀測消失，B 保留。
- AC-R2 Given 設定頁；When 保留期輸入 29、0、-1、空白、「abc」；Then 後端 422、原值不變；輸入 30 通過。通知保留期同理。
- AC-R3 Given 通知紀錄 366 天前與 364 天前各一筆；When 清除；Then 前者消失、後者保留；同樣測試涵蓋指令、手動摘要、每日摘要、價格通知類型。
- AC-R4 Given 保留期設為 30 天，某監看所有掃描輪都超過 30 天（例如監看已停用數月）；When 清除；Then 該監看最近 10 輪（預設 N）完整保留，不論日期；其他監看不受影響。Given 監看只有 6 輪；Then 全部保留。
- AC-R5 Given N 調整為 3；Then 以 3 為準；輸入 2 被拒 422。
- AC-R6 Given 彈性窗輪換取樣的監看，其某日期組合最新一筆觀測位於 N 輪之前；When 清除；Then 清除前後該監看列表「已查到最低價」、日期組合、「較前一輪」漲跌，以及 `/list` 與每日摘要的最低價與漲跌完全相同（以清除前後快照比對）。
- AC-R7 Given 清除後開啟詳情頁；Then 價格歷史與趨勢圖只含保留期內資料，頁面註明「價格紀錄保留最近 N 天」，無錯誤。
- AC-R8 Given 一個進行中（running）的掃描輪與進行中的探索；When 清除作業時間到；Then 清除順延到其結束後，且不刪除進行中的資料。
- AC-R9 Given 服務在清除預定時間未執行、當日稍後啟動且今日尚未清除；Then 啟動後補跑一次；Given 今日已清除；Then 不再清除第二次。
- AC-R10 Given 設定頁將保留期由 180 調降為 60；Then 顯示「下次清除將刪除超過 60 天的資料」，儲存當下不刪除任何資料。
- AC-R11 Given 探索保留；When 清除；Then 探索仍依 FD-6 的 7 天規則，行為與 FD-6 一致。

### 五、清除安全與壓縮

- AC-S1 Given 今日尚未備份且有 1 筆以上可清除資料；When 清除；Then 先出現當日備份檔（位於資料庫同目錄、`*.db`、可被開啟且筆數與清除前一致），再開始刪除；備份時間早於第一筆刪除。
- AC-S2 Given 今日已備份；When 同日再次清除（如補跑）；Then 不產生第二份備份。Given 當日沒有可清除資料；Then 不產生備份。
- AC-S3 Given 備份失敗（例如磁碟寫入失敗）；Then 本次不刪除任何資料，健康頁顯示已遮蔽的失敗原因，下次清除重試。
- AC-S4 Given 清除用備份已超過 7 份；Then 最舊者被刪除；`pre-v<N>` migration 備份不被刪除。
- AC-S5 Given 清除批次進行中服務被強制關閉；When 重啟並再次清除；Then 資料庫無孤兒資料（無觀測缺掃描輪、無明細缺主紀錄；完整性檢查通過），且清除可續跑完成。
- AC-S6 Given 清除完成；Then 監看、全域設定、alert_state、探索、被保留資料引用的紀錄皆不變；已通知過的價格不因清除而再次推播（去重相容）。
- AC-S7 Given 清除完成；Then 健康頁顯示本次清除時間與各類別刪除筆數（掃描輪、觀測、通知、其他）、是否產生備份、耗時。
- AC-S8 Given 壓縮開關開啟、距上次壓縮已滿 7 天、今日摘要已推送、清除已完成、無掃描與探索進行；Then 執行壓縮，並記錄時間與前後檔案大小，健康頁可見；壓縮後資料筆數不變、完整性檢查通過。
- AC-S9 Given 距上次壓縮未滿 7 天；Then 不壓縮。Given 壓縮開關關閉；Then 不壓縮。
- AC-S10 Given 壓縮時間到但有掃描或探索進行中；Then 壓縮順延至其結束後。Given 磁碟可用空間不足；Then 略過壓縮並記錄原因，資料庫不損壞。
- AC-S11 Given README；Then 載明備份檔名規則、位置，以及還原步驟（停止服務、備份覆蓋資料庫、重啟）。

### 六、效能與健康頁

- AC-H1 Given 套用索引的 migration；Then migration 前產生 `pre-v<N>` 備份，既有資料筆數不變，新資料庫不產生備份，索引存在。
- AC-H2 Given 20 個監看、5 萬筆已完成 scan_run、每筆 12 組查詢結果（FD-6 基準方法）；When 量測 `ViewService.list_page()` 暖機 1 次後取 10 次中位數；Then 中位數 < 100 ms，量測結果與環境記入任務單；SQL 次數仍為 1 加每監看 1 次（計數 fake repository 測試）。
- AC-H3 Given 同資料量；When 一輪掃描寫入；Then 寫入耗時不超過改前 120%；健康頁載入 < 300 ms。
- AC-H4 Given 健康頁；When 檢視資料維護區塊；Then 顯示資料庫檔案大小、監看／掃描輪／價格觀測／通知／探索筆數、上次清除時間與各類別刪除筆數、上次備份時間與檔名、上次壓縮時間與前後大小、目前保留期設定；從未清除或壓縮者顯示「尚未執行」。
- AC-H5 Given 5 萬筆掃描紀錄；When 開啟健康頁；Then 筆數統計不使頁面超過 300 ms，並註明統計時間。
- AC-H6 Given 新增的健康頁、設定頁、`/help` 與指令回覆全部文案；When 檢查禁用字；Then 皆通過 BANNED_PHRASES 測試。
- AC-H7 Given 全部新增的回覆、紀錄、頁面；When 掃描 token 原文；Then 不含（見 AC-P9）。

## 風險與依賴

- 授權風險（高）：指令入口完全靠 chat id 授權，無其他認證。因應：FR-P2 嚴格比對、未授權零回覆零記錄、指令集不含任何改條件動作（FR-P10）、`/scan` 與 `/digest` 受額度與既有規則約束。若 bot token 外洩，攻擊者仍無法經指令修改條件，但可偽造不到授權 chat（需知 chat id）；token 外洩處置見 README。
- `getUpdates` 互斥風險（高）：Telegram 同一 bot 同一時間只允許一個 `getUpdates` 消費者；服務輪詢與 `telegram-setup` 精靈會衝突，且精靈的 `getUpdates` 可能吞掉授權指令（FR-P8）。已知 FD-4 SW10 宣稱「服務執行中也能使用精靈」，本批需修正該說法（開放問題 2）。
- 離線積壓風險（中）：停機後重啟若盲目執行舊指令，可能在使用者已不預期時 `/pause` 或觸發查價；因應 FR-P5。
- 清除誤傷風險（高）：清除錯誤可能刪掉目前最低價所依賴的資料，或讓列表／摘要數字突變、讓已通知價格重複推播。因應：FR-R5、R6、S3、S4、S6，並以清除前後快照比對測試。彈性窗輪換取樣使「最近 N 輪」未必涵蓋所有日期組合的最新觀測，需 tech-architect 評估。
- 資料模型風險（中）：新增通知類型（指令、手動摘要）可能需要擴充 `notification.kind` 約束，需 migration；索引也是 migration；兩者皆須沿用備份與回復慣例。清除須處理通知對觀測的參照（外鍵）與去重鍵相容。
- 壓縮風險（中）：VACUUM 需要約等於資料庫大小的暫存空間並短暫獨佔資料庫；因應 FR-S6 的條件式執行。
- 資料可得性風險（中）：保留期讓價格歷史與趨勢圖縮短；因應 FR-R7 如實揭露；保留期可調。
- 與單一 worker 的相容性（中）：`/scan` 與探索、排程共用 worker，須沿用 FD-6 順延規則，不丟件不重複。輪詢本身不得佔用 worker。
- 額度風險（低）：`/scan` 可被快速連發耗用額度；受全域每小時額度約束，被拒時如實回覆；是否另加單監看冷卻見開放問題 6。
- 風控閘門：指令回覆皆為事實查詢結果，非建議類文案，原則上不適用章程風險閘門；但新增回覆樣板仍依 ADR C-17 定稿後交 risk-compliance-officer 看一次，預期判定「不適用」（開放問題 12）。若日後加入任何建議性指令須重送審查。
- UI 驗收：涉及設定頁開關與健康頁新增區塊，完成前須 qa-e2e 實機驗收；無人值守環境起不了 dev server 時依 e2e-fallback。真實 Telegram 收發（AC-K4、AC-K8、AC-P2 的真機）須 CEO 或總經理手動驗收；效能數字（AC-H2）須實跑並附原始輸出。
- 祕密與遮蔽：輪詢是新的 token 外洩高風險點（URL 內含 token），所有錯誤路徑須有自動化測試（AC-P9）。

## 開放問題（待 CEO 或其他部門回答）

預設值已標示；未覆議則照預設進行。

1. 【tech-architect】長輪詢實作方式：如何在不佔用排程 worker 的前提下於背景輪詢、拉取逾時秒數、退避策略、已處理訊息偏移量（offset）的持久化方式以確保 FR-P4 不重複執行、設定關閉後停止的最長等待。
2. 【總經理／tech-architect，預設：精靈偵測到衝突時只印說明並結束，不消耗授權指令】`telegram-setup` 與服務輪詢互斥（FR-P8）。預設作法：精靈遇到 409 衝突時說明「請先關閉指令功能或停止服務」；是否需要精靈在關閉指令功能後才可取得 chat id（因關閉後服務不輪詢，無衝突），由架構確認並修正 FD-4 SW10 的說法。
3. 【CEO，預設：超過 10 分鐘的積壓指令不執行並回一則說明】離線期間累積的指令是否執行？預設只執行 10 分鐘內的，其餘提示重新傳送。
4. 【總經理，預設：編號 = 網頁監看列表顯示的監看編號（資料庫 id）】指令的「編號」定義；刪除監看後編號不重用的行為以現有資料庫為準，若會重用需由架構提出替代。
5. 【CEO，預設：大小寫不分、接受 `/指令@bot名稱` 後綴】指令格式的寬容度。
6. 【CEO，預設：不另加單監看冷卻，只受全域額度與「已在查價中不重複排入」約束】`/scan` 是否需要單一監看冷卻時間（例如 5 分鐘內不可重複）。
7. 【CEO，預設：保留期 180／365 天；清除每日一次，時間為每日摘要時間後 30 分鐘；壓縮每週一次接在當日清除後】清除與壓縮的具體時刻與頻率是否另有偏好。
8. 【CEO，預設：N=10 可在設定頁調整，下限 3】「每監看至少保留最近 N 輪」是否開放調整。
9. 【總經理，預設：清除用備份保留最近 7 份】備份保留份數。
10. 【CEO，預設：不提供網頁「立即清除／立即壓縮」按鈕與還原介面】是否需要手動觸發與網頁還原。預設只做自動排程與 README 還原步驟。
11. 【tech-architect】FR-R6 彈性窗輪換取樣下，「最近 N 輪」不足以保證快照數字不變時的額外保留方式（例如保留各日期組合最新一筆觀測）；通知對觀測的外鍵處理；通知去重鍵與清除相容；清除範圍中「略過事件」等附屬表的歸屬；新增通知類型的 migration 與索引 migration 是否合併；是否需增補 ADR-0002。
12. 【risk-compliance-officer】指令回覆樣板（含 `/help`、`/watch`、`/scan` 結果、`/status`）C-17 審查，預期判定「不適用」。
13. 【tech-architect】`/status`、`/list` 等指令的資料來源是否重用既有 `ViewService` 與摘要組字，避免兩份計算；回覆長度上限與 `MAX_MESSAGE_LENGTH` 的關係。
14. 【CEO，預設：輪詢暫時失敗不推播告警，只在健康頁顯示】指令輪詢連續失敗是否要透過 Telegram 告警（無法送達時告警本身也可能失敗）。
15. 【qa-e2e】設定頁開關、健康頁新增區塊的實機驗收路徑；真實 Telegram 的手動驗收清單；5 萬筆資料的效能量測環境與方法；無人值守依 e2e-fallback。
