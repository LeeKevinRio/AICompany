# ADR-M001：manjong-unity 架構與前後端切分

- 狀態：proposed（待 CEO 核可）
- 日期：2026-10-03
- 範圍：只適用產品線 `product/manjong-unity`。產品 ADR 放在 `work/manjong-unity/adr/`，編號加 `M` 前綴，
  避免跟 main 的 `docs/adr/` 編號撞號（產品分支永遠不 merge 回 main）。

## 背景

CEO 指定：Unity 6.3 LTS 做用戶端、WebGL 優先、後端用 TypeScript；第一版是單機（1 人 vs 3 AI），
但要有訪客帳號、假金幣與排行榜，之後會做線上多人。

## 決策

1. **伺服器權威（server-authoritative）**：規則引擎、洗牌、AI、結算全部用 TypeScript 寫在後端。
   Unity 只負責畫面與輸入，送出「選了哪個合法動作（actionId）」。
   - 「單機」指的是一位真人玩家，不是離線。WebGL 本來就在瀏覽器裡跑，需要網路可以接受。
2. **第一版通訊用 HTTP JSON（REST），不用 WebSocket**：
   - 單人對 AI 是回合制，每次動作都是一問一答：玩家送動作 → 伺服器跑完所有 AI 直到下一次需要玩家決定 →
     回傳中間每一步的事件與該時點的畫面（steps），用戶端依序播放。
   - Unity WebGL 不支援 `System.Net.WebSockets`，REST 走 `UnityWebRequest` 在 Editor 與 WebGL 行為一致，免外掛。
3. **後端框架**：Node.js 22 + Fastify（`@fastify/cors`、`@fastify/static`），測試用 Vitest。
4. **儲存**：玩家資料先用 JSON 檔（原子寫入）包在 `PlayerRepository` 介面後；牌局狀態放記憶體（重啟即失效）。
5. **認證**：訪客登入發隨機 token（32 bytes），伺服器只存 SHA-256 雜湊；用戶端存在 `PlayerPrefs`。
6. **Unity 用戶端全程式碼建 UI**（uGUI + 執行期產生的圓角圖），以 `RuntimeInitializeOnLoadMethod` 啟動，
   不依賴手拉的 scene 或 prefab；JSON 用 `JsonUtility`，因此 API 只用固定形狀的物件與陣列（不送 null、不用多型）。
7. **字型**：jf open 粉圓（OFL / Apache 2.0，可愛圓體）子集化後放進 `Resources`，因為 WebGL 沒有系統字型可以 fallback。
8. **部署形態**：伺服器可同時提供 WebGL 靜態檔（同源，免 CORS）；開發時 Unity Editor 直接打 `http://127.0.0.1:7316`。

## 考慮過的替代方案

| 方案 | 不採用的理由 |
| --- | --- |
| 規則寫在 Unity C#（純前端單機） | 金幣與排行榜在用戶端算等於沒有防作弊；之後做線上多人還要再寫一份 TS 版 |
| C# 與 TS 各寫一份規則 | 兩份規則一定會不一致，測試成本加倍 |
| 一開始就用 Colyseus / WebSocket | 單機不需要即時推播；WebGL 要另裝 WebSocket 外掛。留到線上多人時再導入 |
| SQLite（`node:sqlite`） | Node 22 仍標示 experimental；單一玩家規模用 JSON 檔足夠，介面已抽象，之後可換 |

## 後果

- 好處：規則只有一份且可完整單元測試；排行榜資料不能由用戶端偽造；之後做線上多人時引擎可直接沿用。
- 代價：沒有網路就不能玩；伺服器重啟會中斷進行中的牌局（第一版可接受）。
- 之後做線上多人：引擎不動，外層加 WebSocket 房間（評估 Colyseus），需另出 ADR。
