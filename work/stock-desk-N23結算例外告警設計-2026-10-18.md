## 1. 現況盤點（事實）

路徑皆相對 `apps/stock-desk/backend/`，除非另註。查證日 2026-10-18。

### 1.1 結算程式尚不存在

- `app/` 底下沒有 `forecast/` 目錄；`app/scheduler.py` 全檔沒有 `forecast` 字樣（grep 0 筆）。
- 所以本提案的觸發點全部是對 ADR-0027 D-1、D-7.2 規劃中的 `recorder.py`、`settlement.py`、`correction.py` 的要求，不是改現有程式。

### 1.2 log 通道

- 只有 Python `logging` 寫到 stdout/stderr：`app/scheduler.py:782` `logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")`。沒有 handler 分流、沒有結構化 log、沒有 log 外送。（R-1 修補分支已改為 `configure_logging()`，尚未合併。）
- 慣用格式是單行 `key=value`：`app/scheduler.py:351-370`（`data refresh run: trigger=... outcome=...`）、`:581-592`（`dividend sync run: ...`）。
- 容器部署時，log 的取得方式是 `docker compose logs scheduler`（`compose.yaml:29-48`，沒有設 logging driver，`restart: unless-stopped`）；主機部署時是 `*>> logs\scheduler.log`（`docs/族群動能-主機部署手冊.md:139-148`）。
- 營運現行的「告警」是人工掃 log：部署手冊 §5（`docs/族群動能-主機部署手冊.md:310-356`）用 `Select-String` 掃 `scheduler.log`，而且多數規則是「連續出現超過一次排程週期才算持續」（`:330-333`），與本案「第一次就告警」相反。同節 `:353-357` 明說「沒有自動告警機制」。

### 1.3 推播通道（現有）

- `app/alerts/notify.py` 推 Discord／Telegram webhook，設定只讀環境變數 `ALERT_DISCORD_WEBHOOK_URL`、`ALERT_TELEGRAM_BOT_TOKEN`、`ALERT_TELEGRAM_CHAT_ID`（`:32-34`）；單次 POST 逾時 5 秒（`:40`）；送不出去只記 WARNING、不拋例外（`:75-78`）。
- 該模組只收 `AlertEvent`（`app/alerts/models.py:253-269`，有必填的 `rule_id`、`symbol`、`market`），格式化函式 `format_message`（`notify.py:53-`）會帶「本工具為研究與教育用途，非投資建議。」這類使用者面句子。所以不能直接拿來送維運告警。
- 使用者告警在 `app/scheduler.py:380` 受 `settings.alerts.enabled` 控制，推播在 `:420` 受 `settings.alerts.notify_webhooks` 控制；兩者是使用者可關的設定。維運告警不可共用這兩個開關。
- 使用者告警有冷卻機制（`app/alerts/engine.py:375-383`、`:446`，`cooldown_minutes`）。這是「壓制重複」的機制，本案明確不採用。

### 1.4 排程器怎麼報錯

- 每個 job 都包 `_guarded`（`app/scheduler.py:604-613`）：`except Exception: logger.exception("scheduled job %s failed; it stays scheduled", name)`，只落 ERROR log 與 traceback，沒有推播。模組說明見 `:60-66`。
- 沒有任何 APScheduler listener：`app/scheduler.py` 內無 `add_listener`、`EVENT_JOB_*`（grep 0 筆）。
- 所有 job 都 `max_instances=1`、`coalesce=True`（`:640-641`、`:655-656`、`:669-670`、`:684-685`、`:698-699`）；被略過的觸發點目前不留任何痕跡。ADR-0027 D-7.1 的 N-23 子點已要求為 `EVENT_JOB_MAX_INSTANCES`、`EVENT_JOB_MISSED` 加 listener 並記 WARNING（ADR-0027 第 773 行）。**該子點原寫的「告警規格依 ADR-0026」是指向錯誤（ADR-0026 全檔沒有告警條文，tech-architect 查證），已由 ADR-0027 字面五改為指向 ADR-0029。**
- APScheduler 實際版本 3.11.3（`uv.lock:48-49`，本機 `.venv` 亦驗為 3.11.3）；`EVENT_JOB_MAX_INSTANCES`=65536、`EVENT_JOB_MISSED`=16384 存在。事件物件屬性已於 `.venv` 原始碼確認：`EVENT_JOB_MAX_INSTANCES` 為 `JobSubmissionEvent`，屬性 `scheduled_run_times`（list）；`EVENT_JOB_MISSED` 為 `JobExecutionEvent`，屬性 `scheduled_run_time`（單一值）。

### 1.5 有無「第一次就告警」的機制

- 沒有。現況是兩種極端：job 失敗只有 ERROR log（沒人推）；使用者告警有冷卻（會壓制）。
- 另有一個既有缺陷（與本案相關，必須先修，見 §3 R-1）：`app/alerts/notify.py:75-78` 把例外原文寫進 log 與 `DeliveryResult.detail`。我在本機用 httpx 0.28.1 的 MockTransport 以假 token 驗證：`HTTPStatusError` 字串含完整請求 URL（`Client error '404 Not Found' for url 'https://api.telegram.org/botFAKETOKEN123/sendMessage'`）。Telegram 的 URL 內含 bot token，所以 Telegram 推播一旦遇到 4xx/5xx，token 會進 log。這違反 CLAUDE.md §4 的祕密守則；維運告警一旦走同一條路徑，會把這個風險放大。

### 1.6 ADR-0027 的相關條文（以字串定位）

- D-9.3 `split_or_reduction_suspected` 之下的 `span_sessions` 子點：「例外訊息與 WARNING 至少帶：符合判準卻未登記的 `session_date` 清單、受影響的預測筆數、D_reg、快照範圍（更正作業為重查範圍與 `market_scan_to`）」；另「不得捕捉本例外後繼續寫入」。
- D-9.2「R 倒退」：「R 小於前一筆 `forecast_settle_eval.market_run_max` 時，視為市場 DB 被還原：記 WARNING，本次不寫入（fail-closed），直到 devops-sre 依 ADR-0026 D-9.4 處理並修訂本點」。（tech-architect 裁定改為型別化例外 `MarketRunRegressedError`，檢查點提前到 ①′，參考值擴及更正作業的 `market_scan_to`。）
- D-7.2 步驟隔離：結算失敗的例外只在 `recorder.py` 編排函式中、`run_settlement_evaluation()` 呼叫的外面接住；接住時主 DB 交易已 rollback（D-9.2 ⑦）；缺日稽核照常執行。
- D-7.1：22:10 執行、23:10 重試、啟動 3 分鐘後補跑；`max_instances=1`；單一 job。
- ADR-0026 D-9.4（整檔還原只限操作者手動）：R 倒退的來源。
- D-1 模組表：`app.alerts.*` 在 `app.forecast` 底下只可達 `views` 與型別模組（FL import graph，ADR-0027 第 2453 行）。

## 2. 設計

### 2.1 原則

1. **每次發生都留 log；每次執行至少推播一次；不設次數門檻、不設冷卻。**
2. **告警在 rollback 之後、由編排層發出**，不在寫入交易內、不在 `run_settlement_evaluation()` 內（該函式是唯一寫入端，簽章與 AST 規則已定，不加網路 I/O）。
3. **告警不得影響流程**：送不出去不拋例外，編排函式照 D-7.2 繼續跑缺日稽核。
4. **內容只有技術欄位**：無祕密、無個人資料（無代號、持倉、金額）、無使用者面句子（不帶免責聲明、不帶任何方向或建議字句、不帶處置指示）。
5. **不提供任何關閉開關**（環境變數、設定表、API 都不提供），比照 `dividend_sync` 的「No environment variable switches it off」。

### 2.2 觸發點

單一位置：`recorder.py` 編排函式內，D-7.2 步驟隔離的 `except` 區塊（與「回傳非成功結果」的分支）。理由：那裡是 rollback 之後、下一步之前，而且各步的失敗都經過那裡。送出器以必填關鍵字參數 `ops_alert_sink` 注入，沒有預設值（ADR-0029 D-1）。

| 事件 | 判定來源 | 發出位置 |
|---|---|---|
| E-1 `forecast.unregistered_unobserved_weekday` | 結算評估或更正作業拋出型別化例外 `UnregisteredUnobservedWeekdayError`（由 `run_settlement_evaluation()`、`run_correction_job()` 最外層從 `SpanRegistrationGap` 轉換） | 編排函式接住結算步驟、更正作業步驟的 `except` |
| E-2 `forecast.market_run_regressed` | `source = settlement`：`run_settlement_evaluation()` 在 ①′ 拋型別化例外 `MarketRunRegressedError`。`source = audit`、`correction`：共同守衛 `market_run_regression` 成立（ADR-0027 D-7 第 2 點 Q7） | 編排函式接住結算步驟；缺日稽核與更正作業步驟 |
| E-3b／E-3c／E-3d | 見 §2.7 | 見 §2.7 |

已由 tech-architect 裁定（原本的「對 dev-lead 的實作要求」）：

- 兩個例外帶結構化屬性（欄位見 §2.3），不得靠解析例外字串取欄位。
- R 倒退定為型別化例外，檢查點在 ①′（讀 R 之後、②之前），參考值＝最後一列 `forecast_settle_eval.market_run_max` 與最近一個已有 `forecast_correction_job_end` 的作業的 `market_scan_to` 兩者取大，以一次主 DB 唯讀查詢取得，不讀市場 DB。
- 其他未分類的結算例外：併入 E-3d（§2.7），擴為任一步失敗。

### 2.3 事件名稱與欄位

事件名稱前綴 `forecast.`，全小寫、點分隔，與 log 的 `event=` 欄位及推播標題一致。所有時間為 UTC ISO8601（公司資料慣例）。

**共同欄位**

| 欄位 | 內容 |
|---|---|
| `event` | 事件名稱 |
| `severity` | 固定 `WARNING` |
| `occurred_at` | 編排層接住當下的 store 時鐘（UTC） |
| `execution_started_at` | **編排函式開始時讀一次的 store 時鐘（UTC）**，該次執行的所有告警共用同一個值。不含進入點類別：job 函式拿不到是哪個觸發點，不從時鐘推算。E-3b 沒有執行，為 None |
| `source` | 列舉 `settlement`／`audit`／`correction`，或 None；取值依下方「適用對照」。E-1、E-2 的值與 ADR-0027 例外屬性或守衛呼叫端的 `source` 逐字相同 |
| `step` | 列舉 `record`、`settlement`、`gap_audit`、`late_scan_correction`、`validation_snapshot`、`plan`、`orchestrator`，或 None；前六個依序對應 ADR-0027 D-7 第 2 點的六步。取值依下方「適用對照」 |
| `write_outcome` | 封閉列舉 `not_written`、`written_without_registration`、`deferred`、`not_started`、`unspecified`，或 None（只限 selftest）；定義與取值依下方「適用對照」 |

**適用對照**（tech-architect 2026-10-18 確認；正式規格見 ADR-0029 D-2 規則 4）。表外的組合在 model 建構時拒絕：

| 事件 | `source` | `step` | `write_outcome` |
|---|---|---|---|
| E-1 | `settlement` | `settlement` | `not_written` |
| E-1 | `correction` | `late_scan_correction` | `not_written` |
| E-2 | `settlement` | `settlement` | `not_written` |
| E-2 | `audit` | `gap_audit` | `written_without_registration` |
| E-2 | `correction` | `late_scan_correction` | `deferred`（落檔前提見 ADR-0029 D-7 規則） |
| E-3b | None | None | `not_started` |
| E-3c | `settlement` | `settlement` | `not_started` |
| E-3d | None | 七個 `step` 值之一 | `unspecified` |
| `ops_alert.selftest` | None | None | None |

- `not_written`：該步的結果寫入交易已 rollback；`forecast_outcome`、`forecast_settle_eval`、`forecast_correction_job_end`、`forecast_void_late_diag` 沒有新列（ADR-0027 FL-71 (c)）。同一步先前以獨立交易 commit 的列不在此限：結算評估 ③ 的查證紀錄與 X2 確認（①′ 成立時沒有這些列），以及更正作業 ③ 的 `forecast_correction_job` 列與未觀察平日登記。
- `written_without_registration`：缺日稽核已 commit `forecast_gaps` 與 `forecast_gap_audit`，但沒有做 A-77 第 10 項登記（ADR-0027 D-7 第 2 點 Q7）。只在缺日稽核 commit 之後發出；缺日稽核拋例外時改發 E-3d，不發 E-2。
- `deferred`：更正作業本次不啟動，四類觸發延後，W、W_E、W_V、W_S 都不前進。
- `not_started`：該步沒有啟動，沒有寫入。E-3b 指的是整個 job 的該次觸發。
- `unspecified`：編排函式無法斷言該步留下哪些列。E-3d 一律用這個值，因為任意例外的拋出位置無法由型別判定；各步實際的寫入由 ADR-0027 的 FL 格保證。

### 2.4 log 形式（永遠寫，不去重）

- 專用 logger 名稱 `app.ops_alert`，WARNING，單行 `key=value`，與 `scheduler.py` 現行風格一致。在 `configure_logging()`（R-1／O-1）之下 `app` 是 INFO、root 是 WARNING，所以 WARNING 一定輸出。
- 範例（假值；日期為說明用）：

```
ops alert: event=forecast.unregistered_unobserved_weekday severity=WARNING source=settlement step=settlement execution_started_at=2026-11-02T14:10:01Z occurred_at=2026-11-02T14:10:03Z write_outcome=not_written unregistered_count=2 unregistered_session_dates=2026-10-12,2026-10-14 affected_forecast_count=17 d_reg=2026-10-05 snapshot_from=2026-10-05 snapshot_to=2026-11-02
ops alert: event=forecast.market_run_regressed severity=WARNING source=settlement step=settlement execution_started_at=2026-11-02T15:10:01Z occurred_at=2026-11-02T15:10:02Z write_outcome=not_written market_run_current=812 reference_kind=settle_eval reference_value=840 reference_id=31 reference_started_at=2026-11-02T14:10:01Z
```

- 營運上的搜尋字串固定為 `ops alert: event=`；部署手冊 §5 的待補項列於 ADR-0029「部署手冊 §5 待補項」（devops-sre 在 D_v 前落地）。
- 另外每次執行結束寫一行 INFO `forecast record run:`（含每一步的 outcome；ADR-0027 D-7 第 2 點 Q8）。這行是 §2.6「恢復」的判讀依據，也讓「完全沒有這行」可以被人工或外部檢查發現（見 §3 R-4）。

### 2.5 去重規則（第一次就告警，不得以次數門檻壓制）

- **去重鍵**＝(`event`, `source`, `step`, `execution_started_at`)。同一鍵在同一次執行內只推播一次（防止編排層因重入或雙重接住而送兩次）。`execution_started_at` 為 None 的告警（E-3b、`step = orchestrator` 的 E-3d、selftest）不去重，每次 `emit` 都推播，也不讀、不改鍵集合（tech-architect 2026-10-18 裁定）。理由：E-3b 由 scheduler 的派送執行緒呼叫，`max_instances` 事件發生時正有一次執行在跑，若以它換掉鍵集合，執行中的那一次會重複推播；APScheduler 對同一個觸發時刻只送一次事件；`step = orchestrator` 每次 job 呼叫至多一則。
- 送出器只在行程記憶體保留「目前這次執行」的鍵集合；收到不同執行識別時整個換掉。不寫檔、不寫資料庫。行程重啟只會多推、不會少推。鍵集合的讀寫以 `threading.Lock` 保護；這個鎖只保護行程記憶體內的集合，不構成跨執行狀態。
- **不跨執行去重**：22:10 失敗、23:10 重試仍失敗、隔日 22:10 仍失敗，每次執行都各推播一次。理由：這些事件都是 fail-closed，結算整批停擺，持續期間每個交易日都該被看到；而且這裡沒有「N 次後才告警」或「冷卻 N 分鐘」，第一次發生就推播，符合清單 N-23 (1) 的字面。
- **推播量上限的估算**：每次執行每一步失敗至多一則（取最具體的事件）。每日兩次例行執行（22:10、23:10）加可能的一次啟動補跑；E-2 三個 source 同時成立時每次執行 3 則、每日 6 則；最壞情形每次執行不超過 7 則。若 CEO 認為太吵，唯一允許的調整是「同一個去重鍵內的重複」，不得改成跨執行靜默。
- **不採用的做法**：使用者告警的冷卻（`engine.py:375-383`）、連續 N 次門檻、以內容雜湊跨日壓制。
- **不維護跨執行狀態**：不新增表、不寫狀態檔。代價是推播不帶「第幾次」或「首次發生時間」；操作者以 log 的 `execution_started_at` 與 `GET /api/forecast/status` 的 `last_settle_eval_at`（ADR-0027 D-8 第 5 點）判讀持續天數。
- **推播內容的截斷**（tech-architect A-4 裁定、風控核可，規格見 ADR-0029 D-4）：
  - 推播帶 E-1 的全部欄位；只有 `unregistered_session_dates` 截斷，其餘欄位不截斷、不省略。
  - 清單最多列 20 筆（常數 `OPS_ALERT_PUSH_MAX_LIST_ITEMS`），升冪；永遠帶 `unregistered_count`、最早一日、最晚一日；超過時加「另有 N 筆，完整清單見 scheduler log」；log 永遠完整。不採分則送出。
  - 推播文字長度 ≤ 常數 `OPS_ALERT_PUSH_MAX_CHARS`＝各通道單則上限的較小值減去安全餘量。**各通道上限的數值【未查證】**，見 §7；不寫死。

### 2.6 通道、靜默與恢復

**通道**

- 沿用既有 Discord／Telegram 環境變數（`ALERT_DISCORD_WEBHOOK_URL`、`ALERT_TELEGRAM_BOT_TOKEN`、`ALERT_TELEGRAM_CHAT_ID`），不新增環境變數。憑證由 CEO 自行設定（紅線）；我不碰 `.env`。傳輸統一經 `app/push_channels.py`（ADR-0029 D-1）。
- 與使用者告警**共用通道、不共用開關**：維運告警不讀 `settings.alerts.enabled`、`notify_webhooks`；標題固定 `[stock-desk 維運告警] <event>`，與使用者告警的 `[stock-desk 警示]` 區分。
- 推播文字只由固定標籤常數加 §2.3 的欄位值組成（正面白名單），再以風控的禁用詞清單做第二道掃描；不含免責句、不含任何建議性字句、不含處置指示（ADR-0029 D-4）。
- 送出一律在 rollback 之後、`try/except Exception` 內：逾時沿用 5 秒；失敗只記一行 ERROR `ops alert delivery failed: channel=<discord|telegram> error_class=<例外類別名> [status=<碼>]`，格式由 R-1 的 `describe_failure()` 產生，**不得記例外字串、URL**（見 §3 R-1）。送不出去不阻擋後續步驟。
- **未設任何通道的處理**：結算 job 註冊時（scheduler 啟動）檢查是否至少有一個通道設定完整；沒有時記一行 ERROR `ops alert channel not configured; forecast exceptions will only reach the log`。這只是補強：**D_v 前必須有至少一個通道設定完整，並以 `ops_alert.selftest` 確認送達**（§2.8、ADR-0029 D-10）；只在啟動時記 ERROR 不夠。

**靜默**

- 沒有任何手動靜默、確認或關閉功能。理由：這些事件都是不變式被破壞或資料被還原，唯一的解除方式是處理根因。
- 計畫性整檔還原（ADR-0026 D-9.4）：操作者在還原前先停 scheduler（`docker compose stop scheduler`），還原完成、`mark-restored` 與 X-3a 腳本跑完後再啟動。scheduler 停止期間沒有執行，所以不會有預期內的 E-2。若還原後仍出現 E-2，視為真實事件。
- **收到 E-2 時，立即停 scheduler（`docker compose stop scheduler`），處理完 ADR-0026 D-9.4 才可以重啟**（風控 R-Q7-6，擋 D_v；部署手冊 §5 待補，推播本身不含處置指示）。
- 同一個根因造成的重複推播（§2.5）不屬於需要靜默的情形。

**恢復**

- 恢復的判準（可由事實檢查，不靠推播）：下一次執行的 `forecast record run:` 各步 outcome 為完成、同一次執行沒有 `ops alert:` 行、且 `last_settle_eval_at` 前進。
- 本版不推播「已恢復」訊息，因為需要跨執行狀態（§2.5）。選項 B：恢復通知，需先決定狀態存放處（新表或狀態檔），涉及 ADR；建議不在 D_v 前做，列為後續。推播也不得含「正常」「無異常」等暗示一切正常的字。
- **E-2 停止出現，不代表已處理**：共同守衛不存跨執行狀態，市場 DB 被還原後新寫入的 run 使 R 再度不小於參考值時，判定就不再成立（風控 R-Q7-5、N-20）。處理終點是 ADR-0026 D-9.4，不是推播消失。
- E-2 的處理程序（確認備份 manifest 的最新市場 DB `run_id`、決定接受新的基準或重建）由我在 E-2 發生時另行出處理單；本提案不預先決定放寬 fail-closed。

### 2.7 附帶事件

E-3a 已併入 E-2（`source = audit`／`correction`，見 §2.2、§2.3；tech-architect Q7 裁定）。其餘：

- 每一步失敗只發一則，取最具體的事件（E-1／E-2 優先於 E-3c、E-3d）。前置條件不成立而略過的步驟不另發告警。

**去重與不壓制**

**內容安全**

8. 推播文字與 log 行通過風控的 FL-71 (f) 禁用詞清單（ADR-0027 FL-71 (f) 下方的「推播禁用詞清單」，原文為 `work/reviews/2026-10-18-N23維運告警與Q1至Q9審查-風控.md` 第二節類別 A～F 與白名單例外；是否為測試的單一來源待 TA 與 dev-lead 確認，測試內不手抄）：

   - 正面白名單：推播只由標題常數、事件名稱、`render` 登記的固定標籤常數與欄位值組成；逐一列舉 payload dataclass 的欄位，缺標籤即失敗；
   - 標籤常數本身也要通過類別 A～D 的掃描；

9. 例外含敏感字串（fixture 在例外訊息塞假 token 與假路徑）→ 推播與 log 都不出現（因為只取欄位，不取 `str(exc)`）。

**流程不被影響**

**本次新增的格**
