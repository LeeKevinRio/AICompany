## 1. 現況盤點（事實）

路徑皆相對 `apps/stock-desk/backend/`，除非另註。查證日 2026-10-18。

### 1.1 結算程式尚不存在

- `app/` 底下沒有 `forecast/` 目錄；`app/scheduler.py` 全檔沒有 `forecast` 字樣（grep 0 筆）。
- 所以本提案的觸發點全部是對 ADR-0027 D-1、D-7.2 規劃中的 `recorder.py`、`settlement.py`、`correction.py` 的要求，不是改現有程式。

### 1.2 log 通道

- 只有 Python `logging` 寫到 stdout/stderr：`app/scheduler.py:782` `logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")`。沒有 handler 分流、沒有結構化 log、沒有 log 外送。
- 慣用格式是單行 `key=value`：`app/scheduler.py:351-370`（`data refresh run: trigger=... outcome=...`）、`:581-592`（`dividend sync run: ...`）。
- 容器部署時，log 的取得方式是 `docker compose logs scheduler`（`compose.yaml:29-48`，沒有設 logging driver，`restart: unless-stopped`）；主機部署時是 `*>> logs\scheduler.log`（`docs/族群動能-主機部署手冊.md:139-148`）。
- 營運現行的「告警」是人工掃 log：部署手冊 §5（`docs/族群動能-主機部署手冊.md:310-356`）用 `Select-String` 掃 `scheduler.log`，而且多數規則是「連續出現超過一次排程週期才算持續」（`:330-333`），與本案「第一次就告警」相反。同節 `:353-357` 明說「沒有自動告警機制」。

### 1.3 推播通道（現有）

- `app/alerts/notify.py` 推 Discord／Telegram webhook，設定只讀環境變數 `ALERT_DISCORD_WEBHOOK_URL`、`ALERT_TELEGRAM_BOT_TOKEN`、`ALERT_TELEGRAM_CHAT_ID`（`:32-34`）；單次 POST 逾時 5 秒（`:40`）；送不出去只記 WARNING、不拋例外（`:75-78`）。
- 該模組只收 `AlertEvent`（`app/alerts/models.py:253-269`，有必填的 `rule_id`、`symbol`、`market`），格式化函式 `format_message`（`notify.py:53-`）會帶「本工具為研究與教育用途，非投資建議。」這類使用者面句子。所以不能直接拿來送維運告警。
- 使用者告警在 `app/scheduler.py:380` 受 `settings.alerts.enabled` 控制，推播在 `:420` 受 `settings.alerts.notify_webhooks` 控制；兩者是使用者可關的設定。維運告警不可共用這兩個開關。
- 使用者告警有冷卻機制（`app/alerts/engine.py:375-383`、`:446`，`cooldown_minutes`）。這是「壓制重複」的機制，本案明確不採用。

### 1.4 排程器怎麼報錯

- 每個 job 都包 `_guarded`（`app/scheduler.py:604-613`）：`except Exception: logger.exception("scheduled job %s failed; it stays scheduled", name)`，只落 ERROR log 與 traceback，沒有推播。模組說明見 `:60-66`。
- 沒有任何 APScheduler listener：`app/scheduler.py` 內無 `add_listener`、`EVENT_JOB_*`（grep 0 筆）。
- 所有 job 都 `max_instances=1`、`coalesce=True`（`:640-641`、`:655-656`、`:669-670`、`:684-685`、`:698-699`）；被略過的觸發點目前不留任何痕跡。ADR-0027 D-7.1 的 N-23 子點已要求為 `EVENT_JOB_MAX_INSTANCES`、`EVENT_JOB_MISSED` 加 listener 並記 WARNING（ADR-0027 第 773 行），告警規格「依 ADR-0026（devops-sre，N-23 (1)）」。
- APScheduler 實際版本 3.11.3（`uv.lock:48-49`，本機 `.venv` 亦驗為 3.11.3）；`EVENT_JOB_MAX_INSTANCES`=65536、`EVENT_JOB_MISSED`=16384 存在。

### 1.5 有無「第一次就告警」的機制

- 沒有。現況是兩種極端：job 失敗只有 ERROR log（沒人推）；使用者告警有冷卻（會壓制）。
- 另有一個既有缺陷（與本案相關，必須先修，見 §3 R-1）：`app/alerts/notify.py:75-78` 把例外原文寫進 log 與 `DeliveryResult.detail`。我在本機用 httpx 0.28.1 的 MockTransport 以假 token 驗證：`HTTPStatusError` 字串含完整請求 URL（`Client error '404 Not Found' for url 'https://api.telegram.org/botFAKETOKEN123/sendMessage'`）。Telegram 的 URL 內含 bot token，所以 Telegram 推播一旦遇到 4xx/5xx，token 會進 log。這違反 CLAUDE.md §4 的祕密守則；維運告警一旦走同一條路徑，會把這個風險放大。

### 1.6 ADR-0027 的相關條文（以字串定位）

- D-9.3 `split_or_reduction_suspected` 之下的 `span_sessions` 子點：「例外訊息與 WARNING 至少帶：符合判準卻未登記的 `session_date` 清單、受影響的預測筆數、D_reg、快照範圍（更正作業為重查範圍與 `market_scan_to`）」；另「不得捕捉本例外後繼續寫入」。
- D-9.2「R 倒退」：「R 小於前一筆 `forecast_settle_eval.market_run_max` 時，視為市場 DB 被還原：記 WARNING，本次不寫入（fail-closed），直到 devops-sre 依 ADR-0026 D-9.4 處理並修訂本點」。
- D-7.2 步驟隔離：結算失敗的例外只在 `recorder.py` 編排函式中、`run_settlement_evaluation()` 呼叫的外面接住；接住時主 DB 交易已 rollback（D-9.2 ⑦）；缺日稽核照常執行。
- D-7.1：22:10 執行、23:10 重試、啟動 3 分鐘後補跑；`max_instances=1`。
- ADR-0026 D-9.4（整檔還原只限操作者手動）：R 倒退的來源。
- D-1 模組表：`app.alerts.*` 在 `app.forecast` 底下只可達 `views` 與型別模組（FL import graph，ADR-0027 第 2453 行）。

## 2. 設計

### 2.1 原則

1. **每次發生都留 log；每次執行至少推播一次；不設次數門檻、不設冷卻。**
2. **告警在 rollback 之後、由編排層發出**，不在寫入交易內、不在 `run_settlement_evaluation()` 內（該函式是唯一寫入端，簽章與 AST 規則已定，不加網路 I/O）。
3. **告警不得影響流程**：送不出去不拋例外，編排函式照 D-7.2 繼續跑缺日稽核。
4. **內容只有技術欄位**：無祕密、無個人資料（無代號、持倉、金額）、無使用者面句子（不帶免責聲明、不帶任何方向或建議字句）。
5. **不提供任何關閉開關**（環境變數、設定表、API 都不提供），比照 `dividend_sync` 的「No environment variable switches it off」。

### 2.2 觸發點

單一位置：`recorder.py` 編排函式內，D-7.2 步驟隔離的 `except` 區塊（與「回傳非成功結果」的分支）。理由：那裡是 rollback 之後、缺日稽核之前，而且結算與更正作業兩條路徑都經過那裡。

| 事件 | 判定來源 | 發出位置 |
|---|---|---|
| E-1 `unregistered_unobserved_weekday` | 結算評估或更正作業拋出型別化例外 `UnregisteredUnobservedWeekdayError`（`span_sessions` 拋出） | 編排函式接住結算步驟、更正作業步驟的 `except` |
| E-2 `market_run_regressed` | `run_settlement_evaluation()` 以型別化例外 `MarketRunRegressedError`（或等價的型別化非成功結果）回報 | 編排函式接住結算步驟 |

對 dev-lead 的實作要求（需要 tech-architect 確認，見 §4）：

- 兩個例外要帶結構化屬性（欄位見 §2.3），不得靠解析例外字串取欄位。
- R 倒退目前 ADR 只寫「記 WARNING，本次不寫入」，沒有說是例外或回傳值；請 tech-architect 在 ADR 定為型別化例外或型別化結果，並規定「前一筆 `market_run_max`」是在哪個讀取內取得（避免與 ①「讀一次 R」的單次讀取規則衝突）。
- 其他未分類的結算例外（非 E-1、E-2）：D-7.2 已規定記 WARNING，本案**不**為它新增推播，但建議併入 §2.7 的附帶事件 E-3，由 CEO 決定。

### 2.3 事件名稱與欄位

事件名稱前綴 `forecast.`，全小寫、點分隔，與 log 的 `event=` 欄位及推播標題一致。所有時間為 UTC ISO8601（公司資料慣例）。

**共同欄位（E-1、E-2 都有）**

| 欄位 | 內容 |
|---|---|
| `event` | 事件名稱 |
| `severity` | 固定 `WARNING` |
| `occurred_at` | 編排層接住當下的時鐘（UTC） |
| `execution` | 本次執行識別：交易日 T（Asia/Taipei 日期）加進入點 `cron_2210`／`retry_2310`／`startup`；進入點由 D-7.1 的觸發來源決定 |
| `source` | `settlement`（結算評估）或 `correction`（更正作業） |
| `write_outcome` | 固定 `not_written`（交易已 rollback，沒有留下任何 outcome 或 job_end 列） |

**E-1 `forecast.settle.unregistered_unobserved_weekday`（B-3）**，逐一對應 B-3 說明句要求的欄位：

| B-3 要求 | 欄位 | 說明 |
|---|---|---|
| 符合判準卻未登記的 `session_date` 清單 | `unregistered_session_dates` | 升冪、不重複的 ISO 日期；log 完整列出；推播超過上限時截斷（§2.5） |
| （清單長度） | `unregistered_count` | 完整清單的筆數；推播被截斷時用來呈現總數 |
| 受影響的預測筆數 | `affected_forecast_count` | 整數；只放筆數，不放 `forecast_id`、代號 |
| D_reg | `d_reg` | `ledger_registration_start()` 的值；None 時寫 `none` |
| 快照範圍（結算評估） | `snapshot_from`、`snapshot_to` | 取自該次評估的判定視圖範圍（`forecast_settle_eval.view_range_json` 同義） |
| 重查範圍與 `market_scan_to`（更正作業） | `recheck_from`、`recheck_to`、`market_scan_to` | `source=correction` 時填；`source=settlement` 時 `snapshot_*` 填、`recheck_*` 與 `market_scan_to` 不出現 |

**E-2 `forecast.settle.market_run_regressed`（R 倒退）**

ADR 沒有指定欄位，以下是為了判斷「是不是整檔還原」與銜接 ADR-0026 D-9.4 所需的最小集合：

| 欄位 | 內容 |
|---|---|
| `market_run_current` | 本次讀到的 R（市場 DB 的 `MAX(run_id)`） |
| `market_run_prev_max` | 前一筆 `forecast_settle_eval.market_run_max` |
| `prev_settle_eval_id`、`prev_settle_eval_started_at` | 該前一筆評估的主鍵與開始時間，讓操作者對照備份 manifest 的「最新市場 DB `run_id`」（ADR-0026 D-9.2 第 2 點） |
| `source` | 恆為 `settlement`（更正作業端的對應保護是 D-3「晚到資料的觸發」第 8 點，見 §2.7 的 E-3） |

不放進任何事件的東西：例外原文字串（可能帶路徑或 SQL）、`forecast_id` 清單、代號、持倉與金額、webhook URL、token、DB 檔路徑。

### 2.4 log 形式（永遠寫，不去重）

- 專用 logger 名稱 `ops_alert`，WARNING，單行 `key=value`，與 `scheduler.py` 現行風格一致。
- 範例（假值；日期為說明用）：

```
ops alert: event=forecast.settle.unregistered_unobserved_weekday severity=WARNING source=settlement execution=2026-11-02/cron_2210 occurred_at=2026-11-02T14:10:03Z write_outcome=not_written unregistered_count=2 unregistered_session_dates=2026-10-12,2026-10-14 affected_forecast_count=17 d_reg=2026-10-05 snapshot_from=2026-10-05 snapshot_to=2026-11-02
ops alert: event=forecast.settle.market_run_regressed severity=WARNING source=settlement execution=2026-11-02/retry_2310 occurred_at=2026-11-02T15:10:02Z write_outcome=not_written market_run_current=812 market_run_prev_max=840 prev_settle_eval_id=31 prev_settle_eval_started_at=2026-11-02T14:10:01Z
```

- 營運上的搜尋字串固定為 `ops alert: event=`；部署手冊 §5 應加一小節（devops-sre 在 D_v 前落地）。
- 另外每次結算步驟結束都寫一行 INFO `forecast settle run: execution=... outcome=ok|failed|skipped_deadline`。這行是 §2.6「恢復」的判讀依據，也讓「完全沒有這行」可以被人工或外部檢查發現（見 §3 R-4）。

### 2.5 去重規則（第一次就告警，不得以次數門檻壓制）

- **去重鍵**＝(`event`, `source`, `execution`)。同一鍵在同一次執行內只推播一次（防止編排層因重入或雙重接住而送兩次）。
- **不跨執行去重**：22:10 失敗、23:10 重試仍失敗、隔日 22:10 仍失敗，每次執行都各推播一次。理由：兩個事件都是 fail-closed，結算整批停擺，持續期間每個交易日都該被看到；而且這裡沒有「N 次後才告警」或「冷卻 N 分鐘」，第一次發生就推播，符合清單 N-23 (1) 的字面。
- **推播量上限的估算**：每個交易日每個 (event, source) 最多 3 則（22:10、23:10、啟動補跑）；兩個事件、兩個 source 同時持續時最多 4 個鍵、每日 ≤ 12 則。可接受；若 CEO 認為太吵，唯一允許的調整是「同一個去重鍵內的重複」，不得改成跨執行靜默。
- **不採用的做法**：使用者告警的冷卻（`engine.py:375-383`）、連續 N 次門檻、以內容雜湊跨日壓制。
- **不維護跨執行狀態**：不新增表、不寫狀態檔（預測帳的表是 append-only 且由 ADR 定義，新增表需 ADR；見 §4）。代價是推播不帶「第幾次」或「首次發生時間」；操作者以 log 的 `execution` 欄位與 `GET /api/forecast/status` 的 `last_settle_eval_at`（ADR-0027 D-8 第 5 點）判讀持續天數。
- **推播內容的截斷（需 tech-architect 與風控確認）**：Discord 單則上限 2000 字元。E-1 的 `unregistered_session_dates` 在推播中最多列 20 筆（上限值由 dev-lead 定為常數），超過時加「另有 N 筆，完整清單見 scheduler log」；log 永遠完整。欄位集合與 ADR 的 WARNING 一致，只有推播的清單長度受限。若認為清單必須在推播中完整，替代方案是分多則送，代價是同一個去重鍵會有多則訊息。

### 2.6 通道、靜默與恢復

**通道**

- 沿用既有 Discord／Telegram 環境變數（`ALERT_DISCORD_WEBHOOK_URL`、`ALERT_TELEGRAM_BOT_TOKEN`、`ALERT_TELEGRAM_CHAT_ID`），不新增環境變數。憑證由 CEO 自行設定（紅線）；我不碰 `.env`。
- 與使用者告警**共用通道、不共用開關**：維運告警不讀 `settings.alerts.enabled`、`notify_webhooks`；標題固定 `[stock-desk 維運告警] <event>`，與使用者告警的 `[stock-desk 警示]` 區分。
- 推播文字只含 §2.3 的欄位，用繁體中文標籤加英文鍵值；不含免責句、不含任何建議性字句。
- 送出一律在 rollback 之後、`try/except Exception` 內：逾時沿用 5 秒；失敗只記一行 ERROR `ops alert delivery failed: channel=<discord|telegram> error_class=<例外類別名>`，**不得記例外字串、URL**（見 §3 R-1）。送不出去不阻擋缺日稽核。
- **未設任何通道的處理**：結算 job 註冊時（scheduler 啟動）檢查是否至少有一個通道設定完整；沒有時記一行 ERROR `ops alert channel not configured; settlement exceptions will only reach the log`，並在 D_v 前的部署清單中列為阻擋項（見 §2.8）。否則「第一次就告警」會在無人察覺下變成只寫 log。

**靜默**

- 沒有任何手動靜默、確認或關閉功能。理由：這兩個事件都是不變式被破壞或資料被還原，唯一的解除方式是處理根因。
- 計畫性整檔還原（ADR-0026 D-9.4）：操作者在還原前先停 scheduler（`docker compose stop scheduler`），還原完成、`mark-restored` 與 X-3a 腳本跑完後再啟動。scheduler 停止期間沒有執行，所以不會有預期內的 E-2。若還原後仍出現 E-2，視為真實事件。
- 同一個根因造成的重複推播（§2.5）不屬於需要靜默的情形。

**恢復**

- 恢復的判準（可由事實檢查，不靠推播）：下一次執行的 `forecast settle run: ... outcome=ok` 出現、同一次執行沒有 `ops alert: event=forecast.settle.*`、且 `last_settle_eval_at` 前進。
- 本版不推播「已恢復」訊息，因為需要跨執行狀態（§2.5）。選項 B：恢復通知，需先決定狀態存放處（新表或狀態檔），涉及 ADR；建議不在 D_v 前做，列為後續。
- E-2 的處理終點是 ADR 本身：D-9.2 寫明「直到 devops-sre 依 ADR-0026 D-9.4 處理並修訂本點」。處理程序（確認備份 manifest 的最新市場 DB `run_id`、決定接受新的基準或重建）由我在 E-2 發生時另行出處理單；本提案不預先決定放寬 fail-closed。

### 2.7 附帶事件（範圍外，請 CEO 決定是否併入）

這些事件使用同一套機制，邊際成本很低；因超出清單 N-23 (1) 的字面，先列出不實作：

- E-3a `forecast.late_scan.restore_suspected`：D-3「晚到資料的觸發」第 8 點（W 大於市場 DB `MAX(run_id)`）。欄位：W、目前 `MAX(run_id)`。ADR 同樣指向 devops-sre 處理，建議併入。
- E-3b `forecast.job.skipped`：D-7.1 要求的 `EVENT_JOB_MAX_INSTANCES`／`EVENT_JOB_MISSED` listener。ADR 第 773 行已明寫「告警規格依 ADR-0026（devops-sre，N-23 (1)）」，嚴格說屬於 N-23 (1) 的範圍；欄位：`job_id`、`scheduled_run_time`、`reason`（`max_instances`／`missed`）。去重鍵含被略過的觸發時刻。
- E-3c `forecast.settle.deadline_not_started`：D-7.2「D-7.7 期限已到、結算評估沒有啟動」。欄位：`execution`、`deadline_at`。
- E-3d 其他未分類的結算例外：欄位只放 `exception_class`，不放字串。

### 2.8 D_v 前的驗收清單（devops-sre 負責落地的部分）

## 5. 測試要求（給 qa-automation）

所有測試不得連網（以 `httpx.MockTransport` 注入，比照 `tests/test_alerts_notify.py`）、不得讀真實環境變數（用 `monkeypatch`）、不得碰 `apps/stock-desk/backend/data/*.db`。

**觸發與欄位**

1. 結算評估拋 `UnregisteredUnobservedWeekdayError`（fixture：結算窗內有符合 A-77 第 10 項判準、卻無登記事件的日期）→ 恰好 1 則 E-1 推播與 1 行 `ops alert:` WARNING；欄位逐一斷言：`unregistered_session_dates`（升冪、不重複）、`unregistered_count`、`affected_forecast_count`、`d_reg`（含 None 的格）、`snapshot_from`、`snapshot_to`、`source=settlement`、`write_outcome=not_written`。

**去重與不壓制**

5. 同一次執行內，同一個 (event, source, execution) 被接住兩次 → 推播 1 則、log 2 行。
6. 22:10 失敗、23:10 重試仍失敗、隔日 22:10 仍失敗 → 各推播 1 則（共 3 則）；斷言沒有任何冷卻或次數門檻（注入不同的 `settings.alerts.cooldown_minutes` 與 `notify_webhooks=False`、`alerts.enabled=False`，推播數不變）。
7. 結算與更正作業在同一次執行都失敗 → 2 則（source 不同）。

**內容安全**

8. 推播文字與 log 行：不含 webhook URL、bot token、`forecast_id`、代號、「非投資建議」等免責句、任何方向或建議用字（以固定禁用詞清單斷言，清單由風控提供）。

10. 推播清單截斷：超過上限時推播含「共 N 筆」與截斷提示，log 行含完整清單。
11. `notify.py` 修補（R-1）：Telegram 回 404／500 時，log、`DeliveryResult.detail` 與 caplog 全文都不含假 token 與完整 URL。

**流程不被影響**
