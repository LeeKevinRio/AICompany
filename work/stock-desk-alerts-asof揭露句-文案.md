# stock-desk 警示 fired 訊息——依據資料日揭露句（文案）

- 需求來源：risk-compliance-officer，R4-a（2026-09-15）
- 涉及檔案（僅供對照，不改程式）：
  - `apps/stock-desk/backend/app/alerts/engine.py`（fired 訊息本文組成，第 110～131、169～207、252～256 行）
  - `apps/stock-desk/backend/app/alerts/notify.py`（`format_message`，只加「觸發時間」這是評估時刻）
  - `apps/stock-desk/backend/app/alerts/snapshot.py`（既有層級句 `資料來自 {status} 層（{source}）。`，第 99～103 行）
- 待辦：**面向使用者的揭露文案，定稿字句仍需 risk-compliance-officer 覆核放行**（本文只是文案提案，非最終核可）。

## 情境

三種 fired 訊息本文都要在句尾、資料揭露句之前，插入一句「依據資料日」揭露：

- 價格型：`2330 最新收盤價 594，高於設定的門檻 580。`
- 訊號型：`2330 的 14 日 RSI 最新值 目前為 82，符合設定的條件 gt 70。`
- 風險上限型：`2330 觸發風險上限：第 1 條（單一持股曝險）。……`（可能已先接了 `fx_disclosure`）

字數限制：一句、含 `{as_of}`（ISO 日期字串，如 `2026-09-12`）、放句尾、資料揭露句之前，不換行（沿用既有「句子以空白相接」的拼法）。

## 定稿句

> **上述數值之資料日為 {as_of}。**

理由：
- 主詞「上述數值」通用於三種訊息類型（收盤價／訊號值／風險上限明細），不綁死「最新收盤價」這種只適用價格型的措辭。
- 句型「X 之資料日為 Y」與既有層級句「資料來自 {status} 層（{source}）。」同屬「名詞片語 + 為/來自 + 值」的陳述句家族，語域一致、不突兀。
- 純事實陳述，無動作動詞、無「即時」「保證」「建議」等字眼，也不暗示即時性——反而是用「資料日」這個詞直接把「最新」跟「當下」拆開，正中風控要處理的問題。

## 備選 A

> 本則數值之資料日為 {as_of}，非本次評估時間。

理由：直接點出「不是評估時刻」，跟推播另外附加的「觸發時間：{ISO}」形成對照，消歧義力道更強；缺點是多一個分句，略長，且與「觸發時間」重複提及「時間／評估」概念，資訊有點外溢到 notify.py 那句的職責範圍。適合風控認為「上述數值之資料日為 {as_of}。」還不夠明講差異時的加強版。

## 備選 B

> 上述數值以 {as_of} 之資料為準。

理由：「為準」是台灣金融揭露文常見措辭（如「以官方公告為準」），語感上更貼近正式免責聲明的口吻，跟 FX 揭露句「不是官方收盤匯率」那種偏正式的語域更接近。缺點是「為準」隱含一點「效力依據」的意味，比定稿句多了一絲權威感，若風控希望維持最中性的事實陳述，定稿句仍較安全。

## 既有層級句並列檢查

層級句原文：`資料來自 {status} 層（{source}）。`

與定稿句並列（例如 cached_stale）：

> ……高於設定的門檻 580。 上述數值之資料日為 2026-09-12。 資料來自 cached_stale 層（yfinance）。

讀起來通順：兩句都以「資料」相關的名詞片語開頭、都是「為／來自」的陳述句，資訊也不重疊（一句講「哪一天的資料」，一句講「資料經過哪一層、哪個來源」），前後互補。**不建議微調層級句**，維持原字句即可，可省去層級句改字要重送風控的流程成本。

若日後真要動層級句，才需要另外標示、重送風控——本次提案不觸碰它。

## 完整示例：價格型 fired 訊息（cached_stale 情境）

組裝後（engine.py 產生的 `message`，供 notify.py 使用）：

```
2330 最新收盤價 594，高於設定的門檻 580。 上述數值之資料日為 2026-09-12。 資料來自 cached_stale 層（yfinance）。
```

推播到 Discord／Telegram 的完整文字（`notify.format_message` 組裝後）：

```
[stock-desk 警示] 2330（TW）
2330 最新收盤價 594，高於設定的門檻 580。 上述數值之資料日為 2026-09-12。 資料來自 cached_stale 層（yfinance）。
觸發時間：2026-09-15T09:31:00+00:00
本工具為研究與教育用途，非投資建議。
```

（`觸發時間` 是評估當下、`資料日` 是收盤價所屬的交易日；兩者並列讓使用者一眼看出「最新收盤價」不是「即時」。）

# 指令頁 warnings——`INDEX_DATA_REASON_NOTE` 補受詞（文案）

- 需求來源：risk-compliance-officer 三審，核可但 suggested 補受詞（2026-09-15）
- 涉及檔案（僅供對照，不改程式）：`apps/stock-desk/backend/app/playbook/wording.py` 第 234～238 行
- 原句（維持不動，逐字引用 `{reason}` 不改寫）：

  ```python
  INDEX_DATA_REASON_NOTE = "加權指數資料：{reason}"
  ```

  `{reason}` 是資料層自己的句子（如「最近一次向來源取得資料未成功，暫以本機快取回覆。」），逐字引用、不改寫、不重述。

## 情境

風控核可 `INDEX_DATA_REASON_NOTE` 本身沒問題，但建議補上「這批加權指數序列餵的是哪個判定」的受詞——讀者目前只看得到「加權指數資料出了什麼狀況」，看不出這句話跟指令頁上的哪個判定有關（會影響 M1、也會影響快市判定，兩者都在同一批加權指數序列上）。

限制：一句、含 `{reason}` 佔位（逐字引用不改寫）、事實陳述、無禁用詞、無動作動詞、與既有句「加權指數資料狀態為 {status}（來源 {source}），M1 今日未評估、沿用前一狀態；當日不新開倉。」語域一致。

本次只需擬「補在 `{reason}` 之後的受詞子句」，不動 `{reason}` 本身與其前的 `加權指數資料：` 標籤。

## 定稿句（附加子句）

> **（用於 M1 與快市判定）**

完整組合示範：

```python
INDEX_DATA_REASON_NOTE = "加權指數資料：{reason}（用於 M1 與快市判定）"
```

理由：
- 括號注記是這個檔案既有的慣用寫法（例如 `REFERENCE_PRICE_NOTE = "（依據交易日收盤價，不反映今日盤中變動）"`、`REFERENCE_PRICE_UNAVAILABLE_NOTE = "（無可用參考價）"`），本身就是「附加在別的句子後面、不重複主詞」的補充句型，跟這裡要做的事（在 `{reason}` 後面補一句受詞說明）完全對得上，改動幅度最小。
- 「用於」是功能性、描述性的動詞（陳述系統事實：這批資料被拿去做什麼），不是指令或建議動詞；同一檔案裡風控已核可的 `REFERENCE_PRICE_NOTE` 也用了性質相同的描述性動詞「反映」，語域一致。
- 直接點名「M1」「快市判定」兩個判定名稱，跟既有 `INDEX_DATA_GAP_NOTE`（「M1 今日未評估、沿用前一狀態；當日不新開倉」）、`FAST_MARKET_CARRIED_NOTE`（「快市判定沿用前一次評估結果」）用的是同一套判定名稱，讀者可以直接跟指令頁上其他警示句對起來，不會覺得是新名詞。
- 不重複「加權指數資料」這個主詞（`{reason}` 前面的標籤已經講過一次），維持全句精簡，不把 `INDEX_DATA_REASON_NOTE` 拉長成一段落。

## 備選

> （M1 與快市判定之共同輸入）

完整組合示範：

```python
INDEX_DATA_REASON_NOTE = "加權指數資料：{reason}（M1 與快市判定之共同輸入）"
```

理由：完全不含動詞的名詞片語，是「無動作動詞」限制的最保守版本，若風控希望連「用於」這種描述性動詞都不要出現，選這句最安全。缺點是「輸入」偏工程術語，對一般使用者（非開發者）稍抽象，語感沒有定稿句直覺；且「共同輸入」需要讀者自己組裝「這批資料同時進了兩個判定」的意思，比定稿句多一層理解成本。
