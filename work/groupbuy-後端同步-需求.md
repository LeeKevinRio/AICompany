# groupbuy 後端即時同步 — 需求書（PRD）

- 立案人：CEO（2026-08-05 裁示）
- 撰寫：product-manager
- 狀態：draft（待 tech-architect 技術評估）
- 依據之現況研究：`apps/groupbuy/` 原始碼（groupbuy 分支 worktree），逐檔閱讀清單見文末附註

---

## 背景與目標

### CEO 原始痛點（2026-08-05 原話意譯）
「為何我需要填寫回單碼？應該對方直接加入後我這邊就該知道了。」
買家填單後，賣家（主揪）的後台應自動出現該筆訂單，不需要買家複製回單碼傳給賣家手動匯入。

### 現況（實地研究結果）

groupbuy 目前是**純前端、無伺服器**的工具，所有資料只活在單一瀏覽器的 `localStorage`（key
`groupbuy:groups:v1`，見 `src/data/localStorageRepository.ts`）。因為沒有後端，賣家裝置與買家裝置
之間靠三種「離線同步替代方案」搬資料，本案要解決的正是這三個機制帶來的副作用：

1. **分享連結把整個團定義塞進 URL**（`src/share/groupCodec.ts`）：格式為
   `#/join?d=<base64url(JSON)>`，payload 包含團名、備註、截止時間、逐項商品 `[id, name, price]`。
   刻意**不**帶商品圖片，原因是 base64 圖片會讓 URL / QR code 爆長——這是「無後端」架構的直接限制，
   也是本案要移除的技術債之一。
2. **回單碼**（`src/share/receiptCodec.ts`）：買家在 `JoinPage` 填完單後，前端把訂單（買家名、
   品項、備註）編碼成 `GBR1.<base64url>.<crc>` 短碼，買家手動複製、貼到 LINE 傳給賣家，賣家在
   `DashboardPage` 的「貼上回單碼收單」欄位貼上、解碼、驗證團別後才寫入賣家自己裝置的
   `localStorage`。這就是 CEO 痛點的直接來源——**中間多了一手人工複製貼上**。
3. **現場代填**（`OrderPage`，路由 `/groups/:id/order`）：賣家把手機遞給買家，在同一裝置上直接
   寫入 `localStorage`，沒有回單碼問題，但僅限同裝置面對面場景。

其他現況限制（逐一表態是否納入本案範圍，詳見「範圍內／範圍外」）：

- **賣家多裝置無法同步**：資料只在開團當下那台瀏覽器的 `localStorage`，換手機、換瀏覽器、清快取都會
  遺失，也看不到另一台裝置上的訂單。
- **資料只在單一瀏覽器、清 localStorage 即滅失**：無備份、無雲端副本。
- **URL 長度限制**：目前已靠「不帶圖片」規避，但團購品項一多，連結／QR 仍可能逼近瀏覽器或掃碼器的
  實務上限。
- **買家裝置時鐘決定填單頁的截止判定**（`deadline.ts` 註解已明確承認此為「無後端架構的已知限制，
  非 bug」），資料層 `submitOrder` 雖有二道防線但仍以送單當下的前端狀態為準，沒有伺服器時鐘可校對。

### 目標

把 groupbuy 從「純前端工具」升級為「有伺服器的服務」，使買家送單後**不經任何人工複製貼上動作**，
賣家後台就能看到該筆訂單。這是架構級變更，本 PRD 定義的是「要解決什麼問題、驗收標準是什麼」，
技術怎麼做（框架、資料庫、即時機制）留給 tech-architect 出 ADR。

## 使用者與情境

| 角色 | 情境 |
| --- | --- |
| **賣家（主揪）** | 開團 → 分享連結/QR → 買家陸續填單，後台**即時**看到訂單進來 → 收款後在後台打勾 → 截止後結單 |
| **買家** | 點賣家分享的連結（或掃 QR）→ 看到團購內容 → 填名字與數量送出 → 完成，**不需要**手動回報任何東西給賣家 |

### 關鍵產品決策（本 PRD 表態，非開放問題）

- **買家免帳號**：買家憑連結即可填單，不要求註冊/登入。這是既有體驗的核心優點（「對方不需要安裝任何
  app」，見 `SharePage.tsx` 現有文案），本案不應該倒退成買家也要建帳號才能下單。
- 同名覆蓋語意（`applySubmitOrder`：同一團內同名買家再次送出＝覆蓋原單，`paid` 重置為未收款）
  **沿用不變**，這是現行已驗證過的 MVP 定案，後端版本必須維持一致行為。

### 開放問題（列入下方「開放問題」章節，此處先點出）
- 賣家身分怎麼識別（匿名 token／輕量帳號）——直接影響「多裝置賣家同步」與「後台存取控制」怎麼做，
  待 tech-architect 與 CEO 共同決定。

## 範圍內 / 範圍外

### 「即時」的定義（使用者體感驗收標準，非技術選型）

不代 tech-architect 選 polling / WebSocket / SSE，但驗收標準訂為：

> 買家送出訂單後，賣家後台在**未手動重新整理**的情況下，應於 **10 秒內**自動顯示該筆新訂單
> （收款狀態變更、刪單同理）。

此數字為 product-manager 提議的預設門檻，若 tech-architect 評估後認為技術上／成本上 10 秒不可行
（例如免費方案的 hosting 對長連線有限制），可提出替代數字並說明取捨，回來與 PM／CEO 對齊——但
不可默默放寬到「使用者要手動重整才看得到」，那等於沒解決 CEO 的痛點。

### 範圍內

1. 買家送單 → 賣家後台自動出現該筆訂單（免回單碼、免手動匯入）——**這是本案核心，對應 CEO 原話**。
2. 分享連結改為輕量化（不再把整包團定義塞進 URL），改由賣家端建立的團經後端保存，買家連結只需帶
   可定位到該團的識別碼，JoinPage 向後端取得團定義。
3. 後端強制執行「已截止不接受新單」（不只靠前端 / 買家裝置時鐘）。
4. 既有 localStorage 資料的**遷移路徑要有定案**（可以是「不遷移、新起點」，但必須是明確決策而非
   沒想過）——見開放問題。
5. 賣家後台的基本存取控制（誰能開啟某團的後台、誰能改資料）——新增面向，見「安全與隱私」。

### 範圍外（本輪不做，需求明確排除）

1. **賣家多裝置同步**：本案聚焦「買家送單即時進賣家後台」這個最小痛點，多裝置同步（賣家在手機開的
   團，換平板登入也要看到最新資料）列為下一期（見「分期建議」），本輪不強制做到。
2. **離線降級的完整體驗**（例如後端斷線時買家端仍可暫存、恢復連線後自動補送）：本輪只要求「後端
   不可用時要有清楚的錯誤提示，不能讓使用者以為送出了但其實沒有」，不要求做到完整離線佇列同步。
   是否保留回單碼機制作為手動 fallback，列開放問題請 CEO 裁示。
3. **賣家帳號系統（含登入/註冊 UI、密碼找回等完整帳號體驗）**：本輪先以最小可行的存取控制（例如
   賣家專屬 token）擋掉「任何人猜到網址就能改資料」的風險，不做完整帳號系統。
4. **圖片改存物件儲存（S3 類）的最終架構**：本輪先讓圖片能存到後端（資料庫或簡單物件儲存皆可，
   由 tech-architect 決定），但儲存方案的長期優化（CDN、壓縮策略再升級）列下一期。
5. **回單碼 / 現場代填功能移除**：本輪不移除，保留作為向下相容與最小 fallback（節省重寫成本，
   也降低本輪風險），是否日後除役是開放問題。

## 功能需求（逐條編號）

- **FR-1**　買家在 JoinPage 送出訂單後，資料直接寫入後端（不再產生回單碼作為唯一送單管道）。
- **FR-2**　賣家後台（DashboardPage）在未手動重新整理的情況下，新訂單／收款狀態變更／刪單能在
  驗收標準時間內（見上方「即時的定義」）自動反映。
- **FR-3**　分享連結（`SharePage`／QR）改為輕量化：連結只需帶足以定位團的識別碼，JoinPage 改為
  向後端請求團定義（名稱、備註、商品、截止時間），不再把整包資料塞進 URL。
- **FR-4**　後端在收到買家送單請求時，強制檢查該團是否已截止（手動截止或已過 `deadlineAt`），
  截止後拒絕寫入，不只依賴買家裝置前端狀態。
- **FR-5**　同名覆蓋語意在後端保持一致：同一團內以買家名字為識別，重複送出覆蓋原訂單內容，且
  `paid` 狀態重置為未收款（沿用現行 `applySubmitOrder` 的財務正確性設計）。
- **FR-6**　賣家後台的資料存取有基本控制：非授權對象不能任意開啟他人團的後台頁面讀取訂單明細、
  切換收款狀態或刪單（現行純前端版本因資料只存在賣家自己裝置沒有這個風險，上後端後必須補上）。
- **FR-7**　買家端（JoinPage）呼叫的 API 只能寫入自己的訂單、取得自己團的商品/團資訊，不得回傳
  該團其他買家的訂單明細（維持現行前端隔離原則——買家看不到其他人下了什麼——的後端對應版本）。
- **FR-8**　商品圖片（現行為前端壓縮後的 base64 JPEG，長邊 512px、品質 0.8、單張上限 200KB）改為
  存到後端而非塞進 localStorage；賣家端上傳/顯示圖片，買家端維持現行「不顯示商品圖片」的取捨
  （除非本案決定順便解除此限制，若要解除需另外評估連結長度是否仍受影響——見開放問題）。
- **FR-9**　後端不可用（斷線、逾時、5xx）時，買家送單頁與賣家後台都要有明確錯誤提示，不能讓使用者
  誤以為操作已成功；不要求自動離線佇列與重試（範圍外）。
- **FR-10**　既有 localStorage 資料按照本 PRD「開放問題」章節定案的遷移策略處理（可能是提供匯出
  匯入工具，也可能是明確不遷移並公告），不得在使用者不知情下悄悄消失且無任何說明。
- **FR-11**　回單碼與現場代填兩個現有機制在本輪保留，作為後端不可用時的手動 fallback；回單碼匯入
  UI（DashboardPage「貼上回單碼收單」）繼續存在，行為不變。
- **FR-12**　賣家後台切換收款狀態（`togglePaid`）在後端要處理併發寫入：兩個請求（例如同一賣家
  兩個分頁，或未來多裝置）同時對同一筆訂單操作時，不能讓資料出現不一致或遺失更新（可採
  last-write-wins，但結果必須是明確定義的行為，不能是未定義競態）。
- **FR-13**　同一團同時有兩名買家用相同名字幾乎同時送單時，後端行為必須明確定義（依 FR-5 同名
  覆蓋語意，最後寫入者為準），不得造成資料損毀或兩筆訂單同時存在卻互相覆蓋不完整的情況。

## 驗收條件（每條需求至少一組 Given/When/Then，含失敗路徑）

### FR-1／FR-2：買家送單即時進賣家後台

- Given 賣家已開團並分享連結，後台頁面開啟中且未手動重整
  When 買家透過連結填單並送出
  Then 賣家後台應在 10 秒內自動顯示該筆訂單（買家名、品項、應付合計），不需賣家任何操作

- Given 同一情境
  When 賣家在後台把某筆訂單標記已收款
  Then 若另一個裝置/分頁也開著同一團後台，該狀態變更應在 10 秒內同步顯示（此條同時涉及 FR-12，
  多裝置完整同步屬 Phase 2，此處驗收的是「同裝置內、同一次後端連線」的即時性）

### FR-3：分享連結輕量化

- Given 賣家開一團、商品數量足以讓舊版 URL 明顯變長（例如 20 項商品）
  When 賣家產生分享連結
  Then 連結長度應與商品數量脫鉤（不再隨商品數線性增長），QR code 掃描成功率不因商品數增加而下降

- Given 買家取得分享連結
  When 買家開啟連結（後端可正常回應）
  Then 頁面應正確顯示團名、商品、截止時間，行為與現行「整包塞 URL」版本一致（買家不感知底層變化）

- Given 後端暫時不可用
  When 買家開啟分享連結
  Then 頁面顯示明確錯誤訊息（例如「暫時無法載入團購內容，請稍後再試」），不得顯示空白或誤導性的
  「填單連結無效」（現行版本的「連結無效」文案是給壞 payload 用的，語意上要與「後端掛了」區分）

### FR-4：後端強制擋截止後送單

- Given 團已手動截止（`closed: true`）或已過 `deadlineAt`
  When 買家嘗試送單
  Then 後端拒絕寫入並回傳明確錯誤，前端顯示「此團已截止，無法再送單」

- Given 團在買家開啟填單頁當下尚未截止，但填寫過程中（例如買家拖了很久）已經過了截止時間
  When 買家按下送出
  Then 後端仍應以「送出當下」的伺服器時間為準判定，拒絕已截止的送單（不信任買家裝置時鐘，修正現行
  純前端版本已知的裝置時鐘偏差限制）

### FR-5／FR-13：同名覆蓋與併發送單

- Given 團內已有買家「小明」的訂單
  When 買家再次以「小明」送出不同品項的新單
  Then 後端覆蓋原訂單內容，且該筆訂單的已收款狀態重置為未收款

- Given 兩個裝置幾乎同時以相同買家名字「小華」送出不同內容的訂單
  When 兩個請求幾乎同時抵達後端
  Then 最終該團內「小華」只會有一筆訂單，內容為其中一個請求的完整內容（不得出現欄位互相污染、
  合併出不存在的組合，也不得產生兩筆同名訂單）

### FR-6／FR-7：存取控制與資料邊界

- Given 某團的後台網址被非授權對象取得（例如連結外流、或被猜測 id）
  When 該對象嘗試開啟後台頁面
  Then 系統應拒絕顯示訂單明細/收款操作/刪單功能（具體機制——token、輕量帳號——由
  security-engineer 設計，此處驗收的是「結果」：非授權者看不到、改不了）

- Given 買家透過填單連結呼叫送單 API
  When 該 API 被呼叫
  Then 回應內容不得包含該團其他買家的姓名、品項、金額等訂單明細

### FR-8：商品圖片後端化

- Given 賣家在開團頁面上傳商品圖片
  When 賣家送出開團
  Then 圖片成功存到後端，商品圖片能在賣家後台正常顯示（含 `productTotals` 表格內的縮圖）

- Given 賣家上傳一張超過現行壓縮後仍過大的圖片，或上傳失敗（網路中斷）
  When 送出開團
  Then 系統明確提示圖片上傳失敗，不得讓整個開團動作因圖片問題而莫名失敗或吞掉錯誤

### FR-9：後端不可用的降級提示

- Given 後端服務不可用（模擬斷線或逾時）
  When 買家在 JoinPage 按下送出訂單
  Then 頁面顯示明確錯誤（例如「送出失敗，請檢查網路後重試」），且不得顯示現行版本的「訂單已送出」
  收據畫面（該畫面現行版本是本地產生回單碼、必然成功；後端化後「顯示成功」必須代表「後端真的收到」）

- Given 後端服務不可用
  When 賣家開啟後台頁面
  Then 頁面顯示明確錯誤或降級提示，不得顯示過期/錯誤的資料而不告知使用者資料可能不是最新

### FR-10：既有資料遷移

- Given 既有使用者的瀏覽器已有 localStorage 團購資料（本輪上線前建立）
  When 該使用者更新到後端版本並開啟 app
  Then 依 CEO 裁定的遷移策略執行（見開放問題）——驗收條件待策略定案後補上，本輪 PRD 先要求
  「不得在使用者不知情下讓資料無聲消失」為底線

### FR-11：回單碼／現場代填保留

- Given 後端可用、買家也走新的即時送單流程
  When 賣家仍選擇用「貼上回單碼收單」功能
  Then 該功能行為與現行版本一致（可作為備援管道，例如買家端因故無法連上後端時，仍可用舊方式產生
  回單碼傳給賣家手動匯入）

### FR-12：併發收款打勾

- Given 賣家在兩個分頁/裝置同時開著同一團後台
  When 兩邊幾乎同時對同一筆訂單按下「標記已收」與「取消已收」
  Then 最終狀態為明確的一個值（例如以後端接收到的最後一次操作為準），且兩邊介面最終應同步顯示
  相同狀態，不得停留在互相矛盾的畫面且無法自行修正（重整或下一次同步後應收斂）

## 安全與隱私

純前端時代不存在這個面向（資料只活在使用者自己瀏覽器）；上後端後這是**新增的風控重點**，
指名 **security-engineer** 參與設計審查，至少涵蓋：

1. **賣家後台存取控制**：現行 `/groups/:id` 後台網址本身不含任何驗證，純前端時代沒差（資料只在
   自己裝置）；後端化後，任何拿到或猜到這個 URL 的人理論上都能看到訂單明細、切改收款狀態、刪單。
   需設計最低限度的存取機制（例如賣家專屬 token 綁在網址或裝置、而非帳號密碼），並与「買家免帳號、
   賣家輕量」的產品原則對齊——不要求做到完整帳號系統。
2. **買家個資存到伺服器**：買家姓名、品項、備註等現在會落地存到後端資料庫（現行只存在買家自己的
   收據畫面截圖裡）。需要基本的個資保留期限與刪除機制（即使是小型工具，也不該無限期保留、無法
   刪除）。
3. **分享連結被陌生人開啟亂填**：現行機制下任何拿到連結的人都能填單，這是產品刻意設計（免帳號、
   低摩擦），本案不變更此行為，但需與 security-engineer 確認「填單門檻低」不會被濫用成灌爆某團
   訂單（例如要不要有基本的防灌單機制，如同一裝置短時間重複送單的節流）——列為開放問題非強制需求。
4. **買家端 API 邊界**（對應 FR-7）：買家的請求權限只能寫入自己的訂單、讀取自己團的公開資訊，
   不能查詢其他買家資料或其他團的資料。
5. **圖片上傳的基本檢查**：檔案型別/大小限制沿用現行前端壓縮邏輯的精神（避免任意檔案上傳），
   後端也要再驗一次（不能只信任前端壓縮結果）。

## 開放問題（待 CEO 或其他部門回答）

1. **賣家身分識別機制**：用匿名 token（裝置綁定）還是輕量帳號（例如手機號或 LINE 登入）？
   直接牽動「多裝置賣家同步」與「後台存取控制」的做法。 → **問 tech-architect + CEO 共同決定**
   （牽涉架構複雜度與使用者摩擦的取捨，PM 不代為決定）。
2. **「即時」10 秒的驗收門檻是否可行／要調整**：本 PRD 提議送單後 10 秒內賣家後台自動顯示，是否有
   技術或成本上的困難需要調整這個數字？ → **問 tech-architect**。
3. **後端不可用時是否保留回單碼機制作為降級備援**（本 PRD 已預設 FR-11 保留），或者 CEO 認為應該
   直接讓買家看到「暫時無法送單」而不提供備援管道？ → **問 CEO**（產品取捨，PM 不代為決定）。
4. **既有 localStorage 舊資料的遷移策略**：要不要做匯出/匯入工具？還是明確公告「本次升級後舊資料
   不遷移，請截圖保存」？ → **問 CEO 決定優先序**，若要做遷移工具，**再問 tech-architect** 技術
   可行性與工作量。
5. **Hosting 環境與預算上限**。 → **問 CEO**。
6. **商品圖片儲存方式**（資料庫 blob vs 簡單物件儲存）與對應費用估算。 → **問 tech-architect +
   devops-sre**。
7. **賣家後台存取控制的最低方案**（token 放網址參數 vs 需要一個簡單的登入/配對步驟），需要在
   「防止陌生人亂改資料」與「賣家操作要夠輕量、不能變成要記帳密」之間取捨。 → **問
   security-engineer** 設計最小方案，PM 核對是否符合「賣家輕量」原則。
8. **多裝置賣家同步的優先序**：本 PRD 已建議放到 Phase 2（見下），CEO 是否同意，還是希望第一期
   就要做到？ → **問 CEO 裁決**。
9. **回單碼 / 現場代填長期去留**：本輪保留（FR-11），但這兩個機制有維護成本，是否計畫在後端穩定
   後正式除役？ → **問 CEO**（非本輪決策，先記錄成待辦問題）。
10. **是否要解除「買家端不顯示商品圖片」的限制**：原限制是 URL 長度問題，FR-3 把連結輕量化後，
    這個限制的技術前提可能已經消失，是否要順便讓買家也能看到商品圖？ → **問 CEO**（產品範圍決定，
    若要做需一併評估圖片載入對買家頁面效能/流量的影響，可能歸屬 Phase 2）。
11. **防灌單/濫用填單連結的節流機制**是否需要納入本輪？ → **問 security-engineer 與 CEO**。

## 分期建議

若無法一次做完，建議切法如下（對應 CEO 原始痛點的最小可行切片優先）：

### Phase 1（本輪主軸，直接對應 CEO 痛點）
- FR-1：買家送單直接進後端，賣家後台自動出現（免回單碼）
- FR-3：分享連結輕量化（改帶識別碼，JoinPage 向後端拉團定義）
- FR-2：即時性（同裝置/同一次連線內，10 秒驗收門檻）
- FR-4：後端強制擋截止後送單
- FR-5／FR-13：同名覆蓋與基本併發正確性
- FR-6／FR-7：最低限度的後台存取控制與買家 API 資料邊界（security-engineer 先給最小方案，不做
  完整帳號系統）
- FR-9：後端不可用時的明確錯誤提示
- FR-11：回單碼／現場代填保留不動（降低本輪風險與重寫成本）
- **不含**：賣家多裝置同步（單一賣家仍綁在原本開團那台裝置/瀏覽器即可）、圖片後端化可視情況併入
  或延到 Phase 2（取決 tech-architect 評估工作量）

### Phase 2
- FR-4（多裝置版）：賣家多裝置同步（需先有身分識別機制定案，見開放問題 1）
- FR-8：商品圖片正式後端化（若 Phase 1 未做）
- FR-10：既有 localStorage 資料遷移工具（若 CEO 裁示要做）
- 即時機制若 Phase 1 用 polling 撐過驗收門檻，Phase 2 視流量/成本評估是否要換 WebSocket/SSE

### Phase 3（可選、視 Phase 1/2 使用狀況）
- 回單碼／現場代填正式除役評估
- 個資保留期限與刪除機制正式化
- 若賣家規模擴大，評估是否需要更完整的帳號系統
