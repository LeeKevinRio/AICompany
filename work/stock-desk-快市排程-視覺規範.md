## 2. 四模式色彙方案

### 2.1 設計原則

- **不新增色階**：全部沿用站內既有 Tailwind neutral / 既有語意色（rose / emerald / sky / amber），
  不引入新色相做「模式」本身的判斷色，除了「快市」——快市是本規則集獨有、且必須與既有三態
  （M1 正常/防守、S3 凍結）在視覺上明確可疊加共存，站內目前沒有任何色相在用，用 `indigo` 系。
- **不用純紅綠雙色燈號**：企劃 8.2 已提醒色盲風險，四態一律「色彙 + icon + 文字標籤」三重編碼，
  不得只靠色塊。
- **不做動畫特效**：企劃第 3 節 Braintrust 已否決「凍結/防守做成戲劇性視覺事件」，四態一律靜態色塊，
  不用脈動（pulse）、不用轉場動畫。
- **防守 ≠ 恐慌**：防守模式是規則正常運作的一部分（規則命中就該顯示），不是「出事了」，因此色彙比照站內
  既有「警示但非違反」語意（`amber`，站內既有備援資料源徽章同色相），不用 `rose`。
- **凍結 = 更嚴重但仍非「行動失敗」**：S3/R4 全凍結是規則鏈中最嚴重的狀態，用 `rose`，但**降低飽和度/提高
  暗度**（`rose-950` 底、`rose-200` 字，而非建議卡action badge用的 `rose-300`），刻意比"違反"語意更沉穩，
  避免使用者誤讀成「系統出錯」或「帳戶爆倉」的緊急告警。
- **快市 = 獨立疊加旗標，不是第五種模式**：依 CEO 裁決 6，快市是波動率條件（20 日年化波動率 >30%，或近 5
  交易日任兩日 \|漲跌幅\|≥2%），可與正常/防守/凍結任一狀態同時成立，因此**不與模式徽章合併顯示**，
  獨立一個徽章並排在模式徽章右側，永遠是「疊加」語意而非「取代」。

### 2.2 四態色值表

| 狀態 | Token 組合 | Hex | 底色對主背景 `#000000` | icon（文字建議，最終圖示由 frontend 選 icon set） | 文字標籤（不可省略） |
|---|---|---|---|---|---|
| 正常 | `bg-neutral-900 border border-neutral-800 text-neutral-100`，狀態圓點 `bg-emerald-500` | 底 `#171717`／邊 `#262626`／字 `#f5f5f5`／圓點 `#10b981` | 底 1.05:1（chrome，非內容色，比照捲軸規範既有取捨）／字對底 15.7:1 | 勾號 / checkmark（小圓點即可，不必大圖示——正常態不需要搶視覺） | 「正常」 |
| 防守（M1） | `bg-amber-950/60 border border-amber-700 text-amber-200` | 底 `#451a03`(60% α)／邊 `#b45309`／字 `#fde68a`近似(amber-200) | 字對純黑近似 12:1 以上（amber-200 亮度高，見下方註） | 盾牌 shield | 「防守模式」+ 常駐一句觸發理由摘要（見 2.3） |
| 凍結（S3/R4） | `bg-rose-950/70 border border-rose-700 text-rose-200` | 底 `#4c0519`(70% α)／邊 `#be123c`／字近似 `#fecdd3`(rose-200) | 字對純黑近似 13:1 以上 | 鎖頭 lock | 「全凍結中（第 N/10 日）」，見 2.3 |
| 快市（獨立疊加） | `bg-indigo-950/70 border border-indigo-700 text-indigo-200` | 底 `#1e1b4b`(70% α)／邊 `#4338ca`／字近似 `#c7d2fe`(indigo-200) | 字對純黑近似 12:1 以上 | 閃電 bolt | 「快市」+ 常駐波動率數據（見 2.3，CEO 裁決 6 明文要求） |

> 對比計算方法說明：上表「字對底」欄位為概估（沿用站內既有 `*-300` 系文字色階的對比量級，站內
> `amber-300`/`rose-300`/`emerald-300` 等淺色文字在深色底上普遍落在 7:1～13:1 區間，見既有
> `RiskGauge.tsx`/`AdviceCardView.tsx` 已上線用法）。四態徽章文字一律用 `*-200`（比既有卡片慣用的
> `*-300` 再亮一階），因為徽章本身承載 R1（規則編號摘要）與 R5（as_of/新鮮度）等**必讀文字**，
> 比照 §5「必讀文字 ≥ neutral-400」的精神取上限而非下限。**required｜frontend 實作後跑一次自動化
> 對比檢查（如 axe 或 contrast-ratio CLI）覆蓋這四個新配色，不得只憑本表估算值上線**，此為本規範
> 明確交辦、非可省略項。

### 2.3 徽章必附文字（呼應風控 R1/R5，模式徽章本身也算「指令輸出」的一部分）

- **防守徽章**：「防守模式・依規則 M1（指數連續 3 日低於月線觸發）・啟動於 YYYY-MM-DD」，
  一律展開顯示，不得摺疊、不得只用 icon 代替文字。
- **凍結徽章**：「全凍結・依規則 S3（組合新倉未實現 <−8%）・啟動於 YYYY-MM-DD・剩餘 N/10 日」。
- **快市徽章**：「快市・20 日年化波動率 XX.X%（或：近 5 日 YYYY-MM-DD／YYYY-MM-DD 兩日單日漲跌
  ±X.X%）」——CEO 裁決 6 明文「快市期間拒絕回覆附當前波動率數據與本條說明」，此處是同一顆徽章，
  數據常駐不需要另外點擊才看到。
- 四態徽章一律緊鄰資料基準日與規則版本號（見第 5 節貫穿全頁必附元素），不得讓「模式」看起來是
  獨立於「規則版本」之外的另一套權威來源。

z-10 bg-black/95 backdrop-blur border-b border-neutral-800`，捲動今日指令帳冊時常駐可見。

## 3. 指令行版式：帳冊列（Ledger Row），非傳統 `<table>`

### 3.1 為什麼不用傳統多欄 `<table>`

硬約束 R1 要求每筆指令附「規則編號＋摘要＋日期，不得收合」，R5 要求每筆指令附各數據
`as_of`/新鮮度，CEO 裁決 7 要求每筆指令標「依據資料日／預定執行日／參考價」三個時間標記。
這是每列至少 7–8 個必顯欄位，且部分欄位是完整句子（規則摘要）而非短字串。傳統多欄表格在
這種資訊密度下，要嘛橫向捲動把後面的必顯欄位捲出視野（等同變相收合），要嘛用 `<details>`/
tooltip 把欄位藏進去再展開（字面上就是收合，直接違反 R1）。因此**指令行採「帳冊列」：
每筆指令是一個獨立、全寬、垂直堆疊欄位的區塊**，用 CSS Grid 對齊，視覺上仍有表格的秩序感，
但技術上是 `<ul><li>` 列表而非 `<table>`，資訊不必為了塞進欄寬而被截斷或收合。

### 3.2 與建議卡的容器差異（R8 的具體落地，見第 5 節完整對照表）

| 面向 | 建議卡（`AdviceCardView.tsx`，不變） | 帳冊列（新，本規範） |
|---|---|---|
| 外框 | `rounded-lg border border-neutral-800 p-5`（單一柔和圓角卡） | `border-l-4 border-y border-neutral-800 rounded-none`（左側粗色條 + 上下細分隔線，**不用圓角**，帳冊/流水帳的視覺語彙） |
| 標題語彙 | 「加碼參考／減碼參考／規則評估傾向…」（軟性、可反駁） | 「指令 #NN・規則 {RULE_ID} 已命中」（硬性、事實陳述句，見 3.3） |
| 色彙軸 | 依 **action 語意**上色（`add`=rose、`reduce/stop_loss`=emerald、`take_profit`=sky、`hold`=amber，見 `format.ts:219`） | 依 **規則家族**上色（R/S/P/M1，見 3.4），與 action 語意軸完全脫鉤，避免「同一色相在兩處代表相反方向」的誤讀風險（例如建議卡的 rose 是「加碼／偏多」，若帳冊列也用 rose 代表「停損／賣出」，同一色相在兩個頁面意義相反，是本規範最需要避開的陷阱） |
| 排版單位 | 單張卡片，內部用 `<Section>` 分區 | 列表中的一列，多筆指令垂直堆疊 |

### 3.3 帳冊列內容規格（逐欄位對應硬約束）

```
┌─┬──────────────────────────────────────────────────────────┐
│ │ 指令 #03・規則 S1 已命中・單批停損                          │  ← 標頭列：規則編號＋一句話摘要（R1，永遠展開）
│▌│ 2026-08-11（依規則版本 v{N}）                                │  ← 日期常駐於標頭同排，不得收合（R1）
│▌├──────────────────────────────────────────────────────────┤
│▌│ 台積電 2330・{ACTION_LABEL}・股數 1,200 股                   │  ← 標的／動作（佔位）／股數
│▌│ {ATTRIBUTION_LINE}                                          │  ← R2 常駐歸屬語，佔位待風控定稿
│▌│ 觸發條件：批次成本 605.0 元 × 0.90 = 544.5 元；               │
│▌│ 收盤 542.0 元 < 544.5 元（規則全文可見，非摘要縮寫）           │  ← 規則全文摘要（R1）
│▌├──────────────────────────────────────────────────────────┤
│▌│ 依據資料日：2026-08-11（T）                                  │  ← CEO 裁決 7 三時間標記
│▌│ 預定執行日：2026-08-12（T+1，開盤後 30 分鐘內）               │
│▌│ 參考價：542.0 元（停損類無滑價帶，T+1 開盤無條件市價執行）      │
│▌│ 資料新鮮度：收盤價 as_of 2026-08-11 13:30・來源 TWSE（fresh）  │  ← R5，逐筆常駐，見 3.5 說明
│▌│ 執行狀態：待執行 / 已執行 / MISSED（超出 ±2% 滑價帶）           │  ← T9
└─┴──────────────────────────────────────────────────────────┘
  ↑ border-l-4，色依規則家族（3.4）
```

- 標頭列（規則編號＋摘要＋日期）**永遠展開，不可用 `<details>`／`<summary>`／tooltip／hover-only**
  呈現，這是 R1 逐字要求。
- 觸發條件句要求「公式與輸入來源逐字可見」，沿用 `work/stock-desk-phase8-風控定調.md` §4 C3 的既有
  裁定精神（該裁定用在停損參考位，本規範延伸套用到指令觸發條件，理由相同：公式可見＝讀者能自行
  驗證這不是主觀判斷）。
- `{ATTRIBUTION_LINE}` 是 R2「常駐歸屬語」的版位，由 creative-lead 起草、風控定稿，視覺上固定在
  標的／動作行正下方、與該行**同一視覺區塊內**（不得移到卡尾或摺疊區），字級與標的/動作行一致或
  僅小一階，不得用最小字級處理（比照 `AdviceCardView.tsx:68` 對免責聲明的既有處理原則）。
- 資料新鮮度**不採站內既有「fresh 時不顯示」的沉默慣例**（`DataStatusBadge.tsx`/
  `DataMetaStatusBadge.tsx` 現行邏輯）。這是本規範刻意偏離既有站內慣例之處，需明說理由：R5 要求
  「各數據 as_of/新鮮度」隨指令附帶，既有沉默慣例的設計前提是「一般瀏覽情境下 fresh 是常態、不需要
  提醒」，但這裡是**會被拿去執行的指令**，風險層級不同，即使新鮮就該把 `as_of` 講清楚，不能靠「沒
  出現徽章＝新鮮」這種需要讀者自行推論的隱性語意。因此帳冊列的 as_of／新鮮度是一行**恆常顯示的純
  文字**（不是既有的「有問題才出現的徽章」模式），只有在非 fresh 時額外疊加既有徽章樣式
  （`bg-amber-900/40 text-amber-300` 備援源 / `bg-neutral-800 text-neutral-400` 延遲或不足）做二次
  強調。
- 執行狀態欄位對應 T9（MISSED）與鐵律④／CEO 裁決 7：`MISSED` 狀態用 `bg-neutral-800 text-neutral-300
  border border-neutral-700` 中性徽章（不用 rose，因為 MISSED 不是「錯誤」，是規則設計內的正常分支，
  用中性色避免讀者誤以為系統出錯）。

### 3.4 規則家族色彙（帳冊列左側色條 `border-l-4`，唯一使用色彩的位置）

| 規則家族 | 涵蓋規則 | Token | Hex | 選色理由 |
|---|---|---|---|---|
| R（進場） | R1–R4 | `border-violet-600` | `#7c3aed` | 站內未使用過的色相，與建議卡全色盤（rose/emerald/sky/amber/neutral）完全不重疊，避免任何語意混讀 |
| S（停損） | S1–S3 | `border-orange-600` | `#ea580c` | 刻意**不用 rose**——建議卡的 `rose` 代表「加碼／偏多」，若帳冊列的停損也用 rose，同一色相在兩頁意義相反，是最危險的誤讀組合，故改用 orange（同屬暖色系「需要注意」的直覺，但與 rose 有足夠色相距離） |
| P（停利） | P1–P3 | `border-teal-600` | `#0d9488` | 刻意**不用 sky**——建議卡的 `sky` 已代表「停利參考」，若帳冊列沿用會讓兩頁同色相看似同一件事，但帳冊列是「已執行的事實」而非「參考」，用 teal 維持冷色系「正面」直覺但色相區隔 |
| M1（大盤總開關類指令，如防守期間套用之出場指令） | M1 觸發下的關聯指令 | `border-amber-600` | `#d97706` | 與 2.2 節防守模式徽章同色相，刻意保留一致——這裡的重複是**同義重複**（都指向 M1／防守語境），不是與建議卡衝突，因此允許 |

色條僅施加於容器左側 4px 邊框與規則編號小型 chip（`border border-{color}-700 text-{color}-300
bg-{color}-950/30 px-1.5 py-0.5 rounded text-xs`，樣式配方沿用站內既有徽章配方
`bg-amber-900/40 text-amber-300` 的明暗比例慣例，只換色相），**不施加於本文文字色**——本文文字一律
維持 `text-neutral-100`（標的/動作行）與 `text-neutral-400`（其餘敘述行），確保不論規則家族色彙
是否通過個別對比檢查，內容本身的可讀性都不受影響（延續 §2.2 對「色彩只用於強調層，不用於承載
必讀文字本體」的做法）。

### 3.5 排序與空狀態

- 帳冊列預設排序：依規則優先序（M1 > S3 > S2 > S1 > P3 > P1 > P2 > R）由上到下，同優先序內
  依標的代號排序。理由：CEO 規則集本身定義了優先序，帳冊列排序直接呈現這個優先序，讓使用者
  一眼看到「今天最重要的指令在最上面」，不需要額外的排序 UI。
- 當日無任何指令觸發時（鐵律⑤資料缺漏，或單純沒有規則命中）：不得留白，顯示一列固定格式的
  「無動作」說明卡（同帳冊列容器樣式，`border-l-4 border-neutral-600` 中性色），文字為
  「今日無規則命中，{ACTION_LABEL：無動作}」+ 資料基準日，理由同 R6：沒有指令不代表沒有資料
  基準，仍要誠實交代這是「評估過、沒觸發」還是「資料缺漏、沒評估」。

## 4. EMERGENCY_EXIT 呈現

### 4.1 定調重申（CEO 裁決 6）

「逃生門不是後悔藥」：EMERGENCY_EXIT 存在且必須可達（R11），但成本刻意設計得高——**成本來自流程
摩擦，不是來自視覺恐嚇或道德說教（R13 禁道德壓迫）**。這兩件事分開處理：可達性是位置問題，
成本是互動流程問題，視覺樣式本身既不能藏起來、也不能被畫成「危險紅色警報按鈕」（那是另一種形式
的施壓，一樣違反 R13 的精神——用視覺製造恐懼感讓人卻步，跟用文字說教讓人卻步，本質上是同一件事）。

### 4.2 視覺樣式（永遠可見，但不張牙舞爪）

- 位置：第 0 層狀態列右側，固定可見（`sticky`），不得藏進選單、設定頁或次要頁籤（R11 逐字要求
  「同畫面可達」）。
- 樣式：`border border-neutral-600 text-neutral-200 bg-neutral-900 hover:bg-neutral-800 px-3 py-1.5
  text-sm rounded-md`——**中性色階**，與站內一般次要按鈕同等視覺重量，不用 rose/red 底色、不加
  驚嘆號 icon、不做任何強調性動畫（脈動/發光）。文字固定為「全部出清」（或風控定稿後的等義詞，
  佔位 `{EMERGENCY_EXIT_LABEL}`），字級與其他次要操作一致，**不放大、不加粗**。
- 理由：把成本做進「按下去之後要走的流程」，而不是做進「這顆按鈕看起來多可怕」。一顆長得普通的
  按鈕配合下方 4.3 的多步驟事實確認，比一顆視覺上很嚇人的按鈕更符合 R13——嚇人的按鈕本身就是一種
  施壓，只是用視覺代替文字。

### 4.3 成本落地：多步驟事實確認（非道德勸說）

```
Step 1（點擊按鈕）→ Step 2（確認畫面，全螢幕或大型 modal）→ Step 3（二次確認）
```

Step 2 確認畫面固定顯示以下**事實陳述句**（非疑問句、非勸阻句，逐項附核取方塊，全部勾選才能進入
Step 3）：

```
┌────────────────────────────────────────────────────────────┐
│ 全部出清 — 確認前請閱讀以下事實                                │
│                                                              │
│ □ 此操作將對目前持有的全部標的、全部批次送出出清指令，          │
│    無法只出清部分標的或部分批次。                              │
│ □ 執行後，系統將凍結所有排程動作 20 個交易日                    │
│    （預計恢復日：2026-09-09，依交易日曆計算）。                 │
│ □ 凍結期間內，S/P 系列規則（停損/停利）仍正常運作，              │
│    僅 R 系列（新倉進場）被凍結。                                │
│ □ 目前市場狀態：{正常／防守／凍結／快市，附當前波動率數據}       │
│                                                              │
│                              [ 取消 ]  [ 我已閱讀，繼續 ]      │
└────────────────────────────────────────────────────────────┘
```

- 每一句都是可驗證的事實陳述（「將會發生什麼」），**不出現**任何評價性語言（「你確定嗎」「三思」
  「這是不理性的決定」之類一律禁止，這是 R13 的具體落地）。
- 核取方塊全勾選才能點「我已閱讀，繼續」——這是摩擦成本的來源（強制逐條確認），不是視覺恐嚇。
- 若目前處於快市狀態，Step 2 必須把當前波動率數據放進確認畫面（呼應 CEO 裁決 6「快市期間拒絕回覆
  附當前波動率數據」的精神，這裡是「執行前」而非「拒絕」情境，但同樣的誠實揭露原則適用）。
- Step 3（二次確認）樣式與一般危險操作的雙重確認一致（例如刪除帳號等常見模式），但文案同樣維持
  事實陳述句，不重複使用道德性字眼。

### 4.4 執行後狀態

- 帳冊列（第 1 層）在凍結期間整段替換為一則常駐橫幅（非帳冊列樣式，避免看起來像「一筆指令」）：

```
┌────────────────────────────────────────────────────────────┐
│ 已於 2026-08-12 執行全部出清。                                │
│ 排程凍結中（第 3/20 個交易日），預計 2026-09-09 恢復。          │
│ 凍結期間 S/P 系列規則仍正常運作，若有觸發將照常顯示於下方。      │
└────────────────────────────────────────────────────────────┘
```

  樣式：`border border-neutral-700 bg-neutral-900 text-neutral-200 p-4 rounded-md`，中性色，
  不用 rose（這不是「錯誤」或「違反」，是使用者主動選擇的結果，用警示色會產生「你做錯了」的
  弦外之音，違反 R13 精神）。

### 4.5 拒絕/覆寫相關 UI 的中性化規則（R13，適用範圍不只 EMERGENCY_EXIT）

以下情境（鐵律④盤中求情拒絕、快市期間拒絕請求、凍結期間嘗試繞過）一律套用同一套文案結構，
不因情境不同而加重或減輕語氣：

```
依規則 {RULE_ID}，{事實陳述：目前處於 XX 狀態，第 N/M 期}，此操作將於 {日期} 生效。
```

- **禁止**任何形式的「你不應該」「衝動」「情緒化」「三思而後行」等評價使用者心理狀態的字眼——
  即使立意良善（CEO 本人在快市規則裡明確提到系統是為了對抗自己的恐慌設計的，這是**規則設計動機**，
  不代表 UI 拒絕文案可以在互動當下對使用者說教，動機與呈現是兩件事）。
- **必須**附規則編號、目前狀態、生效/恢復時間點——與帳冊列同一套「事實優先」語彙，讓拒絕本身也
  是「規則執行結果的呈現」，不是「系統在跟你講道理」。
- 視覺樣式：`border border-neutral-700 bg-neutral-900 text-neutral-300`（中性，非 rose 警示色，
  避免拒絕本身被讀成「你做錯事被罵」）。

## 5. 與 RiskGauge／建議卡的區隔規則（總表）

| 面向 | 建議卡 `AdviceCardView` | RiskGauge | 帳冊列（本規範新頁面） |
|---|---|---|---|
| 語意性質 | 軟性、可反駁的參考 | 帳本層風控上限的通過/違反判定（事實性，但範圍是既有 5 條風控上限，非本規則集） | 硬性、CEO 自訂規則的執行紀錄（事實性） |
| 容器 | `rounded-lg border border-neutral-800 p-5`（柔和卡） | `rounded-lg border border-neutral-800 p-5`（與建議卡同款，因兩者性質接近：都是「系統對既有資料的評估呈現」） | `border-l-4 border-y border-neutral-800 rounded-none`（帳冊，見 3.2） |
| 標題語彙 | 「加碼參考」「規則評估傾向停損」等，動詞可直白但框架必須完整（歸屬語/反方論點/失效條件） | 「第 N 條・上限名稱」+「通過/已違反/無法評估」 | 「指令 #NN・規則 {ID} 已命中」，事實陳述句，不用「參考」「評估傾向」等軟化語 |
| 色彙軸 | Action 語意（rose=加碼、emerald=減碼/停損、sky=停利、amber=續抱、neutral=資料不足），見 `format.ts:219` | Status 語意（emerald=通過、rose=已違反、amber=無法評估），見 `format.ts:256` | 規則家族（violet=R、orange=S、teal=P、amber=M1），與前兩者色相/語意軸皆不同（見 3.4 理由） |
| 是否可展開/收合 | 允許（如 `skipped_rules` 用 `<details>`） | 允許（sources 用 `<details>`，且非 fresh 時強制展開） | **不允許**：標頭（規則編號/摘要/日期）與 as_of/新鮮度/依據資料日/預定執行日/參考價 一律不得用 `<details>`，僅有「規則全文完整內容」若過長可選擇性放展開連結，但摘要本身仍需常駐（R1 只禁摘要收合，不禁全文的延伸連結） |
| 免責聲明位置 | 與主結論同視覺區塊（`AdviceCardView.tsx:68`） | 無獨立免責聲明（風控上限判定不適用同一套措辭框架） | 頁面層級固定一則（見第 6 節），不逐列重複，但逐列附 `{ATTRIBUTION_LINE}`（R2，見 3.3） |
| 資料新鮮度顯示邏輯 | fresh 時沉默（既有慣例，`DataStatusBadge`） | 依 `sources` 徽章，同既有慣例 | **不沉默**，逐筆恆常顯示 as_of/新鮮度文字（見 3.3 理由，R5 要求） |

**跨頁一致但不混用的部分**：頁面底色 `neutral-950`/`black`、表格分隔線 `border-neutral-800`、
必讀文字下限 `text-neutral-400`、捲軸樣式（`work/stock-desk-視覺規範-捲軸與表格.md` 全站規則，
無條件套用於排程台）——這些是**版面骨架**，三頁一致；上面表格列出的是**語意層**（色彙軸、容器、
標題語彙），三頁刻意不同。骨架一致是為了讓整站「看起來是同一個產品」，語意層不同是為了不讓使用者
把三種不同保證強度的內容混為一談，兩者不矛盾。
