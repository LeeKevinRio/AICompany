# PRD：flight-deals 機票低價監看器

- 版本：v0.1（spec）
- 發起人：CEO
- 撰寫：product-manager
- 任務單：`work/tasks/FD-1.md`
- 產品分支：`product/flight-deals`

## 背景與目標

CEO 想要「抓到最新最優惠價格的機票」來輔助旅遊規劃，希望能針對想去的目的地定時查價、找出便宜的時段，並在價格夠低時主動通知。

目標：
1. 讓 CEO 用一個小型網頁後台設定「要監看什麼」。
2. 系統依排程自動查價，累積價格歷史。
3. 價格達到條件時，主動以 Telegram 推播。
4. 可在網頁上檢視價格歷史與最便宜時段。

成功指標（MVP，單一使用者，以可驗證行為為準）：
- 能建立至少 1 個監看，並在一個排程週期內產生價格紀錄。
- 符合通知規則時 CEO 在 Telegram 收到訊息，且同價不重複。
- 網頁可看到某監看的價格歷史與最便宜的日期組合。
- 資料源失效時，CEO 能在網頁看到明確的失效狀態，而不是靜默沒資料。

產品前提（須貫穿需求與文案）：
- 免費資料源可能隨時失效或改版，系統必須能偵測並顯示失效。
- 所列價格是「查到當下的參考值」，實際價格與庫存以訂票網站為準。

## 使用者與情境

- 使用者：CEO 本人，單一使用者，本機或自家主機執行；非對外服務。
- 情境 A：CEO 想在某段期間去東京，建立監看（TPE→TYO，6 月內出發、停留 4 到 6 天、預算 TWD 12,000），之後等 Telegram 通知。
- 情境 B：CEO 想知道去曼谷「哪段時間最便宜」，開網頁看價格歷史與最便宜出發日組合。
- 情境 C：某天沒收到通知，CEO 開網頁看健康狀態，確認是資料源壞了、排程沒跑，還是單純沒有符合條件的價格。

## 範圍內 / 範圍外

範圍內（MVP）：
- 單一服務：小型網頁後台 + 排程 + Telegram 推播。
- 監看的新增、檢視、修改、停用、刪除。
- 定時查價與價格歷史儲存。
- Telegram 通知與去重規則。
- 價格歷史與最便宜時段檢視。
- 設定與健康狀態頁（含 Telegram 測試發送）。

範圍外（non-goals）：
- 多使用者、註冊、登入、權限。
- 訂票、付款、代購。
- LINE 通道（列為後續通道；LINE Notify 已終止，Messaging API 需另建 channel）。
- 行動 App 原生版本。
- 對外公開服務與對外 SLA。
- 價格預測、「何時該買」的建議。
- 多人艙等混合、多航段（open-jaw、多城市）行程；MVP 僅支援來回與單程。
- 資料源的選型與實作細節（由 tech-architect 另出 ADR）。

## 功能需求（逐條編號）

### A. 監看管理（CRUD）

- FR-A1 建立監看：欄位含出發地（預設 TPE）、目的地、行程型態（來回／單程）、日期模式（彈性窗或固定日期）、預算門檻（TWD）、艙等（預設經濟艙）、人數（預設 1）。
- FR-A2 彈性窗日期：彈性窗模式須可設定最早出發日、最晚回程日、旅程天數下限與上限；單程模式僅需最早與最晚出發日。
- FR-A3 固定日期：固定日期模式須可設定出發日（來回另加回程日）。
- FR-A4 輸入驗證：必填欄位缺漏、日期早於今天、回程早於出發、天數下限大於上限、預算非正數、出發地等於目的地，皆須拒絕儲存並顯示明確錯誤。
- FR-A5 列表檢視：列出所有監看，顯示路線、日期設定、預算、啟用狀態、目前最低價與上次查價時間。
- FR-A6 修改監看：可修改所有欄位；修改會影響日期範圍或路線時，舊價格歷史須保留且與新設定可區分（具體做法由架構決定）。
- FR-A7 停用與啟用：停用的監看不被排程查價、不發通知，但歷史保留。
- FR-A8 刪除監看：刪除前須二次確認；刪除後該監看的歷史一併移除。
- FR-A9 過期處理：日期已全部過期的監看須自動標示為「已過期」並停止查價。

### B. 排程查價

- FR-B1 定時掃描：系統依固定週期掃描所有啟用中的監看；週期可由設定調整（預設值由架構決定）。
- FR-B2 價格紀錄：每次成功查價須記錄路線、出發／回程日期、價格（TWD）、航空公司、查到時間、資料來源。
- FR-B3 查詢次數上限：每個監看每次掃描的對外查詢次數須有上限，達上限即停止該監看本次掃描並記錄；上限數值由架構決定，且須可由設定調整。
- FR-B4 彈性窗取樣：彈性窗展開的日期組合超過上限時，須有可預期的取樣或優先策略，並在監看詳情說明本次涵蓋了哪些組合（策略細節由架構決定）。
- FR-B5 失敗處理：單次查價失敗（逾時、被擋、格式改變、額度用盡）不得中斷其他監看；須記錄失敗原因與時間。
- FR-B6 資料源失效偵測：連續失敗達一定次數須將資料源標示為「異常」，並依 FR-E 顯示，且向 CEO 發一次 Telegram 告警（恢復前不重複告警）。
- FR-B7 防重入：上一輪掃描尚未結束時，不得啟動重疊的掃描。
- FR-B8 手動觸發：可在網頁對單一監看觸發一次立即查價（同樣受 FR-B3 上限約束）。

### C. 通知

- FR-C1 通知條件（任一成立即推播）：(a) 價格小於等於預算門檻；(b) 相對該監看上次已通知價格下跌達設定比例；(c) 創該監看的歷史新低。
- FR-C2 下跌比例可設：下跌比例門檻為全域設定，預設值由 CEO 確認（見開放問題）。
- FR-C3 去重：同一監看同一組（日期組合 + 價格）不重複推播；價格變動才可再次觸發。
- FR-C4 通知內容：須包含路線、出發／回程日期、價格（TWD）、航空公司、查到時間、資料來源，以及一個可點擊的查票連結。
- FR-C5 文案語氣：通知與網頁價格文字僅作事實陳述（例：「查到 TPE→NRT 06/12–06/17 TWD 8,900」），並附「價格為查到當下的參考值，實際以訂票網站為準」；不得使用「建議現在買」「最佳時機」等建議語氣。
- FR-C6 通知觸發原因：訊息須註明觸發原因（低於門檻／較上次下跌 X%／歷史新低）。
- FR-C7 推播失敗處理：Telegram 發送失敗須記錄並於下一輪重試有限次數；失敗時不得標記為「已通知」。
- FR-C8 通知紀錄：保留每則推播的時間、監看、價格、觸發原因與成功與否，供網頁檢視。
- FR-C9 單輪合併：同一輪掃描中同一監看有多個符合條件的組合時，須合併為一則訊息（列出最便宜的前若干筆），避免洗版；筆數由架構決定。

### D. 價格歷史與最便宜時段檢視

- FR-D1 價格歷史：單一監看詳情頁須顯示隨時間變化的最低價趨勢（圖表或表格皆可）。
- FR-D2 最便宜組合：詳情頁須列出目前已知最便宜的前若干個日期組合（價格、日期、航空公司、查到時間）。
- FR-D3 最便宜時段：須能呈現「哪些出發日／星期／時段整體較便宜」的彙整（至少依出發日期呈現價格分布，例如日曆熱度圖或排序表）。
- FR-D4 資料時效標示：所有價格須顯示查到時間；超過一定時間未更新的價格須標示「可能已過期」。
- FR-D5 查票連結：每筆價格須提供前往訂票網站查票的連結。
- FR-D6 空狀態：尚無價格資料時，須顯示說明（例如「尚未查到價格」）而非空白或錯誤。

### E. 設定與健康狀態

- FR-E1 健康狀態頁：顯示資料源狀態（正常／異常／未知）、最近一次成功與失敗原因、上次掃描開始與結束時間、下次預計掃描時間。
- FR-E2 Telegram 設定：可輸入／確認 Telegram 通道是否已設定完成（祕密僅經環境變數或 `.env`，網頁不得顯示或回傳完整 token）。
- FR-E3 Telegram 測試發送：提供按鈕發送一則測試訊息，並回報成功或失敗原因。
- FR-E4 全域設定：可調整掃描週期、每監看每輪查詢上限、下跌比例門檻、價格過期標示時間。
- FR-E5 使用量檢視：顯示最近一次掃描各監看使用的查詢次數，讓 CEO 掌握用量。
- FR-E6 存取範圍：服務預設僅供本機或內網存取，並於文件說明（無登入為 MVP 前提，故不得預設對外暴露）。

## 驗收條件（每條需求至少一組 Given/When/Then）

### A. 監看管理

- AC-A1 Given 無任何監看；When CEO 填寫目的地 NRT、來回、預算 12000 並送出；Then 監看建立成功，出發地預設 TPE、艙等經濟艙、人數 1，且出現在列表。
- AC-A2 Given 建立表單選彈性窗；When 設定最早出發 6/1、最晚回程 6/30、天數 4–6；Then 儲存後詳情頁正確顯示這些設定。
- AC-A3 Given 選固定日期、來回；When 輸入出發 7/1、回程 7/6；Then 儲存成功，且該監看只查該日期組合。
- AC-A4 Given 表單；When 分別提交 (1) 目的地空白 (2) 回程早於出發 (3) 天數下限 7 大於上限 5 (4) 預算 0 (5) 出發地等於目的地 (6) 出發日為過去；Then 每種情況都被拒絕並顯示對應錯誤，不產生資料。
- AC-A5 Given 已有 3 個監看，其中 1 個已有價格紀錄；When 開啟列表；Then 每列顯示路線、日期設定、預算、啟用狀態；有紀錄者顯示最低價與上次查價時間，無紀錄者顯示「尚未查價」。
- AC-A6 Given 一個已有歷史的監看；When 修改預算；Then 歷史保留；When 修改目的地；Then 舊歷史仍可查閱且標明屬於舊設定。
- AC-A7 Given 一個啟用中的監看；When 停用；Then 下一輪掃描不查它、不發它的通知，歷史仍可檢視；When 重新啟用；Then 下一輪恢復查價。
- AC-A8 Given 一個監看；When 點刪除；Then 先出現確認；確認後該監看與其歷史消失，取消則無變化。
- AC-A9 Given 一個監看所有日期都已早於今天；When 下一輪掃描前後；Then 狀態顯示「已過期」且不再被查價。

### B. 排程查價

- AC-B1 Given 1 個啟用監看且資料源正常；When 一個掃描週期過去；Then 產生至少 1 筆價格紀錄，欄位完整（路線、日期、價格、航空公司、查到時間、來源）。
- AC-B2 Given 設定上限為 N 次；When 一個彈性窗展開超過 N 個組合的監看被掃描；Then 該次對外查詢次數不超過 N，且記錄「達上限」。
- AC-B3 Given 彈性窗組合數大於上限；When 檢視該監看詳情；Then 可看到本次涵蓋了哪些日期組合。
- AC-B4 Given 兩個監看，第一個查價失敗；When 掃描進行；Then 第二個仍正常查價，第一個的失敗原因與時間被記錄。
- AC-B5 Given 資料源連續失敗達門檻；When 達到門檻；Then 健康頁顯示「異常」，CEO 收到一則 Telegram 告警；在恢復前再次失敗不重複告警；恢復後狀態回「正常」。
- AC-B6 Given 上一輪掃描仍在執行；When 下一個排程時間到；Then 不啟動新的一輪，並記錄略過。
- AC-B7 Given 一個啟用監看；When 在網頁按「立即查價」；Then 執行一次查價，結果寫入歷史，且查詢次數不超過上限。

### C. 通知

- AC-C1 Given 預算 10000；When 查到 9500；Then 發出推播，觸發原因為「低於門檻」。
- AC-C2 Given 上次已通知價 10000、下跌比例門檻 5%；When 查到 9400（高於預算門檻但跌 6%）；Then 發出推播，原因為「較上次下跌」。
- AC-C3 Given 該監看歷史最低 9000、價格高於預算；When 查到 8800；Then 發出推播，原因含「歷史新低」。
- AC-C4 Given 某組合價格 9500 已通知；When 下一輪再查到同組合同價 9500；Then 不再推播。
- AC-C5 Given 一則推播；When 檢視訊息內容；Then 含路線、日期、價格（TWD）、航空公司、查到時間、資料來源、可點擊查票連結、觸發原因，以及「價格為查到當下的參考值，實際以訂票網站為準」。
- AC-C6 Given 推播文案；When 檢視全部文字模板；Then 不含「建議」「最佳時機」「現在買」等建議語氣，價格以「查到 … 價」之事實陳述呈現。
- AC-C7 Given Telegram 暫時無法連線；When 符合通知條件；Then 失敗被記錄且該價格未標記為已通知；通道恢復後於後續輪次補發，且不超過重試上限。
- AC-C8 Given 已發過數則推播；When 開啟通知紀錄；Then 可看到每則的時間、監看、價格、原因與成功／失敗。
- AC-C9 Given 同一輪同一監看有 8 個組合符合條件；When 發送通知；Then 只發 1 則合併訊息，內含最便宜的前若干筆。

### D. 價格歷史與最便宜時段

- AC-D1 Given 一個有多天價格紀錄的監看；When 開啟詳情；Then 可看到最低價隨時間的趨勢。
- AC-D2 Given 該監看有多個日期組合的價格；When 開啟詳情；Then 列出最便宜的前若干組合並依價格由低到高排序。
- AC-D3 Given 彈性窗監看已有多個出發日的價格；When 查看最便宜時段；Then 可依出發日期看到價格分布並辨識較便宜的日期。
- AC-D4 Given 一筆價格查到時間已超過過期標示時間；When 顯示；Then 標示「可能已過期」並顯示查到時間。
- AC-D5 Given 任一價格列；When 點查票連結；Then 開啟訂票網站查票頁（帶入路線與日期，能力以資料源可提供者為準）。
- AC-D6 Given 新建立尚無價格的監看；When 開啟詳情；Then 顯示「尚未查到價格」說明，頁面無錯誤。

### E. 設定與健康狀態

- AC-E1 Given 系統運行中；When 開啟健康頁；Then 顯示資料源狀態、最近成功／失敗原因、上次掃描開始與結束時間、下次預計掃描時間。
- AC-E2 Given Telegram 憑證已由環境變數設定；When 開啟設定頁；Then 顯示「已設定」，且頁面與其回應中不出現完整 token；未設定時顯示「未設定」與設定指引。
- AC-E3 Given Telegram 已設定；When 按測試發送；Then CEO 收到測試訊息且頁面顯示成功；Given 設定錯誤；Then 頁面顯示失敗原因。
- AC-E4 Given 設定頁；When 修改掃描週期、查詢上限、下跌比例、過期標示時間並儲存；Then 下一輪起生效，且不合法值（0、負數、非數字）被拒絕。
- AC-E5 Given 剛完成一輪掃描；When 開啟使用量檢視；Then 顯示各監看本輪的查詢次數。
- AC-E6 Given 預設安裝後啟動；When 從非本機／非內網位址連線；Then 預設連不上；部署文件載明此限制與原因。

## 風險與依賴

- 資料源風險（高）：免費來源（候選：Google Flights 非官方抓取、Travelpayouts 快取價 API）可能被擋、改版、額度限制或價格與實際不符。依賴 tech-architect 出 ADR 選型；若涉及付費方案，須升級 CEO。PRD 以 FR-B5、FR-B6、FR-E1 要求失效可見。
- 價格準確性風險：快取價或非即時價可能與實際不一致。以 FR-C5、FR-D4 的「參考值」文案與時效標示因應。
- 服務條款／法遵風險：非官方抓取可能違反來源網站條款；由 tech-architect 於 ADR 評估，必要時諮詢 risk-compliance-officer。
- 風控閘門判定：價格資料為事實查詢結果，非投資／健康／法律建議，原則上不適用章程風險閘門。但推播文案須避免「建議現在買」等建議語氣，改用「查到 ○○ 價」的事實陳述（FR-C5）；若日後加入「建議購買時機」等功能，須重新送 risk-compliance-officer 審查。
- 祕密管理：Telegram bot token、chat id、資料源 API key 僅能來自環境變數或 `.env`（已被 `.gitignore`），`.env.example` 只放假值。
- 無登入風險：單一使用者無登入，故預設僅限本機／內網（FR-E6）；若要對外暴露須另開需求加驗證。
- 排程可靠度：服務需常駐才會查價；本機關機即停。主機形態待 CEO 確認。
