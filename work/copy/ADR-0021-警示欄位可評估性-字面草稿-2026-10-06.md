## 事實核對（起草前查到、影響字面的三點）

1. 個股頁 Beta 卡：`TechnicalIndicatorsPanel.tsx` L604 標題「Beta（相對比較基準指數的敏感度）」，位於 L665「風險量測」分組內。**該卡本身可能顯示「資料不足：缺少比較基準指數的資料，無法計算 Beta。」**（L611）。因此 W-1 只能說「可查看 Beta 卡」，不能說「可看到 Beta 數值」，否則換成另一處不實。
2. 該分組在個股頁「技術分析」`<details>` 內（風控 2026-10-05 位置 1 核對紀錄：`page.tsx:419`）。「風險量測」區預設可能是收合狀態，見未決點 U-2。
3. **欄位對欄位（ref）規則在編輯表單不可改**：`EditAlertRuleModal.tsx` L97 `REF_CONDITION_READONLY_HINT` =「此規則的比較條件為欄位對欄位，目前不支援在此表單修改。」若舊規則是 `ref = beta.value`（或 `field` 為其他欄位、`ref` 為 beta），使用者在 UI 只能刪除，不能「編輯條件」。因此 W-2、W-5 的處置句主案不寫「可編輯」，改寫成對兩種規則形狀都為真的「可改用其他欄位的條件，或刪除此規則」。ADR 原文寫「編輯或刪除」，此為有意的微調，見未決點 U-1。

## W-1：警示表單「訊號欄位」下方常駐說明

位置：`settings/AlertParamFields.tsx` 的 select（L54「訊號欄位」）正下方；建立與編輯共用同一元件，一處改兩處生效。
落地建議（比照既有核可做法）：常駐，不收合、不截斷、不 tooltip、不 sr-only；≥ `text-xs text-neutral-400`；無條件顯示（不因任何欄位選擇而隱藏）。

### 主案 W-1-A（30 字）

> 警示不提供 Beta 作為條件，可在個股頁「風險量測」區查看。

- 為什麼：「不提供」是常態語氣，不含「目前／暫時」，讀不出「之後會有」；「查看」不承諾有數值（見事實 1）。
- 避開的否決理由：
  - 「訊號頁」——UI 無此頁（風控已否決；改用 UI 實有的「個股頁」「風險量測」，後者見 `oneLinerWording.ts` L20、`TechnicalIndicatorsPanel.tsx` L665）。
  - 暗示暫時／可期（不寫「尚未」「目前」「即將」「之後」）。
  - 安撫語（不寫「別擔心」「不影響」）。
  - 命令語氣（無「請」「應」）。

### 替代案 W-1-B（兩句，16＋32＝48 字，各句 ≤ 40）

> 警示不能以 Beta 作為條件。個股頁「風險量測」區有 Beta 卡，資料不足時會標示資料不足。

- 為什麼：把「卡片也可能沒數值」寫進同一處，不讓使用者去個股頁後以為壞了；用詞與 `TechnicalIndicatorsPanel.tsx` L611「資料不足」同源。
- 代價：較長，常駐於表單內會多占一行至兩行；「不能」比「不提供」多了一點「系統限制」的語感。
- 避開的否決理由：同 W-1-A；另不寫成「可看到數值」。

## W-2：舊規則的 skip reason（取代「缺少輸入欄位：…」）

位置：`engine.py` L151–L152（`left` 為 None）與 L155–L156（`ref` 側為 None）兩處；K-6 要求判斷「欄位不在 ALERT_RULE_FIELDS」，不能只看值是否 None，因此這是一組**獨立於「缺少輸入欄位」的新字串**，不是改寫既有那一句（其他欄位真的缺值時，既有「缺少輸入欄位：…」一字不動，K-10）。
`{欄位}` ＝ `describe_field(...)` 的輸出（沿用既有家族，形如 `beta.value（相對指標的 beta）`），beta 與 position.* 舊規則共用同一模板。
可見範圍提醒：此字串只出現在 `/api/alerts/evaluate` 的 outcomes 與 scheduler log（ADR 查證結果 3），一般使用者在 UI 看不到；使用者面的主要揭露是 W-1、W-3，見未決點 U-3。

### 主案 W-2-A（三句，39＋17＋18 字，以 beta 展開計）

> 此規則使用的 {欄位}，警示不提供作為條件。每次檢查都會略過此規則，不會觸發。可改用其他欄位的條件，或刪除此規則。

- beta 展開：「此規則使用的 beta.value（相對指標的 beta），警示不提供作為條件。每次檢查都會略過此規則，不會觸發。可改用其他欄位的條件，或刪除此規則。」
- 字數（beta 展開）：S1 ＝ 39；S2 ＝ 17；S3 ＝ 18（皆 ≤ 40）。
- 為什麼：
  - S1 講原因與「這是警示的規格」，不講「缺少」，讀不出「資料暫時沒來」。
  - S2 的「每次」把常態寫明，並直接說結果（略過、不會觸發），不留「是不是壞了」的空間。
  - S3 給處置，且對 value 型與 ref 型規則都為真（事實 3）。
- 避開的否決理由：暗示暫時（原句「缺少輸入欄位」正是 ADR 查證 3 指出的問題）；單一方向預測（只陳述系統行為，不預測市場）；安撫語；「觸發」用在警示主詞（合規用法）。

### 替代案 W-2-B（依規則形狀分兩種處置句；S1、S2 同主案）

value 型（`comparison.value` 為數字，表單可編輯）S3：

> 可編輯條件，或刪除此規則。

ref 型（欄位對欄位，表單不可改）S3：

> 此規則為欄位對欄位比較，無法在表單修改，可刪除後重新建立。

- 為什麼：資訊最精確，value 型使用者直接得到「編輯」這個 ADR 原意的處置。
- 代價：兩個字串、兩條分支，需 dev 在 engine 內判斷規則形狀，測試 T-2 要斷言兩種；多一個需風控核的字串。`無法在表單修改` 的事實依據是 `EditAlertRuleModal.tsx` L97。
- 避開的否決理由：同主案；另避免在 ref 型規則上寫出做不到的「編輯」。

## W-3：規則清單與編輯對話框的舊規則標示（≤ 12 字）

位置：`AlertRulesSection.tsx` 規則清單（L55–L68）每筆舊規則；`EditAlertRuleModal.tsx` 開啟舊規則時，緊接於「訊號欄位：{signalFieldLabel}」同一列（L323）。標示須常駐、不只靠顏色、不用 tooltip；K-9 要求舊規則的欄位名稱仍顯示「相對指標的 beta」。

### 主案 W-3-A（11 字）

> 不會觸發（欄位不提供）

- 為什麼：清單上最重要的資訊是「這條規則不會響」，其次才是原因；兩者合在 12 字內。「不提供」與 W-1 同詞，使用者在表單看到的、與在清單看到的是同一個說法。
- 避開的否決理由：「缺資料」「暫停」（暗示暫時）；「失效」「異常」「錯誤」（暗示壞了或使用者做錯）；「已停用」（事實不符，規則並未被停用，K-8）；「過期」。
- 註：規則被使用者手動關閉（enabled＝false）時，此標示仍為真，不需分支。

### 替代案 W-3-B（6 字）

> 欄位已不提供

- 為什麼：最短，適合清單空間緊時。
- 代價：沒講「不會觸發」，使用者要自己推論；「已」帶「曾經有、後來拿掉」的語意，與事實相符，但依賴使用者記得原本可選。
- 避開的否決理由：同主案。

## W-4：422 錯誤訊息

位置：`api/alerts.py` POST、PUT、PATCH（params 非 None）；T-3 以此字串斷言。對象主要為 API 呼叫端，因此沿用既有家族的 `describe_field` 形式帶出欄位鍵與中文標籤（開發者對照用）。前端表單選不到這些欄位，使用者面通常看不到此訊息。

### 主案（各一句）

W-4-A（beta，欄位鍵固定）：

> 警示不提供 beta.value（相對指標的 beta）作為條件，請改用其他欄位。

- 字數：39（≤ 40）。

W-4-B（position.*，`{欄位}` ＝ 其中一個，不合併兩者）：

> 警示不提供 {欄位} 作為條件，請改用其他欄位。

- 展開：「警示不提供 position.weight（此標的佔投資組合比重）作為條件，請改用其他欄位。」（44 字，略超原則；見下）；「警示不提供 position.unrealized_pnl_pct（此部位未實現損益率）作為條件，請改用其他欄位。」（更長）。
- 字數說明：模板本體 17 字，展開後因 `describe_field` 帶欄位鍵而超過 40 字。這是欄位鍵本身長度造成，非句子結構問題；若風控要求展開後也 ≤ 40，改用替代案（只帶標籤，不帶鍵）。

- 為什麼（兩句共通）：beta 與 position.* 的訊息結構相同、僅欄位不同，使用者（或 API 開發者）看一次就懂規則；結尾「請改用其他欄位」是唯一可做的下一步。兩條分開寫是因 ADR 要求 beta 一句、position.* 一句，且測試可各自斷言；實作上可共用同一模板。
- 避開的否決理由：不寫成因（不講「沒有載入指數／持倉」）；不寫「暫時」「目前」；不寫「預計支援」「日後開放」（預測／可期）；不用 HTTP 慣用語「invalid／not allowed」英文。

### 替代案 W-4-C（陳述式、只帶標籤，不帶鍵、不用命令語氣）

beta：

> 「相對指標的 beta」不在警示可選的條件欄位內。

position.*：

> 「{標籤}」不在警示可選的條件欄位內。

- 字數：beta 22 字；`此標的佔投資組合比重` 版 24 字；`此部位未實現損益率` 版 23 字（皆 ≤ 40）。
- 為什麼：短、無命令語氣、全部展開後仍 ≤ 40；與 W-1「警示不提供…」同義但換成清單邊界的說法。
- 代價：API 開發者拿不到欄位鍵（但 422 body 的 `loc`／原送出的 params 已含鍵）；少了「改用其他欄位」的下一步提示。
- 避開的否決理由：同主案。

## W-5：release note 一句（第一版，已被風控 VETO，作廢；見下方「W-5 重寫（第二版）」）

位置：隨實際含 ADR-0021 變更的版本發布；比照 RN-1～RN-6，只隨部署發布，不得提前對外（R-1 條件同 RN）。範圍只有兩件：警示可選欄位的變動、既有 beta 規則的處置；不寫 position.*（UI 本來就沒有）、不寫成因、不寫日後計畫。

### 主案 W-5-A（一句，44 字）

> 警示的條件欄位移除 Beta；既有 Beta 規則保留但不會觸發，可改用其他欄位或刪除。

- 字數：44（略超 40 原則，因為把「移除」「保留」「不會觸發」「處置」四件事放進同一句；拆成兩句則違反「一句」的要求）。
- 兩面都寫：一面是「移除」（使用者失去的），另一面是「保留但不會觸發」（舊規則的真實狀態）；沒有「不影響」「無需處理」之類的安撫。
- 為什麼：「保留」對照 K-8（不刪除、不停用、不改寫）；「不會觸發」是 W-2、W-3 同一件事，三處說法一致；處置句與 W-2-A 的 S3 同義（對 ref 型規則也為真）。
- 避開的否決理由：RN 家族已否決的安撫語（「早已顯示」「一致」）；單一方向（RN-5 式兩面）；「訊號頁」；「可能會首次觸發」類預測；「觸發」只用在警示主詞（合規）。

### 替代案 W-5-B（約 40 字，沿用「編輯」，與 ADR 原意最接近）

> 警示的條件欄位移除 Beta；既有 Beta 規則保留但不會觸發，可編輯或刪除。

- 為什麼：較短、與 ADR 原文「編輯或刪除」一致。
- 代價：對 ref 型舊規則「編輯」在表單做不到（事實 3），若風控認為 ref 型 beta 規則在實務上不存在（只能由 API 建立），可採此案；採用前請 dev-lead 確認。
- 避開的否決理由：同主案。

## W-5 重寫（第二版）

- 狀態：**草稿，待 risk-compliance-officer 審**。上方 W-5-A／W-5-B 現稿已被風控 VETO（`work/reviews/2026-10-06-ADR-0021-警示欄位可評估性-字面-風控審查.md`），**作廢，不得使用**；以本段取代。
- 否決理由（簡述）：現稿只寫「移除；既有規則保留但不會觸發」，讀者會推論「先前有效、此版本才失效」，以省略隱藏過去失效。
- 事實前置（dev-lead 已查證，結論 A）：警示端自 2026-07-26 上線（`f4f7baa`）起，snapshot 的 `compute_signals` 歷來只傳 `(symbol, bars)`，從未載入 benchmark；`beta.value` 自 `06ea06b`（2026-07-25）即在 `KNOWN_FIELDS`，API 一直接受含 beta 的警示規則；engine 第一版即對缺值 skip。含 beta 的警示規則從建立起每次評估都被略過，沒有任何可觸發期間。只有個股頁「風險量測」的 Beta 卡自 `5b2db60`（2026-08-03）起有數值。
- 由此決定的寫法：必須明寫「此版本之前，Beta 規則也不會觸發」；不寫「曾有可觸發期間」類字面（事實不符）；只寫事實，不寫成因（不講「沒有載入指數」）、不寫日後計畫、不用「早已」「不影響」「無需處理」。
- 位置與發布：比照 RN-1～RN-6，隨實際含 ADR-0021 變更的版本發布，只隨部署發布（U-6 轉 CEO）。範圍只有兩件：警示可選欄位的變動、既有 Beta 規則的處置；不寫 position.*。
- 處置句與 W-2 第三句同義（「可改用其他欄位的條件，或刪除此規則」），不採「編輯」（U-1 風控裁示）。

### 主案 W-5-C（兩句，52＋35＝87 字）

> 警示的條件欄位移除 Beta；既有的 Beta 規則保留但不會觸發，可改用其他欄位的條件，或刪除此規則。此版本之前，這些規則也不會觸發：自警示功能上線以來，每次檢查都被略過。

- 字數：S1 52（含「移除」「保留」「不會觸發」與處置）；S2 35（揭露過去）。
- 為什麼：
  - S1 保留風控預設的四件事原序（移除、保留、不會觸發、處置），讀者先得到「現在的狀態與可做的事」。
  - S2 緊接著用「此版本之前……也不會觸發」直接回答「以前呢？」，再以「自警示功能上線以來，每次檢查都被略過」給出可核對的範圍與事實（結論 A：沒有任何可觸發期間），不留「先前有效」的推論空間。
  - 「略過」與 W-2 S2「每次檢查都會略過此規則」同詞，三處（W-2、W-3、W-5）說法一致。
- 避開的否決理由：省略過去失效（S2 明寫）；安撫語（無「不影響」「無需處理」「早已」）；成因（不寫）；日後計畫（不寫）；單一方向（「移除」與「保留」兩面都寫）；「觸發」只用在警示規則為主詞。
- 滿足「揭露過去也不會觸發」：**是**（「此版本之前，這些規則也不會觸發」，並附範圍「自警示功能上線以來」）。
- 風險提示（請風控留意）：「自警示功能上線以來，每次檢查都被略過」是對過去的事實陳述，依據為 dev-lead 查證結論 A；落地前若查證結論改變須重送。

### 替代案 W-5-D（兩句，43＋58＝101 字；先揭露過去、再寫變更）

> 此版本之前，含 Beta 條件的警示規則自警示功能上線以來每次檢查都被略過，不會觸發。此版本起警示的條件欄位移除 Beta，既有的 Beta 規則保留，仍不會觸發；可改用其他欄位的條件，或刪除此規則。

- 字數：S1 43；S2 58。
- 為什麼：把「過去也不會觸發」放在最前，讀者最先讀到；「仍不會觸發」把現況與過去接起來。
- 代價：最長；「移除」被放到第二句，變更本身的重點較後；「仍」帶連續性語感，若風控認為有安撫之嫌可退回主案。
- 避開的否決理由：同主案。

### 風險提示（請風控留意）

1. **主詞與「每次檢查都被略過」的真實性**：沿用 W-5 第二版風控核可的邏輯，「以收盤價為條件的警示規則……自警示功能上線以來每次檢查都被略過」，指規則以收盤價為條件的期間；value 型規則可在編輯對話框換條件欄位，原用其他欄位、觸發過、後改成收盤價的規則，在改成之前並非被略過，其被略過的期間自改成起算。限定主詞後該句成立，但請風控確認此解讀與 W-5 一致；若認為需再限縮，請指定字面，creative-lead 不自行改動。

4. **「多則通知」的真實性**：RN-6 為「可能」措辭；本次後果取決於使用者既有收盤價規則的數量與當時行情，字面用「可能」而不寫數量或頻率。請 dev-lead 確認觸發路徑確實會在升級後第一次檢查對多條規則各發一則通知（而非合併或去重），否則「一次出現多則通知」不成立。
