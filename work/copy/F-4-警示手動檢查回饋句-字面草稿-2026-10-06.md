## 1. 事實盤點（已讀原始碼，非推測）

| 項目 | 實際行為 | 出處 |
|---|---|---|
| `evaluated` | `len(rules)`，且 `rules = store.list_rules(enabled_only=True)`：**只含啟用中的規則，但含被略過者** | `engine.py:301`、`:359` |
| `fired` | `len(result.events)`，即 status 為 `fired` 的筆數 | `api/alerts.py:258` |
| `outcomes[]` | 每條啟用規則一筆 `{rule_id, status, reason}`；`event` 不外送 | `api/alerts.py:260-263` |
| status 值 | 恰四種：`fired`、`quiet`、`skipped`、`suppressed`；前端型別為 `string`，非 union | `engine.py:103-106`、`types.ts:1397-1401` |
| 恆等式 | `fired + quiet + suppressed + skipped = evaluated` | `engine.py:322-355` |
| `skipped` | 輸入不可得（無日線、缺匯率、W-2 舊規則欄位不可評估、snapshot 載入失敗、收盤價不合法等）；`reason` 有字 | `engine.py:324`、`:376-386` |
| `quiet` | 輸入可得、條件未成立 | `engine.py:327-329` |
| `suppressed` | **條件已成立**（`crossed` 為真，訊息已組好），但落在冷卻內，**未寫入事件**；`reason` 為「距離上次觸發不足 N 分鐘，本次不重複發出。」 | `engine.py:342-350` |
| 已停用的規則 | 不在 `outcomes`、不在 `evaluated`，但仍列在規則表（顯示「已停用」） | `engine.py:301`、`AlertRulesSection.tsx:124` |

兩個必須在字面層處理的結論：

1. **略過的規則不是「檢查過、沒越線」**：略過 = 沒得出結果。舊句把它們算進「已評估」，並以「觸發 0 筆」收尾，等於把「沒結果」讀成「沒事」。
2. **suppressed 也會造成同型誤讀**：它的條件**已成立**，只是冷卻擋下。「本次觸發 0 筆事件」會讓人以為條件沒成立。最常見情境是使用者連按兩次「手動檢查一次」：第二次必然全數落入 suppressed，畫面卻只說「觸發 0 筆」。這比 skipped 更常出現，所以**建議揭露**（見 §3）。

## 2. 設計決定（先講結論再給字面）

- **數字來源改由 `outcomes` 計數，不再用 API 的 `evaluated`**。「已評估」= status 屬 `fired`／`quiet`／`suppressed` 者；「略過」= status 為 `skipped` 者。不用 `evaluated - skipped` 推算，避免日後出現新 status 值時被誤算成「已評估」。（實作交 dev-lead／frontend，字面不綁死寫法。）
- **不寫「共 N 條規則」**：`evaluated` 只含啟用中，規則表另含已停用者，寫「共」會與畫面對不上。故用「已評估 X 條規則、略過 Y 條」兩個並列計數，讀者自然看出是兩個互斥的桶。
- 沿用既有詞：規則、事件、略過、觸發、冷卻、已評估、符合條件（W-2／W-5 已用）。不新造同義詞。
- 不安撫、不寫成因、不命令式；略過一律不附原因，原因（reason）見 §6 建議。

## 3. 各案字面

以下 `{E}` = 已評估數、`{S}` = 略過數、`{F}` = 觸發數、`{P}` = suppressed 數（冷卻擋下）。

### F-4-A（推薦）：兩個並列計數，略過 0 時照列

第一句（恆顯示）：

> 已評估 {E} 條規則、略過 {S} 條，本次觸發 {F} 筆事件。

第二句（**僅 `{P}` > 0 時附加**）：

> 已評估的規則中，{P} 條符合條件但在冷卻中，未發出事件。

為什麼：
- 一個固定模板、無分支，數字位置每次相同；使用者學會讀「略過」那一格，**看到「略過 0 條」是肯定事實，而不是靠「沒提」來推論**。
- 「已評估 0 條」在全略過時直接可見，不靠讀者算減法。
- 「略過」與 W-2／W-5 同詞；沒有「未評估」「沒檢查」等新同義詞。
- 與舊句只差在數字口徑與多一個計數，改動最小。

代價：略過 0 時多了「、略過 0 條」，多數時候是雜訊，但字面是真的、且固定結構利於測試。

### F-4-B：略過獨立成句，0 時省略

第一句（恆顯示）：

> 已評估 {E} 條規則，本次觸發 {F} 筆事件。

第二句（**僅 `{S}` > 0 時附加**）：

> 另有 {S} 條規則被略過，未評估。

第三句（**僅 `{P}` > 0 時附加**，同 A 的第二句）：

> 已評估的規則中，{P} 條符合條件但在冷卻中，未發出事件。

為什麼：略過 0 時畫面與現行完全一致，沒有視覺雜訊；略過時明寫「未評估」，直接切斷「略過 = 檢查過」的讀法。
代價：略過 0 與「功能沒出現」無法從畫面區分；有分支，三句各自條件顯示，測試組合較多；「未評估」是新詞，較 A 多一個字面要核可。

### F-4-C：以分項算式呈現，略過 0 時照列

> 本次檢查啟用中的規則：已評估 {E} 條、略過 {S} 條；觸發 {F} 筆事件。

冷卻句同 A 的第二句。

為什麼：「啟用中的規則」明確限定母數，防止讀者拿規則表（含已停用）對帳對不上；分號把「觸發」放在「評估」之後，讀起來是評估的結果。
代價：偏長，且「本次檢查啟用中的規則」冗詞多，在窄螢幕易換行；與舊句差距最大。僅在風控認為必須明寫母數時採用。

- B：`已評估 0 條規則，本次觸發 0 筆事件。另有 5 條規則被略過，未評估。`
- C：`本次檢查啟用中的規則：已評估 0 條、略過 5 條；觸發 0 筆事件。`

- (d) 5 條：1 觸發、1 冷卻擋下、1 未越線、2 略過（A）：

  `目前沒有啟用中的規則，本次未評估任何規則。`

## 5. 為什麼揭露 suppressed

- 語意：suppressed =「條件已成立，但在冷卻內，所以沒寫事件」（`engine.py:342-350`）。它不是略過（輸入齊全、已評估），也不是 quiet。
- 只報「觸發 0 筆」會把「條件成立但被擋」讀成「條件沒成立」，與略過同屬假陰性，只是方向相反（略過是「沒結果」被讀成「沒事」，冷卻是「有結果」被讀成「沒事」）。
- 實際最常見情境：使用者手動連按兩次。若不揭露，第二次畫面必然是「觸發 0 筆」。
- 字面處理：只在 `{P}` > 0 時附加（它是偶發診斷，不是每次的固定格）；用「符合條件」描述事實、用「冷卻」沿用設定頁既有詞（`SettingsForm.tsx:182`）；不寫「重複」「正常」等評價詞，也不寫成「這是預期行為」之類安撫。
- 請風控留意：「符合條件」指該規則的條件在本次評估成立。對 `risk_limit_breach` 等類型，語意仍是「該規則自己的條件成立」；若風控認為此詞在該類型上過寬，請指定替代字面，creative-lead 不自行改動。

## 6. 顏色（視覺，**需 art-lead 確認**）

- 現況 `text-emerald-300` 是正面色，與「已評估 N 條規則，本次觸發 0 筆事件」配起來即是正面假保證的視覺半邊。
- 建議（需 art-lead 定）：
  1. **首選**：不論計數為何，一律改中性 `text-neutral-300`。理由：這句是「這次發生了什麼」的紀錄，不是成功／失敗；「觸發 0 筆」不是好消息。單一色、無分支。
  2. **最低限度**：`{S}` > 0 或 `{P}` > 0 時改 `text-neutral-300`，其餘維持 emerald。缺點：全綠時仍帶正面暗示，且色彩有分支。
- 不建議用紅／琥珀：略過可能是日常現象（例如 W-2 舊規則每次必略過），警示色會製造不必要的緊張，且與設定頁錯誤色（`text-red-400`）混淆。此點由 art-lead 裁量。
- 無障礙：略過／冷卻資訊都在文字內，不靠顏色單獨傳達；`role="status"` 維持不變。

## 9. 風控請裁量的點

1. 「已評估」口徑由「全部啟用規則」改為「排除略過者」，是否認為這個口徑變更本身需在 release note／CEO 知悉清單寫明（任務單 R-B2 已要求「舊『已評估』含被略過的規則」寫入知悉清單）。
2. 冷卻句「符合條件但在冷卻中，未發出事件」是否可接受（見 §5 風險提示）。
3. 全略過（案 c）時，句尾「本次觸發 0 筆事件」是否仍需保留；A 案因「已評估 0 條」已在同句，creative-lead 認為保留不致誤導，但請風控確認。
4. (f) 特例句是否核可。

## 10. 僅列建議、不出字面（需 PM／art-lead）

**略過原因（`reason`）目前前端完全不渲染**（`AlertEvaluationOutcome.reason` 已在型別內，但 `AlertRulesSection.tsx` 只用 `evaluated` 與 `fired`）。建議在回饋句下方提供「查看略過原因」展開：

- 價值：使用者看到「略過 2 條」後，目前沒有任何入口得知是哪兩條、為何；計數只揭露了「有」，沒解決「怎麼辦」。對 W-2 這類每次必略過的舊規則尤其需要。
- 內容來源：逐條規則（可用 `rule_id` 對規則表）＋`reason` 原文。`reason` 為後端字串，部分來自資料層（`snapshot.reason`），**進入畫面前每一種 reason 都屬面向使用者字面，需風控逐類審過**，尤其要確認沒有「最新」等禁詞（例如既有的「沒有可用的最新收盤價。」`engine.py:404` 含「最新」，與 W-R2 同型，需另案處理）。
- 同理可列出冷卻擋下的規則與其 reason。
- 這是新互動（展開／收合、鍵盤操作、資訊階層），需 product-manager 定範圍、art-lead 定視覺；本稿不出字面。

## 12. art-lead 顏色裁量（2026-10-07，回應 §6）

作者：art-lead　依據：已讀 `AlertRulesSection.tsx`、`DataStatusBadge.tsx`、`layout.tsx`、`globals.css` 與頁內各 emerald／amber 用處（非憑截圖）。

### 12.1 結論

**採 creative-lead §6 首選：一律中性 `text-neutral-300`，不做條件式配色。不加圖示，不加色塊／左邊框。** 不用紅、不用琥珀、不留 emerald。

### 12.2 為什麼一律中性、不做條件式

1. **emerald 在本產品的語意是「操作成功／狀態健康」**。實際用處：設定已儲存（`SettingsForm.tsx:464`）、CSV 匯入成功（`ImportCsvSection.tsx:67`）、淨值 fresh 狀態 chip（`NetWorthSection.tsx:44`）、資料夾可用 chip（`DirectorySection.tsx:63`）、部位頁成功狀態（`positions/page.tsx:196`）。這些都是「結果良好」的判定。本句是「這次發生了什麼」的紀錄，「觸發 0 筆」「略過 0 條」都不是好消息，也不是壞消息；繼續用 emerald 會在視覺上補回風控要拆掉的正面假保證。
2. **條件式（有略過／冷卻才中性，其餘 emerald）會讓顏色本身變成判定**：全綠 = 「沒事」，等於把 `{S}=0`、`{P}=0` 升格成一個正面結論，而「略過 0」只是計數事實。且兩種狀態的視覺差只有色相，違反「不靠顏色單獨傳達」。不採。
3. **不用琥珀**：頁內 amber 專屬「這條規則本身有缺陷」——W-3 的 `text-amber-400` ＋ `border-l-2 border-amber-400`（`AlertRulesSection.tsx:134`）是附在特定規則列上的持續性警示；`NetWorthSection`／`PriceChart` 的 amber 是「值得注意、需使用者處理」。略過可能是日常現象（W-2 舊規則每次必略過），冷卻擋下是連按第二次的必然結果；用琥珀會把例行結果標成警訊，習慣化後又會稀釋 W-3 的警示力，也讓同一畫面出現兩個互不相干的 amber 意義。
4. **不用紅**：頁內 red 專屬錯誤與破壞性動作（`text-red-400` 欄位錯誤、刪除鈕、`border-red-900 bg-red-950/40` 失敗框）。略過／冷卻不是失敗。
5. **與「資料不足」chip 的先例一致**：`DataStatusBadge.tsx:24-28` 已確立「最嚴重狀態用更亮＋框線表達，不用紅」。本句連「最嚴重」都談不上，故最低調的中性即可，不另做強調。

### 12.3 對比度（數值計算，WCAG 相對亮度）

頁面背景：`layout.tsx:15` body 為 `bg-black`（#000000）；`globals.css` 的 `--background` 為 #0a0a0a。本區塊 `<section>` 無自帶背景，故落在其中之一。

| 前景 | 背景 | 對比 | 判定 |
|---|---|---|---|
| neutral-300 #d4d4d4 | #000000 | 約 14.2:1 | 通過 AA（4.5:1）與 AAA（7:1） |
| neutral-300 #d4d4d4 | #0a0a0a | 約 13.4:1 | 通過 AA／AAA |
| neutral-300 #d4d4d4 | neutral-900 #171717（若日後包框） | 約 12:1 | 通過 AA／AAA |
| 對照：舊 emerald-300 #6ee7b7 | #000000 | 約 14:1 | 同級，換色不損可讀性 |

neutral-300 與同列「手動檢查一次」按鈕字（`text-neutral-300`）、規則表內文（`text-neutral-300`）同色，階層上落在 h2 的 neutral-100 之下，合理。不降到 neutral-400：此句承載風控要求的揭露，不應是次要灰字。

### 12.4 是否需要圖示或前綴

**不需要。** 理由：

- 風控原則是「資訊不得只靠顏色傳達」。本案選一律中性後，**顏色已不承載任何資訊**；略過數、冷卻數全在文字內（固定模板，「略過 0 條」本身就是肯定事實）。沒有顏色依賴，就沒有需要圖示補強的缺口。
- 圖示（勾、驚嘆號、資訊圈）每一個都帶判定意涵：勾 = 成功、驚嘆號 = 警訊，皆與「不下判定」的字面設計相衝。中性資訊圈雖無判定，但為單句回饋增加裝飾與 `aria-hidden` 處理，沒有對應收益。
- 不加前綴字（如「注意：」「提示：」）：風控禁止安撫／祈使語氣的同一精神，且改動字面需重審。
- 不採 W-3 式「左邊框＋文字」的中性版本（`border-l-2 border-neutral-500`）：要有條件才出現，就又成了分支；常駐則是純裝飾。略過 > 0 若每次都被特別標出，W-2 舊規則會讓使用者習慣忽略，反而稀釋。
- 結構上的區隔用**換行**即可：冷卻句獨立成一行（見 12.5），不靠顏色、字重或圖示。

### 12.5 給 frontend-engineer 的 class 規格

實作對象：`AlertRulesSection.tsx:216-220` 的回饋區塊（字面以風控定稿為準；以下只規範樣式）。

```tsx
{evaluateMutation.isSuccess && (
  <div role="status" className="mt-2 space-y-1 text-sm leading-relaxed text-neutral-300 break-words">
    <p>{/* 第一句（恆顯示；(f) 特例句也用同一個 <p>） */}</p>
    {cooldownCount > 0 && <p>{/* 冷卻句（僅 P > 0） */}</p>}
  </div>
)}
```

規格逐項：

| 項目 | 規格 | 備註 |
|---|---|---|
| 容器 | 單一 `<div role="status">`，內含 1–2 個 `<p>` | 保持單一 live region，兩句一併被讀出；`role="status"` 不變 |
| 文字色 | `text-neutral-300`（#d4d4d4） | 任何計數組合都相同；**不得**有 emerald／amber／red 的條件分支 |
| 字級 | `text-sm`（14px，由現行 `text-xs` 放大一級） | 這是風控要求揭露的資訊，不宜維持 12px；`text-sm` 與頁內其他狀態訊息框一致。若 dev-lead 認為版面不允許，退而求其次可保留 `text-xs`，但不得再小 |
| 行高 | `leading-relaxed`（1.625） | 繁中多行段落可讀性；兩句最壞情況會到 3–4 行 |
| 間距 | 容器 `mt-2`；兩句之間 `space-y-1`（4px） | 冷卻句獨立一行，作為結構區隔 |
| 換行 | 預設換行＋`break-words` | 不得用 `whitespace-nowrap`、`truncate`、`overflow-hidden`、固定 `h-*`／`max-h-*`、`line-clamp-*` |
| 邊框／底色 | 無 | 與現況一致（現況就是無框純文字）；不要升級成 emerald 框，也不要新增中性框 |
| 圖示／前綴 | 無 | 見 12.4 |
| `text-balance` | 不用 | 避免數字與量詞被平衡斷行拆開，且與 W-3 的窄欄用途不同 |

### 12.6 驗收條件（qa-e2e 實機；單元測試併入 dev-lead 的 (a)–(f) 六案）

視覺／版面（Playwright 或實機，375×667 與 390×844 兩個 viewport 皆測）：

1. 觸發「手動檢查一次」後，回饋區塊在 375 與 390 寬皆**完整可見**：每一句的首字與句號都在視窗內，無水平捲軸（`document.documentElement.scrollWidth <= innerWidth`），無文字被裁切或省略號。
2. 最壞情況字面必測：展開例 (d)（兩句，含冷卻句）與 (e)（5 條全冷卻）；另測 (c) 全略過與 (f) 特例句。每種都完整顯示，行數自然增長，不撐破 `<section class="p-5">`，不與下方表單重疊（表單 `mt-4` 之上有足夠間距）。
3. 兩句分行：冷卻句在獨立一行起頭，不與第一句黏成同一行（以 DOM 兩個 `<p>` 為準）。
4. 顏色：回饋區塊（容器與 `<p>`）computed color 為 rgb(212, 212, 212)；**所有計數組合**皆相同；class 字串不含 `emerald`、`amber`、`red`、`rose`。
5. 對比度：以 computed color 對實際背景量測 ≥ 4.5:1（預期約 13–14:1）。
6. `role="status"` 仍存在且為單一元素；螢幕閱讀器順序為第一句 → 冷卻句。
7. 重複按壓：第二次按「手動檢查一次」，回饋區塊會重新出現（pending 期間消失、完成後重現），且內容反映第二次結果（例 (e)）。
8. 既有按鈕（`border-neutral-700 text-xs text-neutral-300`）與 h2 版面不受影響；標題列在 375 仍可換行（`flex-wrap` 不動）。

### 12.7 順帶發現（不屬本案顏色裁量，列給 dev-lead／PM）

- `evaluateMutation` 目前**只渲染 `isSuccess`**，沒有 `isError` 分支：若手動檢查請求失敗，畫面完全無回饋，使用者會看不出「失敗」與「還沒按」。建議補失敗框，樣式沿用頁內既有失敗樣式：`role="alert"`、`mt-2 rounded-md border border-red-900 bg-red-950/40 px-4 py-3 text-sm text-red-300`（同 `AlertRulesSection.tsx:305`）。失敗字面屬面向使用者文案，需另案交 creative-lead 出字、風控審。
- 若日後做 §10「查看略過原因」展開：連結／按鈕沿用頁內既有互動色 `text-sky-400 underline hover:text-sky-300`（同「編輯」），展開內容用 `text-xs text-neutral-400`；視覺規範待 PM 定範圍後另出。
