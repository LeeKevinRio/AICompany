## 1. sticky 狀態列高度上限

### 1.1 量測基準（qa-e2e 實測，非估算）

| | 1280×900 | 375×812 |
|---|---|---|
| 出清前（normal 模式，`mode_reason` 1 行） | 87px（9.7%） | 87px（10.7%） |
| 出清後重新整理（frozen，橫幅不在） | 87px（9.7%） | 127px（15.6%） |
| 出清成功、橫幅在 sticky 內（現況，要消除） | 273～405px | 379～531px |

375 寬的 127px 組成：border 1 + py-3 24 + 徽章列 34 + mt-2 8 + `mode_reason` 3 行 × 20 = 60。這個值是「橫幅不存在時的下限」，由逐字不可改的 `mode_reason` 決定，無法再縮。

### 1.2 定案

| 條件 | 375×812 | 1280×900 |
|---|---|---|
| **V-1 絕對上限**（測試條件：mode = `emergency_frozen`，快市未啟動；捲動 0／中段／底部皆成立） | ≤ **138px**（視窗 17%） | ≤ **108px**（視窗 12%） |
| **V-2 成功前後不變**（同寬度、同 mode、同 `/today` 資料，比較「成功且橫幅顯示中」與「重新整理後」） | 差 ≤ **±4px** | 差 ≤ **±4px** |
| 下方可讀區 | ≥ 視窗 **83%**（≥ 674px） | ≥ 視窗 88% |

理由：
- 375 的 138px = 基準 127px + 11px 餘量，只容許量測誤差與字型差，不容許再多一行（一行 = +20px）。
- 1280 的 108px = 基準 87px + 21px，容許 `mode_reason` 在 1024～1279 之間折成 2 行（+20px = 107px）。
- V-2 才是真正的判準：橫幅對狀態列的貢獻必須是 0px。V-1 是保險。

### 1.3 邊界與已知缺口

- **快市啟動時**：多一顆「快市」徽章與一行 `fast_market.reason`，375 寬時徽章列會折行、再多 1～3 行文字，狀態列自然超過 138px。這與橫幅無關，屬於狀態列本身的內容。
  - 此情境的判準只有 V-2（±4px）。
  - 同時不得超過 PM 的 162px／135px（沒有放寬）。若在「橫幅不存在」時就已超過，記為既有問題回報 PM，不算橫幅回歸，也不得用放寬上限處理。
  - 這個情境沒有實測值。**【r2 改】** r1 寫「列入 qa-automation 補測 P3」；PRD v2 FR-3／AC-32 已把它升為 **FR-3 的阻擋條件**（不是補測）：「快市啟動 + frozen + 長橫幅」下 V-9 必須通過，FR-3 才算完成。判準與失敗處理見 §4.2、§4.3。
- **【r2 補】後備外殼不受 V-1／V-2 約束**：`/today` 非 success 時的 sticky 外殼（§10，59px）只含觸發鈕，不是 V-1 所指的「狀態列」；它的高度以 V-33 為準。V-1、V-2 仍只量 `/today` 為 success 的狀態列。
- 不得用 `max-h`、`overflow-*`、`line-clamp` 壓狀態列來達標（等同摺疊揭露）。
- NavBar（`<header>`）不是 sticky（已確認 `NavBar.tsx` 與 `layout.tsx` 無 sticky），所以本頁唯一的 sticky 元素是狀態列，所有偏移量只需扣狀態列。

## 2. 橫幅離開 sticky 之後的規格

### 2.1 位置與順序（由上到下）

```
<NavBar>            （非 sticky）
<ModeStatusBar>     （sticky，唯一；`/today` 為 success 時）
<main>
  <h1>排程台</h1>
  <div role="status">  ← 常駐的空容器，橫幅在其中（見 2.4）
     橫幅（出清成功後才有）
  </div>
  歸屬語區塊（page 層 data.attribution）
  §6 總覽區塊（page_summary）
  警示（warnings）
  Cap1 揭露／規則集確認
  今日指令帳冊 → 部位快照 → 結算
</main>
```

**【r2 新】`/today` 為 pending 或 error 時的順序（FR-1、FR-13e）。** 狀態列內容依 `isSuccess` 閘門不渲染（FR-7c），但 `<main>` 內的 `role="status"` 容器與橫幅不在閘門內，永遠在 `<h1>` 之後：

```
<NavBar>                          （非 sticky）
<sticky 外殼：只有「全部出清」>      （§10；位置在 <main> 之前，與 success 時狀態列同一座標）
<main>
  <h1>排程台</h1>
  <div role="status">橫幅（若有）</div>     ← 先於骨架與錯誤面板
  pending：骨架（SkeletonBlock × 3，mt-6）
  error：  ErrorPanel「無法載入排程台資料」（mt-6）
</main>
```

- **橫幅在骨架／「無法載入排程台資料」之前。** 理由：橫幅是使用者剛做的不可逆操作的回執，且 `/today` 失敗時它是整頁唯一的 R 揭露處（風控底線：整頁 R 不得為 0 次），不能被一塊紅色錯誤面板擠到下面。錯誤面板是頁面層的載入狀態，優先序低於回執。
- 橫幅 `mt-4` 在兩種狀態下都由橫幅自己提供；骨架／錯誤面板原有的 `mt-6` 不改，因此橫幅存在時，橫幅下緣到錯誤面板（或骨架）上緣 = **24px**；橫幅不存在時，容器高度 0，錯誤面板與骨架的位置與實作前完全相同。
- 後備觸發鈕不在 `<main>` 內，不參與上述 flow，所以不會被骨架、錯誤面板、橫幅推動（版面細節見 §10）。

- **在 `<h1>` 之後、歸屬語之前。** 理由：
  - `<h1>` 留在原位，頁面標題不會被橫幅推走（現況 375 寬時 `<h1>` 被推到 y=706，貼近視窗底）。
  - 橫幅是「剛才這個操作的結果」，應該最先被讀到，優先於靜態的歸屬語與總覽。
  - 歸屬語仍在指令帳冊之上，沒有違反 R2「歸屬語是顯示指令的條件」。歸屬語被往下推的量最多是橫幅高度，且仍在可見、非摺疊的元素內。
- 不放 `<h1>` 之前：橫幅在 `<h1>` 之前會讓頁面沒有標題的首屏出現一大塊結果，閱讀順序顛倒。

### 2.2 視覺層級

橫幅是內容區裡「權重最高的一塊」，但仍是中性色階，不是警示。

| 屬性 | 值 | 說明 |
|---|---|---|
| 容器 class | `mt-4 w-full rounded-md border border-neutral-600 bg-neutral-900 p-4 text-sm text-neutral-200 scroll-mt-40 lg:scroll-mt-32` | 與 §4.4 的差異：`border-neutral-700` → `border-neutral-600`（見 §7 修訂）；移除 `max-w-sm`；新增 `mt-4 w-full` 與 `scroll-mt-*` |
| 圓角 | `rounded-md`，四邊同 | §4.4 規定「非帳冊列樣式」：不得有 `border-l-4`、不得 `rounded-none` |
| 顏色 | 只能用 `neutral-*`。**子樹不得出現 `rose`、`red`、`amber`、`orange` 等任何彩色 class** | §4.4 與 R13：這是使用者主動選擇的結果，不是錯誤 |
| `message` | `<p>` 繼承 `text-neutral-200`（14px / 20px 行高） | 維持現行 |
| `mode_reason`（條件顯示） | `<p className="mt-1 text-neutral-300">` | 維持現行 |
| `attribution`（非 null） | `<p className="mt-1 text-neutral-400">` | 維持現行 |
| `warnings`（非空） | `<ul className="mt-2 list-disc space-y-1 pl-5 text-neutral-400">` | 維持現行 |
| 不得加入 | 圖示、emoji、驚嘆號、粗體強調、陰影、動畫、transition、關閉鈕、摺疊 | 沒有新增可見字面 |
| 不得限制 | `max-h`、`overflow-*`、`line-clamp`、`truncate`、`hidden` | AC-5：橫幅完整可讀，無內部捲軸 |

對比（已用 sRGB 公式實算，底 `neutral-900` = `#171717`）：`neutral-200` 約 14.2:1、`neutral-300` 約 12.1:1、`neutral-400` 約 7.1:1，皆 ≥ 4.5:1。字級不低於現行（都是 `text-sm`）。

### 2.3 寬度

- **滿版：移除 `max-w-sm`**，容器寬度 = `<main>` 內容欄寬（375 寬 = 343px；1280 寬 = 992px）。
- `max-w-sm`（384px）是為 sticky 右欄設計的。放到內容區後，橫幅左右邊緣必須與下方歸屬語區塊、§6 總覽區塊的左右邊緣對齊（同一欄線），否則頁面出現第二條欄線。
- 不再用 `max-w-3xl` 之類縮窄：其他區塊都是滿欄寬，只有橫幅縮窄會讓它看起來像側欄。1280 寬時一行約 68 個全形字，與既有區塊相同。
- 對齊方式：左對齊（不是原本 `items-end` 的右對齊）。

### 2.4 間距與可及性

- 上間距：橫幅 `mt-4`（16px），距 `<h1>` 16px。
- 下間距：不需要加 `mb-*`，下一個區塊（歸屬語、總覽、警示都是 `mt-4`）提供 16px。橫幅與歸屬語之間 = 16px。
- 橫幅內部各段間距維持現行（`mt-1`／`mt-2`），不調整。
- **live region（should，不新增字面）**：頁面主內容區放一個**常駐**的空容器 `<div role="status">`，沒有任何 class（空時高度 0，不佔位）；橫幅在成功後才渲染進這個容器。原因：多數螢幕閱讀器只會宣告「已存在的 live region 內的變化」，整個 region 連同內容一起新增時常被略過。橫幅的 `mt-4` 寫在橫幅自己身上，不寫在 `role="status"` 的容器上。
- **【r2 補】容器位置在 `today.isSuccess` 閘門之外（FR-7a）**，`/today` 為 pending、error、success 三種狀態都存在，且**是同一個 DOM 節點**（狀態切換前後引用相同、不重新掛載）。理由：live region 要「先存在、後有內容」才可靠；若容器隨閘門卸載再掛載，橫幅出現時等於整個 region 新增，宣告可能被略過。驗收見 V-26。
- 焦點維持 N-163 已驗收的行為：成功後焦點回「全部出清」觸發鈕，不搬到橫幅。橫幅不可聚焦（不加 `tabIndex`）。

## 4. 成功後橫幅捲入視窗（FR-3）

### 4.1 規則

1. **觸發時機**：橫幅掛載（`isSuccess` 為真、橫幅首次渲染）後，執行一次。重新取得 `/today` 造成的重新渲染不得再次觸發捲動。
2. **是否捲動**：量測橫幅上緣 `top` 與狀態列下緣 `barBottom`。
   - 當 `top < barBottom + 16`（被遮住或貼太近）**或** `top > 0.66 × innerHeight`（落在視窗下方三分之一以外）時才捲動。
   - 否則不捲動（頁面頂端出清時，橫幅本來就在視窗內，不得產生多餘捲動，對應 AC-7）。
3. **怎麼捲**：`element.scrollIntoView({ block: "start", behavior: "auto" })`。
   - **不做平滑捲動**，無論使用者是否設定 `prefers-reduced-motion`。理由：這個流程的視覺基調是「無動畫」（§2.1、§4.2），且 `positions/page.tsx` 已有同樣的 `behavior: "auto"` 慣例，全域 CSS 沒有 `scroll-behavior`。這樣 reduced-motion 的要求是自然滿足，不需要另寫分支。
4. **偏移量**：寫在橫幅容器的 class 上：`scroll-mt-40 lg:scroll-mt-32`。

| 視窗寬 | scroll-margin-top | 狀態列上限（V-1） | 捲動後橫幅上緣到狀態列下緣的空隙 |
|---|---|---|---|
| < 1024（含 375） | `scroll-mt-40` = **160px** | 138px | 22px（上限時）～ 33px（127px 時） |
| ≥ 1024（含 1280） | `lg:scroll-mt-32` = **128px** | 108px | 20px（上限時）～ 41px（87px 時） |

### 4.2 為什麼用固定偏移，不用即時量測

出清當下，狀態列顯示舊模式（normal，`mode_reason` 1 行，375 寬 87px）；`/today` 重新取得後才變成 frozen（375 寬 127px）。如果用「捲動當下的狀態列高度」當偏移，捲完後狀態列變高 40px，橫幅上緣會被新的狀態列蓋住。固定偏移是依「最終狀態的上限 + 16px」算出，兩個時點都不會被遮。

固定偏移在快市啟動（狀態列超過上限）時可能不夠。**【r2 改】** r1 稱這是「§1.3 的未驗情境」；依 PRD v2 FR-3／AC-32 與風控裁示，它是 **FR-3 的阻擋條件**：「快市啟動 + frozen + 長橫幅（attribution、warnings 皆非空）」下 V-9 必須通過，FR-3 才算完成。若固定偏移下橫幅第一行被不透明的狀態列蓋住，改用「即時量測狀態列高度 + 16px」並重驗，不得為此放寬 §1 的上限。

## 5. 狀態列背景改為不透明

### 5.1 結論：改

`ModeStatusBar` 外層：`sticky top-0 z-10 border-b border-neutral-800 bg-black/95 backdrop-blur` → `sticky top-0 z-10 border-b border-neutral-800 bg-black`。

### 5.2 理由

- `bg-black/95` 讓下方內容以 5% 透出，再加上 `backdrop-blur`，內容邊緣在狀態列下緣會有模糊殘影。qa-e2e 的 `375x812-B1-after-success-scroll-mid.png` 狀態列下緣（y≈520～545）確實看到文字被切邊的疊影，與此相符（computed style 沒量，我不把它當作已證實，但修法成本為零，也沒有任何不改的理由）。
- 狀態列承載揭露類文案（`mode_reason`）。揭露文字底下不應有任何其他內容透出，這是可讀性的最低要求。
- 頁面底色就是 `bg-black`（`layout.tsx` body），不透明後在頁面頂端與現況肉眼無差別。
- 移除 `backdrop-blur` 同時消除 N-159 記載的副作用來源（`backdrop-filter` 會讓 `position: fixed` 子孫以它為 containing block）。對話框的 portal 保留不動（不回退 N-159 的修法，也不動 `EmergencyExitPortal.test.ts`）。

### 5.3 驗收

- **V-14**：狀態列 `getComputedStyle(...).backgroundColor` 為 `rgb(0, 0, 0)`（alpha = 1）；`backdropFilter` 為 `none`。或檢查 class：含 `bg-black`，不含 `bg-black/`、不含 `backdrop-blur`。
- **V-15（像素）**：捲動到某個有非黑背景的內容區塊（例如 §6 總覽區塊 `bg-neutral-900/60`）橫跨狀態列下緣時截圖，取狀態列底部的空白帶（`barRect.bottom − 4` 這一列，`py-3` 的下內距，沒有文字），水平置中的取樣點必須是 `#000000`，不得有灰階殘影。
- 既有的 `border-b border-neutral-800` 保留，作為狀態列與內容的分界。

## 10. 【r2 新】後備觸發鈕（FR-13e、AC-44）

範圍：`/today` 為 pending（含 `retry: 1` 的重試等待）、首次載入失敗、背景重新取得失敗（已有資料但 `isSuccess` 變 false）時，「全部出清」觸發鈕的位置與視覺。`/today` 為 success 時的位置與樣式不變（N-163、N-164 已驗收，PRD AC-45）。不新增任何可見字面，不用紅色。

### 10.1 結論

| 項 | 結論 |
|---|---|
| 位置 | `<NavBar>` 之後、`<main>` 之前的 **sticky 外殼**，觸發鈕靠右。座標與 `/today` 為 success 時狀態列內的觸發鈕**相同**（同一欄線、同一列 y）。 |
| 外殼 class | 外層 `sticky top-0 z-10 border-b border-neutral-800 bg-black`；內層 `mx-auto max-w-5xl px-4 py-3`；列 `flex items-center justify-end`。除列的 `justify-end`（取代 `flex-wrap … justify-between gap-3`）外，與 §5 的狀態列同款。 |
| 外殼高度 | **59px** = 邊框 1 + `py-3` 24 + 觸發鈕 34；375 與 1280 相同。 |
| 觸發鈕樣式 | 與現有完全相同：`rounded-md border border-neutral-600 bg-neutral-900 px-3 py-1.5 text-sm text-neutral-200 hover:bg-neutral-800`。不紅、不加粗、不加圖示。 |
| 狀態 | 不得 disabled、`aria-disabled`、隱藏、延後出現（EX-2）；首次繪製即在。 |
| 捲動 | **sticky**：捲動時留在視窗頂端，與 success 時同等容易找到（PRD FR-13e 預設期望）。 |
| 順序 | 外殼 → `<main>`：`<h1>` → 橫幅 → 骨架／`ErrorPanel`（§2.1）。 |
| 換位位移 | 觸發鈕 0px（V-34）；觸發鈕以下的內容位移 = 外殼高度差（見 10.5）。 |

### 10.2 為什麼是這個位置（備案與否決理由）

| 備案 | 結論 | 理由 |
|---|---|---|
| **同座標 sticky 外殼（採用）** | 採用 | 換位時觸發鈕不動；捲動時仍在；不與 `<main>` 內任何元素搶位；高度 59px，只佔 375×812 視窗 7.3%。 |
| 放在 `<h1>` 同列（`<main>` 內，標題右側） | 否決 | x、y 都與 success 時不同，換位位移大；非 sticky，頁面一捲動就找不到；橫幅或錯誤面板出現後位置還會被推走。 |
| 放在橫幅或 `ErrorPanel` 下方 | 否決 | 橫幅（有 `warnings` 時很高）會把它推出首屏，違反 AC-44「第一個畫面可見」；位置隨橫幅有無浮動。 |
| 固定在視窗右下角（`fixed` 浮動鈕） | 否決 | 375 寬會蓋住帳冊與內容；浮動鈕是一種視覺強調，與 §4.2「成本來自流程摩擦，不是視覺恐嚇」的基調相反；與 success 時位置無關，換位位移最大。 |
| 非 sticky 的頂部列 | 否決 | 首屏可見，但捲動後消失，與 success 時（sticky）不等價；`/today` 失敗時橫幅可能撐高頁面，使用者更需要它常駐。 |

### 10.4 與骨架、錯誤面板、橫幅的關係

- 觸發鈕在 `<main>` 之外，所以骨架（pending）與 `ErrorPanel`（error）不會與它重疊，也不會把它推動。
- 紅色的 `ErrorPanel`「無法載入排程台資料」維持原樣（PRD 範圍外：不改 `/today` 失敗畫面）。它是頁面層的載入狀態，與出清結果無關；觸發鈕在其上方、橫幅之上方，視覺上屬於「頁面常駐控制」，不屬於錯誤面板的一部分。
- 橫幅在 `ErrorPanel` 與骨架之上（§2.1）。橫幅有 `warnings` 而很高時，觸發鈕因為 sticky 仍在視窗內。

### 10.5 換位時的位移（推算，未實測）

`/today` 由非 success 轉 success（或反向）時，外殼高度由 59px 變為狀態列高度：

| 情境（快市未啟動） | 狀態列高度 | 外殼高度差 | 觸發鈕位移 | 觸發鈕以下內容的位移 |
|---|---|---|---|---|
| 1280，`mode_reason` 1 行 | 87px | +28px | **0** | +28px |
| 375，`emergency_frozen`（`mode_reason` 3 行） | 127px | +68px | **0** | +68px |
| 375，`normal`（`mode_reason` 1 行） | 87px | +28px | **0** | +28px |

- 觸發鈕本身不動，這是本節的設計目標：`/today` 在使用者伸手去按的瞬間恢復，觸發鈕也不會跑掉（PRD 風險 14）。
- 觸發鈕以下的內容會下移，**不補償**，不用 `min-height` 把外殼撐到 87／127px。理由：① 127px 的組成含 `mode_reason` 的行數，逐字不可改、無法預知；② 預留空白就是空洞（V-17 的同一原則）；③ pending → success、error → success 時，其下的骨架或錯誤面板本來就整塊被替換，位移對使用者不是新的視覺事件。
- 唯一持續存在的元素是橫幅。`/today` 恢復且 R 逐字相等時，橫幅內的 R 被移除（375：−64px；1280：−24px，見 §6.1），與外殼增高（+68／+28px）相抵，橫幅以下內容的淨位移約 **+4px**。橫幅上緣本身下移 +68／+28px，但與外殼下緣的距離不變（兩者同步下移），不會被遮。
- 這個換位位移與 §6.1 的橫幅 R 位移發生在同一個 commit（V-16），使用者看到的是一次整體調整，不是兩次。

### 10.6 捲動與可達

- 外殼 sticky，捲動 0／中段／底部都可見（V-33）。
- 59px 遠低於 V-1 的 138／108px，不會壓縮可讀區。
- 後備態下橫幅捲入視窗：外殼 59px，小於 `scroll-mt-40`（160）與 `lg:scroll-mt-32`（128），不會遮住橫幅；判準見 V-37 與 §4.2。

### 10.7 實作建議（不強制）

規範只定幾何與行為，寫法由 frontend-engineer 與 tech-architect 決定。art-lead 的建議：**sticky 外殼（外層、內層、列）常駐，觸發鈕不換 DOM 節點；只有外殼內的「左側徽章群、規則版本、`mode_reason`、快市文字」依 `today.isSuccess` 閘門掛載或卸載。** 這樣：

- 任一時刻觸發鈕恰好一個（AC-41）、換位位移為 0（V-34）；
- 觸發鈕不會被卸載，對話框步驟、焦點不被重置（AC-42），關閉後不會把焦點還給已卸載的舊節點（AC-43、FR-13f）。
- 不放寬 FR-7c：狀態列的內容仍只依 `isSuccess` 渲染，不用舊資料。外殼常駐不等於狀態列常駐；外殼內不得渲染任何模式相關內容。

若採兩個節點（success 時在狀態列內、非 success 時在獨立外殼），須通過 V-29～V-38，焦點歸還另依 AC-43。

## 11. 【r2 新】出清失敗面板的色階評估（風控 suggested）

### 11.1 結論

**改用中性色階。不用琥珀色，也不沿用紅色。** 面板是出清專用的新元件，不改共用 `ErrorPanel`（PRD FR-8b、AC-29）。字面由風控定稿，一字不改，本規範不重述（來源：風控裁示「3. NB-6 失敗字面」、後端 `wording.py` 常數）。

### 11.2 評估

評估的問題不是「哪個顏色看起來比較有警示感」，而是：**哪個色階不替使用者先下判斷。** 風控定稿的字面刻意把三種狀態並列（尚未處理／只暫停 R 系列／已暫停且已產生賣出指令），第 3 句還說明再次送出的後果。顏色一旦偏向任何一邊，就會蓋過文字。

| 色階 | 現有語意（站內） | 對讀法的影響 | 結論 |
|---|---|---|---|
| 紅色（現行 `ErrorPanel`：`border-red-900 bg-red-950/40 text-red-300`） | 站內 `rose` 在建議卡為「加碼／偏多」，在 status 軸為「已違反」；紅色一般語意為「失敗、被拒絕」 | 強化「失敗 = 沒處理」，與字面「也可能已暫停並已產生賣出指令」相反；使用者讀到紅色就會先認定沒送出，風險是不看第 3 句而再次送出，N-166 合併前會多產生一組賣出指令。另外 r1 的紅線「不用紅色」就是針對出清流程，現行紅色面板本來就與它不一致 | **否決** |
| 琥珀色（`amber`） | 站內已有三種用途：M1 防守模式徽章（`bg-amber-950/60 border-amber-700 text-amber-200`）、備援資料源徽章（`bg-amber-900/40 text-amber-300`）、建議卡「續抱」 | 比紅色弱，但仍是「警告」語意，偏向「有問題、未完成」；更大的問題是**同一頁面撞色義**：排程台在防守模式時狀態列就是琥珀色徽章，使用者可能把這塊琥珀面板讀成「防守模式相關」或「資料源備援」。現有規範的色彙軸原則就是避免同一色相在兩處代表不同意思 | **否決** |
| **中性（`neutral-*`）** | 本流程既有基調：觸發鈕、橫幅、對話框全部是中性色階 | 不偏向任何一個狀態，把判斷交給文字；與「成本來自流程摩擦，不是視覺恐嚇」一致 | **採用** |

中性色階的風險是「被當成對話框裡的一般文字而漏看」。靠**結構**補，不靠色相補：

- 有邊框的獨立方塊，邊框用 `border-neutral-500`（比對話框的 `border-neutral-700` 亮兩階），與 Step 3 上方的核取句清單（無邊框、`text-neutral-300`）一眼可分。
- 標籤一行用 `font-semibold text-neutral-100`，內文 `text-neutral-300`，有明確的標籤 / 內文階層。
- 位置在核取句清單與兩顆按鈕之間（現有 ErrorPanel 的同一個位置），在使用者視線進入按鈕前必經。
- `role="alert"`（與現有 `ErrorPanel` 相同），輔助科技會即時宣告；這不新增可見字面。
- 焦點不搬動，仍在「確認送出全部出清」（N-163）。

另一個相關事實：失敗面板（`mutation.isError`）與成功橫幅（`mutation.isSuccess`）出自同一個 mutation，不會同時存在，所以兩者都是中性色階不會造成混淆；且一個在對話框內、一個在主內容區。

### 11.3 規格

位置：對話框 Step 3，`<ul>`（核取句覆述）之後、按鈕列之前，取代現有的 `<div className="mt-3"><ErrorPanel … /></div>`。只在出清失敗時出現。

```
<div role="alert" class="mt-4 rounded-md border border-neutral-500 bg-neutral-900 px-4 py-3">
  <p class="text-sm font-semibold text-neutral-100">{標籤}</p>
  <p class="mt-2 text-sm text-neutral-300">{內文第 1 句}</p>
  <p class="mt-2 text-sm text-neutral-300">{內文第 2 句}</p>
  <p class="mt-2 text-sm text-neutral-300">{內文第 3 句}</p>
</div>
```

| 屬性 | 值 |
|---|---|
| 標籤 | 1 個 `<p>`，`text-sm font-semibold text-neutral-100` |
| 內文 | 3 個獨立 `<p>`，`text-sm text-neutral-300`，各 `mt-2`；不合併、不用 `<br>` |
| 容器 | `mt-4 rounded-md border border-neutral-500 bg-neutral-900 px-4 py-3`，`role="alert"` |
| 不得有 | 彩色 class、`border-l-4`（與帳冊列區分）、圖示、emoji、驚嘆號、陰影、動畫、`transition`、關閉鈕、`max-h`／`overflow-*`／`line-clamp`、`tabIndex` |
| 不得附加 | 後端原文、HTTP 狀態碼、例外訊息（PRD FR-8b） |
| 對比（sRGB 實算） | `neutral-100` 對 `neutral-900` 約 16.4:1；`neutral-300` 對 `neutral-900` 約 12.1:1；邊框 `neutral-500` 對對話框底 `neutral-950` 約 4.2:1（非文字，≥ 3:1） |

只用現有 Tailwind token，與觸發鈕、橫幅、對話框用的是同一組中性色階，沒有新增色階。

對話框高度：面板在 375 寬約佔 11～13 行（估算，未實測），Step 3 整體可能超過矮視窗。對話框容器本來就有 `max-h-[calc(100dvh-2rem)] overflow-y-auto`，由它自己捲動，不新增巢狀捲動；V-41 驗在 375×812 與 375×667 下面板標籤行可見、全文可讀、兩顆按鈕可達。

### 11.4 風險與知會

- 這是視覺決定，不是風控必改項。已把「為什麼不是紅色、琥珀色」寫清楚，供風控知悉；若風控認為中性色階使使用者更容易漏看，應回報 art-lead，改走「加強結構」（例如加粗邊框到 `border-neutral-400`），不改成彩色。
- 面板字面屬 NB-6 定稿，N-166 合併時必須連同字面回審（PRD D-2）。色階結論不因此改變；回審若修改字面，面板結構（4 段落）若變，須回頭改 V-40。
