## 1. sticky 狀態列高度上限

### 1.1 量測基準（qa-e2e 實測，非估算）

| | 1280×900 | 375×812 |
|---|---|---|
| 出清前（normal 模式，`mode_reason` 1 行） | 87px（9.7%） | 87px（10.7%） |
| 出清後重新整理（frozen，橫幅不在） | 87px（9.7%） | 127px（15.6%） |
| 出清成功、橫幅在 sticky 內（現況，要消除） | 273～405px | 379～531px |

375 寬的 127px 組成：border 1 + py-3 24 + 徽章列 34 + mt-2 8 + `mode_reason` 3 行 × 20 = 60。這個值是「橫幅不存在時的下限」，由逐字不可改的 `mode_reason` 決定，無法再縮。

### 1.2 定案

| 條件 | 375×812 | 1280×900 |
|---|---|---|
| **V-1 絕對上限**（測試條件：mode = `emergency_frozen`，快市未啟動；捲動 0／中段／底部皆成立） | ≤ **138px**（視窗 17%） | ≤ **108px**（視窗 12%） |
| **V-2 成功前後不變**（同寬度、同 mode、同 `/today` 資料，比較「成功且橫幅顯示中」與「重新整理後」） | 差 ≤ **±4px** | 差 ≤ **±4px** |
| 下方可讀區 | ≥ 視窗 **83%**（≥ 674px） | ≥ 視窗 88% |

理由：
- 375 的 138px = 基準 127px + 11px 餘量，只容許量測誤差與字型差，不容許再多一行（一行 = +20px）。
- 1280 的 108px = 基準 87px + 21px，容許 `mode_reason` 在 1024～1279 之間折成 2 行（+20px = 107px）。
- V-2 才是真正的判準：橫幅對狀態列的貢獻必須是 0px。V-1 是保險。

### 1.3 邊界與已知缺口

- **快市啟動時**：多一顆「快市」徽章與一行 `fast_market.reason`，375 寬時徽章列會折行、再多 1～3 行文字，狀態列自然超過 138px。這與橫幅無關，屬於狀態列本身的內容。
  - 此情境的判準只有 V-2（±4px）。
  - 同時不得超過 PM 的 162px／135px（沒有放寬）。若在「橫幅不存在」時就已超過，記為既有問題回報 PM，不算橫幅回歸，也不得用放寬上限處理。
  - 這個情境沒有實測值。**【r2 改】** r1 寫「列入 qa-automation 補測 P3」；PRD v2 FR-3／AC-32 已把它升為 **FR-3 的阻擋條件**（不是補測）：「快市啟動 + frozen + 長橫幅」下 V-9 必須通過，FR-3 才算完成。判準與失敗處理見 §4.2、§4.3。
- **【r3 改】** r2 此處寫「後備外殼（59px）不受 V-1／V-2 約束」；r3 方案 B 已沒有後備外殼，`/today` 非 success 時整頁沒有任何 sticky 元素（V-36），本條作廢。V-1、V-2 只量 `/today` 為 success 的狀態列，不變。
- 不得用 `max-h`、`overflow-*`、`line-clamp` 壓狀態列來達標（等同摺疊揭露）。
- NavBar（`<header>`）不是 sticky（已確認 `NavBar.tsx` 與 `layout.tsx` 無 sticky），所以本頁唯一的 sticky 元素是狀態列，所有偏移量只需扣狀態列。

## 2. 橫幅離開 sticky 之後的規格

### 2.1 位置與順序（由上到下）

```
<NavBar>            （非 sticky）
<ModeStatusBar>     （sticky，唯一；`/today` 為 success 時）
<main>
  <h1>排程台</h1>
  <div role="status">  ← 常駐的空容器，橫幅在其中（見 2.4）
     橫幅（出清成功後才有）
  </div>
  歸屬語區塊（page 層 data.attribution）
  §6 總覽區塊（page_summary）
  警示（warnings）
  Cap1 揭露／規則集確認
  今日指令帳冊 → 部位快照 → 結算
</main>
```

**【r2 新、r3 改】`/today` 為 pending 或 error 時的順序（FR-1、FR-13e）。** 狀態列內容依 `isSuccess` 閘門不渲染（FR-7c），整頁沒有 sticky 元素。`<main>` 內的 `role="status"` 容器與橫幅不在閘門內。後備觸發鈕與 `<h1>` 同列（§10，方案 B）：

```
<NavBar>                                   （非 sticky）
<main>
  [h1 列]  <h1>排程台</h1>          [全部出清]     ← 後備觸發鈕，靠右；success 時這一列只有 <h1>
  <div role="status">橫幅（若有）</div>             ← 先於骨架與錯誤面板；同一個 DOM 節點
  pending：骨架（SkeletonBlock × 3，mt-6）
  error：  ErrorPanel「無法載入排程台資料」（mt-6）  ← 不共用框線、不含觸發鈕
</main>
```

- **橫幅在骨架／「無法載入排程台資料」之前。** 理由：橫幅是使用者剛做的不可逆操作的回執，且 `/today` 失敗時它是整頁唯一的 R 揭露處（風控底線：整頁 R 不得為 0 次），不能被一塊紅色錯誤面板擠到下面。錯誤面板是頁面層的載入狀態，優先序低於回執。
- 橫幅 `mt-4` 在兩種狀態下都由橫幅自己提供；骨架／錯誤面板原有的 `mt-6` 不改，因此橫幅存在時，橫幅下緣到錯誤面板（或骨架）上緣 = **24px**；橫幅不存在時，容器高度 0，錯誤面板與骨架的位置與實作前完全相同（`<h1>` 列下緣到它 24px）。
- **【r3 新】h1 列在 success 與非 success 時都存在**（success 時只有 `<h1>`）。`role="status"` 容器是這一列的下一個兄弟元素，不因觸發鈕掛載或卸載而重新掛載（V-26）。
- 觸發鈕不在橫幅容器內、不在骨架內、不在 `ErrorPanel` 內，也不插在橫幅與歸屬語／帳冊之間（風控 F-5）。與 `ErrorPanel` 或骨架之間留 24px 間距，不共用框線（V-32）。

（以下為 r1 的位置理由，內容不變。）

- **在 `<h1>` 之後、歸屬語之前。** 理由：
  - `<h1>` 留在原位，頁面標題不會被橫幅推走（現況 375 寬時 `<h1>` 被推到 y=706，貼近視窗底）。
  - 橫幅是「剛才這個操作的結果」，應該最先被讀到，優先於靜態的歸屬語與總覽。
  - 歸屬語仍在指令帳冊之上，沒有違反 R2「歸屬語是顯示指令的條件」。歸屬語被往下推的量最多是橫幅高度，且仍在可見、非摺疊的元素內。
- 不放 `<h1>` 之前：橫幅在 `<h1>` 之前會讓頁面沒有標題的首屏出現一大塊結果，閱讀順序顛倒。

### 2.2 視覺層級

橫幅是內容區裡「權重最高的一塊」，但仍是中性色階，不是警示。

| 屬性 | 值 | 說明 |
|---|---|---|
| 容器 class | `mt-4 w-full rounded-md border border-neutral-600 bg-neutral-900 p-4 text-sm text-neutral-200 scroll-mt-40 lg:scroll-mt-32` | 與 §4.4 的差異：`border-neutral-700` → `border-neutral-600`（見 §7 修訂）；移除 `max-w-sm`；新增 `mt-4 w-full` 與 `scroll-mt-*` |
| 圓角 | `rounded-md`，四邊同 | §4.4 規定「非帳冊列樣式」：不得有 `border-l-4`、不得 `rounded-none` |
| 顏色 | 只能用 `neutral-*`。**子樹不得出現 `rose`、`red`、`amber`、`orange` 等任何彩色 class** | §4.4 與 R13：這是使用者主動選擇的結果，不是錯誤 |
| `message` | `<p>` 繼承 `text-neutral-200`（14px / 20px 行高） | 維持現行 |
| `mode_reason`（條件顯示） | `<p className="mt-1 text-neutral-300">` | 維持現行 |
| `attribution`（非 null） | `<p className="mt-1 text-neutral-400">` | 維持現行 |
| `warnings`（非空） | `<ul className="mt-2 list-disc space-y-1 pl-5 text-neutral-400">` | 維持現行 |
| 不得加入 | 圖示、emoji、驚嘆號、粗體強調、陰影、動畫、transition、關閉鈕、摺疊 | 沒有新增可見字面 |
| 不得限制 | `max-h`、`overflow-*`、`line-clamp`、`truncate`、`hidden` | AC-5：橫幅完整可讀，無內部捲軸 |

對比（已用 sRGB 公式實算，底 `neutral-900` = `#171717`）：`neutral-200` 約 14.2:1、`neutral-300` 約 12.1:1、`neutral-400` 約 7.1:1，皆 ≥ 4.5:1。字級不低於現行（都是 `text-sm`）。

### 2.3 寬度

- **滿版：移除 `max-w-sm`**，容器寬度 = `<main>` 內容欄寬（375 寬 = 343px；1280 寬 = 992px）。
- `max-w-sm`（384px）是為 sticky 右欄設計的。放到內容區後，橫幅左右邊緣必須與下方歸屬語區塊、§6 總覽區塊的左右邊緣對齊（同一欄線），否則頁面出現第二條欄線。
- 不再用 `max-w-3xl` 之類縮窄：其他區塊都是滿欄寬，只有橫幅縮窄會讓它看起來像側欄。1280 寬時一行約 68 個全形字，與既有區塊相同。
- 對齊方式：左對齊（不是原本 `items-end` 的右對齊）。

### 2.4 間距與可及性

- 上間距：橫幅 `mt-4`（16px），距 `<h1>` 16px。
- 下間距：不需要加 `mb-*`，下一個區塊（歸屬語、總覽、警示都是 `mt-4`）提供 16px。橫幅與歸屬語之間 = 16px。
- 橫幅內部各段間距維持現行（`mt-1`／`mt-2`），不調整。
- **live region（should，不新增字面）**：頁面主內容區放一個**常駐**的空容器 `<div role="status">`，沒有任何 class（空時高度 0，不佔位）；橫幅在成功後才渲染進這個容器。原因：多數螢幕閱讀器只會宣告「已存在的 live region 內的變化」，整個 region 連同內容一起新增時常被略過。橫幅的 `mt-4` 寫在橫幅自己身上，不寫在 `role="status"` 的容器上。
- **【r2 補】容器位置在 `today.isSuccess` 閘門之外（FR-7a）**，`/today` 為 pending、error、success 三種狀態都存在，且**是同一個 DOM 節點**（狀態切換前後引用相同、不重新掛載）。理由：live region 要「先存在、後有內容」才可靠；若容器隨閘門卸載再掛載，橫幅出現時等於整個 region 新增，宣告可能被略過。驗收見 V-26。
- 焦點維持 N-163 已驗收的行為：成功後焦點回「全部出清」觸發鈕，不搬到橫幅。橫幅不可聚焦（不加 `tabIndex`）。

## 3. NB-7：1280 寬的單列排版

橫幅離開後，狀態列只剩既有的 flex 列，不需新增 class。驗收規格：

| 項目 | 規格 |
|---|---|
| 容器 | 維持 `flex flex-wrap items-center justify-between gap-3`（不改） |
| 排列（視窗寬 ≥ 1024，快市未啟動） | 左：模式徽章＋規則版本；右：「全部出清」。**同一列**，兩者垂直中心差 ≤ 1px，左右邊緣分別對齊 `<main>` 內容欄左右邊緣 |
| 列高 | 34px（徽章 `py-1.5` + `text-sm` 20px + 邊框 2px）；整條狀態列 = 1 + 24 + 34 + 8 + 20 = **87px**（`mode_reason` 1 行） |

## 4. 成功後橫幅捲入視窗（FR-3）

### 4.1 規則

1. **觸發時機**：橫幅掛載（`isSuccess` 為真、橫幅首次渲染）後，執行一次。重新取得 `/today` 造成的重新渲染不得再次觸發捲動。
2. **是否捲動**：量測橫幅上緣 `top` 與狀態列下緣 `barBottom`。
   - 當 `top < barBottom + 16`（被遮住或貼太近）**或** `top > 0.66 × innerHeight`（落在視窗下方三分之一以外）時才捲動。
   - 否則不捲動（頁面頂端出清時，橫幅本來就在視窗內，不得產生多餘捲動，對應 AC-7）。
3. **怎麼捲**：`element.scrollIntoView({ block: "start", behavior: "auto" })`。
   - **不做平滑捲動**，無論使用者是否設定 `prefers-reduced-motion`。理由：這個流程的視覺基調是「無動畫」（§2.1、§4.2），且 `positions/page.tsx` 已有同樣的 `behavior: "auto"` 慣例，全域 CSS 沒有 `scroll-behavior`。這樣 reduced-motion 的要求是自然滿足，不需要另寫分支。
4. **偏移量**：寫在橫幅容器的 class 上：`scroll-mt-40 lg:scroll-mt-32`。

| 視窗寬 | scroll-margin-top | 狀態列上限（V-1） | 捲動後橫幅上緣到狀態列下緣的空隙 |
|---|---|---|---|
| < 1024（含 375） | `scroll-mt-40` = **160px** | 138px | 22px（上限時）～ 33px（127px 時） |
| ≥ 1024（含 1280） | `lg:scroll-mt-32` = **128px** | 108px | 20px（上限時）～ 41px（87px 時） |

### 4.2 為什麼用固定偏移，不用即時量測

出清當下，狀態列顯示舊模式（normal，`mode_reason` 1 行，375 寬 87px）；`/today` 重新取得後才變成 frozen（375 寬 127px）。如果用「捲動當下的狀態列高度」當偏移，捲完後狀態列變高 40px，橫幅上緣會被新的狀態列蓋住。固定偏移是依「最終狀態的上限 + 16px」算出，兩個時點都不會被遮。

固定偏移在快市啟動（狀態列超過上限）時可能不夠。**【r2 改】** r1 稱這是「§1.3 的未驗情境」；依 PRD v2 FR-3／AC-32 與風控裁示，它是 **FR-3 的阻擋條件**：「快市啟動 + frozen + 長橫幅（attribution、warnings 皆非空）」下 V-9 必須通過，FR-3 才算完成。若固定偏移下橫幅第一行被不透明的狀態列蓋住，改用「即時量測狀態列高度 + 16px」並重驗，不得為此放寬 §1 的上限。

**【r2 補、r3 改】`/today` 非 success 時的偏移。** r2 以 59px 外殼計算；r3 方案 B 沒有外殼，此時整頁沒有 sticky 元素（V-36）。§4.1 的「是否捲動」判定裡，狀態列下緣 `barBottom` 在沒有 sticky 元素時取 0（只剩「`top > 0.66 × innerHeight`」與「`top < 16`」兩個條件）。捲動後橫幅上緣離視窗頂 160px（375）／128px（1280），只是上方多一段空白，沒有遮住任何東西。V-9 的 12～48px 區間只在 `/today` 為 success 時量；非 success 時的判準是 V-37。
**【r3 新】焦點回歸不得抵銷這次捲動（風控 F-7）。** 出清成功後焦點回到觸發鈕。方案 B 的觸發鈕不是 sticky，`focus()` 預設會捲動；必須用 `focus({ preventScroll: true })` 或等效做法，使焦點回歸前後 `scrollY` 差 0，橫幅第一行「EMERGENCY_EXIT 已受理：……」仍在視窗內（V-12、V-38）。

### 4.3 驗收（對應 AC-6、AC-7）

- **V-9（已捲到底後出清，375×812）**：成功且 `/today` 完成同步後，`bannerRect.top − barRect.bottom` 在 **12px～48px** 之間。**【r2 補】** 另須在「快市啟動 + `emergency_frozen` + 長橫幅（`attribution`、`warnings` 皆非空），375×812 與 1280×900 兩個寬度」下通過，且橫幅第一行完全可見；此條件為 FR-3 的阻擋條件（PRD AC-32），不是 P3 補測。
- **V-10（頁面頂端出清，1280×900）**：成功後 `window.scrollY` 與出清前相同（差 0px，不產生多餘捲動）。
- **V-11（頁面頂端出清，375×812）**：同上，`scrollY` 不變。
- **V-12**【r3 補】：成功後 `document.activeElement` 是「全部出清」觸發鈕。**r3 補（風控 F-7、A-9）：在 `/today` 為 success、pending、首次載入失敗、背景重新取得失敗四種狀態下都成立**（兩個寬度）。非 success 的三種狀態下，焦點不得落在 `ErrorPanel`「無法載入排程台資料」或其中任何控制項、不得落在 `<body>`；焦點回歸前後 `scrollY` 差 0（FR-3 的那一次捲動除外，且須用 `preventScroll`）；焦點回歸後橫幅第一行「EMERGENCY_EXIT 已受理：……」的矩形完整在視窗內（`top ≥ 0` 且 `bottom ≤ innerHeight`），沒有被捲出畫面，也沒有被任何元素遮住。

## 5. 狀態列背景改為不透明

### 5.1 結論：改

`ModeStatusBar` 外層：`sticky top-0 z-10 border-b border-neutral-800 bg-black/95 backdrop-blur` → `sticky top-0 z-10 border-b border-neutral-800 bg-black`。

### 5.2 理由

- `bg-black/95` 讓下方內容以 5% 透出，再加上 `backdrop-blur`，內容邊緣在狀態列下緣會有模糊殘影。qa-e2e 的 `375x812-B1-after-success-scroll-mid.png` 狀態列下緣（y≈520～545）確實看到文字被切邊的疊影，與此相符（computed style 沒量，我不把它當作已證實，但修法成本為零，也沒有任何不改的理由）。
- 狀態列承載揭露類文案（`mode_reason`）。揭露文字底下不應有任何其他內容透出，這是可讀性的最低要求。
- 頁面底色就是 `bg-black`（`layout.tsx` body），不透明後在頁面頂端與現況肉眼無差別。
- 移除 `backdrop-blur` 同時消除 N-159 記載的副作用來源（`backdrop-filter` 會讓 `position: fixed` 子孫以它為 containing block）。對話框的 portal 保留不動（不回退 N-159 的修法，也不動 `EmergencyExitPortal.test.ts`）。

### 5.3 驗收

- **V-14**：狀態列 `getComputedStyle(...).backgroundColor` 為 `rgb(0, 0, 0)`（alpha = 1）；`backdropFilter` 為 `none`。或檢查 class：含 `bg-black`，不含 `bg-black/`、不含 `backdrop-blur`。
- **V-15（像素）**：捲動到某個有非黑背景的內容區塊（例如 §6 總覽區塊 `bg-neutral-900/60`）橫跨狀態列下緣時截圖，取狀態列底部的空白帶（`barRect.bottom − 4` 這一列，`py-3` 的下內距，沒有文字），水平置中的取樣點必須是 `#000000`，不得有灰階殘影。
- 既有的 `border-b border-neutral-800` 保留，作為狀態列與內容的分界。

### 10.1 A-1 的決定：採方案 B（非 sticky、放在 `<main>` 內，與 `<h1>` 同列靠右）

風控給的二選一：方案 A（保留 sticky，但非 success 時外殼不得有任何背景、`border-b`、橫條）、方案 B（非 sticky，放在 `<main>` 內）。**我選方案 B。** 理由：

1. **方案 A 的「空位」問題沒有真正消除。** 外殼若維持 sticky 且在 `<main>` 之前，就是在狀態列所在的那個座標留一條 59px 的空帶、觸發鈕靠右。即使沒有背景與底線，使用者的視線仍會落在「頁面上方、狀態列該在的地方，只有一顆按鈕」。NB-6 第 2 句偏偏就叫人看那裡。方案 B 讓那個座標完全空出來（`/today` 失敗時，頁面頂端只有 NavBar，緊接著是 `<h1>`），「頁面上方的狀態列」就明確不存在。
2. **方案 A 的 sticky 觸發鈕會變成浮動鈕。** 外殼透明後，捲動時只有一顆不透明按鈕浮在內容上，會蓋住下方文字（r2 否決右下浮動鈕時的同一個理由）；若外殼要擋住下方的點擊，還得靠 `pointer-events` 繞過，變複雜。
3. **方案 B 與風控偏好一致**（Q8 裁示：偏好放在 `<main>` 裡、非 sticky、靠右、排在骨架與失敗面板之前）。
4. **方案 B 的代價與補救。**
   - 代價一：不是 sticky，捲動後觸發鈕會離開視窗，不如 success 時「同等容易找到」。補救：非 success 時頁面很短（只有 `<h1>`、橫幅、一塊骨架或錯誤面板）；觸發鈕在 h1 列、橫幅之上，位置不受橫幅高度影響，首屏必在視窗內（V-31）。`/today` 恢復後觸發鈕回到 sticky 的狀態列。
   - 代價二：換位時觸發鈕有垂直位移，不再是 0（V-34：約 20px，水平 0）。`/today` 在使用者伸手的瞬間恢復，觸發鈕只會往上移約 20px，按下去只是開對話框，後面還有三步（PRD 風險 14，風控知悉：沒有揭露面疑慮）。
   - 代價三：非 success 轉 success 時，狀態列掛上，頁面內容整體下移狀態列的高度（87／127px），這與 r1 就存在的行為相同（pending → success 本來就會掛上狀態列），見 10.5。

為何與 `<h1>` 同列、而不是 `<h1>` 下方一列：同列版面緊湊、少佔約 50px 高度（375×812 上橫幅與錯誤面板更早進入視野）、換位的垂直位移比下方一列小得多（約 20px 對 68px）。風控的「h1 下方」是偏好，不是條件。

結論表：

| 項 | 結論 |
|---|---|
| 位置 | `<main>` 內，h1 列最右。h1 列 = `flex items-center justify-between`，左 `<h1>`，右觸發鈕。success 時這一列只有 `<h1>`（列一直存在，`role="status"` 容器是它的下一個兄弟）。 |
| 外觀 | 觸發鈕本身以外沒有任何視覺：h1 列沒有背景、邊框、陰影、分隔線；觸發鈕左側只有 `<h1>`，沒有空位、沒有「—」、沒有任何模式文字。 |
| 觸發鈕樣式 | 與現有完全相同：`rounded-md border border-neutral-600 bg-neutral-900 px-3 py-1.5 text-sm text-neutral-200 hover:bg-neutral-800`。不紅、不加粗、不加圖示。 |
| 狀態 | 不得 disabled、`aria-disabled`、隱藏、延後出現（EX-2）；首次繪製即在。 |
| 捲動 | 非 sticky（`position: static`）。非 success 時整頁沒有 sticky、fixed 元素。 |
| 焦點回歸 | 用 `focus({ preventScroll: true })` 或等效做法（風控 F-7），不抵銷 FR-3 的捲入；焦點不落在 `ErrorPanel`、不落在 `<body>`。 |
| 順序 | `<h1>` 列 → 橫幅 → 骨架／`ErrorPanel`（§2.1）。 |
| 換位位移 | 水平 0；垂直約 +20px（非 success 較低）。見 10.5。 |

### 10.2 備案與否決理由

| 備案 | 結論 | 理由 |
|---|---|---|
| 方案 B：`<main>` 內、與 `<h1>` 同列靠右（採用） | **採用** | 見 10.1。 |
| 方案 A：sticky 透明外殼，只有觸發鈕 | 否決 | 頂端空帶仍在狀態列座標，且觸發鈕浮在內容上；見 10.1。 |
| r2 方案：sticky 外殼，同款 `bg-black border-b`，59px | **風控 VETO，撤回** | 像狀態列，且有徽章空位。 |
| `<h1>` 下方獨立一列 | 否決 | 可行但多佔約 50px、換位垂直位移約 68px；沒有比同列更好。 |
| 放在橫幅或 `ErrorPanel` 下方 | 否決 | 橫幅（有 `warnings` 時很高）會把它推出首屏，違反 AC-44「第一個畫面可見」；放進 `ErrorPanel` 更被風控 F-5 明確禁止。 |
| 固定在視窗右下角（`fixed` 浮動鈕） | 否決 | 375 寬會蓋住內容；浮動鈕是視覺強調，與 §4.2「成本來自流程摩擦，不是視覺恐嚇」相反。 |

### 10.4 與骨架、錯誤面板、橫幅的關係（風控 F-5）

- 觸發鈕**不在**橫幅容器內、不在骨架內、不在 `ErrorPanel` 內，也不與它們共用框線；h1 列到 `ErrorPanel` 或骨架的間距是 24px（V-32）。
- 觸發鈕不是 `ErrorPanel` 的動作鈕，沒有任何視覺或結構把它綁成「載入失敗的解法」（風控：那會被讀成載入失敗的解法是出清，屬於誘導）。
- 紅色的 `ErrorPanel`「無法載入排程台資料」維持原樣（PRD 範圍外）。它是頁面層的載入狀態，與出清結果無關。
- 橫幅在 h1 列之下、`ErrorPanel` 與骨架之上（§2.1）。觸發鈕不插在橫幅與歸屬語、帳冊之間。
- 觸發鈕旁邊**不加任何揭露**（風控 Q8 裁示 2：預先否決「無法取得目前模式」類字面），也不加 `aria-describedby`、`title`、tooltip、旁註（V-35）。

### 10.5 換位時的位移（推算，未實測）

`/today` 在非 success 與 success 之間切換時：

| 項 | 非 success → success | 備註 |
|---|---|---|
| 觸發鈕水平 | 0 | 右緣同一條欄線 |
| 觸發鈕垂直 | 由距 `<main>` 上緣 32px，移到狀態列內距狀態列上緣 12px：**上移約 20px**（以 NavBar 下緣為基準；success 時 `<main>` 在狀態列之下，下面「頁面內容下移」是另一回事） | V-34 |
| 頁面內容（h1 列以下） | 下移狀態列高度減 1px：1280 約 +86px；375 `emergency_frozen` 約 +126px；375 `normal` 約 +86px | 狀態列掛上，與 r1 就存在的行為相同；不補償、不預留空位 |
| 橫幅上緣 | 下移同上（約 +85／+125px） | 橫幅內 R 同時被移除（375：−64px；1280：−24px，見 §6.1），橫幅以下內容淨位移約 +61px |
| 橫幅被遮？ | 否 | 狀態列同時掛上，頁面整體下移，橫幅不會被新掛上的狀態列蓋住（V-9 在同步後量） |

- 頁面內容下移 86／126px 是方案 B 相對 r2 的主要代價（r2 外殼已佔 59px，下移只有 28／68px）。在 `scrollY` = 0 時 Chrome 的 scroll anchoring 不介入，所以使用者會看到整頁往下掉一次；已捲動時 scroll anchoring 通常會保持視覺位置穩定（機制推論，未實測）。這個位移只發生在 `/today` 由失敗或載入中恢復的那一次，且 pending → success 的狀態列掛上本來就是 r1 的既有行為。
- 這個位移與 §6.1 的橫幅 R 位移發生在同一個 commit（V-16），使用者看到的是一次整體調整。
- 不用 `min-height` 或空白占位去補償，理由：空洞比位移更糟（V-17 的同一原則），也會再度形成「頁面上方有一塊東西」的外觀，與 10.1 的理由 1 相衝突。

### 10.6 捲動與可達

- 觸發鈕非 sticky：捲動後離開視窗。補救見 10.1 代價一：非 success 時頁面短、觸發鈕在橫幅之上、首屏必可見。
- 後備態下橫幅捲入視窗：沒有 sticky 元素，不會遮住橫幅（V-37、§4.2）。
- 焦點回歸使用 `preventScroll`，不把橫幅第一行捲出畫面（V-12、V-38(c)）。

### 10.7 實作約束（取代 r2 的「外殼常駐」建議）

規範只定幾何與行為，寫法由 frontend-engineer 與 tech-architect 決定。**r2 的「外殼常駐、只卸載徽章群」建議已撤回，不得採用**（風控：那會讓 `/today` 失敗時看到「同一條狀態列上的徽章消失了」，比 r2 更糟）。約束：

- 觸發鈕任一時刻恰好 1 個（AC-41）；success 時在狀態列內，非 success 時在 h1 列內。實作用單一元件、依 `today.isSuccess` 切換位置，或用兩個節點，都可；須通過 V-29～V-38。
- 對話框狀態（步驟、勾選、送出鎖）與觸發鈕所在位置脫鉤（AC-42、FR-13d）；焦點歸還給關閉當下存在的那一顆（FR-13f），不得還給已卸載的舊節點。
- 橫幅 `mode_reason` 的隱藏條件綁 `today.isSuccess`，**不得**綁「觸發鈕容器或 h1 列存在」（V-16；風控 F-6、FE-2）。
- h1 列在 success 時只有 `<h1>`、非 success 時 `<h1>` 與觸發鈕；`role="status"` 容器是 h1 列的下一個兄弟，不隨觸發鈕掛載或卸載而重新掛載（V-26）。

### 10.8 限制與未驗

- **快市啟動 + 375 寬**：success 狀態列的徽章列可能折行，把觸發鈕擠到第二列，此時換位的垂直位移比 V-34 的約 20px 再多約一個列高，V-34 的 ±3px 不適用，只記錄實測值回報 art-lead。要消除它得改狀態列版型，那會動 N-163、N-164 已驗收的位置，不在本次範圍。
- **hydration 前**：頁面是 client component，觸發鈕在 hydration 完成前不可互動。這是實作層問題，不是視覺規範能解；qa-e2e 在 V-29 量首次繪製時請同時記錄「可互動時間」，如有明顯落差回報 PM 與 tech-architect。
- NavBar 高度未實測，所以 V-31 只驗「在視窗內」，不寫死 y 值。
- 全節的位移與幾何數值為推算，qa-e2e 實測後若與推算不符，以實測為準，並回報 art-lead 修訂本節。

## 11. 【r2 新、r3 補】出清失敗面板的色階評估（風控 suggested）

風控 r2 核對裁示：**方向 CONDITIONAL APPROVE**（同意以撞色義否決琥珀、以結構補漏看風險、不需升到 `border-neutral-400`）。r3 補上的條件：V-41 的標籤行可見性（A-6）、「出清失敗加上 `/today` 失敗」組合（A-7、V-46）、「不會同時存在」前提更正（A-8，見 11.2 末）、V-38／V-41 以修訂降級句與 N1 量測（A-5）。色階結論不變。

### 11.1 結論

**改用中性色階。不用琥珀色，也不沿用紅色。** 面板是出清專用的新元件，不改共用 `ErrorPanel`（PRD FR-8b、AC-29）。字面由風控定稿，一字不改，本規範不重述（來源：風控裁示「3. NB-6 失敗字面」、後端 `wording.py` 常數）。

### 11.2 評估

評估的問題不是「哪個顏色看起來比較有警示感」，而是：**哪個色階不替使用者先下判斷。** 風控定稿的字面刻意把三種狀態並列（尚未處理／只暫停 R 系列／已暫停且已產生賣出指令），第 3 句還說明再次送出的後果。顏色一旦偏向任何一邊，就會蓋過文字。

| 色階 | 現有語意（站內） | 對讀法的影響 | 結論 |
|---|---|---|---|
| 紅色（現行 `ErrorPanel`：`border-red-900 bg-red-950/40 text-red-300`） | 站內 `rose` 在建議卡為「加碼／偏多」，在 status 軸為「已違反」；紅色一般語意為「失敗、被拒絕」 | 強化「失敗 = 沒處理」，與字面「也可能已暫停並已產生賣出指令」相反；使用者讀到紅色就會先認定沒送出，風險是不看第 3 句而再次送出，N-166 合併前會多產生一組賣出指令。另外 r1 的紅線「不用紅色」就是針對出清流程，現行紅色面板本來就與它不一致 | **否決** |
| 琥珀色（`amber`） | 站內已有三種用途：M1 防守模式徽章（`bg-amber-950/60 border-amber-700 text-amber-200`）、備援資料源徽章（`bg-amber-900/40 text-amber-300`）、建議卡「續抱」 | 比紅色弱，但仍是「警告」語意，偏向「有問題、未完成」；更大的問題是**同一頁面撞色義**：排程台在防守模式時狀態列就是琥珀色徽章，使用者可能把這塊琥珀面板讀成「防守模式相關」或「資料源備援」。現有規範的色彙軸原則就是避免同一色相在兩處代表不同意思 | **否決** |
| **中性（`neutral-*`）** | 本流程既有基調：觸發鈕、橫幅、對話框全部是中性色階 | 不偏向任何一個狀態，把判斷交給文字；與「成本來自流程摩擦，不是視覺恐嚇」一致 | **採用** |

中性色階的風險是「被當成對話框裡的一般文字而漏看」。靠**結構**補，不靠色相補：

- 有邊框的獨立方塊，邊框用 `border-neutral-500`（比對話框的 `border-neutral-700` 亮兩階），與 Step 3 上方的核取句清單（無邊框、`text-neutral-300`）一眼可分。
- 標籤一行用 `font-semibold text-neutral-100`，內文 `text-neutral-300`，有明確的標籤 / 內文階層。
- 位置在核取句清單與兩顆按鈕之間（現有 ErrorPanel 的同一個位置），在使用者視線進入按鈕前必經。
- `role="alert"`（與現有 `ErrorPanel` 相同），輔助科技會即時宣告；這不新增可見字面。
- 焦點不搬動，仍在「確認送出全部出清」（N-163）。

**【r3 改（風控 A-8、逐條意見 5）】** r2 此處寫「失敗面板（`mutation.isError`）與成功橫幅（`mutation.isSuccess`）出自同一個 mutation，不會同時存在」，**此前提不再成立**：依 V-42，橫幅在第二次送出的進行中與失敗後都保留（它是第一次受理的回執，仍為真），所以「舊橫幅（主內容區）」與「失敗面板（對話框內）」**可能同時在畫面上**。兩者都是中性色階，仍不會混淆，理由改為：① 容器不同：失敗面板在 `fixed` 的對話框內，橫幅在遮罩之後的主內容區（遮罩為 `bg-black/70`）；② 邊框不同：失敗面板 `border-neutral-500`，橫幅 `border-neutral-600`，兩者不是同一條；③ 兩者說的都是真的：橫幅說「第一次已受理」，面板說「這一次無法確認」，不互相矛盾。風控請知悉這個同時出現的組合。

### 11.3 規格

位置：對話框 Step 3，`<ul>`（核取句覆述）之後、按鈕列之前，取代現有的 `<div className="mt-3"><ErrorPanel … /></div>`。只在出清失敗時出現。

```
<div role="alert" class="mt-4 rounded-md border border-neutral-500 bg-neutral-900 px-4 py-3">
  <p class="text-sm font-semibold text-neutral-100">{標籤}</p>
  <p class="mt-2 text-sm text-neutral-300">{內文第 1 句}</p>
  <p class="mt-2 text-sm text-neutral-300">{內文第 2 句}</p>
  <p class="mt-2 text-sm text-neutral-300">{內文第 3 句}</p>
</div>
```

| 屬性 | 值 |
|---|---|
| 標籤 | 1 個 `<p>`，`text-sm font-semibold text-neutral-100` |
| 內文 | 3 個獨立 `<p>`，`text-sm text-neutral-300`，各 `mt-2`；不合併、不用 `<br>` |
| 容器 | `mt-4 rounded-md border border-neutral-500 bg-neutral-900 px-4 py-3`，`role="alert"` |
| 不得有 | 彩色 class、`border-l-4`（與帳冊列區分）、圖示、emoji、驚嘆號、陰影、動畫、`transition`、關閉鈕、`max-h`／`overflow-*`／`line-clamp`、`tabIndex` |
| 不得附加 | 後端原文、HTTP 狀態碼、例外訊息（PRD FR-8b） |
| 對比（sRGB 實算） | `neutral-100` 對 `neutral-900` 約 16.4:1；`neutral-300` 對 `neutral-900` 約 12.1:1；邊框 `neutral-500` 對對話框底 `neutral-950` 約 4.2:1（非文字，≥ 3:1） |

只用現有 Tailwind token，與觸發鈕、橫幅、對話框用的是同一組中性色階，沒有新增色階。

對話框高度：面板在 375 寬約佔 11～13 行（估算，未實測），Step 3 整體可能超過矮視窗。對話框容器本來就有 `max-h-[calc(100dvh-2rem)] overflow-y-auto`，由它自己捲動，不新增巢狀捲動；V-41 驗在 375×812 與 375×667 下面板標籤行可見、全文可讀、兩顆按鈕可達。**【r3 補】** 最高的組合是：Q8 修訂降級句（比舊句長）＋ N1 在畫面上（§13）＋ 失敗面板，同時出現在 375×667；V-41 要在這個組合下量。標籤行要在不靠使用者操作、不靠 scroll anchoring 的情況下進入可視區（程式捲對話框容器，`behavior: "auto"`，不搬動焦點），見 V-41。
**【r3 補】** 失敗面板放在 N1 的 `role="status"` 容器之外：N1 在標題下方、清單上方；失敗面板在清單下方、按鈕上方。兩者各有自己的容器，互不包含（V-43）。

### 11.4 風險與知會

- 這是視覺決定，不是風控必改項。已把「為什麼不是紅色、琥珀色」寫清楚，供風控知悉；若風控認為中性色階使使用者更容易漏看，應回報 art-lead，改走「加強結構」（例如加粗邊框到 `border-neutral-400`），不改成彩色。

## 13. 【r3 新】N1：核取句更新提示（風控 Q11 R-6、F-10）

N1 是本規範唯一新增的可見字面（見檔頭）。字面由風控 Q11 裁示逐字定稿，後端 `wording.py` 新增常數、前端鏡射並加守門測試（F-10）；**本規範不重述、不代擬字面**，只定版面。顯示條件的行為（R-1～R-5）屬實作範圍，本節只轉成可量測的視覺與結構約束。

### 13.1 結論

| 項 | 結論 |
|---|---|
| 位置 | 對話框標題（`<h2>`）之下、當步內容（Step 2 核取清單／Step 3 覆述清單）之上 |
| 容器 | 一個常駐的 `<div role="status">`（polite），**沒有任何 class**（空時高度 0，不佔位）；N1 只是往容器裡放內容。容器在 Step 2、Step 3 之間以及 R-5 退回第 2 步時是**同一個 DOM 節點** |
| 樣式 | `<p className="mt-3 text-sm text-neutral-300">`；不加 `font-*`、不沿用 §11 的外框與底色、沒有彩色、圖示、動畫、倒數、關閉鈕 |
| 顯示條件 | 只在「系統清掉至少一個勾選」時；不在開啟時、不在 R-2、不在正常流程（V-45） |
| 保留 | 一直保留到對話框關閉，不需關閉鈕，不擋任何操作 |
| 焦點 | 不搬動；R-5 退回第 2 步時，焦點依現行規則落在第 2 步標題 |

### 13.2 結構

```
<dialog 內層面板>
  <h2 tabIndex=-1>{當步標題}</h2>        ← 步驟標題（文字依步驟）；焦點目標
  <div role="status">                     ← 常駐、無 class、空時高 0；跨步驟同一節點
    <p class="mt-3 text-sm text-neutral-300">{N1}</p>   ← 只在條件成立時
  </div>
  Step 2：核取清單（`<ul class="mt-4 …">`）＋「取消」「我已閱讀，繼續」
  Step 3：覆述清單（`<ul class="mt-4 …">`）＋〔失敗面板，§11〕＋「取消」「確認送出全部出清」
</dialog 內層面板>
```

- 「容器跨步驟同一節點」的視覺與可及性理由：R-5 退回第 2 步時，Step 2 的內容整塊重新渲染；若容器在 Step 2 的子樹內，退步時容器與 N1 同時新增，多數螢幕閱讀器會略過。容器必須先存在。
- 這意味著標題與容器不在步驟專屬子樹內。標題是否合併成單一 `<h2>`（文字依步驟切換）或以其他寫法達成「容器同一節點 + 位置在標題下方」，由 frontend-engineer 決定；須通過 V-43。標題移動焦點的現行規則（每一步移到標題，不移到核取框）不變。
- 失敗面板（§11）與 N1 容器互不包含：N1 在清單上方，失敗面板在清單下方。

### 13.3 樣式與版面數值

- class：容器無；N1 的 `<p>`：`mt-3 text-sm text-neutral-300`（14px／行高 20px；`mt-3` = 12px）。
- 標題到 N1：12px；N1 到清單：清單原有的 `mt-4`（16px）。
- 對比（sRGB 實算）：`neutral-300` 對對話框底 `neutral-950` 約 13.3:1，≥ 4.5:1。
- 為什麼不加外框或粗體：N1 不是警示，是一句事實告知（風控：沒有勸阻、恫嚇或倒數；EX-5、H-1）；加外框會讓它與 §11 的失敗面板搶層級，也會讓使用者以為出事了。中性、與清單同級的文字就夠，使用者重新勾選時就在清單上方，視線自然經過。
- 高度影響（估算，未實測）：N1 約 38 字，375 寬對話框內文寬約 301px（每行約 21 字）佔 2 行，加 `mt-3` 約 52px；1280 寬約 470px（每行約 33 字）也佔 2 行。N1 出現時對話框會變高 52px，容器本來就有 `max-h` + `overflow-y-auto`，不新增巢狀捲動。這就是 V-38(b)、V-41 要在「修訂降級句＋N1＋失敗面板」最高組合下量的原因。

### 13.4 顯示條件（行為面，轉成約束，寫法交 frontend-engineer 與 tech-architect）

依風控 Q11 R-6：

- 只在**至少一個勾選被系統清掉**時顯示，使 N1 的字面恆真（變動的那一句原本沒勾，就不顯示）。
- 不在以下情況顯示：對話框開啟時、R-2（`/today` 轉為非 success，不換句）、正常流程。
- 一直保留到對話框關閉；關閉後重新開啟時不出現。
- 不是前置條件，不擋送出；重新勾選後照常可以繼續（EX-2）。

量測見 V-43（結構）、V-44（樣式與互動）、V-45（顯示條件）。
