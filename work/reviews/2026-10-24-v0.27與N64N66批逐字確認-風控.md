#### 三、各點理由

- **(i) 甲案**：決定 run 取「範圍快照含該範圍、`run_id` 最大」，是確定性規則，和 `plan_coverage_log` 的取法一致。之後的 run 只能改原因，不能減列，被蓋過的原因留在 `basis_json` 並公開揭露。
- **(ii) 聯集**：可以堵住「把範圍移出自選來消掉缺日列」，方向偏嚴。ADR-0027 失效條件 F-3 的計數單位留給 N-85，已照實並陳。
- **(iii) 第 2 項判為不變**，我同意 quant 第二節 B 的五點，另補兩點：
  - 第 2 項放在第 3 項之後反而行不通。寫入 `late=1` 的補跑 run，end 是 `ok`，範圍又在它的快照裡，照第 3 項會被判成帳目矛盾而停擺。所以「第 2 項優先」是讓這份列舉能一致運作的唯一讀法，不是在兩種既有讀法之間挑一種寬鬆的。
  - 它沒有開出新的操縱路徑。截止後補記本來就是 D-7 第 6 點的既有機制，單一 run 時代也會產生 `late_only`；而且缺日列寫入後只增不改，可以改變原因的時間窗只到首次稽核為止。另外，這種日子會計入逾時率（門檻 10%），被蓋過的原因也照 V27-03 分列揭露。
  - `db_restored` 先於 `late_only` 會讓 TG-c 的計數變多，屬於收緊面。
  - 殘餘：若 N-85 決定排除 `late_only`，這一項就會有放寬面，已登記要在 N-85 具名評估。
- **(iv) fail-closed**：查證過 `outcome` 的判定（L1011）。`partial` 等於至少有一個範圍被拒寫，`ok` 等於全部寫入，所以「end 為 `ok`／`partial`、範圍不在 `refused_scopes_json`、又沒有紀錄」只可能是資料損毀，停擺是正確的。已知會觸發的正常路徑是 claim 晚於 run 才登記（N-84），已列為定案前的前提，也寫進下方給 CEO 的句子。
- **(v)**：兩張表和 `forecast_run`／`_end` 同型，B-4 也寫了與重放的雙向隔離。「記錄一步嘗試」避開了 v0.26 的「嘗試紀錄」，可以接受。新值目前只在內部。
- **(vi)**：歸屬窗是半開區間，彼此不重疊，FL-76 (g) 測了兩個邊界。歸屬錯日的話，`record_start_failed` 與 `scheduler_down` 都計入 TG-c，不會造成放寬。
- **(vii)**：補了 R-2、R-3 之後，「被蓋過的原因不刪除」才有完整的規格與測試支撐。
- **(viii)**：沒有 end 的 run 本來就能從 `forecast_run` 與 `forecast_run_end` 直接查出來，沒有任何告警或統計依賴 FL-18 原句的字面，資訊也保留在 `basis_json`。所以不屬測試放寬。
- **V27-03**：九值 0 也照列，`'*'` 和逐範圍的列分開計，各格加總可以大於列數。逐字由 creative-lead 起草再送我審，格式核可。上畫面時仍適用 D-8 L1193「統計只到 `gap_judged_through`」。

> 系統每天晚上自動記錄預測，同一天有時會重試好幾次。這次在設計文件與事先宣告裡同時講清楚三件事。
> 第一，「那天哪幾檔沒記到」以當天所有執行合起來算，事後把某檔從清單拿掉也消不掉，所以缺漏筆數只會比「只看最後一次」的算法多、不會少；「缺漏太多就重審」的門檻也只會更早觸發。「為什麼沒記到」以最後一次有處理到該檔的那次為準，前幾次的原因另外留底、公開分列，不會被抹掉。這幾條登記在事先宣告裡，之後要改必須走正式的規則變更流程。
> 第二，以前程式在一開始準備階段就出錯時，會被誤記成「排程根本沒跑」；現在會先寫一筆「已開始執行」的紀錄，分得出兩者。為此資料庫多兩張表：預測帳由 18 張變 20 張，全部由 23 張變 25 張。
> 第三，補一句指引：歷史重放區塊只要出現，就要在最上方常駐寫明資料取自非官方來源 yfinance、狀態是備援源（backup）。
> 以上不改變命中率、樣本數等驗證統計的算法。代價有兩個。一是帳本若出現前後對不上（正常情況下不應發生），每天的缺漏檢查與統計更新會整個暫停，直到查明；目前已知會觸發的一種情形，是在已經記錄過的日子新增追蹤項目，所以相關規則（N-84）定案前，不在這種日子新增。二是如果連「已開始執行」那一筆都寫不進資料庫（例如硬碟出問題），那天仍只能記成「排程沒跑」，要靠維運通知才會發現。這次只需要您知悉，不需要另外同意。
