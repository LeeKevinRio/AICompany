### [RC-427] 選路徑丙，以及理由

**為什麼不選乙（照 RC-415 全面改寫）**
- 改寫成 CEO 文件，等於維持「兩套 CEO 啟動方式」。這正是 tech-architect 要防的混用根源。
- 手冊裡獨有的內容（attestation、暖身回補、`sqlite3 .backup`、問題碼、第 6、7 節）本來就不該由 CEO 操作，改寫成給 CEO 的版本也沒有意義。
- CEO 的日常啟動已經寫在 README 第 12～15 行（「CEO 日常用的是原生路徑：Windows 雙擊 `dev-up.bat`」，我讀過字面）。

**為什麼不只做甲**
- 讀者會從很多地方直接跳進節內，看不到檔頭：
  - 搜尋 `STOCK_DESK_DB_PATH` 或「備份」；
  - ADR 的行號引用，例如 ADR-0026 引用手冊 `:90-94`、`:236-240`、`:290-306`；
  - CEO 文件的引用，例如 `work/dispatch/2026-11-13-R2探測手動步驟-備用.md` 第 43 行寫「照主機部署手冊、用 `$env:STOCK_DESK_DB_PATH` 指定」。
- 0.3 節距檔頭約 80 行，0.2 節的 PowerShell 片段和 `'User'`／`'Machine'` 永久設定也一樣遠。
- 照做的後果是每晚拒絕記錄、資料分成兩份，而且永久設定不會自己消失。這不是「讀過檔頭就會記得」可以承擔的風險。
- **回答你的問題：檔頭標註不足以防止只翻到 0.3 節的讀者照做。**

**為什麼不刪行**
- 刪行等於改寫 devops-sre 依 ADR-0012 維護的工程內容。
- 0.3 那段寫法在記錄期間對工程人員也是錯的，但改不改、怎麼改，屬於 tech-architect 和 devops-sre 的判斷（RC-436），不是我在法遵閘門上該代改的。
- 就地插一行警示，已經足以讓 CEO 讀者在危險段落前停下來。

### [RC-433] 要不要 CEO 決定或知悉：不必決定，要知悉（required）

**不需要 CEO 事先決定，理由：**
- C-52 裁定的是部署形態：判定程序與 API 程序從同一個 git checkout 直接執行。`dev-up.bat` 從同一個 checkout 的 `backend` 目錄啟動兩者，本身就符合這個形態。
- 手冊只是一種執行方式的說明，改判它的讀者不改變 C-52。
- tech-architect 已裁示 C-52 沒有錯，缺的 attestation 已依 RC-420 告知 CEO。
- ADR-0012 把手冊交給 devops-sre 維護，這一點也不變。
- 只有 CEO 推翻改判時，才改走乙（RC-415 全面改寫）。

**要讓 CEO 知悉，理由：**
- 檔頭原本寫「適用對象：CEO」。他過去可能讀過，甚至照做過。
- CEO 可以推翻這個改判，前提是他知道有這件事。

### [RC-437] R2 不擴大；另訂 R3-0（收到畫面行時）與 R3（請再執行一次）

**R2 套在「CEO 剛回報啟動失敗」上，錯在三處：**
- 依據不是狀態報告；

  - 之後一定要接著送 R3。不送 R3 時（例如 devops-sre 判斷要先由 coordinator 引導安裝），另外的解除字面先送我。
