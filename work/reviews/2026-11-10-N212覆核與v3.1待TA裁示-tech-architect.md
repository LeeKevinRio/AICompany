- **A-1 P-1／P-2／P-3 的資料表（採用，附約束）**
  - **裁示**：只用 `playbook_batches` 依 symbol 分組，不過濾 status，不併入 `playbook_symbols`。
  - **理由**：這不是「偏保守的近似」，而是 ADR-0043 D1 的定義本身：
    - D1 第 1 點：名單 = `playbook_batches` 的 distinct symbol，列一律不刪；
    - D1 第 2 點：啟用 = 在名單內，且 `entry_stopped = 0`；
    - 部署前 `entry_stopped` 欄還不存在（v3.1 §1 才以 `DEFAULT 0` 新增），所以部署當下名單內每一檔都是啟用，`COUNT(DISTINCT symbol)` 就等於 D1 的啟用檔數。
    - 只有 closed、skipped 批次的標的照樣算，這與 D1 一致。
  - **約束**：
    - p3.sql 不得加 `entry_stopped` 條件。部署前會因缺欄而 ERROR。
    - p3.sql 檔頭加英文註解，說明只在 N-207 部署前的 schema 上等於 D1 啟用檔數，N-207 部署後不得再用本檔判定 R-14。
- **A-2 斷號定義（採用）**
  - **裁示**：斷號 = `COUNT(*) <> MAX - MIN + 1`。「最小值不等於 1」與「最小值小於 1」是可以重疊的兩個獨立計數。
  - **理由**：
    - (symbol, batch_no) 是 PK（`store.py:87`）。整數下 COUNT 不會大於跨距，等號成立就等於連號。
    - P-1 加上 P-2 的五個計數，合起來恰好等於「批號集合不等於 {1..bpt}，或含非整數」，沒有漏判。
    - 「最小值小於 1」要單列，因為它另外觸發 RC-12「立即回報 CEO」。
- **A-3 第五個計數（採用）**
  - **裁示**：依列計。
  - **理由**：§9.3「輸出形狀」與〔TA-v3補-10〕第 4 點都寫「列數」；STOP 只看是否大於 0，依列或依檔都不影響判定。
- **A-4 P-3 的輸出形狀（採用兩值，不改單值）**
  - **裁示**：輸出 `<distinct 檔數>,<n_targets>`。
  - **理由**：§9.3 STOP-2 有三種處置（大於就停、小於就揭露、等於 0 走首次設定），需要兩個值。單值的布林會丟掉「小於」與「等於 0」兩種情形。
  - **讀法補充**（併入〔TA-v3補-9〕「空表時每一項都回 0」）：這句指資料計數。P-3 的第二值是參數回顯，不受此限。空表時輸出 `0,5`，正確。

  - **理由**：見 B-4；N-207 鎖內讀參數的 on_date 確定為 `today_tpe`。
- **A-7 參數值型別（採用 ERROR 方向；修改寫法，required）**
  - **現況問題**：現行 `typeof(COALESCE(json_extract(...), 3))` 有兩個缺口：
    - 遇到 JSON `null` 會靜默套用 3／5。但 app 的 `RuleParams.model_validate` 遇到 `null` 會失敗，結果是盤點說正常、app 卻 500。
    - payload 不是 JSON 物件時（例如 `'3'`）也會套用預設值。
  - **改法**：p1、p2 的 bpt CTE 改成下列寫法；p3 的 nt CTE 照同一型式，key 換成 `n_targets`、預設值換成 5。
    ```sql
    bpt AS (
      SELECT CASE
        WHEN NOT EXISTS (SELECT 1 FROM cur) THEN 3
        WHEN json_type((SELECT payload FROM cur)) <> 'object' THEN NULL
        WHEN json_type((SELECT payload FROM cur), '$.batches_per_target') IS NULL THEN 3
        WHEN json_type((SELECT payload FROM cur), '$.batches_per_target') = 'integer'
          THEN json_extract((SELECT payload FROM cur), '$.batches_per_target')
        ELSE NULL
      END AS v
    )
    ```
  - **外層守衛**：改為 `CASE WHEN (SELECT v FROM bpt) IS NULL THEN NULL ELSE ... END`，仍然強制求值。
  - **語意**：
    - key 不存在：套用預設值，與 pydantic 的欄位預設一致；
    - key 是 `null`、`true`、實數、文字，或 payload 不是物件：ERROR，視為未完成盤點，回 TA；
    - payload 不是合法 JSON：`json_type` 會出錯，ERROR。
  - **方向**：這些情形只可能來自 app 外的寫入，ERROR 是多停、不會少停。這是對〔TA-v3補-10〕第 2 點的補充，不改原意。
  - **測試**：補 JSON `null`、`true`、`3.0`、payload 為 `'3'`、key 不存在五種情形的斷言。

  - `scripts/` 不計入覆蓋率可以接受，前提是 `tests/test_n207_preflight.py` 在 CI 的全套 pytest 內執行。

- **多值逗號格式（接受，附約束）**
  - 每格必須是整數，runner 印出前以 `type(v) is int` 檢查。
  - 任一格是 NULL 或非整數時，整行印 `<項目>\tERROR`，並以非 0 結束。
  - 以 `,` 串接，不加空白。
  - 順序固定為 §9.3「輸出形狀」的列序。P-2 依序是：最大值大於 bpt、最小值不等於 1、最小值小於 1、斷號、非整數列數。
  - 順序寫在 runner 的 docstring，並由測試逐字釘住整行輸出。

1. **「不在名單內」的位置與範圍（採用：排在第 1、第 2 步之間，標記與取消都拒絕）**
   - **新順序**：
     - (1) 凍結且 `new_value == 1` → `portfolio_frozen`；
     - (1′) 該檔不在名單內 → `RosterRefusal("not_in_roster")`，標記與取消都適用；
     - (2) `history_readable` 為 False → `hv_history_unreadable`；
     - (3) 冪等；
     - (4) 寫入。
   - **理由**：FR-29 寫「勾選或取消……僅限名單內標的」，取消也在範圍內。排在冪等之前，可避免對不在名單內、T = 0 的取消回「冪等成功」。
   - **判定來源**：只用 `RosterFacts` 內該檔 `(batch_no, batch_round, status)` 清單是否非空（D1 第 1 點），不得另寫查詢。停止新進場的標的仍在名單內。
   - **字面**：
     - 標記 → W-05l（原文寫「不能標記高波動」）；
     - 取消 → 走 B-5 的一般失敗分支（`reason_code: "not_in_roster"`）。W-05l 套在取消上不實；這條路只可能來自直接打 API，名單頁不會出現。
   - **後續**：送風控確認（屬加嚴）。PM 在 AC-38 加一個 Given「不在名單；嘗試取消；拒絕、零寫入、不顯示『已取消』」。
2. **冪等計畫的 `hv_changed_on`（採用 (a)）**
   - **裁示**：`plan_change` 在第 (1′)、(2) 步通過後，呼叫一次 `high_volatility_changed_on(...)`，第 3 步的零寫入計畫與第 4 步的寫入計畫都帶這個值。C11 的 `ValueError` 條款不改。
   - **理由**：ADR-0043 D7 第 3 點的「預覽摘要」明列「預覽時算出的 `changed_on`」，沒有排除冪等。代價是冪等預覽跨台北日期時多一次 `preview_stale`，方向是多拒絕。app/ 內唯一的呼叫點仍是 `plan_change`。
   - **測試**：
     - 同日冪等確認：零寫入、沒有稽核列；
     - 跨台北日期確認：`preview_stale`、零寫入。
3. **`_read_roster_max_date` 的呼叫者（採用：直接呼叫的允許清單，不改 ADR）；`roster_facts` 加 `op`：確認**
