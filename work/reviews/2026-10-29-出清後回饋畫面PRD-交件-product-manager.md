## NB-6 後端查證結果（讀 code，未執行）

`POST /emergency-exit` 的流程是：讀取資料，接著 `freeze_emergency` 寫入凍結狀態（獨立連線與交易），再 `record_directives` 寫入稽核日誌（另一個獨立交易），最後才在 API 層組回應。整段沒有單一交易，沒有請求 ID 或冪等鍵，回應也沒有「已處理」標記。

500 因此可能落在三種狀態，前端無法區分：
- 凍結寫入前出錯：整筆未處理。
- 兩個交易之間出錯：凍結已生效，但稽核日誌沒有出清的指令列。
- 兩個交易都完成後、組回應時出錯：已完整處理。

網路層失敗同理。

**結論：文案不得暗示已處理或未處理。**
- 改用「結果不確定」的中性語氣，並導向狀態列。
- 失敗後自動重新取得 `/today`，用現有的模式徽章當事實來源。
- 不封鎖重試，因為出口零摩擦（EX-2）。
- 我另擬了一組草案文案，標明「僅供風控審閱，不得直接上線」。定稿前維持現行文案。
- 現行 label「送出失敗」的「失敗」二字在不確定情境下可能被讀成「沒處理」，一併請風控判斷。

與 N-166 的關聯：我的讀 code 觀察是 `record_directives` 是 INSERT，我沒看到出清會關閉批次，所以重複呼叫可能重複寫入稽核日誌。這是觀察，不是驗證，請 tech-architect 確認。
