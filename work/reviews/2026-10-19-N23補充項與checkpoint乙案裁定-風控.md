## 一、本次結論

**整體可以修改後核可，沒有否決。** checkpoint 採**乙案**；甲案只在乙案的前提查證不過時才用。

最重要的八項發現：

1. **TA (2b) 漏改一處列舉。** ADR L1309（D-11 第 2 點 N-5 甲案）也寫了 `cause ∈ {suspended_f3, db_restored}`。只改 L1811 的話，兩處列舉會不一致。
2. **R-Q7-3 沒有處理事先宣告那一側。** v0.21 §4.2「更正作業揭露」(iv)（L977）仍以 `market_scan_restore_suspected = 1` 作為唯一來源。第二批落檔後，這一句的揭露會變弱，要與 (1e) 同批改。
3. **空的市場 DB 沒有定義，會在不該放行時放行（fail-open）。** `MAX(run_id)` 是 null 時，「r_now < 參考值」沒有定義，守衛可能被略過。要明定以 0 計。
4. **quant 指出的「同時到期順延」漏洞屬實。** 在 TA (2a) 下，60 那一列的 `skipped_observed_sessions = 0`，不受過渡規則管，判定時點卻被移動了。【事實：TA 檔 L114、L116、L117】
5. **乙案的「完整前綴」閘門有一個硬前提：E 內每一種紀錄都要有到得了的終局狀態。** 如果證據不足的紀錄不寫 outcome 列，閘門會永遠擋住，F-2 的退出期限就永遠不會判定。這是負面那一側放行，查證之前 v0.22 第 2 點不得落檔。
6. **「前綴有變動」少列了一類事件。** 觀察日集合或第 0 相位格點改變的事件（X2 確認、未觀察平日登記）沒有明列，要補，不能只靠「判斷不了的算成立」兜底。
7. **TA N-20 的前提「`recorded_at` 只增」不成立。** 依 data-engineer 的查證，`recorded_at` 不單調、也不唯一。身分比對的設計本身仍然成立，但前提句要改寫，比對只能用原字串相等。另外，身分比對**不得早於** ADR-0026 備份順序規定落地，否則照規定整組還原也可能讓守衛永久成立。
8. **紀錄問題：ADR 工作樹 L4474 引用了一份不存在的風控確認。** 那裡已經套用 FL-71 (f)「比對規則」的改寫，歸屬寫的是「風控 2026-10-19 知悉確認需補 B-1」。但 `work/reviews/` 沒有任何 2026-10-19 的檔案，「B-1」也查不到指什麼。內容我在本文核可，歸屬要改成指向本文轉存後的檔案。

#### A. R-Q7-3：`forecast_gap_audit` 的揭露來源

**為什麼可以偏離我的原案：** 我原案把 r_now 放在 json 裡，守衛不成立時整欄為 null。TA 改成每列都填 `market_run_*`。這樣守衛自行解除之後，仍然留得下 R 的走勢，N-20 也能據此界定受影響的期間。這比原案嚴，我採用。

- **[(1a)～(1g)、備用句、約束第 1 點] required**：`market_run_now` 一律改為 `market_run_current`，與 `MarketRunRegression` 及 E-2 用同一套名稱（TA ADR-0029 審查第二節 C 第 2 點）。其他字面不變。
- **[D-7 第 2 點] required（第一批即可落）**：
  - 定位字串（grep 唯一）：``r_now 由呼叫端傳入它自己那一次讀到的市場 DB `MAX(run_id)`。``

#### B. checkpoint 略過：裁定乙案

**為什麼選乙案。** 乙案下，判定樣本 P_j 與 seed 都和判定日無關，可以用來挑時點的手段只剩判定窗內的更正，而「前綴有變動」正好擋住這一種。甲案的殘餘比較大：延後擷取資料會移動 seed，而且不會被標成延後。TA (2a) 原稿另外還有第 4 點所說的同時到期漏洞。

**Q-a（樣本與閘門）：修改後核可。方向是補定義（兩面）。**
- 收緊面：樣本固定之後，延後判定躲不掉負面結果。以 T 排序也不受結算順序影響，這比 `outcome_id` 好。
- 放寬面（照實並陳）：閘門會讓檢查點判定在日曆上晚於 n(S) 首次達到 n_j 的日子，包括 n＝150（族群 250）的退出期限。
- 我的判斷是：這是在定義原本沒有規定的判定時點，n_j 和退出期限本身沒有改。延後長度受既有的等待期限（k ≥ 5）與 N-29 (b) 待重算期限限制，所以不需要 CEO 明示同意，CEO 知悉即可。CEO 若把底線 2 讀成也包含「判定時點」，請提出；但不設閘門會讓前綴在事後改變，更糟。
- **required（前提，擋 v0.22 第 2 點落檔）**：TA 核對證據不足的紀錄是否寫 outcome 列，以及 E 內每一種紀錄是否都有到得了的終局、而且有期限上限。只要有一種沒有，閘門就可能永遠擋住 F-2，第 2 點就不得落檔，要退回重新設計。
- **required**：閘門造成的延後要在 §4.2 揭露（字句見第四節 quant 第 2 點）。

**Q-b：核可。** 不改 UNIQUE。相鄰對以 `checkpoint_n` 配對，不會少任何一對。

**Q-c（`eval_key = n{n}`）：修改後核可。方向是補定義（兩面），不得只寫「補定義＋放寬」。**
- 收緊面：seed 在登記時就確定，判定日不再能移動 seed。F-2 條件二經 §4.3 (c) 依賴 bootstrap，所以這一面對 F-2 是承重的。
- 放寬面：
  - 同一 n 的期間不再每天重抽，所以只因 MC 雜訊造成的降級會減少；
  - 檢查點當天如果剛好抽到偏有利的 bootstrap 結果，在 n 增加之前不會再被重抽挑戰。
- 以下都沒有改，所以 CEO 知悉即可：重抽次數、區塊長度、α\*，以及「每天重算降級」的規則（資料變動造成的降級照樣當天生效）。L1062 寫的「每日偷看的降級偏誤」只是被接受的副作用，不是核可過的保護機制。
- **required**：放寬面要寫在條文本體裡，不能只寫在修訂紀錄（字句見第四節 quant 第 3 點）。

**Q-d（收窄成「延後判定而且前綴有變動」）：修改後核可。**
- 前綴沒有變動時，延後判定的結果與準時判定逐位相同；只有 m 不同，而 m 只會讓判定更嚴。這時擋正面結果沒有保護作用，只是懲罰，所以收窄是合理的。
- **required**：「前綴有變動」要補一項：prev 之後，有任何使觀察日集合或第 0 相位格點改變的事件。
- 殘餘：判定窗內的更正可能讓條件一由成立變成不成立，也就是準時判定會下架、延後判定不會。這一面不擋，理由同 N-5 乙案被駁回（強制視為成立會使 LM-75、LM-87 不屬實，ADR L2120、L3819）。我以 §4.2 逐筆揭露為條件書面接受，最終責任由 CEO 負。ADR Consequences 要寫明這件事（字句見第四節 tech-writer 第 3 點）。

**Q-e：核可。** 整檔還原使 m 變小的例外，已由 m_eff 的下限 8 與 N-5 甲案涵蓋。

**Q-f：修改後核可。** 第 (iii) 項採用，並補一句：「prev 沒有記下 n_complete 時，視同成立。」

**`checkpoint_delayed` 與 LM-74：修改後核可。**
- 改名採用（涵蓋略過與順延兩種情形），優先序為 `suspended_f3` → `db_restored` → `checkpoint_delayed`。
- **LM-74「到事先宣告的期限，仍未能證明優於基準」在 `cause = checkpoint_delayed` 時仍然屬實。** 理由：
  - 正面結果依事先宣告的規則不認列，有效狀態不是 `better_than_baseline`，「未能證明」照字面成立；
  - 這句話沒有主張模型比基準差；
  - 原始結果另記於 `stats_json.raw_checkpoint_result`，並在 §4.2 揭露。
- **required**：L1309 也要改列舉；L1812 要補一句，說明 §4.2「延後判定的檢查點」依 `checkpoint_timing` 判定、不依 `cause`（字句見第四節 tech-writer 第 2 點）。

**使用者面一致性（required 查證，擋 D_v）**：乙案下，checkpoint 列的 n 等於 n_j，而同一天 daily 列的 n 可能比較大。TA 要確認並寫明：「優於基準（附區間、n、期間）」的區間、n、期間都出自同一列 snapshot，不得混用兩列。我沒有查到現行條文有這條規定。

#### C. R-Q7-5 與 data-engineer 查證的影響

- **丙案（比對身分、不鎖存）：修改後核可。**
  - 只有參考 run 確實存在、而且身分相符時，守衛才會解除。違規的單獨還原會讓身分一直不符，所以實際效果等於鎖存，卻不需要存狀態，也沒有人工解除工具。這符合我原本的要求。
- **影響一：`recorded_at` 不單調、不唯一。**
  - 丙案只比「同一 `run_id` 之下的身分是否相等」，不依賴排序，所以設計仍然成立。
  - 但 TA N-20 那句前提「只增不改」要刪掉，改寫成「不改寫（append-only trigger，屬自律層級）；只以原字串相等比對，不解析、不比較大小、不作為鍵」。
  - reader 要在同一次唯讀查詢裡，一起讀出 `MAX(run_id)` 和它的 `recorded_at`。
  - 殘餘的漏報（兩條時間線的同號 run 在同一微秒寫入）照實標為推論。
- **影響二：備份順序。** TA 理由 (iii)「依 D-9.4 整組還原後守衛自己解除」，只在市場 DB 備份涵蓋主 DB 備份所引用的 run 時才成立。
  - 沒有順序規定時，照規定整組還原也可能讓守衛永久成立。方向是 fail-closed，但只能靠修訂 ADR 解除，實務上會逼出手動改 DB 或繞過守衛的壓力。
  - 所以 **ADR-0026 的順序規定與 manifest 檢查，必須與 N-20 同批或更早落檔；在那之前，不得實作身分比對。**
  - 解除路徑仍然只有一條：「用檢查通過的備份組重做，或修訂本點」。不得新增人工解除用的 CLI。
- **suggested**：
  - 身分一併比對 `kind` 與 `session_date`。兩欄都不可改寫，所以只會更嚴、不會誤報。
  - TA 評估是否把 `forecast_gap_audit.market_run_current` 的歷史最大值納入參考值。這要另存 `recorded_at`，屬於 N-20 範圍。
- **連帶（N-20 同批）**：身分不符而 r_now ≥ 參考值的情形出現之後，下列各處要同批改寫：(1c) 的「若且唯若」、FL-67 (n) 的拒絕格、(1e)「稽核列回到 null」一句、D-9.2「處理終點」一句。

#### D. C6、C25、5a、5b、FL-71 (f)

- **C6 確認、C25 補格、(k) 但書的兩種版本**：核可，照 TA。
- **5a**：核可，照 TA。
- **5b**：核可，照 TA。分類只影響告警是 WARNING 還是 E-3d。時鐘倒退時會被誤判為步驟失敗，方向是多推播，安全；plan 不寫的代價也可以計數。`ValidationSnapshotPartialSetError` 只讓推播多一種來源，推播欄位不變，依 ADR-0029 失效條件屬知悉級。

  - 工作樹 L2412 現行字面我核可，可保留：英文不分大小寫，適用全部英文項，含 A 類 regex 與 F 類；`\b` 用 ASCII 判定；中英文相接時也要比對得到。
  - 理由：ASCII 詞界只會讓緊鄰中文的英文詞多命中；不分大小寫只會多擋，不會少擋。
  - suggested：修訂紀錄 L4474 的方向改標「收緊（明文化）」。
  - **required**：L4474 的歸屬改為本文轉存後的檔案路徑；「需補 B-1」要說明出處，說明不了就刪除。不得引用還沒有出具的風控確認。
