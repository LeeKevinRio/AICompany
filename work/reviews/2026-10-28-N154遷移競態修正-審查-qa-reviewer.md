## 逐項查核（對應你列的 7 點）

**1. `add_missing_columns`（`app/data/sqlite_util.py:78-129`）：正確**
- **快速路徑不取鎖是安全的。**
  - 欄位只增不減，所以「欄位已齊」的判斷不會被後來的操作推翻。
  - 看到舊 schema 的最壞結果是多進一次鎖內流程，不會做錯事。
  - `_missing_columns` 把 PRAGMA 的 cursor 整個消耗完才返回，不會留下讀取交易卡住後面的 `BEGIN IMMEDIATE`。
- **鎖內重查正確。**
  - 輸家在 `BEGIN IMMEDIATE` 前沒有開任何讀取交易，所以 busy handler 會生效，等的是 `busy_timeout`。
  - 取得鎖後重新執行 `PRAGMA table_info`，會驗證 schema cookie，看到贏家剛加的欄位，迴圈為空，直接 COMMIT 釋放鎖。
- **ROLLBACK 處理正確。**
  - 先檢查 `conn.in_transaction` 再 ROLLBACK，避免 SQLite 已自動回滾時，第二次 ROLLBACK 蓋掉真正的錯誤。這比 `kelly` 的無條件 `ROLLBACK` 更穩。
  - 多欄位放在同一個交易，中途失敗會整批回滾（有測試）。
- **呼叫時已在交易中**：`BEGIN IMMEDIATE` 會拋 `cannot start a transaction within a transaction`。
  - 這個 `BEGIN` 在 `try` 之外，所以不會誤把呼叫者的交易 ROLLBACK 掉。結果是大聲失敗，而非靜默錯誤。
  - docstring 已寫明前置條件。
  - 實際上四個呼叫點（alerts、dividends、playbook、sectors）前面都只有 `enable_wal`、PRAGMA 與 DDL。Python sqlite3 只對 DML 隱式開交易，所以不會踩到。
- **與 `isolation_level` 的互動**：這幾個 store 都用預設的 legacy 模式，顯式 `BEGIN`、`COMMIT` 會直接透傳。
  - helper 自己 COMMIT 後，外層 `with conn:` 看到 `in_transaction=False`，不會重複提交。
  - 也沒有任何一個呼叫者用 `isolation_level=None` 傳進來。`dividends/store.py:249` 的 `isolation_level=None` 是另一個寫入方法的專用連線，與 schema 初始化無關。
- 表名和欄位名是 f-string 直接內插，docstring 已標明只能傳呼叫者自己的常數。

**2. `alerts/store.py` 的 `bar_as_of`：一致，無風險**

- `SELECT *` 只出現在 `playbook_directives`、`playbook_schedule`，而 playbook 的 CREATE 沒有被改動。

**5. `CorsVisibleServerErrorMiddleware`（`app/api/server_error.py`）：正確**
- **response 已開始時只重拋：正確。**
  - 用包裝過的 `send` 追蹤 `http.response.start`。
  - 已開始就只 `raise`，不再送第二個 start，避免協定錯誤。
  - 有直接單元測試。
- **外洩安全：沒有。**
  - 本文是固定常數 `b"Internal Server Error"`，沒有使用例外訊息或 traceback。
  - 例外原樣重拋，traceback 只進伺服器 log，與 Starlette 原行為相同。
  - 外層 `ServerErrorMiddleware` 看到 response 已開始，不會再送一次。
- **與 403 guard、HTTPException：不衝突。**
  - HTTPException 和 `RequestValidationError` 由更內層的 `ExceptionMiddleware` 處理，到不了這一層。
  - 403 guard 在這一層外面，它的回應不經過這個 middleware，仍帶 CORS header。
  - 非 http scope（lifespan、websocket）直接放行。
  - `except Exception` 不攔 `CancelledError` 等 BaseException，合理。
  - app 內沒有註冊任何 `exception_handler`（Grep 確認），所以「內層先攔再重拋」不會繞過自訂 500 handler。
- **掛載順序（`main.py:59-69`）：正確。**
  - Starlette 後加的在外層，所以順序是 CORS（最外）→ client header guard → 本 middleware（最內）。
  - 500 因此會被 CORS 加上 header；測試也驗證了 `access-control-allow-origin`。
  - 唯一沒涵蓋的是 guard 或 CORS 自身拋例外，這屬於極端情況，不處理可接受。
- **是否超出 N-154 範圍：**
  - 這是症狀層面的診斷改善，不是根因修復。N-154 根因是遷移競態，這個 middleware 讓 500 在瀏覽器裡不再被誤判為 CORS 錯誤，是同一事件的衍生處置。
  - 它是全域行為變更，影響所有 route，風險面比 store 修正大。
  - 它已是獨立 commit（fa6cc42），這是正確做法。
  - 我的意見：可以隨本分支合併，但請在 PR 描述標明兩個 commit 的性質不同，讓 CEO 知情；若想保守，也可拆成獨立 PR。這是範圍管理的建議，不是品質問題。
