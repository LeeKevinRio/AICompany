## 逐條意見

**第 1 項：S8 渲染條件（條件定稿）**

- [`engine.emergency_mode_reason`] 條件要從 `trading_days_between(data_date, until) > freeze_days` 改成下面這條 → required
  - 定稿：`calendar.trading_days_between(data_date, until) > freeze_days + 1` 成立時用 S8，否則用原本的 `MODE_REASON_EMERGENCY` 計數句。
  - S8 字面和 `MODE_REASON_EMERGENCY` 字面都不改。`emergency_frozen_day` 的 clamp 也不改。
- 為什麼是 +1：
  - `trading_days_between` 算的是 `(start, end]`。
  - 出清當天收盤前，`data_date` 是前一個交易日，算出來剛好是 freeze_days + 1。那一天確實是暫停第 1 天（自提交日起），「第 1/20」是真的。
  - 剩餘天數大於等於 freeze_days + 2，代表資料落後兩個交易日以上，或是 F-c（既有截止日晚於新算值）。這時才會連續好幾次被 clamp 成「第 1」，才是我原本要排除的不實情境。
- 為什麼不採另外兩個方案：
  - 改用 `as_of` 計數：否決。`_resolve_mode` 判斷模式用的是 `data_date <= until`，計數也要用同一個基準，否則凍結的最後一天前後，模式和計數會對不上，等於重開 VETO-4 的計數語意。
  - 顯示「第 0/20」：否決。它牴觸「自提交日起」，使用者也會讀成「還沒開始暫停」。
- [測試] 要補下面三項 → required
  - 邊界：剩餘 = freeze_days + 1 → 計數句，而且含「第 1/{freeze_days}」。
  - 邊界：剩餘 = freeze_days + 2 → S8。
  - F-T4 和 `test_today_uses_the_uncounted_mode_line_and_the_kept_check` 的情境，剩餘天數要改成至少 freeze_days + 2，否則它在新條件下驗不到 S8。
- [V-16 去重的前提] 出清回應的 mode_reason 和同一天 `/today` 的 mode_reason，要用同一個函式、同一個 `data_date` 算出來 → suggested
  - 建議加一支測試斷言兩者逐字相同。不相同不算法遵違規（只是兩處都顯示），但會讓 N-164/N-165 的隱藏條件永遠不成立。

**第 2 項：日期清單（條件定稿）**

- [service 組 message] 日期清單和 S3 判斷要用全部覆蓋列 → required
  - `{pending_execution_dates}`：取所有符合 C-4 的覆蓋列（`rule_id='EMERGENCY' AND action='sell' AND settled=0`、而且屬於本次判定為已覆蓋的批次）的 `execution_date` 全部，去重、遞增排序、ISO 格式，以「、」連接。
  - S3 是否觸發：同樣以全部覆蓋列判斷，只要任一列 `execution_date < as_of` 就加 S3。
  - `{past_due_dates}`：全部過期列的日期，去重、遞增排序，格式同上。
  - `{pending_batches}`、`{pending_shares}` 的定義不變：以 (symbol, batch_no) 去重，股數取 `remaining_shares` 合計，不可翻倍。
- 理由：
  - N-166 之前「隔天再按、前一天沒結算」會產生同一批次、兩個不同執行日的兩列。使用者可能收過兩次回應，看過兩個日期。
  - S1、S2 寫著「這些先前的指令仍然有效」，卻只列其中一個日期，等於隱藏系統裡實際存在的狀態。
  - 若「最舊一列」是依寫入順序（例如跨 UTC 日界的情況），它的執行日不一定最早，S3 可能完全不觸發，構成漏報。
  - 同一批次列出兩個日期，不會讓人讀成要賣兩次。S1 的「以上述 {pending_batches} 批、共 {pending_shares} 股為準」已經以不翻倍的股數為準。
- [測試] 要補下面這項 → required
  - 舊資料中同一批次有兩列，執行日 D2 < D3：S1 列出「D2、D3」；D2、D3 都已過期時，S3 兩個都列。
  - 只有 D2 已過期、D3 還沒到時：S3 只列 D2，S1 兩個都列。
- [`pending_directives` 欄位形狀] 每批一列或全部列出，屬 API 設計，交 qa-reviewer 和 tech-architect 判斷 → suggested：建議全部列出，跟 message 一致
  - 附帶條件（required，針對未來）：任何畫面若要渲染 `pending_directives`（含 CEO 先前事項 2 的常駐檢視），必須列出全部覆蓋列，或先送本人審。

**第 3 項：NB-6 合併後版本（逐字定稿，APPROVE）**

全形標點依 `wording.py` 慣例。下面是一個標籤加三段內文；第 3 段內有兩個句號，算同一段，不得拆開、合併、增刪或改序。

- 標籤：「無法確認全部出清的處理結果」（不改）
- 第 1 句：「這次送出未取得可確認結果的回應。目前可能尚未處理，也可能已受理：R 系列（新倉進場）已暫停，持有批次也都已有賣出指令。」
- 第 2 句：「頁面上方的狀態列在重新取得資料後，其模式徽章會顯示 R 系列（新倉進場）目前是否已暫停，但不會顯示賣出指令；若這次送出前 R 系列就已暫停，徽章也無法顯示這次是否已受理。」
- 第 3 句：「你可以再次送出：已有尚未結算之出清賣出指令的持有批次，不會再重複產生賣出指令；但再次送出可能延後 R 系列（新倉進場）的預計恢復日。再次送出若取得回應，回應會說明該次的處理結果，包括先前已有、尚未結算的賣出指令。」

依附錄 C 和 C-1 逐項核對：

- **第 1 句拿掉「只暫停了……而尚未產生賣出指令」。**
  - C-1 規定指令和凍結在同一個 `BEGIN IMMEDIATE` 寫入，T-5 證明失敗時兩者一起 ROLLBACK，所以狀態 (ii) 消失。
  - 但 500 仍會落在 (i) 或 (iii)，所以兩種都要列，不得斷言。
  - 「已受理」和回應 message 開頭的「EMERGENCY_EXIT 已受理」用同一個詞。
  - EMPTY 支（沒有持有批次）在「持有批次也都已有」底下是空集合，說法仍然為真。
- **第 2 句加入「送出前就已暫停」的限制。** N-166 之後，若送出前沒有暫停，徽章顯示暫停就代表這次已受理。但 EX-3 的再出清是在凍結中送出，那時徽章一定是暫停，判斷不了。不寫這句，使用者會從第 1 句推論「看到暫停就代表已受理」，那就是我 VETO PM 草案第 3 點的同一種誤導。
- **第 3 句：**
  - 只陳述事實，不用「安全」或「放心」（這兩個詞永久禁止）。說明可以再送（EX-2），同時揭露代價：預計恢復日可能延後。這依 CEO #77 和 S6 的事實：同一天重送不延後，隔天或跨 UTC 日界重送會延後。
  - 「包括先前已有、尚未結算的賣出指令」是給第一次回應遺失的使用者，對應 S1、S2 的設計。
  - 不寫「回應會說明先前是否受理」。原因見下面的「新發現」：結算之後，回應講不出這件事。
- [上線耦合] → required
  - 這個合併後版本**只能出現在已包含 N-166 commit 的 build**。若在沒有 N-166 的後端上顯示，第 3 句「不會再重複產生」就是不實陳述，等於暗示重送安全，本人 VETO。
  - 反過來，N-166 合併之後，合併前的版本不得留在任何 build，因為第 1 句的 (ii) 是不實陳述。
  - 作法：
    - N-164/N-165 若晚於 N-166 合併，直接採用本版。
    - 若早於 N-166 合併，先上合併前版本，由 N-166 的 PR 換成本版，並更新守門測試。
  - 單一來源仍然是 `wording.py`，前端鏡射，並加逐字守門測試（沿用前次必改項第 10 點）。
- [其他條件] 前次裁示中第 9 項的其他規定不變：不附後端原文或 HTTP 狀態碼；5xx、4xx、網路、解析失敗都適用；不改共用的 `ErrorPanel`。
- [ADR-0033 Consequences 與附錄 C 的「重試變安全」] 這是內部技術敘述，不算違規 → suggested
  - tech-writer 和 PM 不得把「安全」這個詞搬進任何面向使用者的文案。

**新發現（不擋 N-166 和 NB-6，要 CEO 另開追蹤）**

- 情境：第一次送出其實已 commit，但回應遺失。使用者等到下一個交易日開盤、結算之後才重送。
- 這時覆蓋列已結算，批次已 closed，重送會走 EMPTY 支：「目前無持有批次，未產生賣出指令」。
- 但這位使用者從沒拿到指令，所以從沒在券商賣出。系統的帳已經當作賣掉了，實際上他還持有。EMPTY 的字面會讓他誤以為沒有東西要賣。
- 這和前次 CEO 事項 2（出清指令沒有任何常駐檢視處）是同一個根源，建議併案，由 backend 評估，新字面送本人審。
- 第 3 句因此刻意不宣稱「回應會說明先前那次是否受理」。

## 否決理由
- 第 1 項照現行條件實作：VETO。它把 VETO-4 計數要求的例外擴大到一般流程，在最常查看的時點拿掉了真實的計數。
- 第 2 項現行設計用來產生使用者看得到的日期：VETO。它隱藏系統裡存在的覆蓋指令日期，而且 S3 可能漏報，違反「不隱藏不確定性」和「失效條件須揭露」。
- 兩項都照上面的定稿修正即解除，不需要再送本人審。qa-reviewer 照上面列出的測試逐條驗證即可。
