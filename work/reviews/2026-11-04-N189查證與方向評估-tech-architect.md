# N-189 查證與方向評估（tech-architect，唯讀）

## 一、本次結論

**N-189 在程式層面成立。** engine 評估 S/P 時讀的是帳冊現況，也就是 `remaining_shares`、`p1_done`、`p2_done`、`p3_last_date`。這幾個值只有結算時才會改變，評估路徑完全沒有讀在途賣單。K1 含 `execution_date`，所以跨日的重複賣單擋不住。

**(a) 跨預定執行日：成立。**
- D1 產生的 S1、P 賣單（預定 D2 執行）若還沒結算，下一個資料日的評估會用沒扣過的股數，再發一次同規則或別的規則的賣單。
- 這是新的 K1，會照常寫入。

**(b) 同日、K1 不同：分兩層看。**
- 同一次評估內有互斥：每批最多一列；S2 優先於逐批規則；逐批順序是 S1 → P3 → P1 → P2。
- 同一預定執行日的兩次評估之間，沒有優先或互斥規則，只有「同規則」會被 K1 擋下。
- 「P1 之後又出 S1」已列在 ADR-0035 Consequences 第 185 行，被接受為殘留風險。

**發生條件。** 正常情況下，同一個 `/today` 會先結算、後評估（`service.py:1572` 在 `:1618` 之前），所以 T+1 會先結算掉。缺口出現在「Y 在預定執行日沒有 bar，但評估時 Y 的資料可用」。這不只是資料落後：
- **休市日（F7／N-176）是固定、每年會重複的觸發源。** 平日休市時，預定執行日落在休市日，那一列永遠結算不了。
- 單一標的資料落後，或指數比個股早出 bar，也會觸發。

**新發現（讀碼推論，未執行，不能當作保護）：**
- 同一請求裡，結算先載入一次 bars，評估再載入一次。第二次載入可能落在 layer 0，回傳 `cached_stale`；engine 不採用這個狀態。
- 若屬實，跨日路徑 (a) 在正式環境多半會被意外遮蔽。但代價是：只要某檔有到期未結算的列，它的 S/P 就不會被評估；遇到休市日是永久不評估。
- 這也會影響 N-188 的前提，需要 qa-automation 用真實 ladder 實測。

**方向。**
- 揭露類可以先做，不與 accepted ADR 衝突。但它是真正的在途讀取，要經 TA 補充擴充 ADR-0035 補充四 2.3 的切面。
- 行為修正類（扣除在途、或在途時暫停 S/P）都會改變停損涵蓋的股數或時效，而且依賴 N-176 給在途單一個終點。這屬於 ADR-0036（尚未起草）的範圍，需要 CEO 裁決。

**時序。** 不併入 N-168，也不併入 N-188。揭露的實作等 N-168 合進 product 之後再開。補充五起草時，要為 N-189 的同列 note 預留順序位置。

#### 1. 兩條路徑是否成立

- **engine 評估時沒有在途資料。** `evaluate()` 的輸入只有 `book = list_batches()`（`playbook/service.py:1616-1626`）。`read_in_flight` 在 `:1576` 讀了，但沒有交給 engine。它的內容也只有 EMERGENCY 賣單（`store.py:1274-1291`）和 G1 擋下的買單（`:341-351`），沒有一般 S/P 賣單。
- **各規則的股數算法（都不扣在途）：**

| 規則 | 股數 | 位置 |
|---|---|---|
| S1 | `remaining_shares` 全數 | `engine.py:437` |
| P3 | `remaining_shares // 3` | `:477` |

  - `p1_done`、`p2_done` 沒立起來，P1、P2 會再觸發。
  - `p3_last_date` 沒寫入，P3 的冷卻失效，會再觸發。
  - 批次仍是 open，S1 會再全數賣出。
- **K1 擋不住。** K1 是 `(symbol, batch_no, rule_id, action, execution_date)`（`store.py:369-377`），新的預定執行日就是新的 K1，`_new_decisions` 照寫（`:403-426`）。

**(b) 同日、K1 不同：同一次評估內有互斥，兩次評估之間沒有。**

- **同一次評估內的互斥：**
  - `_evaluate_batch_exits` 依 S1 → P3 → P1 → P2 → 移動停利的順序，每批命中第一條就 return（`engine.py:419`、`:468`、`:516`、`:558`、`:603`）。
  - S2 觸發時會跳過整檔的逐批評估（`:1234-1252`），並把各批加入 `touched`（`:707`）。
- **同一預定執行日的兩次評估之間：**
  - 只有同規則會被 K1 擋下。
  - 第二次評估若因 Y 的 bar 補進來、防守模式翻轉（S1 門檻改用 0.93，`engine.py:430`），或帳冊變動（N-188），改命中另一條規則，就會寫入第二張賣單。
  - 組合可能是 P1＋S1、P3＋S1、逐批＋S2、S2＋逐批。
- **ADR-0035 的態度。** Consequences 第 185 行明文接受「同一批同一天可能先後出現不同規則的賣單（例如 P1 之後又出 S1）。帳冊有 `min` 保護，但使用者會收到兩張單，屬殘留風險」。ADR 沒有要求揭露。
- **相鄰小發現（不屬本單，只記錄）：**
  - P2 減碼和 P2 移動停利的 K1 相同（rule_id 都是 `P2`）。同日第一次出 P2 減碼、第二次改成移動停利出清時，第二列會被 K1 擋下，方向是少賣。
  - `trailing_on` 不屬於 FILL_DEPENDENT，會在評估時就寫入（`store.py:1121-1122`）。所以 P2 那列如果 MISSED，移動停利仍會維持啟動。

#### 2. 實際發生條件與頻率

**一般情況會先結算：是。**
- 預定執行日 E 的列，在 `as_of ≥ E` 時就算到期（`store.py:1343-1345`）。
- 下一個資料日的評估需要有日期 ≥ E 的 bar。只要 Y 有 E 的 bar，同一請求的結算就會先把這列判掉（`service.py:1054-1071`）。
- 台股收盤後的 bar，UTC 日期就是 E，所以 `as_of` 不會落後。

**缺口不只出現在資料落後。** 成立的組合是「E 列到期未結算（Y 沒有 E 的 bar），而評估時 Y 的快照可用」，來源有四個：

1. **休市日（N-176／F7）：固定，每年重複。**
   - 預定執行日超出已觀察的範圍時，改用平日規則推算（`data/calendar.py:74-93`）。平日休市時，E 就落在休市日。
   - 結算要求 `bar.date == execution_date` 完全相符，所以那一列永遠 pending。
   - 只要休市前一天有 S/P 觸發、休市後條件仍在，就會再發一張。每次休市事件約一張，因為新列結算後旗標才會立起來。
   - qa 已重現 R1 和 EMERGENCY 在這個情境下永遠 pending（追蹤清單:281）；S/P 是同一個機制。
2. **單一標的資料落後，或指數比個股早出 bar。** `data_date` 取所有序列的最大值（`service.py:1587`），Y 則用自己最新那根 bar。
3. **同一請求內兩次載入的結果不同。** 結算（`:1046`）和評估（`:1579`）各自呼叫 `_load_symbol_bars`，第一次失敗、第二次成功時就會成立。這是低機率情況。
4. **並發。** 兩個請求之間的 claim／settle 窗口，屬 F2 類。

**重要的相鄰觀察（讀碼推論，未執行，需實測）：**
- 正式環境的 ladder 都開了 `cache_first=True`（`api/deps.py:125-145`）。layer 0 從快取回應時，狀態一律是 `CACHED_STALE`（`data/service.py:848-853`、`:856-884`）。engine 只採用 `fresh` 和 `backup`（`engine.py:58`、`:63-65`）。
- 因此推論：某檔有到期未結算的列時，結算那次載入會先 live 抓取並寫進快取，評估那次載入就會落在 layer 0，變成 `cached_stale`，這檔不評估（`engine.py:1197-1210`）。
- **對 N-189 的影響：** 路徑 (a) 在正式環境多半被遮蔽。但這是副作用，不是保護。ADR-0039 Decision 3 已經讓出清分類沿用 `run.loaded`；之後只要有人讓評估也沿用同一份序列，遮蔽就會消失，路徑 (a) 全面打開。
- **反面的實害：** 有到期未結算列的標的，S/P 當次不會評估。遇到休市日，那一列永遠到期未結算，這檔的停損就永久不評估（有 `DATA_GAP_HOLDING_NOTE` 揭露）。
- **對 N-188 的影響：** N-188 的前提是「結算判不了，但快照可用」，在同一請求內可能也被遮蔽。我**不建議**據此調降 N-188 的優先度，要先實測。
- 測試多半用假的 resolver，可能沒有覆蓋這個行為。

**N-177 的關係（已追蹤，提醒優先度）：**
- S2 成交後不動帳，所以已結算的 S2 不再是 pending，不會被上述遮蔽。
- 價格沒回升之前，每天都會再發一張全數的 S2。這是**未被遮蔽、每天都會發生**的同類超賣，目前列 P2，建議風控一併重看。

#### 3. 現有保護與揭露

- **`store.settle` 的 `min`（`store.py:1442-1444`）：**
