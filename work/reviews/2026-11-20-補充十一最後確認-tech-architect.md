## 各部門回報（tech-architect）

**1. C1～C6 與 C2 的四種情形**

先看 `report.main`（第 680～696 行）實際會回什麼：
- `status` 只會回 0、3、4。
- `verify --all` 只會回 0、1、3、4。
- argparse 參數錯誤時不會回傳 2，而是丟出 `SystemExit(2)`。一鍵檔的參數寫死，這種情形只會是程式錯誤。

所以四種情形依下面的規則分，彼此不重疊、不遺漏，也都能用結束碼實作：
- `status` 回 3／4 → (a)，依結束碼印 RC-291 對應的 STOP 句。
- `status` 回 0 → 才執行 `verify`。
  - `verify` 回 0／1 → (b)
  - `verify` 回 3／4 → (c)
- 其他一律歸 (d)，包括：任一段回其他值、`SystemExit`（含 argparse 的 2）、其他例外、`KeyboardInterrupt`、以及寫檔失敗。
- 你問的 `status` 回 3／4 以外的非零值（例如 argparse 的 2）屬於 (d)。

另外，`run_command` 是先把整段組好，最後才一次 `print`。所以 3／4 時，被攔下的 stdout 本來就是空的。即便如此，規格還是寫成「一律丟棄」。

「第一段已顯示就不收回」和「`status.txt` 只在取得完整輸出之後才寫入」兩者相容。做法是逐段印出，最後一次寫檔：
- `status` 回 0 後，立刻印第一段與分隔句，再執行 `verify`。這樣 `verify` 跑很久時，畫面不會長時間沒有輸出。
- `verify` 回傳後，印第二段（結束碼 1 時再加行動句），或改印 RC-299 的 STOP 句。
- 最後把已印出的內容一次寫進 `status.txt`。
- 結果：(b)、(c) 時畫面和檔案逐字相同；(d) 時畫面保留已印出的內容，接著印 ERROR 句，不寫檔。這也符合 RC-291 的「ERROR 句與狀態內容同時出現時照樣整段貼回」。
- 存檔資料夾的 git 工作樹檢查要排在 `status` 之前。否則 (b)、(c) 印完之後才 STOP，就多出 C2 沒涵蓋的第五種情形。

**2. 內部一致性**

清單上的舊說法逐一查過，已經不存在：「只執行 status」「不得執行 verify」「之前或同時」「沿用 report 既有的拒絕句」「每一行再套 d4_violations」。仍需處理的是下面幾處：
- 第 2 點「輸出」第一款：還寫「輸出由 `report status` 原樣產生」（替換 R1）。
- 第 2 點「前置檢查」的「不做 port 與 git 檢查」，和「輸出」的 git 工作樹 STOP 容易被讀成矛盾（替換 R2）。
- 缺執行順序（新增 R3）。
- S-21a 第五項「畫面都只有固定句」，和 (d) 的「已印出的不收回」衝突（替換 R4）。
- 「性質」第二款「送風控」已經過時（替換 R5）。

**3. 佔位與檔頭**

要補上核可敘述（替換 R6、R7）。

**4. 和補充八、九、十的關係**

**5. 寫入時點**
