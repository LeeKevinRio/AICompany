**問題清單**
- [Edge case／可實作性][medium] N110-1（L1066）把 `scopes_missed`、序列化與 `error_class` 移進中止用 run_end 寫入函式，但沒規定這些計算要放在該函式唯一的 `except Exception` 所包住的 try 之內。這正是風控 suggested 提的點。
  - 若計算放在 try 之外，計算失敗（例如序列化拋例外）會從寫入函式往外拋。範圍迴圈函式 except 區塊裡的不帶參數 `raise` 不會執行，E-3d 的 `exception_class` 會變成計算錯誤的類別，違反 L1047 與 L1048「記 WARNING、仍拋原例外、該 run 記 `job_error`」的原意。
  - AST 抓不到這一點，FL-74 (h) 只涵蓋「run_end 寫不進去」，沒有涵蓋「計算失敗」。
  - 建議：在 L1066 或 FL-74 (b) 補一句「這些計算與序列化都在該寫入函式唯一的 `try` 之內」。FL-74 (h) 再加一格：注入計算失敗 → `exception_class` 仍為原中止例外、WARNING 一行、該 run 沒有 end。請 TA 在下一批補，並在 dev-lead 實作該函式之前定案。可新增追蹤項。
- [Edge case][low] N110-2（FL-76 (p)）的條件「每個位置引數與關鍵字引數的值都是 `ast.Name`」放過 `**kw`：`keyword.arg is None`，但其 `value` 是 `ast.Name`；`*args` 是 `ast.Starred`，會被擋。兩者不對稱。
  - 因 FL-74 (b) 已限制 except 區塊只有該呼叫加 `raise`，且 `**kw` 的 dict 在 try 之前只能是空字面值，實務上構不成繞過。
  - 建議明文寫「`keyword.arg` 不為 None」，也就是不接受 `**` 展開，讓條件對稱可判定。
  - 另提醒 dev-lead：引數不能是屬性（例如 `self.conn`、`snapshot.run_id`）或字面值，連線、時鐘、`run_id` 都要先成為參數或區域名稱。這是條件的本意，但實作時容易踩到。
- [可維護性][low] N109-1 的白名單混用模組層級（`views`、`display.py` 等）與函式層級（`store.py` 的寫入、寫入驗證、`content_hash`），但 `store.py` 內這幾個函式沒有名稱。
  - `store.py` 若有通用的讀取函式（`SELECT *` 轉 dataclass）或 dataclass 欄位宣告，AST 要如何判定「讀」並不明確。
  - 建議 dev-lead 實作前在 ADR 或測試中釘出函式名，並明定「讀」的 AST 判準（識別字或字串 `scope_reason` 的出現位置）。風控的 `SELECT *` 疑慮已有 N-112。
- [Edge case／可維護性][low] L331 的寫入驗證有兩處小不對稱。
  - (a) `trigger = on_demand ⇒ queried` 沒帶 `supersedes_id IS NULL`，而取值規則（E2）帶了。若更正列的 `trigger` 與原始列不同，兩條驗證會互相矛盾。ADR 沒有明寫更正列的 `trigger` 等於原始列。建議補一句，或讓驗證條件對稱。
  - (b) 取值是由寫入函式決定，驗證又「依上述規則重算」，兩者若用同一實作就變成自證。FL-77 (o) 只說重算放在 `store.py` 的純函式。建議比照 A-25 分割驗證「以與決定不同的純函式重算」，把這句寫進 (o)。
