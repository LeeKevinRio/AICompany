# N-168 出清後待結算 R 買單：方案裁示（risk-compliance-officer）

## 一、本次結論

**審查結論：CONDITIONAL APPROVE B-2a（風控版）。** 風控版和 PM 的 B-2a 方向相同，但有 7 處差異，見第二節之二。第二節之五的條件只要缺一項，就視同 VETO。

六個方案的裁示：

| 方案 | 裁示 | 一句話理由 |
|---|---|---|
| A 出清時撤回 | 附條件接受（不建議） | 不能援引 R12。U-A 情境下帳冊少報且無法回收，必須由 CEO 書面承擔。 |
| B-1 結算時略過 | **否決** | A 的缺點全有，告知還更晚，而且「因凍結未成交」是對券商端的不實陳述（R10）。 |
| B-2a 轉 open＋標示 | **附條件接受（建議）** | 延續全系統既有的帳冊假設，符合 R10；出口不動。 |
| B-2b 系統自動賣出 | **否決，建議列為永久紅線** | 原則問題，字面修不了。 |
| C 只揭露 | 單獨成案**否決**，作為 B-2a 的必要元件納入 | 揭露時點對不上使用者最需要資訊的時點。 |
| D 使用者回報成交 | 可接受為後續方向，不併入 N-168 | 附條件，見第二節之一。 |

另外三點：
- **不接受修改**已定稿的 `EMERGENCY_EXIT_RESULT`、`EMERGENCY_EXIT_EMPTY`。改用條件式附加句 W-B1。
- 出清確認面板維持不動，同意 PM。
- **PM 低估了 U-B 的實害。** U-B 的風險不只是「看到幻影批次」，而是系統會對使用者並未持有的股數發出 S/P 或 EMERGENCY 賣出指令。使用者照做，就可能誤下賣單（超賣或違約交割的風險）。所以我加了 W-B2L、W-B7 兩句必要揭露。

## 二、各部門回報

### risk-compliance-officer（本人，唯讀）

#### 1. 六個方案逐一表態

**B-2a 是否符合 R10：符合，但有條件。**
- 理由：
  - R10 的內容是「產品說明明載不下單，拒絕機制不影響帳戶處分權」。
  - B-2a 沒有發明新的假設。全系統對每一筆指令本來就是「依預定執行日開盤價在帳冊判定」，`SETTLEMENT_SUMMARY` 與 §6 第③句也已經寫明「實際成交結果以你的券商回報為準」。
  - B-2a 不替使用者處分帳戶，出口也不加任何前置條件。
- 條件：
  - (a) 只能用帳冊語言，例如「帳冊判定成交」「記為持有」。任何地方都不得出現「你已買進」或沒有限定詞的「已成交」。
  - (b) 必須明講「無法替你在券商撤單」。
  - (c) 「已成交」與「未成交」兩種可能要對稱陳述。

**A 能否援引 R12：不能。** 差異有三點：
- 觸發原因不同：R12 是系統自己的輸入不可信。A 的原因是使用者行為，資料本身沒有問題。
- 實作上沒有先例：R12 實際落地為 R6／鐵律⑤，也就是「當日不產生指令」（`wording.py:225` DATA_GAP_NOTE）。我讀碼沒有找到任何撤回已發出指令的機制，`DirectiveStatus` 也沒有撤回值。所以 R12 從來沒有「撤回一筆使用者可能已經照做的指令」的前例。
- 失效方向不同：R12 是在使用者行動前就不給，不會造成帳冊與實際部位分歧。A 是在使用者可能已經行動後才撤，會造成少報。

所以 A 只能以「意圖優先」的產品立場自己成案，ADR 與字面都不得寫「依 R12」。A 還有一個更嚴重的問題：U-A 使用者真實持有的部位在系統內**永遠收不回來**。帳冊沒有修正入口（PRD R-3），再次出清也涵蓋不到這筆部位，因為它不在帳冊裡。這等於長期違反 S-2 的精神，只能由 CEO 書面承擔。

**B-1：否決。**
- U-A 的使用者已經在券商成交，系統卻在結算時標「未成交」類狀態，這是對券商端事實的不實陳述（R10）。
- 告知發生在使用者早已行動之後。

**B-2b：否決，建議列為永久紅線。**「使用者沒有在該次操作中提交出清時，系統主動產生 EMERGENCY 指令」屬原則問題，理由有四：
1. 豁免基礎會不成立。排程台之所以能用指令式輸出，前提是判斷主體是使用者。系統自己替使用者再出清，判斷主體就變成系統。`EXIT_ATTRIBUTION`、S4、S5 都會變成不實陳述，任何新的歸屬語都只能寫「本系統的判斷」，排程台就退回建議式（B1 定調、R4）。
2. U-B 情境下，系統會叫使用者賣一筆並不存在的部位，會有誤下賣單、超賣、違約交割的實害。
3. 繞過 EX-5 的確認步驟。
4. 字面修不了，任何措辭都救不回第 1 點。

能重開的唯一途徑是 CEO 修改豁免框架，再加上一輪新的風控審查。即使將來有 D（使用者回報成交），正確的路徑仍然是由使用者自己再次出清，不是系統自動產生。

**C：單獨成案否決，作為 B-2a 的必要元件納入。**
- T1 之後批次沒有任何標示就出現，等於把不確定性藏在使用者最需要資訊的那個時點。

**D：可接受為後續方向。** 條件如下：
- 回報不得擋出清，也不得成為出清的前置條件（EX-2）。
- 使用者一直沒回報時，預設行為必須是 B-2a 而不是 A。
- 使用者回報要依 R16 落檔，標明「使用者自行回報」與時間戳，不得當作券商確認。
- 要有獨立的 PRD 與風控審查。

#### 2. 風控建議方案：B-2a，與 PM 的 7 處差異

- **D1 標示字面：** 「出清後成交」只能當內部識別名稱，不得面向使用者。理由：「成交」在 U-B 情境下是斷言券商端的事實；「出清後」也有歧義，因為出清的賣出指令可能還沒結算。改用 W-B2。
- **D2 不修改 RESULT／EMPTY：** 這兩句在沒有待成交買單時仍然為真。它們也是 N-166 的 S1 到 S9 剛定稿時的基底，修改會連帶牽動 S1 與 S7，回歸面太大。改用條件式附加句 W-B1。
- **D3 新增 W-B2L 與 W-B7：** 帶「出清前指令」標示的批次，它的每一行 S/P 或 EMERGENCY 賣出指令，以及之後再次出清的回應，都要明講「若未成交，請勿就這批到券商下賣單」。原因有二：
  - N-166 審查已確認，出清後的橫幅不顯示指令列（`EmergencyExitControl.tsx:311-326`），所以這個揭露必須放進 message。
  - S1、S2 有「以上述 X 批為準」這一句，套到幻影批次上會叫 U-B 使用者賣一批不存在的股數。W-B7 用「這幾批的賣出指令不適用於你」把這個衝突解掉。
- **D4 W-B1 加上「無法替你在券商撤單」：** U-A 使用者最有效的補救，是在 T1 開盤前自行到券商撤單。這句是 R10 範圍內的事實，不是建議。
- **D5 `/today` 的揭露 W-B6 必須緊接在 FROZEN_NOTE 之後：** 理由有二：
  - FROZEN_NOTE 寫的是「R 系列進場不執行」（`wording.py:290`），遇到這種待成交買單時，範圍講得太大。
  - 讀碼推定：出清後 `/today` 會在凍結模式下重新評估，`TodayResponse.directives` 只放當次評估產出的指令，所以 T0 那一行買單會從帳冊畫面消失。W-B6 可能是使用者唯一看得到它的地方。
- **D6 標示要以落檔事實判定：** 不得用可被覆寫的 `emergency_until` 反推，因為 C-5 取 max、再次出清也會覆寫。標示要持續到批次 closed 為止，凍結結束後也不撤掉，因為 U-B 的不一致不會隨凍結結束而消失。能不能由既有資料推得，由 TA 判斷。
- **D7 再出清的路徑句：** 只准寫「可再次提交全部出清」。PRD 方案 C 描述中的「需再次出清」，「需」字屬於催促，否決。

#### 3. 揭露是否足夠，會不會被讀成勸阻（EX-5）

只講兩種可能是**必要但不夠**。要另外做到四件事：

1. **時點全覆蓋：** 出清回應（W-B1）、`/today`（W-B6）、結算（W-B3）、批次列與該批每一行指令（W-B2、W-B2L）、再次出清的回應（W-B7）。
2. **未成交那一支要附可操作的安全句：** 也就是「請勿就這批到券商下賣單」。沒有這句，兩支並陳只是裝飾。
3. **已成交那一支要附「無法替你在券商撤單」。**
4. **勸阻防線：**
   - W 系列各句不得談再出清的代價，例如延長暫停、價差。延長凍結的事實已由確認面板核取句 2 承載（C-5 保證預告值等於實際值），並由 N-166 的 S6 在事件發生時揭露。
   - 禁用詞：「需」「應」「建議」「務必」「盡快」「否則」「安全」「已取消」「已撤單」。
   - 兩支不得有預設或「較可能」的暗示。

做到以上四點，就不構成勸阻。另外，EX-5 規範的是確認面板，W 系列都是送出後的回應，不在 EX-5 的直接範圍內，但精神照樣適用。

#### 4. 既有字面的修改：不接受，改採附加句

- RESULT、EMPTY、S1 到 S9、MODE_REASON_EMERGENCY、FROZEN_NOTE、SETTLEMENT_SUMMARY、RULE_TEXT[EMERGENCY] 一字不動。
- 「R 系列（新倉進場）暫停」的範圍，由 W-B1 第二句（出清回應）和 W-B6 第二句（`/today`）承擔。
- W-B4（幻影批次揭露）不另立一句，也不併入 SETTLEMENT_SUMMARY，內容分別併入 W-B3 與 W-B2L。

**message 組合順序**（接續 N-166 的組合順序）：
- RESULT 支：RESULT＋［S2］＋［S3］＋［W-B7］＋［W-B1］＋［W-B1p］＋［S6］
- ALREADY_PENDING 支：S1＋［S3］＋［W-B7］＋［W-B1］＋［W-B1p］＋［S6］
- EMPTY 支：EMPTY＋［W-B1］＋［W-B1p］＋［S6］
- F-c 情境下照樣用 S7 替換凍結子句。W-B1 第二句在「維持暫停」的語境下仍然成立。

**與 N-166 的互動**（書面釐清，修訂範圍只限 N-168）：
- N-166 把歸屬語的渲染條件改成「message 有描述任何指令就渲染」。這條限於 **EMERGENCY 指令**。
- W-B1 列出的是先前已發出的 R 指令狀態，不觸發 EXIT 類歸屬語（EXIT_ATTRIBUTION、S4、S5 用在 R 買單上都是不實陳述），也不在出清橫幅另掛規則歸屬語。EMPTY 支的歸屬語維持 None。
- W-B7 要放在 S1 或 S2 之後，用來覆蓋它們對標示批次的「以上述…為準」。

#### 5. 字面定稿（B-2a，CONDITIONAL APPROVE）

全形標點依 wording.py 館規，「S/P」照現行檔案寫半形。

**共用佔位符格式（逐字）：**
- `{entry_items}` 的每項格式為「{symbol}第 {batch_no} 批買進 {shares} 股（規則 {rule_id}，預定執行日 {execution_date}）」。依 execution_date、symbol、batch_no 遞增排序，以「、」連接。
- `{labeled_items}` 的每項格式為「{symbol}第 {batch_no} 批 {shares} 股」，其中 shares 取 remaining_shares。
- 股數沿用 `_format_shares`。日期用 ISO 格式。

**W-B1 `EMERGENCY_EXIT_PENDING_ENTRY_NOTE`**
- 渲染條件：出清當下存在 action=buy、R 系列、`settled=0`、`status=pending` 的指令。
- 用於三支 message。

「另有 {entry_count} 筆在本次提交前已產生、尚未結算的 R 系列買進指令，不在本次出清範圍，本次未取消、未修改：{entry_items}。本次 R 系列（新倉進場）暫停，是指暫停期間不再產生新的進場指令，不包括上述已產生的指令。本系統不下單，無法得知你是否已依這些指令在券商下單，也無法替你在券商撤單；帳冊會照常以預定執行日開盤價判定，判定成交即記為持有批次並扣除帳冊現金。若你在券商的買進實際成交，實際持股以你的券商回報為準；若未成交（包括未下單或已自行撤單），帳冊判定成交的批次將與你的實際持股不符。上述批次在帳冊記為持有後，可再次提交全部出清，替它們產生賣出指令。」

**W-B1p `EMERGENCY_EXIT_PENDING_ENTRY_PAST_DUE_NOTE`**
- 渲染條件：上述任一筆的 execution_date < as_of（與 S3 同一規則）。

「上述買進指令中，預定執行日 {entry_past_due_dates} 已過、仍未結算；本系統無法得知你在券商是否已買進，請以你的券商回報為準。」

**W-B6 `PENDING_ENTRY_FROZEN_NOTE`**（對應 FR-2）
- 渲染條件：`/today` 的 mode 為 emergency_frozen，且存在上述待成交買單。凍結模式不會產生新的 R 指令，所以不需要新增任何狀態就能判定。
- 位置：warnings 中緊接在 FROZEN_NOTE 之後。

「尚有 {entry_count} 筆在全部出清提交前已產生、尚未結算的 R 系列買進指令：{entry_items}。暫停期間不再產生新的進場指令，但這幾筆已產生的指令未被取消，帳冊會照常以預定執行日開盤價判定，判定成交即記為持有批次並扣除帳冊現金。本系統不下單，也無法替你在券商撤單：若你在券商的買進實際成交，實際持股以你的券商回報為準；若未成交（包括未下單或已自行撤單），帳冊判定成交的批次將與你的實際持股不符。」

**W-B2 `ENTRY_BEFORE_EXIT_LABEL`**（批次標示）
- 渲染條件：批次為 open，且符合 D6 的落檔事實。持續到批次 closed。
- 排版容不下時一律回審，不得縮寫或截斷。

「出清前的買進指令，暫停期間記入帳冊」

**W-B2L `ENTRY_BEFORE_EXIT_NOTE`**
- 位置有兩處，同列、不摺疊、不用 tooltip：
  - 批次列，緊接在 W-B2 之後；
  - 該批次每一行指令（S/P/EMERGENCY），包含 `/today` 帳冊與出清回應的 directives。

「此批次來自你提交全部出清前已產生的 R 系列買進指令，於 {entry_date} 以開盤價在帳冊判定成交後記為持有，未涵蓋在先前的出清內。本系統不下單：若你在券商的這筆買進實際成交，實際持股以你的券商回報為準；若未成交（包括未下單或已自行撤單），你在券商並無對應這批的持股，請勿就這批到券商下賣單。」

**W-B3 `SETTLEMENT_ENTRY_BEFORE_EXIT_NOTE`**
- 渲染條件：本次結算有至少 1 筆符合標示條件的買單被判定為 executed。
- 位置：settlement.warnings 中緊接在 SETTLEMENT_SUMMARY 之後。

「本次結算中，有 {count} 筆是你提交全部出清前已產生的 R 系列買進指令，帳冊已依預定執行日開盤價判定成交，記為持有批次並扣除帳冊現金：{entry_items}。這些批次未涵蓋在先前的出清內，S/P 系列停損停利會照常評估它們。本系統不下單，無法得知你在券商的這些買進是否實際成交：若已成交，實際持股以你的券商回報為準；若未成交（包括未下單或已自行撤單），這些批次與你的實際持股不符。如需讓這些批次也產生賣出指令，可再次提交全部出清。」

**W-B7 `EMERGENCY_EXIT_LABELED_BATCH_NOTE`**
- 渲染條件：本次新寫入的指令，或 pending 覆蓋的指令中，含有符合標示條件的批次。

「上述賣出指令中，有 {labeled_count} 批來自你提交全部出清前已產生、之後在帳冊判定成交的 R 系列買進指令：{labeled_items}。本系統不下單：若你在券商的這些買進實際成交，實際持股以你的券商回報為準；若未成交（包括未下單或已自行撤單），你在券商並無對應這幾批的持股，這幾批的賣出指令不適用於你，請勿就這幾批到券商下賣單；這幾批的賣出指令在帳冊判定成交後，帳冊即不再將其記為持有，帳冊現金會因買進與賣出的判定價格不同，與你的實際現金有差額。」

W-B5（ALREADY_PENDING 支）不另立一句，由 W-B1 與 W-B7 依上面的組合順序承擔。

#### 6. A 方案的 must 級要求與預審稿（CEO 改選 A 時用）

**must 級要求：**
- **MA-1：** W-A1 與 W-A2 放在同一則 message，不得用 tooltip，也不得縮寫。禁用「已取消你的買單」「已為你撤單」「已撤銷委託」這類說法。面向使用者的文字不得單獨使用「撤回」或「取消」。
- **MA-2：** W-A3 不得沿用 MISSED，也不得計入 missed_count。
