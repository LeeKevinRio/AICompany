# 本次結論

**決定：接受現行行為，程式邏輯不改。** S2 處於 `skipped` 時，使用者經 W-2 覆寫寫入的 0.15，下次啟動時照樣會被改成 0.10，並顯示 migrated 告知。要補的只有兩件事：一組釘住此行為的測試，以及一段 docstring。

- 不需要風控或 CEO 裁示：字面、ADR、CEO #63 的範圍都不變。
- 風控「N-156 字面定稿」dev-lead 待辦第 14 項、qa NON-BLOCKING-7 以本回覆結案。
- ADR-0032 不改（ADR-0001:18 禁止原地改寫）。這是確認既有設計，不是新的架構決策，因此不另立 ADR。

## 評估摘要（理由）

1. **這個後果原本就是刻意設計，而且已經揭露。**
   - 風控 2026-10-26 遷移未執行逐字審第 67-69 行寫明：「使用者在這段期間如果刻意存回 15%，下次啟動時會被改成 10%……不寫這條規則，這個後果就被藏起來了」。U1 的括號句（`migrations.py:223-225`）就是為這個情境加的。
   - U5「所有區段都通過驗證時才會執行這次調整……按儲存之後也一樣」（`migrations.py:243-247`）陳述的也是同一件事。
   - W-2 只是讓同一情境多了一條入口。可能發生改寫的情況只有一種：紀錄是 `skipped`（`migrations.py:480-483`）。這時設定頁一定同時顯示 U1 與 U5，所以揭露一定跟著出現。
2. **方向是收緊，而且有明確的逃生口。**
   - 遷移後 migrated 告知的 1-5 寫「包括改回 0.15」。使用者再寫一次 0.15，`note_cap1_write` 會設 `changed_by_user`（`migrations.py:446-456`）。紀錄已是終態（`:104`、`:34-35`），之後永不再改。
   - 這與 CEO #63 書面同意的內容一致：風控 2026-10-26 第1條上限下修審查第 94、157 行寫的是「如果那個 15% 是你刻意設的，可以改回去」。
3. **儲存層分辨不出「刻意的 0.15」和「凍結的舊預設 0.15」。**
   - `store.write` 對每個沒有保留（kept）的區段，都會把當下生效的值整段寫回（`store.py:285-289`）。只存費率的 PUT 也會把已存的 0.15 重寫一次。
   - 若規則改成「寫入 0.15 就不再遷移」，會廢掉 CEO #63 要抓的核心情境：舊預設 0.15 凍結在存檔裡。
   - 只對 W-2 開例外則不一致：一般儲存路徑（例如 cost_model 損毀、risk_budget 從 0.12 改存 0.15）同樣是使用者明確確認的值，卻不受保護。
4. **任何改法都會觸發既有的失效條件。** 涉及 I-6（風控 10-26 第 200-202 行，「紀錄只在建構 store 時更新」）、M-1（第 242 行）、M-7（第 247 行），以及 `migrations.py:38-43` 的不變式「It never touches a skipped record」。U1、U5、S1 都要回送風控重審。

**接受的代價（請 coordinator 轉知）**
- 從下次啟動到使用者再改回之前，第 1 條上限是 0.10。加碼可能變成續抱，也可能開始收到上限推播（1-3 已揭露）。
- 使用者總共要做兩次放寬確認。
- 以本機單人桌面應用來說，可以接受。

## 對實作的約束（交 dev-lead，可與前端同批或另開 chore）

- **C-1** 不得新增任何「寫入時改變 skipped 紀錄」的路徑。`note_cap1_write` 對非 migrated 的紀錄維持直接 return（`migrations.py:447-448`）。
- **C-2** `migrate_cap1_default` 的判定只看啟動當下的原始 payload。不得讀取 W-2 或任何寫入歷史，也不得新增欄位記錄「使用者確認過」。
- **C-3** 在 `migrations.py` 模組 docstring 的「Any invalid section, no migration」段末（約 :27）補一句英文。建議文字：
  > A value written while the record is ``skipped`` -- by a plain save or a W-2 overwrite -- is judged by the same rule at the next start: a stored 0.15 is migrated even if the user has just confirmed it (TA reply to risk N-156 to-do 14, accepted by design). The way out is writing 0.15 again after the migration, which sets ``changed_by_user`` on a terminal record.
- **C-4** 測試放在 `tests/test_settings_migrations.py` 的「A skipped record outlives a save」一節（約 :513 之後），沿用 `_seed`、`_full_document`、`_record`、`MIGRATED_AT`、`LATER`。每個測試的 docstring 都要寫：「accepted by design per TA reply (risk N-156 to-do 14 / qa NB-7); changing it requires risk re-review of U1/U5/S1 (I-6, M-1, M-7) and a CEO ruling on #63」。

## 測試規格

**T-1 `test_a_w2_overwrite_to_the_old_default_during_a_skip_is_migrated_on_the_next_start`**
- 準備：
  - `document = _full_document(0.12)`，`document["risk_budget"] = '{"not": "valid"}'`，寫入 db。
  - `SettingsStore(db, now=MIGRATED_AT)`。
  - 斷言 `status == "skipped"`、`failed_sections == ("risk_budget",)`，取 `before = _record(store)`。
- 動作一：`store.write({"risk_budget": RiskBudget(max_position_weight=0.15)}, overwrite_fallback_sections=("risk_budget",))`。
- 斷言（同一行程、尚未重啟）：
  - `_record(store) == before`：狀態、`recorded_at`、`changed_by_user=False` 都不變（I-6）。
  - `load_with_status().fallback_sections == ()`，且值為 0.15。
  - `settings_notice(current_max_position_weight=0.15, risk_budget_fallback=False)` 逐字等於 U0、U1（含「（已存值等於 15.00% 時改為 10.00%）」）、U2（`current_pct="15.00%"`）、U4、U5。
  - 先取 `snapshot = _rows(db)`。
- 動作二：`restarted = SettingsStore(db, now=LATER)`。
- 斷言：
  - `restarted.load().risk_budget.max_position_weight == 0.10`。
  - 紀錄為 `status="migrated"`、`previous_value=0.15`、`new_value=0.10`、`recorded_at=LATER.isoformat()`、`failed_sections=()`、`changed_by_user=False`。
  - `short_notice(current_max_position_weight=0.10)` 逐字等於 migrated 短句（時間為 `LATER_TEXT`）。
  - settings 告知含 1-3。
  - 「只改一個 key」：`json.loads(risk_budget 原始 payload) == {**RiskBudget(max_position_weight=0.15).model_dump(), "max_position_weight": 0.10}`。
  - 其他三段的列（payload 與 updated_at）與 `snapshot` 相同。
- 動作三（逃生口）：`_put_cap1(restarted, 0.15)`，接著 `SettingsStore(db, now=LATER + timedelta(days=1))`。
- 斷言：值為 0.15；`status="migrated"`；`recorded_at` 仍是 `LATER`；`changed_by_user=True`。

**T-2 `test_a_plain_save_of_the_old_default_during_a_skip_is_migrated_the_same_way`**（防止日後只修 W-2 路徑）
- 用 `_skipped_store(tmp_path, "cost_model", max_position_weight=0.12)` 建立，再 `_put_cap1(store, 0.15)`。
- 斷言一：用 `SettingsStore(db, now=LATER)` 重啟，cost_model 仍損毀。此時應為 `status == "skipped"`、`recorded_at == LATER.isoformat()`、值仍是 0.15、原始 payload 一個 byte 都不變。這釘住「所有區段都通過驗證時才會執行」。
- 斷言二：用 `_seed` 修好 cost_model，再以第三個時間點重啟。此時應為 migrated、值 0.10、`previous_value == 0.15`。

**T-3 `test_a_w2_overwrite_during_a_skip_with_another_value_is_kept`**（參數化 0.12 與 0.10）
- 準備與 T-1 相同。W-2 覆寫為參數值，然後重啟。
- 斷言：`status == "not_applicable"`；值等於參數值；`settings_notice(...)` 與 `short_notice(...)` 都是 `None`。

**T-4（選做，API 層）** 經 `PUT /api/settings`，帶 `overwrite_fallback_sections: ["risk_budget"]` 與 `max_position_weight: 0.15`，重建 store 後，`GET /api/settings` 的 `cap1_migration.status == "migrated"`。
