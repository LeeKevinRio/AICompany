**C. N-118 腳本的常數：方法論建議（只給文字建議，腳本沒有改）**

1. **`TAIL_GAP_DAYS`：建議取 3，不取 7。**
   - 這個值是日曆天：除息日減去「除息日前最後一個 ok run 的 session_date」。
   - 正常情況下，除息日前一個交易日到除息日相差 1 天，跨週末是 3 天。大於 3，代表除息日前至少漏看了一個平日，除非剛好遇到連假。
   - C1 唯一的誤判來源就是「除息日前最後一批回應漏列」（風控 R-Q2），所以尾段要盡量完整。取 7，等於把最後將近一週沒觀察到的事件也算成「持續列出」。這正好落在要驗證的區間，會高估證據。
   - 取 3 的代價是：遇到連假（例如農曆年）的事件會被多標。方向是 fail-closed，而腳本沒有交易日曆，無法分辨連假，所以接受這個代價。
   - 連帶建議：樣本是否足夠（下一點）只計尾段完整的 closed 事件，也就是 gap ≤ 3 的事件。tail-gap 事件另外列數，不計入足夠性。
2. **樣本足夠性：`MIN_USABLE_RUNS` 從 20 提高到 60（以不同的 session_date 計），`MIN_TESTABLE_CLOSED` 從 30 提高到 60。**
   - 要估的是「單次回應不完整」的機率，這是 run 層級的事件。同一個 run 裡的事件高度相關，所以有效樣本大致是 run 數，不是事件數。
   - 用 rule of three 算 0 次失敗時的 95% 上界（約 3/n）：
     - 20 個 run 只能說「每次回應不完整的機率 ≤ 15%」，太弱。
     - 60 個 run（約 3 個月的交易日）可以到 ≤ 5%。
     - 60 個事件也可以到 ≤ 5%。
   - 這兩項建議另外要求：
     - 涵蓋除權息旺季，也就是至少有一部分 session 在 6～9 月。淡季的預告表列數少，對漏列不敏感。
     - 結論欄位除了計數，也印出這兩個上界，讓風控看到的是區間，不只是「達標」。
   - 依 data-engineer 的查證，市場 DB 目前很小，閘門很可能長期關著。這是風控已接受的 fail-closed 結果。
3. **整批下降：維持 3 與 0.10，但把衡量對象改掉。**
   - 現行比較的是原始 `row_count` 的跌幅。但事件過了除息日，本來就會正常移出預告表，旺季時同一天大量除息，跌幅超過 10% 是常態，會誤報。
   - 建議改量「提前消失數」：上一個 run 有、本 run 沒有，而且 ex_date 晚於本 run session_date 的 key 數。門檻是 ≥ 3，而且 ≥ 0.10 × 上一個 run 中 ex_date 晚於本 run session_date 的 key 數。原始 `row_count` 跌幅照列，不設門檻。
   - 絕對值 3 用來過濾單一事件改期的雜訊。10% 夠嚴，足以抓到半批以上的截斷。
   - 反例規則「任何 closed 的 vanished_returned 事件」建議維持零容忍，這一條方向正確。
4. **程序上最重要的一點：** 上面這些數值，都必須在 CEO 跑腳本、貼回輸出之前定案並登記。看過輸出才定門檻，就是事後調參，同樣違反事先宣告的精神。建議由 coordinator 送風控確認後寫回腳本常數，再請 CEO 執行。
