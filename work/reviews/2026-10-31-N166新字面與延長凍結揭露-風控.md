## 1. 本次結論

**審查結論：CONDITIONAL APPROVE。** 下方第 3 節列的條件全部做到，N-166 才能合併；少任何一項就視同 VETO。

1. **`EMERGENCY_EXIT_ALREADY_PENDING`**：字面定稿如 S1。內容自成一段，原因是前端出清後的橫幅只顯示 message、mode_reason、attribution、warnings，不顯示任何指令列（`EmergencyExitControl.tsx:311-326`）。Q5 狀態 (iii) 裡，使用者可能從沒收到第一次的回應，所以這句必須把先前那份指令的內容完整講一遍。
2. **要掛歸屬語，但不能沿用 `EXIT_ATTRIBUTION`。** 新增兩句：只有先前指令時用 S4（PRIOR）；本次新指令和先前指令同時存在時用 S5（MIXED）。題 7「directives 空時不渲染」改為「message 有描述任何指令（不論本次或先前）就渲染」。
3. **#77 延長凍結**：只放在回應 message，不放 mode_reason。三支 message 都適用，只要真的延長，就在句尾加 S6。這句不需要儲存任何新狀態。另外補上 F-c 情境（既有截止日晚於新算值）的替代字面 S7、S8、S9。理由是採 max 之後，這個情境會在正常流程中出現，而現行字面在這種情況會變成不實陳述。
4. **部分覆蓋（RESULT 支）**：現行字面不夠，要加 S2。若先前指令的預定執行日已過，再加 S3。
5. **NB-6**：要維持到 N-166 合併，而且本審查第 3 節的條件全部落地為止。合併後，「重送是安全的」這類說法改為永久禁止，不會因合併而解禁。

## 2. 各部門回報

### risk-compliance-officer（本人，唯讀）

**逐字定稿**（「」內為逐字；全形標點依 wording.py 慣例；「S/P」照現行檔案寫半形）

**S1 `EMERGENCY_EXIT_ALREADY_PENDING`**（新增；APPROVE）
「EMERGENCY_EXIT 已受理：本次未產生新的賣出指令。目前全部 {pending_batches} 批、共 {pending_shares} 股的持有批次，都已有你先前提交全部出清時產生、尚未結算的賣出指令（預定執行日 {pending_execution_dates} 開盤以市價單送出）；這些先前的指令仍然有效，本次未取消、未修改，也未重新產生。本次回應不是另一筆賣出指令，請勿據此到券商重複下單；若你尚未依先前的指令下單，以上述 {pending_batches} 批、共 {pending_shares} 股為準。市價單在跌停或無量時可能無法成交，實際成交結果以你的券商回報為準；R 系列（新倉進場）自 {executed_at} 起暫停 {freeze_days} 交易日（依交易日曆），預計 {until} 恢復；S/P 系列停損停利仍照常評估。」

逐項對照 CEO 的要求：
- 「請勿據此到券商重複下單」：告訴使用者不要重複下單。
- 「仍然有效，本次未取消、未修改」：告訴使用者先前的指令仍然有效。「有效」限定在本系統內的狀態，不宣稱券商端的狀態。
- 全句沒有「已執行／已成交／已出清」這類完成式（R10、覆審定稿）。
- 全句沒有「安全／放心重送」，也沒有任何暗示重送是安全的說法。
- 「若你尚未…以上述…為準」是給 Q5 狀態 (iii) 的使用者（第一次回應遺失）。沒有這句，「請勿重複下單」會讓這種使用者完全不賣，等於擋住出口，牴觸 EX-2。

**S2 `EMERGENCY_EXIT_PENDING_NOTE`**（新增；APPROVE）
- 用途：有新指令、同時也有既有覆蓋時，接在 RESULT 全文之後。
「另有 {pending_batches} 批、共 {pending_shares} 股已有你先前提交全部出清時產生、尚未結算的賣出指令（預定執行日 {pending_execution_dates} 開盤以市價單送出），本次未重新產生；這些先前的指令仍然有效，請勿就這 {pending_batches} 批到券商重複下單；若你尚未依先前的指令下單，以這 {pending_batches} 批、共 {pending_shares} 股為準。」
- 理由：RESULT 的「已產生 {batches} 批」只算新指令。使用者送出的是「全部出清」，只看到部分批數，會以為其他批次沒有處理，或以為要自己再補單。

**S3 `EMERGENCY_EXIT_PENDING_PAST_DUE_NOTE`**（新增；APPROVE）
- 用途：只要任一先前指令的 execution_date < as_of，就接在 S1 或 S2 之後。
「先前的指令中，預定執行日 {past_due_dates} 已過、仍未結算；本系統不下單，也無法得知你在券商是否已賣出，請以你的券商回報為準。」

**S4 `EXIT_ATTRIBUTION_PRIOR`**（新增；APPROVE）
- 用途：ALREADY_PENDING 支的 attribution。
「此指令是你在先前操作中提交的「全部出清」要求之機械執行結果，非本系統的判斷或建議；EMERGENCY_EXIT 不依賴規則集，無論規則集是否已確認皆可送出。」

**S5 `EXIT_ATTRIBUTION_MIXED`**（新增；APPROVE）
- 用途：RESULT 支、且 pending 不是空的時候的 attribution。
「本次新產生與先前已有的賣出指令，都是你分別在本次與先前操作中提交的「全部出清」要求之機械執行結果，非本系統的判斷或建議；EMERGENCY_EXIT 不依賴規則集，無論規則集是否已確認皆可送出。」

歸屬語的用法：
- RESULT 支、且沒有 pending：照舊用 `EXIT_ATTRIBUTION`，一字不改。
- EMPTY 支：照舊為 None。

**S6 `EMERGENCY_EXIT_FREEZE_EXTENDED_NOTE`**（新增；APPROVE）
- 用途：三支 message 都適用，接在整段 message 的最後。
- 渲染條件要三項同時成立：鎖內讀到的 `previous_until` 不是 None；`as_of <= previous_until`（也就是本來就在凍結中）；生效的 `until > previous_until`。
「因本次再次提交全部出清，R 系列（新倉進場）的預計恢復日由 {previous_until} 延後至 {until}，暫停交易日數改自 {executed_at} 起重新計算。」
- 放在 message 的理由：mode_reason 由 `emergency_frozen_day` 從 until 往回倒數（`engine.py:124-138`），延長後當天會顯示「第 1/20」。使用者需要知道計數為什麼重算，而這只有在事件發生的那次回應裡講得出來。
- 不放 mode_reason 的理由：要在狀態列每天講「曾被延後」，就得儲存舊截止日或旗標，違反 C-9。而且狀態列的「預計 {until} 恢復」每天即時算，本來就正確。

**S7 凍結延續子句**（F-c 情境專用；APPROVE）
- 情境：既有截止日晚於 `shift(as_of, freeze_days)`。
- 用法：替換三支 message 句尾從「R 系列（新倉進場）自 {executed_at} 起暫停…」到「…照常評估。」這一段。
「R 系列（新倉進場）維持暫停，預計 {until} 恢復（依交易日曆；沿用先前已設定、較晚的恢復日，本次未縮短）；S/P 系列停損停利仍照常評估。」

**S8 `MODE_REASON_EMERGENCY` 無計數版**（APPROVE）
- 渲染條件：只在 `trading_days_between(data_date, until) > freeze_days` 時使用。這時計數會被 clamp 住，連續多天都顯示「第 1/20」，是不實的。
「緊急出清後凍結：R 系列（新倉進場）暫停中，預計 {until} 恢復（依交易日曆）；S/P 系列停損停利仍照常評估。」
- 這是 VETO-4「第 N/20」要求的例外，只限這個異常分支，由本人核可。

**S9 核取句 2 的 F-c 版**（APPROVE）
- 渲染條件：只在 `build_exit_confirm` 依 max 規則得出的截止日不等於 `shift(as_of, freeze_days)` 時使用。
「送出後，R 系列（新倉進場）維持暫停（預計恢復日：{FREEZE_UNTIL}，依交易日曆計算；沿用先前已設定、較晚的恢復日）。」

**組合順序**
- RESULT 支：RESULT ＋［S2］＋［S3］＋［S6］
- ALREADY_PENDING 支：S1 ＋［S3］＋［S6］
- EMPTY 支：EMPTY ＋［S6］
- F-c 情境下，三支的凍結子句一律換成 S7；S6 和 S7 不會同時成立。

**逐條意見**

- [wording.py] 新增 S1～S9 共九個常數，字面逐字照抄 → required
- [service 組 message] 佔位符的定義 → required
  - {pending_batches}：被覆蓋的 open 批次數，以 (symbol, batch_no) 去重。
  - {pending_shares}：這些批次的 remaining_shares 合計，不可用 pending 指令股數相加。原因是既有 DB 可能已有 N-166 之前留下的重複列，相加會再次出現雙倍股數。
  - {pending_execution_dates}／{past_due_dates}：去重、遞增排序、ISO 格式，以「、」連接。
  - {previous_until}：C-2 在鎖內讀到的 `emergency_until`。
- [mode_reason] 不新增任何「延後／重複」字樣，維持只從 `emergency_until`、日曆、params 即時算出（C-9）→ required
- [store] S6、S8 不得新增 column、state key 或旗標。S6 的事實只在當次 transaction 的記憶體中比對產生 → required
  - message 若照舊留存在 R16 紀錄裡可以接受：「由 X 延後至 Y」是事件當時的事實，存下來永遠為真，不是 mode_reason 快照。
- [前端] 不需要改程式碼。橫幅照原文顯示 message 和 attribution，所以 S1、S4、S5 自然會出現。`EmergencyExitControl.tsx:307-309` 的註解要補上「ALREADY_PENDING」→ suggested
- [核取句 1]「全部批次送出出清指令」在重複按的情況下，嚴格說只補還沒覆蓋的批次 → 不改
  - 理由：操作的淨效果仍然是全部批次都有出清指令，送出後的 message 會講清楚實際狀況。
- [確認畫面] 延長凍結時，送出前不另加揭露句 → 不要求
  - 理由：C-5 保證核取句 2 的預計恢復日就是實際值。再加一句等於在出口加摩擦（EX-2、EX-5）。
- [ErrorPanel「全部出清送出失敗」] 500 時後端可能已寫入，「失敗」是斷言 → 歸入 NB-6 處理，不擋 N-166
  - 要求：NB-6 的文案不得斷言「什麼都沒發生」，也不得暗示重送安全。

**否決理由**：本次不否決。但若沒有 S1 裡「若你尚未依先前的指令下單…為準」這一句，本人會 VETO。理由是牴觸 EX-2：出口實質上被一句「請勿重複下單」擋住。
