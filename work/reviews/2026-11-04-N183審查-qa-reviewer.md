## 各部門回報

### 重點 1：fetchStatusSignal 與 hook
- `fetchStatusSignal` 的對應是 fetching 回 true、idle 回 false、paused 回 null，正確。
- hook 在 effect 開頭 `if (fetching === null) return;`，所以 `fetchingRef` 和 controller 都不更新。paused 時 phase 維持 waiting，連線恢復後真正從 fetching 變成 idle 才進判定。
- 時序：paused 是 effect 依賴值的暫時變化（true、null、true）。第二個 true 會再呼叫一次 `fetchingChanged(true)`。測試 (a) 的 `fetching → paused → fetching → idle` 涵蓋這條路徑並通過，所以重複呼叫是安全的。
- 補償的其他邏輯完全沒動：觸發門檻 12、目標 16、同步點 2 frame 且上限 60、額度、手動捲動偵測。diff 裡 `receiptCompensation.ts` 只新增一個純函式，hook 只有一行 import 和 effect 這 3 行。
- 初次掛載時若 `fetchStatus` 就是 paused，`fetchingRef` 維持初值，不會誤判。

### 重點 2：新增行為測試
- (a) 兩種情境都有效：
  - fetching 後 paused：沒有捲動，phase 為 waiting；恢復後 fetching → idle 才補償一次，量到 `160-(277+16)`。
  - arm 時 refetch 已在進行中（`arm(1, true)`）：paused 後 `flushFrames` 沒有捲動，idle 後才有 1 次捲動。
- (b) 已知限制被鎖住：
  - 測試依序驗證「arm 前已結束」不判定、phase 維持 waiting，再來一次 idle 也不是同步點，要下一次 fetching → idle 才補償。
  - 註解寫明這是交件解讀點 4 的已知限制，並寫出理由（首捲用即時的狀態列高度，損失視窗很小），也註明「要改須連同規格一起改」。寫法恰當。
- 測試用的 `feed` 輔助函式在測試端重現 hook 的「null 跳過」。hook 本身沒有被實際執行，所以這是間接保護，補強靠下面第 3 點的結構測試。這是 low（可維護性），不阻擋，理由是專案測試為純 Node vitest。

### 重點 3：結構測試是否擋得住
- `innerHeight`、`visualViewport`、`clientHeight`：hook 與 lib 各自擋，並保留 `OVER_HALF`。
- `onscroll`：hook 與 lib 都加了，且不分大小寫，也就擋得住 `onScroll`。
- 防回退：要求 hook 含 `fetchStatusSignal(fetchStatus)`，且不得出現 `fetchStatus\s*===`。
- 新增 low 項目（可維護性）：這條防回退只擋 `===`。回退時若寫成 `!==`、`switch` 或 `fetchStatus == "fetching"`，結構測試擋不住。建議之後把正則放寬成 `fetchStatus\s*[!=]==?`，並補一條 `switch\s*\(fetchStatus`。不阻擋，因為「必須含 `fetchStatusSignal(fetchStatus)`」那條已有主要防護。
