# quant-researcher 回報：`^TWII` 缺一天 bar 的機制分析（只讀，未改任何檔案）

## 一、本次結論

**這個問題不需要在 CEO 正式登記之前處理，登記也不必為它延後。不過要在接線 PR 裡、第一筆 `forecast_run` 之前補一條「只留證據、不改計算」的防線。**

理由有三：
- **程式做的就是已登記的定義。** 事先宣告 v0.32 附錄 B.1 §2.1 寫明：「核心期間的觀察日＝快照中連續的定案 bar。不讀交易日曆……所以『L 日』一律指 L 根 bar」（L2780-2781）。σ_d 另有 V32-03 註（L1113）。所以位置對齊不是 bug，改成按日曆對齊反而等於改規則。
- **缺口真正的害處在證據。** 被丟的列在 adapter 就消失了，連 `dropped_rows_json` 都沒有記錄。日後驗證層就算標得出「這筆有缺日」，也分不出原因（來源給了 null 列，還是休市）。
- **`record_forecasts` 目前在 app 內沒有任何呼叫者**（data-engineer 報告 L63），還沒有任何紀錄。現在加防線，既不會觸發 D-4 第 6 點的跨 commit 重算，也不會讓既有紀錄的證據缺一塊。

## 二、各部門回報（quant-researcher）

### 1. 機制：全部按位置取，不按交易日曆對齊【已證實】

- **取數方式**：
  - `_cut_snapshot` 取最後 `size` 根 bar（`inputs.py:192-196`）。
  - `snapshot_view` 只檢查嚴格遞增，不檢查連續（`inputs.py:174-176、280-290`）。
  - 各特徵都按 lag 索引讀值：`mean_close` 取 `closes[:L]`（`engine.py:223-230`），z 的分子是 `closes[0]/closes[L]`（`engine.py:261-267`），r_k 是 c_k 除以 c_{k+1}（`volatility.py:126-139`）。
- **合成序列實測**：拿掉真實 lag 10 那一天後，快照 lag 0～9 的日期不變，lag 10 起全部往前錯一個交易日。腳本在 `/tmp/claude-0/-home-user-AICompany/3f76d891-50d3-55e1-b39d-925b8a90241a/scratchpad/gap_demo.py`。
- **各特徵受到的影響**（缺口位於快照 lag g-1 與 lag g 之間）：

| 特徵 | 受影響的條件 | 會發生什麼 |
|---|---|---|
| `close` | 只要 g ≥ 1 就不受影響 | — |
| `ma20` / `ma60` | g ≤ 19 / g ≤ 59 | 窗口多吃進更早的一根 bar：20 根 bar 實際橫跨 21 個交易日（MA60 同理） |
| `z_past_3` / `z_past_5` / `z_past_20` | g ≤ L | 分子其實是 L+1 個交易日的報酬，卻仍以 √L 換算 |
| σ_d（`z_past_*` 的分母，也存進 `band_def`） | g ≤ 60 | 跨缺口的那個位置是兩日報酬，被當成一個日報酬計入，σ_d 偏大；窗口也往前延伸一天 |
| `vol_ratio_20_120` | g ≤ 20 時分子受影響，g ≤ 120 時分母受影響 | 同上，混入一個兩日報酬 |
| B1、B2、B8 | 同樣按位置計算（`baselines.py:75-131`） | B2 的 250 個位置中，跨缺口的位置變成 h+1 日的實現標籤 |

- **不會觸發任何缺項代碼**：`E-BARS-SHORT` 只數根數；N_SNAPSHOT 是 315，遠大於所需的 121 根。
- **一次缺日的影響期**：之後約 120 筆紀錄的特徵都會受影響；B2 受影響約 314 筆。
- **缺的是最新一天 T 時**【已證實】：
  - null 列不會變成 `DroppedRow`，所以不會進入 `inputs_not_ready`，也不會判 `insufficient`。T-1 直接被當成最新一天（`inputs.py:228-246`）。
  - 若 T-1 已有紀錄，判 `no_new_session`（`recorder.py:366-368`）；若 T-1 還沒有紀錄，就補寫一筆 T-1 的紀錄，且依 D-3 第 3 點會是 `late=1`。
  - 實質上就是 D-3 第 2 點禁止的「改用前一天」，只是沒人察覺。
  - F-2 數的是「最新快照中出現、但沒有紀錄的 session」，T 不在快照裡，所以不會被算到。
  - `Phase0Grid` 以各快照 session 的聯集取格點（`store.py:424-438`）。這一天若在每份快照都缺，之後的格點全部錯開一相位（推論）。

### 2. 實現標籤：核心按位置，驗證層按交易日曆

- **dirdef 本身**：沒有位置邏輯【已證實】。
- **核心的暫定對照**【已證實】：
  - T+h 取快照中 T 之後第 h 根 bar（`scoring.py:189-193`）。
  - 接著與「所有已存快照的定案 session 聯集」比對，不一致就判 `session_gap`（`scoring.py:197-199`，`report.py:215`）。
  - 這一天若在**每一份**快照都缺，比對照樣通過，T+h 會悄悄變成第 h+1 個交易日。
  - 不過暫定對照的結果不寫入任何表（D-5 第 5 點），不會污染紀錄。
- **驗證層（凍結的設計）**【已證實】：
  - T+h 是觀察日（D-8.1，來自市場 DB）中的第 h 個交易日（§6.3「觸發」L1871-1875）。
  - T+h 的 bar 不可用時，該日不算已觀察到，先順延，之後依 `missing_bar_after_wait` 處理（§1.1 L925）。最後判 `unresolvable_missing_data`，計入作廢率與最不利情境 W。
  - 這些條文已寫明，但在核心期間隨 ADR-0030 D-8 凍結：§0.1 表把 §6.3 標為隨 D-8 凍結（L898）；ADR-0030 L45、L226 凍結驗證層與缺日稽核，L56、L301 已揭露「作廢可能較多」。

### 3. 事先宣告是否已涵蓋

- **已寫明的部分**【已證實】：
  - 特徵按位置計算（B.1 §2.1 L2780-2781；§2.4 L2815）。
  - σ_d 與日後依觀察日重建的結果不一致時：「不得回頭改寫已記錄的 σ_d(T)；兩者不一致的筆數由驗證層揭露」（V32-03，L1113）。
  - 記錄當下只有「T 日 bar 不定案」會判 `inputs_not_ready`（L925）。
  - 格點失去後不得補位（§4.1 L1275）。
- **沒寫到的部分**：
  - 來源丟列造成的缺口：沒有記錄時點的判定，也沒有揭露規定。
  - MA、z、vol_ratio 跨缺口時的揭露。
  - 「T 被跳過」的情況。
- **結論**：現行程式符合已登記的條文。
- **登記後還能補的**：
  - 只記錄證據、不改變 `compute_outlook` 對任何快照的輸出：屬資料品質防線，不必另開新 claim。
  - 驗證層把「輸入窗含缺日」判為作廢並計入 W：屬收緊，依 D-8 第 5 點可行。
- **會被視為改規則或改定義、須另行宣告並從零計數的**：
  - 改成按日曆對齊。
  - 新增缺項代碼。§5.2 標題 L1750 明寫「新增代碼視同改定義，要升版」；`MISSING_CODES` 有測試鎖定（`tests/test_outlook_missing_codes.py:42-51`）。

### 4. 事後能否辨識

- **可以標出來，但要有獨立的交易日曆**【推論，依據已證實】。`bars_json` 有完整的 `session_date`，只要對一份獨立日曆就找得到缺口。
- **辨識不出、或辨識不準的情況**：
  - **app 內唯一的交易日曆是用 bar 日期反推的**（`calendar.py:31-44`），和受檢資料同源，對不出缺口；`session_calendar.py` 自己也沒有交易日清單（L15-19）。
  - **退回「週一至週五」規則**：每個休市日都會被誤標成缺口。官方休市日表尚未接入（§9.3 第 18 點 (i)，屬 ADR 決策）。
  - **改用市場 DB 觀察日 D-8.1 (i)**：可用，但它本身也會因排程停擺而缺日。
  - **跨快照比對**：只有在來源後來補上那一列時才有效。
  - **原因永遠分不出來**：被丟的列不在 `dropped_rows_json` 裡，無法分辨是來源 null 還是休市。
  - **T 被跳過**：只會表現為「少一筆紀錄」。

### 5. 嚴重度與建議

- **登記前處理**：只有「改按日曆對齊」需要在登記前做。但那要重開 v0.32 的 sha、規則雜湊與 dirdef，還要一份現在沒有的官方日曆。不值得，也不建議。
- **接線 PR 處理（建議）**：成本低，此時沒有既有紀錄要重算。
- **只留給驗證層**：做得到標記，但原因證據已失，作廢會偏多。ADR-0030 L56 已接受這項代價，但能補救的部分不必放棄。

**(a) 不改任何已凍結物的做法**

- **既有代碼沒有語意相符的**：
  - `E-BARS-SHORT` 是根數不足，不是缺日。
  - `E-PRICE-UNUSABLE` 指快照中「已存在的 bar」收盤不可用；被丟的列根本不在快照裡。
  - `E-VOL-*`、`E-PIT-UNVERIFIED` 都不相干。
  - `inputs_not_ready` 是 run 的 outcome，不是缺項代碼；D-3 第 2 點只把它用在「T 不定案」。
  - `session_gap` 只存在於暫定對照。
- **建議做法**：
  1. cache 路徑比照 raw 路徑既有的 `null_gap_rows`（`yfinance.py:28、361-381`），把 null 列往上傳，記進 `dropped_rows_json`，並給一個新的 reason。
     - `DropReason` 加值屬 ADR-0030 補充，需 TA 起草、風控確認，不涉及規則雜湊。
     - 這一步不改快照的 bar、不改 T、不改計算。`dropped_rows_json` 在 DB 層沒有 reason 的 CHECK（`schema.py:167-168`），但 `DropReason` 是 Literal，程式要一起改。
  2. 操作者報告列出「快照 session 對照週一至週五／所有快照聯集」的缺口日期，只列日期，不含標籤或統計（受 D-3 第 5 點約束）。
  3. data-engineer 保存一份獨立的 TWSE 交易日來源，供驗證層使用。
- **可選（需 TA 裁定）**：若最新一列是平日的 null 列，且已過 15:00，就比照 D-3 第 2 點判 `inputs_not_ready`。前提是 data-engineer 先查證 Yahoo 不會在休市日也吐 null 列。
- **不建議**：快照只要含缺口就一律拒寫。一次缺日會讓之後約 120～314 筆紀錄寫不出來，F-2 必然觸發。

**(b) 要動已凍結物的做法及後果**

- 改按日曆對齊，或新增 `E-SESSION-GAP` 一類代碼：dirdef 與規則都要升版，事先宣告要出新版。登記後才做的話，依 V32-05 要登記新 claim，n 歸零；若程式已變更，D-4 第 6 點的重算會先判 `gate_closed`。
- 保留「收盤有效、開盤為 null」的列進快照：牽涉 D-5 的 bar 內容與 canonical（canonical 拒收 None），需 TA 出 ADR 補充。

### 6. 紙上對沖的 `open_unusable`：同意，但要補幾點

以下列入第二段事先宣告的草擬清單，現在不寫宣告：
1. **「應有交易日」的日曆來源要事先指定**：寫明來源、版本、涵蓋範圍。不能用 `session_calendar`，它沒有交易日清單；也不能用以 bar 反推的日曆。日曆不可得時，一律判 `unusable`。
2. **T+1 指日曆上的下一個交易日**，不是快照中的下一根 bar。
3. **開盤的可用條件**：為有限值、> 0、low ≤ open ≤ high（含端點）。high、low 本身也要是有限值、> 0，且 high ≥ low，否則判 `unusable`。這根 bar 還必須已定案（`is_final`）。
4. **以哪一次擷取為準要事先固定**（例如第一次定案擷取），不得挑選擷取次。
5. **處理方式**：判作廢、計入作廢率與 W；不得以收盤價或隔日開盤代替。
6. **TWSE 外部核對（data-engineer R3）**：只能收緊，核對時點要事先固定。
