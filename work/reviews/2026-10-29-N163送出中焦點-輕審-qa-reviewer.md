## NON-BLOCKING

1. **[Edge case][medium] `mutation.isPending` 在同一 tick 內仍是 false，有重入窗口；建議加 ref 型同步鎖。**
   - 位置：`apps/stock-desk/frontend/app/playbook/EmergencyExitControl.tsx:94-105`（`submit`）。
   - 我查了受測樹內 `@tanstack/query-core` 的 `notifyManager.js:3,13-21`。`mutate()` 內部的 dispatch 是同步的，但通知 observer 走 `systemSetTimeoutZero`（setTimeout 0）。React 要等到那個 macrotask 觸發、再 re-render 後，`mutation.isPending` 才會是 true。
   - `submit` 讀的是上一次 render 閉包裡的 `mutation.isPending`。所以在同一個 tick（例如 `button.click()` 連呼兩次、自動化工具、主執行緒卡頓時瀏覽器佇列中兩個已排隊的 click）內，第二次呼叫看到的仍是 false。
   - 第二次 `mutate()` 不會被 React Query 去重。observer 會換掉 `#currentMutation` 並再發一次 POST。
   - 一般人手動雙擊間隔遠大於 setTimeout 0 加一次 render，所以實務機率低。
   - 這不是回歸：原本的原生 `disabled` 也要等 re-render 才生效，窗口相同。本次新增的防護只補了「pending 已 render 之後」的途徑（Enter、Space、點擊 aria-disabled 按鈕），這部分有效。
   - 建議：加 `const submittingRef = useRef(false)`。`submit` 開頭檢查 `submittingRef.current || mutation.isPending`，通過後立刻設為 true。在 `mutate` 的 `onSettled` 設回 false（或用 `mutateAsync().finally`）。`cancel` 可共用同一個 ref。再加一則原始碼掃描測試，斷言 ref 檢查在 `mutate(` 之前。
   - 後端是否冪等我沒查到明確證據。`service.py` 的 emergency_exit 註解沒有寫重複呼叫的行為，需要時請 tech-architect 或 backend 確認。

2. **[可維護性][low] `aria-disabled={mutation.isPending}` 在非 pending 時渲染成 `aria-disabled="false"`。** 功能無誤，Tailwind 的 `aria-disabled:` 只匹配 `="true"`。如要少一個屬性，可改 `aria-disabled={mutation.isPending || undefined}`。測試 1 的 `toHaveLength(2)` 比對的是字串 `aria-disabled={mutation.isPending}`，改的話要同步改測試。

3. **[可維護性][low] 測試 6 偏弱。** 「恰好 4 處 `.focus()`」和 `}, [step]);` 的比對，對未來新增合理的 `.focus()` 會誤報，對行為回歸又只是間接。交件已誠實註明只是原始碼掃描。實機驗收補上即可，不用現在改。

4. **[可維護性][low] 註解用詞。** 檔內註解「these two buttons use `aria-disabled`」前面混了中文「送出中」。CLAUDE.md 規定程式碼註解一律英文，建議改成 "While submitting, these two buttons…"（`EmergencyExitControl.tsx:259`）。

## 逐項查核（對應你列的 5 點）
1. **重入**：結果如上。pending 已 render 之後的所有途徑（click、Enter、Space）都被 `submit:98` 與 `cancel:89` 擋住，且位置在 `mutate` / `setStep` 之前。同一 tick 窗口見 NON-BLOCKING 1。失敗後 `isPending` 回 false，使用者可以再按送出，行為正確。
2. **四項不變**：
   - Esc 鎖：`useEffect` 第 131-138 行仍有 `!mutation.isPending`，未動。
   - Tab 限制：`FOCUSABLE_SELECTOR` 只排除 `[disabled]`，`focusTrap.ts` 未改。焦點留在 dialog 內，`onKeyDown` 才會冒泡到 dialog 根節點。這也正是原缺陷的根因：焦點掉到 body 後，keydown 不在 dialog 內，trap 失效。
   - 失敗後焦點：焦點 effect 只依賴 `[step]`，pending 和 error 不會重跑。按鈕是同一個 DOM 節點，只換文字，焦點留在「確認送出全部出清」。
   - 成功後歸還：`onSuccess` 觸發 `setStep("idle")`，`wasOpen` 為真，焦點回 `triggerRef`。路徑未動。
3. **樣式**：Tailwind 4 的 `aria-disabled:` 對應 `[aria-disabled="true"]`，寫法正確。`aria-disabled:hover:bg-*` 疊加後是 `[aria-disabled=true]:hover`，特異度高於 `hover:`，hover 會被蓋掉。取消鈕的基底沒有背景色，用 `bg-transparent` 正確；送出鈕還原為 `bg-neutral-800`，與基底一致。取消鈕補上 `cursor-not-allowed`，符合 ui-delivery-checklist 2.6 三通道。我沒自己 build，交件稱 build 後 CSS 已確認，實機請再看 hover。
4. **範圍**：只動兩檔。字面、API、核取方塊、Step 2 的 `disabled={!allExitChecksConfirmed(checks)}`（第 226 行）都沒動，diff 中也沒有出現。`submit` 唯一呼叫點是 `onClick={submit}`，簽章改成接 event 沒有其他呼叫端受影響。`React.MouseEvent` 沿用檔內已有的 `React.KeyboardEvent` 全域型別用法。
5. **測試**：
   - 新增 6 則，都是在檔尾追加，既有斷言沒有被改動或放寬（diff 只有 `@@ -154,3 +154,77 @@` 一段純新增）。
   - 測試 1 的兩條 regex 能分辨 `aria-disabled=` 與原生 `disabled=`（前置 `(?<![-\w])`）。
   - 測試 3、4 驗證防護位置在 `mutate` / `setStep` 之前，`functionBody` 對 `function submit(event: React.MouseEvent<HTMLButtonElement>)` 的括號解析正確（先找第一個 `)` 再找 `{`）。
   - 測試 5 驗證 `focus()` 在 `mutate` 之前，並確認 `onClick={submit}`。
   - 結論：6 則是有效的結構性防回歸，但無法驗證真實焦點、真實 CSS，也沒有覆蓋 NON-BLOCKING 1 的同 tick 重入。
