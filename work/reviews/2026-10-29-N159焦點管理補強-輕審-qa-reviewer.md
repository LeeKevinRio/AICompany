## 七項核對
1. **焦點移入落標題：理由成立，採納。**
   - `EmergencyExitControl.tsx` 的 effect（依 `[step]`）在 `step !== "idle"` 時呼叫 `headingRef.current?.focus()`。兩個 `<h2>` 都有 `ref` 與 `tabIndex={-1}`。
   - 出清是不可逆的高摩擦流程（視覺規範 §4.3、EX-2）。焦點若落在第一個核取方塊，使用者一按 Space 就勾掉第一條事實，繞過逐條閱讀。落標題可以避開，螢幕閱讀器也會先讀出步驟名稱。
   - WAI-ARIA APG 允許在內容需先閱讀時，把焦點放在靜態元素（`tabIndex=-1`）。這與 `EditPositionModal` 的「落第一個欄位」不同，但該 modal 是編輯表單，語意不同，可接受。
   - Tab 路徑沒有問題：`FOCUSABLE_SELECTOR` 排除 `tabindex="-1"`，標題聚焦時 `activeIndex=-1`。`trapTabTarget` 對 Tab 回 0（第一個可聚焦元素），對 Shift+Tab 回 last。
   - Step 2 切到 Step 3 時，兩個 `<h2>` 在不同的條件分支，會 unmount 再 mount。ref 在 commit 階段掛上，早於 effect，所以焦點會落在新標題。
   - 初次 mount 時 `previousStepRef` 為 `"idle"`，`wasOpen=false`，不會搶焦點。StrictMode 的 effect 雙跑也不會出事。
2. **焦點歸還：三條路徑成立，unmount 與消失的情境安全。**
   - 取消、Esc、送出成功都經過 `setStep("idle")`，effect 走 `else if (wasOpen) triggerRef.current?.focus()`。portal 內的焦點元素被移除後，在 effect 階段把焦點交還觸發鈕，時序正確。
   - 元件 unmount：effect 只在 `step` 變動時跑，unmount 不會觸發 focus。`?.` 對 null ref 安全，不會 throw。mutate 的 per-call `onSuccess` 在元件 unmount 後 React Query 本來就不呼叫。這種情況焦點落在 `body`，是瀏覽器預設行為。
   - 送出成功後 `invalidateQueries(["playbook-today"])`，`page.tsx:48` 的 `today.isSuccess` 在背景 refetch 期間仍為 true，所以 `ModeStatusBar` 與 `EmergencyExitControl` 不會 unmount。
   - 觸發按鈕本身沒有 `disabled` 條件，且 `ModeStatusBar.tsx:50` 無條件渲染它。模式改成 emergency_frozen 也不會讓它消失。因此焦點會正常回到「全部出清」。
   - 若日後觸發鈕改成 disabled，`focus()` 會靜默失敗，焦點落 body，不會 crash。這是未來變更的風險，目前不成立。
3. **Esc：成立。**
   - `if (step === "idle") return;` 保證只在開啟時註冊。cleanup 呼叫 `removeEventListener`，使用同一個 `handleKeyDown` 參考，無洩漏。
   - 依賴 `[step, mutation.isPending]`，`isPending` 不會 stale。送出中 Esc 無效。
   - `cancelRef` 的 sync effect 沒有 deps、每次 render 更新，宣告順序在 Esc effect 之前，`cancel` 閉包取得最新的 `checkTexts.length`，無 stale closure。
   - Esc 只呼叫 `cancelRef.current()`，不碰 `mutate`。做法與 `EditPositionModal.tsx:115-124` 一致。
4. **焦點限制：成立。**
   - 共用 `FOCUSABLE_SELECTOR` 與 `trapTabTarget`，掛在 role=dialog 根節點的 `onKeyDown`，邏輯與 `EditPositionModal.tsx:136-149` 逐行相同。
   - Step 2 的 disabled「我已閱讀，繼續」被選擇器排除，Step 3 也一樣，符合預期。
5. **dvh：寫法正確。**
   - `supports-[height:100dvh]:max-h-[calc(100dvh-2rem)]` 是合法的 Tailwind arbitrary `supports` 變體，產出 `@supports (height:100dvh)` 區塊。
   - 它在 CSS 裡排在基礎 `max-h` 之後，所以支援 dvh 的瀏覽器會用 dvh，不支援的退回 `100vh`。交件者說已用 build 後的 CSS 確認先後順序。

   - `focusTrap.ts` 與 `ModeStatusBar.tsx` 沒有 diff。

## NON-BLOCKING
- **NB-7（low，測試）**：Esc 測試沒有斷言「只在開啟時註冊」，也就是 `if (step === "idle") return;` 與 deps 含 `mutation.isPending`。有人拿掉 guard，測試仍會綠。建議補兩條斷言：`/if \(step === "idle"\) return;/`，以及 `/\[step, mutation\.isPending\]/`。位置：`EmergencyExitPortal.test.ts` 的 Esc 那則。
- **NB-8（low，測試）**：標題斷言 `<h2\s+ref=\{headingRef\}\s+tabIndex=\{-1\}` 綁死屬性順序，之後有人調整順序會誤報紅。可接受，只是提醒。
- **NB-9（low，a11y，建議 qa-e2e 觀察，不要求本輪改）**：Step 3 送出中，被聚焦的「確認送出」按鈕變 disabled。部分瀏覽器會讓焦點掉到 `body`。若送出失敗，錯誤面板出現但焦點不在 dialog 內：
  - dialog 根節點的 `onKeyDown` 收不到 Tab，focus trap 暫時失效，直到使用者點擊。
  - Esc 因為掛在 document 仍有效。
  - 後續可考慮失敗時把焦點回標題或錯誤面板。
- **NB-10（info）**：標題程式化聚焦時，瀏覽器預設 focus outline 可能出現（鍵盤觸發時較明顯）。交件者已揭露未隱藏，由 art-lead 定奪。
- **NB-11（info）**：Esc 掛在 document，不 `stopPropagation`。若同頁有其他 document 層級 Esc 監聽（如 NavBar 下拉），會同時觸發。目前 dialog 開啟時不太可能與下拉同時開著，列為觀察。

## 給 qa-e2e 的複驗重點
1. 開啟「全部出清」：焦點在 Step 2 標題。按 Space 不會勾任何核取方塊。Tab 第一下落到第一個核取方塊。
2. 按「我已閱讀，繼續」：焦點落到 Step 3 標題，不是 body。
3. Tab 與 Shift+Tab 在 Step 2 與 Step 3 都在 dialog 內循環。標題聚焦時按 Shift+Tab 應跳到最後一個可聚焦元素。
4. Esc：Step 2 與 Step 3 都關閉，Network 沒有 `POST /emergency-exit`。重開後核取方塊全為未勾。
5. 送出中按 Esc 無效。取消鈕此時 disabled。
6. 焦點歸還：取消、Esc、送出成功三條路徑，焦點都回到「全部出清」按鈕。送出成功後模式轉為 emergency_frozen，確認觸發鈕仍在且焦點在它上面。
7. 送出失敗（模擬 API 錯誤）：看 ErrorPanel 出現時焦點位置（NB-9）。Tab 是否仍被限制在 dialog 內。再按 Esc 能關閉並歸還焦點。
8. 短視窗與手機瀏覽器（含網址列收合）：面板不超出可視範圍，內部可捲動。dvh 在支援的瀏覽器生效。
9. 標題聚焦時的 outline 外觀。滑鼠點開與鍵盤開啟兩種方式都看一次，回報給 art-lead。
10. 頁面捲動後開啟：overlay 仍覆蓋整個視窗，不被 sticky 狀態列的 stacking context 影響。這是上一輪 portal 修正的回歸項。
