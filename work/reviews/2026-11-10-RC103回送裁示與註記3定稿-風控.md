#### RC-108：(a) 的 time_order 例外，附條件接受（以 R-c 補記處理）

**接受理由**
1. **方向是多標，不是漏標。** 出錯時，畫面告訴使用者「這一列的股數依重設前取得的值計算」，實際上它用的是現行值。最壞的結果是使用者多檢查一列本來正確的指令。這不是保證性語氣，也沒有隱藏風險。N10-01 第二句（帳冊子句）在這種情況下仍然為真。
2. **範圍是過渡性的。** 只影響 `td_basis` 為 NULL 的列，也就是 N-210a 部署前已落檔的列，以及回退期間寫入的列。新列以逐字比對判定，不受時鐘影響。
3. **這不是 RC-96 改寫造成的新缺陷。** 用原稿「之前產生」，在同一個情境下一樣不成立。(iii-a) 依賴時鐘，是 ADR-0044 Options 表裡 (iii-a) 自己列出的缺點 (2)。
4. **其他處置都更差：**
   - 依 `td_flag_basis` 分版，違反 RC-53 條件 1、Decision 5 與 C-N210-15；
   - 在 N10-01 加「若系統時鐘曾被校正」之類的保留語，會讓大多數本來為真的列也帶上不必要的不確定性，而且同樣等於分版；
   - 「舊列一律判 unknown」已經被 RC-53 條件 3 否決。
5. R-c 原本就是風控裁示接受的殘留（ADR-0044 Consequences 表）。這次只是補上另一個方向，而且是傷害較小的方向，在我的裁示權限內。

**條件（required）**
1. N10-01、N10-02 的字面一字不改，也不依判定依據分版。
2. 註記 3 照 RC-111 的定稿落檔，不用 TA 的原文。
3. **新列不得落到 time_order（qa 核對）。** N-210a 要加測試：用 tmp DB 種入「規則集已確認、TD 三個鍵都不存在」的狀態，由 `commit_evaluation` 寫入一張 R1 列，斷言三件事：
   - 該列的 `td_basis` 不是 SQL NULL；
   - decode 之後三個鍵都是 null；
   - 之後寫入 TD，這一列的 `td_flag_basis == "recorded"`。

   理由：如果 encode 遇到全 null 的戳記時回傳 None，A8 狀態下的新列就會掉回 time_order，例外就不只限於舊列了。TA 要求的 `decode(encode(s)) == s` 性質測試，只測 helper 本身，抓不到這種寫入端的問題。
4. **自我更正 RC-96。** RC-96 寫「time_order 的 yes：讀取早於 created_at，created_at 早於 set_at，set_at 早於 commit。成立。」這句要加上「以時鐘不倒退為前提」，由註記 3 第二點記錄。
