## 第 1 部分：唯讀現況計數（先給 CEO 跑）

### 1.1 這段指令做什麼、不做什麼

- 用 stdlib `sqlite3` 以 `mode=ro` URI 開啟**複本**，接著下 `PRAGMA query_only=ON`。之後只送 `SELECT`。檔案不存在就拒絕（exit 2），不會新建。
- 以 `python -I` 執行：不讀 `PYTHONPATH`、不載入目前目錄的模組、不 import `app`、不連網、不讀 `.env`。
- **只輸出數字，不輸出任何代號**（代號、股數、價格屬持股資料，RC-6）。輸出也不印 DB 路徑，所以整段輸出可以直接貼回。
- 腳本內容全部是 ASCII（中文字以 `\u` 跳脫），因為 Windows PowerShell 5.1 把字串餵給外部程式時，預設用 ASCII 編碼；有非 ASCII 字元會變成 `?`。

### 1.2 輸出項目對照

| 輸出 | 意思 |
|---|---|
| `(a) distinct_symbols` | `playbook_batches` 裡有幾個不同的 symbol（任務要求的 (a)） |
| `(a2) symbols_with_planned_or_open` | 其中還有 `planned` 或 `open` 批次的檔數。批次全部 `closed`／`skipped` 的檔不再占用資金，所以真正決定每批金額是否正確的是這個數字（§2.7）。這是 dev-lead 加的輔助項 |
| `(b) batches_per_symbol_distribution` | 每檔批數的分布，例如 `3 batches: 5 symbols` 代表 5 檔各有 3 批 |
| `(b2) symbols_whose_batch_no_is_not_1..k` | `batch_no` 不是 1、2、…、k 連號的檔數。手寫 SQL 時最容易出這種錯，正常應為 0。這是 dev-lead 加的輔助項 |
| `(c) batches_by_status` | `planned`／`open`／`closed`／`skipped` 各幾批；`other_status` 是這四種以外的狀態，正常應為 0（`BatchStatus` 只有這四種，`app/playbook/models.py:44`） |
| `(d) rule_params_in_force_on` | 以這台電腦今天的日期，讀現行參數。讀法與 `PlaybookStore.active_params` 相同：`effective_date <= 今天`，依 `effective_date`、`version` 取最新一列（`app/playbook/store.py:1115-1131`） |
| `n_targets`、`batches_per_target` | 現行參數值。沒有任何參數列時印 `未設定`，並註明系統預設值 5／3 的來源 `app/playbook/models.py:88-89`（`store.py:812-820` 的 `system_default_params` 就是用這組預設）。參數列存在但缺這個鍵時印 `KEY_ABSENT`，同樣套用預設 |
| `pending_versions_after_today` | 生效日在今天之後、還沒生效的參數版本數。不是 0 時，不要做第 2 部分 |
| `(e) distinct_symbols == n_targets` | (a) 是否等於 `n_targets`（任務要求的 (e) 前半） |
| `(e2) symbols_with_planned_or_open == n_targets` | (a2) 是否等於 `n_targets` |
| `(e3) every symbol has batches_per_target batches` | (b) 是否每一檔的批數都等於 `batches_per_target`（任務要求的 (e) 後半）；DB 沒有任何批次時為 `False` |

### 2.4 ① 季末 REBALANCE 先做，而且不得與資金確認同時執行

- REBALANCE 目前沒有畫面入口，只能直接呼叫 API（風控 2026-11-07 更正版通知，`work/reviews/2026-11-07-N177修訂四比對與N197裁示-風控.md:171`）。服務執行中時：

  ```powershell
  (Invoke-RestMethod -Method Post -Uri "http://localhost:8000/api/playbook/rebalance").status
  # "ok": continue. "insufficient_data": a held symbol has no usable price; stop here and report.
  ```

  只印 `status`，因為完整回應含總資產與現金，屬私人資料。

- **不得與資金確認同時執行**，這是風控的既有通知：REBALANCE 與資金確認（排程台頁面的「確認規則集並設定資本額」按鈕，以及直接呼叫 `POST /api/playbook/confirm-rules`）不要同時執行；若懷疑曾同時執行，等兩者都完成後，依原本要的先後，再執行一次較後的那一項（全文見上述檔案 `:171`）。實務上：做 REBALANCE 的這段時間，不要開排程台頁面按確認、也不要呼叫 confirm-rules。
- 新增標的的步驟（⑦）在服務停止時進行，本身不會與 REBALANCE 或資金確認並發。
- **為什麼 REBALANCE 放在新增之前** [待 TA 核對]：REBALANCE 只計 `open` 且有剩餘股數的批次與現金（`app/playbook/service.py:1830-1870`），新加的 `planned` 批次不影響 TOTAL_DEPLOY，所以兩者先後不改變算出來的數字。但新標的的每批金額會讀當下的 TOTAL_DEPLOY（`app/playbook/engine.py:204-205`）。先 REBALANCE、停機、新增、再啟動，可以確保新標的第一次被評估時，用的已經是新一季的 TOTAL_DEPLOY；反過來做，啟動後到 REBALANCE 之間若有評估，新標的會先用舊值。

### 2.5 ⑤ 新增清單檔與代號格式

清單檔放在 repo 以外，例如 `$WORK\new-targets.txt`，用記事本建立。一行一個代號；空白行與 `#` 開頭的行會被略過。

```powershell
$TARGETS = "$WORK\new-targets.txt"
notepad $TARGETS
```

**代號格式**：

- 台股證交所或櫃買中心的**純代號**：4 到 6 位數字，後面可以接 1 個**大寫**英文字母（例如 `NNNN`、`NNNNN`、`NNNNNL`）。
- 不加 `.TW`、`.TWO` 等後綴，不加空白、全形字或股票名稱。
- 字母結尾是 `K` 的（外幣計價單位）不收，這與 `app/data/admission.py:125-136` 的台股規則一致。
- 排程台只支援台股（`app/playbook/service.py:95`，`PLAYBOOK_MARKET = "TW"`）。

code 本身在 `ensure_batches` 不檢查任何格式（N-203 查證 §1.4 第 6 點）：寫錯時抓不到日線，依鐵律⑤該檔每天都不出指令、只出警示，不會報錯。所以下面的寫入指令自己加了兩道檢查：上面的格式規則；以及 DB 裡的證券目錄（`security_directory`，market = `TW`）有資料時，代號必須在目錄裡。目錄是空的時只會印 `WARN`，只做格式檢查。這兩道檢查是**指令自己的**，比 code 嚴格；合法代號被擋下時，請停下來回報，不要改指令。

**清單檔與輸出含代號，屬持股資料（RC-6）**：清單檔留在 CEO 本機，不放進 repo；`work/` 只記筆數。

### 2.6 ⑥⑦ 新增標的：用 `ensure_batches`，`batches_per_target` 取自參數

**規則**：新增一律走 `PlaybookStore.ensure_batches`（`app/playbook/store.py:858-868`），`batches_per_target` **必須等於現行參數**的 `batches_per_target`，不要手填數字，也不要手寫 `INSERT`。

理由（N-203 查證 §1.4 第 4 點）：code 不會拿傳入的批數去對照參數。末批要吸收整檔的零頭（`engine.py:208-215`）。手填的批數比參數少，末批永遠不會出現，每檔少投入；比參數多，第 `batches_per_target` 批以後每批都照末批公式算，造成超買。附錄 A 的 C5 另外實測到：對**已經全部 `closed`** 的標的以較大的批數再呼叫一次，會在後面**多長出一個 `planned` 批次**，等於讓已出清的標的重新開始買。

下面的指令把這些都包起來：

- 參數從同一個 DB 以 `active_params(今天)` 讀出，直接傳給 `ensure_batches`；
- 有待生效的參數版本時拒絕（exit 6）；
- 清單裡有任何一檔已經有批次列時拒絕（exit 4，見 §2.8）；
- 既有標的的批數不全等於參數時拒絕（exit 5）；
- 新增後「還有 `planned` 或 `open` 批次的檔數」不等於 `n_targets` 時拒絕（exit 6，見 §2.7）；
- 預設是 dry run，不寫入；加 `--apply` 才寫入，寫完逐檔核對「批次 1 到 `batches_per_target`、全部 `planned`」；
- 只印筆數與行號，不印代號。

### 2.7 檔數改變時，`n_targets` 的影響

- 每批金額 = `TOTAL_DEPLOY ÷ n_targets ÷ batches_per_target`（`app/playbook/engine.py:204-205`）。`n_targets` 是參數（預設 5，`models.py:88`），code **不會**比對 DB 裡實際有幾檔（N-203 查證 §1.4 第 3 點）。
- [待 TA 核對] 批次全部 `closed`／`skipped` 的檔不再下單，所以決定總投入的是「還有 `planned` 或 `open` 批次的檔數」（第 1 部分的 (a2)）：
  - (a2) 大於 `n_targets`：每檔仍照 `TOTAL_DEPLOY ÷ n_targets` 配置，總計畫投入會超過 TOTAL_DEPLOY（6 檔對 5 時多 20%），只剩鐵律①的現金下限擋著。
  - (a2) 小於 `n_targets`：少投入（4 檔對 5 時少 20%）。
- 因為只能新增、不能移除，**新增只會讓 (a2) 變大**。所以手動新增唯一不影響金額的做法，是補上已全部 `closed`／`skipped` 的檔留下的空位，補完 (a2) 剛好等於 `n_targets`。寫入指令只允許這種情況。
- **要改變檔數本身（改 `n_targets`），不在本說明範圍**：
  - 改參數的 `request_rule_change`（`app/playbook/service.py:2410-2433`）沒有 API；
  - 依鐵律④，新版本要到下一個交易日才生效；
  - [待 TA 核對] 改了 `n_targets`，所有標的剩下 `planned` 批次的金額都會變；已經買了部分批次的標的，末批是用新的每檔配置減去已買股數算出（`engine.py:208-215`），可能變成只買 1 股，也可能變大。
  - 請等 N-207，或另請 TA 出程序。
- cap-1 說明句裡的「排程台的 N 檔」讀的是 `n_targets` 參數，不是 DB 實際檔數（`app/api/playbook_cap1_wording.py:106-110`）。

### 2.8 同一檔重新加入不會生效

- `ensure_batches` 用 `INSERT OR IGNORE`，遇到已存在的 `(symbol, batch_no)` 什麼都不做，也不報錯（`app/playbook/store.py:864-868`）。
- 附錄 A 的 C5 實測：已全部 `closed` 的標的再呼叫一次，批次列前後完全相同。
- 所以，已經出清、被 S2 列入黑名單、或被 R3 跳過的標的，**沒有辦法重新加入**。現行標的也不會因為「再加一次」而多出批次。
- 寫入指令遇到清單裡有任何已有批次列的代號，整批拒絕（exit 4），不會只寫一部分。

### 2.9 只能新增、不能移除

- code 裡沒有刪除或停用標的的路徑（N-203 查證 §1.2）。
- 舊標的還沒買的批次（`planned`）**會繼續出買單**：R 系列對每個 symbol 取第一個 `planned` 批次下 R1 買單（`app/playbook/engine.py:738-750`），標的集合又直接來自 DB 裡的批次列（`app/playbook/service.py:2158-2159`）。
- **要停掉，目前沒有安全做法，必須等 N-207。** 下面 §2.10 列的兩種手動做法都禁止。

### 2.10 明確禁止

1. **禁止手動 `DELETE FROM playbook_batches`。**
2. **禁止用 `UPDATE` 改 `playbook_batches.status`**（任何方向都不行）。

依據：ADR-0035（accepted）的不變式「批次永遠不會重置，`ensure_batches` 用 `INSERT OR IGNORE`，所以任何 (symbol, batch_no) 一生最多只有一列 executed 的 R1 buy」（`docs/adr/0035-stock-desk-排程台同一預定執行日重複評估的決策冪等.md:101`；ADR 內引用的 `store.py:315-325` 是舊行號，現在是 `store.py:858-868`）。N-172、N-177 的偵測與修復評估都以這條不變式為前提。

- `DELETE` 之後，既有指令列的 `batch_no` 找不到批次列，結算時只標記排程、不動帳冊（`store.py:1616-1618`）；N-172 偵測腳本也會把這種情況判為異常（`backend/scripts/n172_duplicate_probe.py:438`）。刪掉再重新加入同一檔，就會出現「同一個 (symbol, batch_no) 不只一列 executed 的 R1 buy」，直接違反不變式。
- `UPDATE` 改回 `planned` 就是重置批次，直接違反不變式。改成 `skipped`／`closed` 看起來像「停掉」，但不會留下任何指令列或稽核紀錄（風控 R16 要求每一條指令都有紀錄），而且這種狀態轉換從來不是由規則以外的路徑做的，安全性沒有人評估過。這屬於 N-207 要由 TA 決定的停用語意。
- 同理，也不要手寫 `INSERT INTO playbook_batches`，一律走 §2.6 的指令。
