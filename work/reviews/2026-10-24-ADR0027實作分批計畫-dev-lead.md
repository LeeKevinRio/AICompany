### 四、ADR 字面的矛盾、做不到或要澄清之處

行號都是 ADR-0027，另有註明的除外。

1. **【矛盾】dirdef 常數的位置。** L235 把 dirdef 放在 `app/forecast/definitions.py`；L251 規定 `app.outlook.*` 不得 import `app.forecast.*`；但 L252 的 `volatility.py` 要「取自 dirdef」，L254 的 `baselines.py` 也要用 K_h。三條不可能同時成立。建議常數另放一個葉模組，例如 `app/dirdef/`，forecast 和 outlook 都可以 import。
2. **【矛盾】缺日列能不能被後來的 run 改原因。**
   - L1274 說「之後的 run 可以改變一列的 `reason`」，但 L774 有 UNIQUE(session, claim_id, scope_key)，L263 又規定只增不改，列一旦寫入就不可能改。
   - L781 的 `scope_key='*'` ⇔ 該日沒有任何 run：寫完 `*` 列之後若又有同一天的晚到 run（例如週末啟動補跑），既有列就違反這條不變式。
   - 稽核每次要不要重判已判定的日子、只補不存在的列、寫入驗證只驗本交易寫入的列，都沒有寫。
3. **【做不到】`plan_outcome`。** L863 說它的欄位另案定義，但 L263 與 FL-1（L2514）要求「所有 `plan_*` 表」都有 trigger。沒有欄位就建不了表，B3 只能先排除它。
4. **【順序衝突】依賴兩份未實作的 proposed ADR。**
   - FL-1（L2514）要求啟動時檢查 schema，D-2 第 5 點與 FL-4（L266、L2517）要求登記 `schema_migrations`。這些依賴 ADR-0026 D-6，而 L3347 自己也寫了實作順序是「ADR-0026 D-8、D-6 → …」。
   - 但 ADR-0026 還是 proposed、沒有實作，而且閘門關閉期間不宜把 schema 套上真主 DB。
   - 建議：檢查函式先做，只在 tmp DB 上測；啟動接線留到 B14。
5. **【範圍】ADR-0028。** `is_final_bar`、`session_calendar.py`、VS-6（L982-986、L1029、L2393）全都在 ADR-0028（proposed、沒有實作）。
6. **N-110。** L1065 要 except 區塊填 `scopes_missed`，但 FL-74 (b)（L2540）只允許 except 區塊呼叫一個函式。已在追蹤清單，處理方式見第三節第 4 點。
7. **N-109。** L288 允許同一範圍有 holding、watchlist 兩個 reason，L330 的 `scope_reason` 卻是單一欄位。已在追蹤清單。
8. **【澄清】on-demand 並發撞 UNIQUE 時重讀。**
   - L1079 要求 on-demand 並發撞到 UNIQUE 時重讀；FL-77 (h)（L2578）禁止 `recorder.py`、`store.py` 用 except 指名 `IntegrityError`。
   - 我實測：SQLite 3.45.1 的 trigger `RAISE(ABORT)` 在 Python 端拋的也是 `sqlite3.IntegrityError`。
   - 所以要定：這段重讀程式放在哪個模組，以及怎麼分辨「唯一鍵衝突」和「只增不改被擋」。
9. **【澄清】on-demand 的 run。** `trigger = on_demand` 的 run 要不要寫 `forecast_run`？它的 `no_pending_scopes_json`（NOT NULL）填什麼？A-25 的分割驗證「聯集恰等於傳入的排程範圍」對 on-demand 怎麼適用？（L269、L287-288）
10. **【澄清】claim 登記的進入點。** 誰在什麼時點寫 `forecast_claim_registry`（啟動時從程式登記表同步，還是操作者跑 CLI），沒有定義（L236、L1564-1567）。這會影響 `registered_at`，進而影響 L967 的 Q3 規則、N-84 與 G-3。
