#### B. 方向判定：A-2 第 2 項「`late_only` 先於 run 的原因」

**判定：不變（確認字面讀法）。CEO 知悉。** 理由有五點：
1. **只有補跑能產生 `late=1`**〔事實〕：依 ADR D-7 第 6 點，補跑遇到已逾時才寫 `late=1`。所以「前面有失敗的 run、後面只有逾時紀錄」本來就是多 run 的情形。單一 run 的時代，這種情形不會發生，也就沒有「run 原因優先」的既有讀法。
2. **字面條件成立**：D-8 第 2 點的「只有 late 紀錄：`late_only`」是紀錄本身的事實，和 run 無關。這種日子這個條件照字面成立。
3. **N-64 原列的候選規則得到相同結果**：該候選是「取 `run_id` 最大、快照含該範圍的 run」。在這種日子，它取到的正是寫入逾時紀錄的那次補跑，結果一樣是 `late_only`。
4. **與既有渲染規則一致**：D-8 第 5 點和 FL-20 規定這類範圍以 LM-37 逾時句呈現，TG-c 不計。如果改記失敗原因，同一日會同時被呈現成「逾時」和「缺漏」，等於重複計算。
5. **失效條件沒有變鬆**：這種日子計入逾時率（門檻 10%），而缺日本來就不進逾時率的分母。所以對失效條件來說，把缺日改記成逾時只會更嚴。被蓋過的原因留在 `basis_json`，並依 V27-03 分列揭露，沒有資訊被移除。

**另一面（已寫進 V27-02 的另一面 ①）**：相對「依該範圍最後一個未寫入的 run 的失敗原因記」這個讀法，ADR-0027 TG-c 的計數會比較少。這是 UI 上的計數，不是驗證統計。
