## 實作摘要

**根因**
- `AlertStore._init_schema` 的 `_migrate_add_bar_as_of_column` 寫法是「先 `PRAGMA table_info`，再 `ALTER`」。Python sqlite3 只會在 DML 前隱式開交易，DDL 與 PRAGMA 都是 autocommit，所以檢查和 ALTER 之間沒有任何鎖保護。
- 原本 `_CREATE_EVENTS_SQL` 沒有宣告 `bar_as_of`，所以每一顆全新 DB 都一定會走 ALTER。
- `get_alert_store` 用的是 `lru_cache`，它不保證只算一次：首頁同時打進來的幾個請求，會在 threadpool 裡同時建構 store。兩個連線都讀到「欄位缺少」，輸家的 ALTER 在 reprepare 時就拋 `duplicate column name: bar_as_of`。
- 未修的 code 已實測重現：8 執行緒一組跑 10 次，失敗 5 次；6 行程一組跑 3 次，失敗 1 次。錯誤字串和 e2e 看到的一致。

**修法**
1. 新增共用 helper `app/data/sqlite_util.py::add_missing_columns(conn, table, {column: definition})`。
   - 先用一次 PRAGMA 快速判斷，欄位都在就直接 return，不取鎖。
   - 有缺的才 `BEGIN IMMEDIATE` 取寫入鎖（會等 busy_timeout），在鎖內重讀 schema，再 ALTER，最後 COMMIT。
   - 鎖在 SQLite 檔案層級，所以對多執行緒和 backend／scheduler 兩個行程都有效，不靠行程內鎖。
   - 多個欄位在同一個交易裡完成，中途失敗就全部 ROLLBACK。ROLLBACK 前會先看 `in_transaction`，避免把原本的錯誤蓋掉。
   - 我沒有採用「吞掉 duplicate column」的做法：鎖內重新檢查後不會再出現 duplicate。其他錯誤（no such table、database is locked 等）一律照拋。
2. `alerts/store.py`：改用 helper。另外在 `_CREATE_EVENTS_SQL` 的最後直接宣告 `bar_as_of TEXT`，位置和 ALTER 的結果相同，所以全新 DB 完全不用 ALTER。
3. `dividends/store.py`、`playbook/store.py`：改用 helper。playbook 依 table 分組，每個 table 呼叫一次。
4. `sectors/store.py::_legacy_stats_rows`：pre-v9 的 `sector_rank_stats` 原本也是「檢查 → COUNT → DROP」的同型競態。現在改成在 `BEGIN IMMEDIATE` 鎖內重新檢查。不修的話，輸家可能撞到 no such table，或把贏家剛重建好的空表（連同 triggers）一起刪掉。
5. （可選第 4 項，已做，風險評估為低）新增 `app/api/server_error.py::CorsVisibleServerErrorMiddleware`，掛在 CORS 內層（最內層）。
   - 遇到未處理例外時，先送出和 Starlette 預設相同的純文字 500，讓 CORS 幫它加上 header，然後原樣重拋。
   - 我核對過 Starlette 1.3.1 的 `ServerErrorMiddleware`：它看到回應已經開始，就不會再送，只重拋。所以 server 照樣記錄 traceback，TestClient 在 `raise_server_exceptions=True` 時也照樣拋。
   - 回應已經開始之後才發生的例外，只重拋，不會送第二個 start。
   - HTTPException、403 header guard 都不受影響。
   - 它和 migration 修正分在不同 commit。如果審查認為範圍外，可以單獨 revert fa6cc42。
