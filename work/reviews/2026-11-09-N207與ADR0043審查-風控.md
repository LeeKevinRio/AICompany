### 逐條意見

**A. engine 輪內計算（FR-42；ADR-0043 D3 第 5 點）**

我逐式比對了 `engine.py:186-215` 的現行版和 D3 第 5 點的新版：
- 第 1 輪的 offset 是 0，新舊兩版逐式相同；
- 第 2 輪以後只在同一輪內計算，舊輪批次不計入；
- 開新輪的前提是舊輪全部終結，所以不會出現跨輪的持股。

每檔配額仍是 TD ÷ n_targets，沒有放寬。「沒改什麼」的 4 項我都接受，包括「skipped 由末批補足」，這是第 1 輪現況照搬。

- **R-1**：部署前唯讀盤點時，若任一檔有以下情況，要停下回報 TA 與風控，不得直接上線：
  - 第 1 輪批數不等於 bpt；
  - `batch_no` 最大值大於 bpt；
  - 從 0 起編；
  - 有斷號。

  理由：T1、T2 會讓這些舊資料原樣沿用舊算法。從 0 起編的資料沒有末批補足；批數多於 bpt 的資料，從第 bpt 批起每一批都走末批分支，有可能只買 1 股。這是靜默沿用，使用者事前不會知道。

- **R-2**：D3 第 5 點的「不變的部分」要寫明鐵律①的現金底線只看 open 批次，不受 engine 輸入過濾影響。我已核對 `engine.py:1037-1043`，open 批次由 `engine_batches` 恆納入。這句目前只出現在送風控的清單裡，ADR 本文沒有。

- suggested：加一條測試，斷言 `planned_batch_shares` 只會對整輪都在輸入裡的批次被呼叫。理由：輪次不完整時 offset 會算錯，目前只靠「已停止標的的 planned 不進輸入」這個前提間接保證。

**B. C-B11 範圍判定與補充四（CEO #60：拆除護欄的條文）**

判定本身（C-B11 屬 N-168 的範圍，N-168 已合併）可以接受。四處要改：

- **R-3 生效條款**：D3 第 7 點與補充四都要改成「自 CEO 核可 ADR-0043（含本補充）之日起生效；核可前以 proposed 狀態落檔，qa-reviewer 依 C-B11 字面判 BLOCKING」。理由：ADR-0034 是 accepted ADR，原文「落檔起生效」會讓護欄在 CEO 核可前就拆掉。

- **R-4「仍然有效的不變式」要和 D3 第 7 點完全同列**。補充四目前少了「engine 不讀寫 TOTAL_DEPLOY 戳記、名單狀態或任何 I/O」。另外兩點要寫清楚：
  - B-2a 要寫出內容：出清當時未結算的 R 買單照常結算並標示，停損停利照常評估；
  - C-B10 要綁定 CEO #80 永久紅線，並寫明「本判定不影響 #80，#80 亦不得以範圍判定的方式解除」。

  「S、P 系列不因名單狀態被壓住」要具體化為：「open 批次在任何名單狀態、戳記閘、輪次之下，都交給 engine 評估 S、P 與 EMERGENCY」。

- **R-5「不得讀成 engine 從此開放修改」要防繞道**。N-207 本身就是在 service 層用 `engine_batches` 過濾輸入來改變 R 系列的結果，所以要補上：
  - 「在 engine 之外以過濾或改寫輸入、或後處理輸出，而改變 R、S、P 判斷結果或股數者，視同改動引擎邏輯」；
  - 這類改動與直接改 engine 一樣，「須有自己的 ADR、經風控審查並經 CEO 核可」（原文只有前兩項）；
  - 「本判定不構成日後豁免的先例」。

- **R-6**：同一判定延伸到 ADR-0041「engine 零 diff」（N-177a 的範圍）與 N198-C1（N-198 的範圍）時，要寫明一點：N-177a、N-198 目前都還沒合入，這兩項約束對它們各自的 diff 仍然完全有效。本判定的意思只是「它們不約束 N-207」，不是放寬它們自己。

- suggested：ADR-0035、0041、0042 檔頭各加一行指向 ADR-0043 D3 第 7 點的註記，方便追溯。

**C. 兩處非字面的語意改變：都需要揭露**

- **R-7 `/today` 批次快照**：
  - 只要有被排除的批次，`/today` 就要有一行常駐揭露，依類別列出數量，並指向名單頁，不得收合。類別至少要有「已停止新進場標的的待進場批次」與「待生效批次」；「舊輪批次」列數量即可。
  - 這行要由 API 層組出，以守住 N207-C3 對 `_snapshot_rows` 零 diff 的約束。
  - 理由：待生效標的若在 `/today` 完全消失，使用者可能誤以為它不在名單內，或以為不需要 REBALANCE。

- **R-8「規則已全數評估」**：要處理的是 `NO_RULE_HIT_NOTE`（「今日規則已全數評估，無任何規則命中，未產生指令。」）。
  - 現有先例：S1 暫停、S2 黑名單時，R 系列沒有評估，旗標判為 false（`engine.py:1277-1281`）。
  - 現在的情況：已停止標的或待生效標的的 planned 批次被排除在輸入外，R 系列同樣沒有評估，旗標卻可能是 true。這會把沒評估說成評估過。
  - 要求：只要有任何名單內標的的 planned 批次被排除，原句就不得單獨出現。二擇一：
    - (a) 在 service 或 API 層把旗標判為 false；
    - (b) 改用加註範圍的變體句，寫出「已停止新進場 N 檔、待生效 M 檔未評估進場規則」。
  - 兩者都只能在 engine 之外實作。
  - 另外，TA 對範圍的描述不完整：除了「已停止而且沒有 open」，已停止但同時有 open 與 planned 的標的，planned 也一樣沒有評估。ADR 的 Consequences 段和 N207-T22 都要照此修正。

**D. 甲案（#123）是否放寬 #121**

- **R-9 判定：屬放寬。**
  - 字面：#121 是「等 REBALANCE」，甲案多了資金確認這條解開路徑。
  - 實質：`confirm_rules` 的 TD 是「capital × deploy_ratio」，只依提交的數字計算，不看持股（`service.py:2013-2016`）；REBALANCE 則依當日資產重算。
  - **CEO 已明示同意**：#123 是 CEO 2026-11-09 在知悉「與 #121 字面有差異、是否屬放寬由風控判定」的前提下選的。現在風控判定屬放寬，所以 #123 就是對這項放寬的明示同意。
  - ADR D6 要寫入這段同意紀錄，並把「Q-C12 待 CEO 選」改為定案。

- **R-10 以 API 重送資金確認：需要揭露。**
  - 背景：首次確認後，畫面上的確認入口就不再出現（`RuleSetConfirmPanel` 只在 `mode === "unconfirmed"` 時顯示）。所以甲案多出的實質路徑只剩用 API 重送。
  - 風險：這樣做會用提交的數字覆寫現金，TD 也不看持股；若誤把總資產當成現金填入，鐵律①的現金底線預算會被灌大。
  - 要求：
    - (a) 待生效說明句只把資金確認寫成「首次設定時」的解開方式，不得寫成通用的解開方法；
    - (b) 手動操作說明（#118）與 N-209 的 REBALANCE 入口說明都要寫明：重送資金確認會覆寫現金、TD 不看持股，不能用來代替 REBALANCE；
    - (c) coordinator 在決策包補一則知悉事項。原因：CEO 決定清單第 1 項的摘要沒寫到現金覆寫，只有 D6 表的缺點欄寫了。
  - suggested：TA 另案評估「已有 open 批次時重送資金確認」要不要拒絕或警示。

**E. 其他判定項目**

- **R-11 季度窗口的已知限制**：揭露句要寫成雙向，不得寫「只會變窄」。具體要求：
  - 日曆資料不足時，國定假日可能被當成交易日（窗口提早結束或延後開始）；
  - 某個交易日的資料整天缺漏時，窗口可能提早開始或延後結束；
  - 拒絕訊息裡的下一個窗口起訖都是未來日期，一定是用週一到週五推算的，要註明「依系統日曆推算，遇休市可能不同」；
  - 拒絕原因要寫成「依系統日曆判定」，不得寫成「已過窗口」這種絕對說法。

  已知的系統性影響（屬保守方向，可以接受）：每年 Q4 換 Q1 時，1 月 1 日在推算中被當成交易日，窗口會在 1/1 13:30 結束，而不是 1/2 13:30。

- **R-12 組合凍結的殘留**：資料落後的那幾天，名單入口已放行，但 engine 仍處於凍結。這比 FR-40 的字面寬，但不會增加買進：engine 仍壓住 R 系列，新批次也還在閘後。
  - CEO 要在 ADR-0043 改為 accepted 之前，明示回答 TA 決定清單第 3 項（Q-C11）。這不擋 proposed 落檔。
  - suggested：這段期間在名單頁加一句事實說明，例如「今日頁的凍結以資料日判定，資料更新後才解除；名單變更不會讓凍結提早解除」。

- **R-13 高波動接線**：既有 `high_volatility=1` 的列，部署當下就會生效。效果是這些標的的 P3 過熱減碼門檻從 BIAS25 大於 15% 提高為大於 20%，減碼變少，屬放寬賣出規則。
  - 盤點列數大於 0 時：CEO 要在部署前明示確認保留這些標記，或先取消；此外 app 內要有一次性的部署通知，在本機畫面列出受影響代號、門檻變化與「自部署起生效」。
  - 列數為 0 時：不需要通知，在 release note 記錄即可。

- **R-14 啟用檔數大於 n_targets 的既有資料**：每檔仍以 TD ÷ n_targets 計算，全部進場時投入會超過 TOTAL_DEPLOY（只受現金底線限制），屬突破風險上限。
  - 盤點若發現實際檔數大於 n_targets，要停下回報 CEO 與 TA，不得只靠揭露就上線。
  - FR-41 的揭露句要寫明上述後果。

- **R-15 cap-1（FR-28；修訂 ADR-0031 已核可的字面）**：
  - ① 的分母維持 n_targets，這是正確的，因為名額不補。另外要加一句「目前啟用 X 檔，名額空缺不補，每檔預定投入金額不因此提高」。
  - ③ 的例示（`LINE_BOOK_EXAMPLE`，1 ÷ n_targets）在有空缺時會低估集中度。例如啟用 4 檔時，等權每檔約 25%，不是 20%。所以有空缺時，要改用 1 ÷ 啟用檔數，或並陳較高的那個數字。
  - 啟用檔數為 0 時，改用 `_UNAVAILABLE` 變體。
  - 逐字由風控定稿。

- **R-16 字面清單要補 6 句**：
  - confirm-rules 依 FR-24 的拒絕句（名單為空、超額各一句）；
  - FR-13「已是停止狀態」的回覆；
  - R-7 的 `/today` 排除揭露行；
  - R-8 的加註範圍變體句；
  - 第 11 句的 `/today` 輪次說明；
  - R-13 的部署通知。

- **R-17**：N-209（REBALANCE 畫面入口，#124）合入之前，N-207 不得上線。待生效相關字面只有在 N-209 已合入時，才可以提到「REBALANCE 入口」。

- **R-18**：「待生效」一詞只留給戳記閘用。高波動改用「M 月 D 日起適用」或「尚未適用」，不得用「待生效」。

- ABA 殘留：同意 TA 的判斷，只在 ADR 記錄，不對使用者揭露。理由：方向保守，閘只會不開，畫面持續顯示待生效也是實情。
