## 逐項裁定

### 第 1 項：要補缺值句

**理由**
- 「每檔分 0 批」或「每檔分 -1 批」把不合理的原始值寫進句子，違反補充裁定第 4 節「不得把原始值（0 或負數）插進句子」的精神。那條原本只寫了 n_targets，現在擴及 batches_per_target。
- 更實質的問題是這句話本身會變成不實陳述。`store.py:313` 的 `range(1, batches_per_target + 1)` 在批數 ≤ 0 時一批都不會建立。這時 ① 後半句還寫「每檔標的的預定投入金額為…約為…的 14%」，等於陳述一筆不會發生的投入。這是隱藏不確定性，我不放行。

**逐字定稿**（全形標點；識別字前後各一個半形空格，和現行 ①-缺 一致）

- **①-缺b**（只有 `batches_per_target ≤ 0`）：
  「此規則集的每檔批數 batches_per_target 不是正整數，本區塊不陳述每檔規模與每檔佔比。」
- **①-缺nb**（`n_targets ≤ 0` 且 `batches_per_target ≤ 0`）：
  「此規則集的每檔規模無法由目前參數算出（標的檔數 n_targets 與每檔批數 batches_per_target 都不是正整數），本區塊不陳述每檔佔比。」

① 的位置只會出現一句，四種情況如下：

| n_targets | batches_per_target | ① 位置 | ③ 位置 | per_target_pct | per_target_book_pct |
|---|---|---|---|---|---|
| > 0 | > 0 | ① 原句 | ③ 原句 | 有值 | 有值 |
| ≤ 0 | > 0 | ①-缺（現行） | ③-缺 | null | null |
| > 0 | ≤ 0 | ①-缺b | ③ 原句 | null | 有值 |
| ≤ 0 | ≤ 0 | ①-缺nb | ③-缺 | null | null |

規則：
- 只要 ① 換成任何一種缺值句，`per_target_pct` 就是 `null`（不能是 `0`，AV-16），讓欄位與句子講的內容一致。
- ③ 只看 n_targets。它是條件例示，純算術，與批數無關，所以只有批數不合理時 ③ 照常輸出。
- ② 的替換規則不變，與上面互相獨立。④ 永遠不變。`lines` 固定 4 句，順序固定。
- 禁用詞：已比對 `shared/forbidden-terms.json` 全部詞條，並對 `adviceWording.ts` 抽查關鍵字，都沒有命中。兩句都沒有「建議」、祈使語或補救指引，也不陳述系統行為（不寫「不會產生任何一批」，避免多一個要另外驗證的宣稱）。

### 第 2 項：不算頂替，接受

**理由**
- 「不得以 10% 頂替」禁止的是揭露層自己補一個數字，例如 `DEFAULT_MAX_POSITION_WEIGHT`、前端常數，或讀取失敗時自填預設值。這種數字可能和建議端實際套用的值不同。
- 段損毀時，`SettingsStore.load()` 回傳的 0.10 是全系統當下實際生效的值。建議端（`api/advice.py:182`）、設定頁（`api/settings.py:440`）、portfolio、kelly 讀的都是同一個 `load()`，個股頁的第 1 條判定也是拿 10% 比。所以揭露寫 10% 是如實陳述，符合 C-4 的同源要求。
- 反過來改用 ②-缺，揭露會說「讀取失敗」，但設定頁與個股頁同時顯示並套用 10%。同一個使用者會在兩處看到互相矛盾的說法，這正是 D-2 (3) 要避免的靜默矛盾。

**條件**
- ②-缺 只在 `get_cap1_weight()` 回 `None` 時使用，也就是丟例外或讀到非有限值，維持現況。
- router 與 `get_cap1_weight` 不得另外判定「段損毀」，例如自己讀 `app_settings` 原始 payload 或呼叫 `_parse_section`。那會讓揭露端多讀設定層內部，是新的耦合（C-6、H1），而且會產生和建議端不同的第二種判定。
- 建議端不必在本 PR 同步揭露。R4-6 也禁止本 PR 改動 advice、settings、portfolio 的回應。

**另開 CEO 事項（不擋 N-155，但我要求開案）**
- 現況：`store.py:152-165` 在 risk_budget 段驗證失敗時，靜默回到預設 0.10，只記 log，使用者看不到任何提示。`failed_sections` 只存在 S2 遷移當次的紀錄裡（`migrations.py:320`），之後再損毀就不會出現在任何畫面。
- 風險：使用者若原本設在 5%，段損毀後第 1 條會被放寬成 10%，使用者不知情，CEO 也沒有同意。這牴觸本職「放寬上限需 CEO 明確同意」的原則。`store.py` 模組 docstring 說這是「conservative default」，對低於 10% 的設定並不成立。
- 建議由 TA 出規格、dev-lead 實作：設定層要能向使用者揭露「該段已回落預設值」，設定頁與建議端都要顯示。
- 該案落地時，排程台揭露的 ② 要回審。

### 第 3 項：接受，不另設較短的 timeout

**理由**
- 設定與排程台用同一個 DB 檔（`resolve_db_path()`），busy timeout 也相同（`data/cache.py:36` 的 `BUSY_TIMEOUT_MS = 5000`，`playbook/store.py:294` 同值）。檔案被鎖時，`/today` 自己讀 playbook 表也會等同樣久。只把設定讀取的 timeout 縮短，並不能讓停損指令更早出來。
- 只縮短揭露這一側，反而會造成不一致：短暫爭用時揭露說「讀取失敗」，等滿 5 秒的建議端卻讀到真值。
- 設定 DB 已開 WAL（`store.py:101`），一般讀取不會被寫入擋住。

**R4-4「不得延遲」的正式解讀**
第 1 條的讀取不得帶來超過端點自身 DB 存取上限的等待。具體是：只讀一次，不重試、不 sleep、不走網路，等待上限就是同一個 `BUSY_TIMEOUT_MS`。現行 `deps.py:405-412` 符合。

**suggested（請 qa-reviewer 確認）**
`lru_cache` 不會快取例外。如果 `_default_settings_store()` 建構時一直失敗，每次請求都會重新建構並重跑一次 S2 遷移（含寫入交易），每次最多多等 5 秒。請確認這是可以接受的退化，或請 TA 評估改成負向快取。

### 第 4 項：接受

**理由**
- `/today` 的 `rules_version = 0` 表示「今天沒有評估任何使用者規則」（`service.py:590`，page_summary 依此 fail-closed）。揭露的 `rules_version` 依 B-3 是「數字取自哪一版參數」（`service.py:579`）。兩者語意本來就不同，不是同一件事出現兩個值。
- 兩個都不會顯示：C-2 與 F-3 禁止前端顯示 `rules_version`。unconfirmed 時今日頁也不渲染 `/today` 那一份揭露，只在確認面板渲染 `/rule-set` 的那一份，它的版本與面板一致。
- 測試 `tests/test_api_playbook_cap1_disclosure.py:850-851` 已釘住 unconfirmed 時兩份揭露的 `rules_version` 都等於 in-force 版本。

**suggested**
在 ADR-0031 C-5 和 `PlaybookCap1Disclosure.rules_version` 的欄位註解補一句：unconfirmed 時，這個值是 in-force 版本，與回應頂層的 `rules_version = 0` 語意不同，任何人都不得拿這兩個值互相對帳。

## 字面抽查結果：逐字相符

- **方法**：用同一個 pattern 分別 grep 補充裁定第 4 節與 `app/api/playbook_cap1_wording.py`。模組裡的每一段字串字面都以行首、行尾錨定，裁定那邊用拼接後的整句比對。
- **兩邊都命中**的有：`TITLE`、①、②、③、④、②-缺、①-缺、③-缺（模組 `:49-94`）。
- **碼位**：「・」「÷」「（）」「，」「；」「：」「「」」都由同一個 pattern 匹配成功，所以碼位相同。
- **拼接**：模組靠相鄰字串自動串接，片段之間沒有多出空白，也沒有遺漏。
- **插值**：插值欄位不帶「約」（`format_pct` 只輸出數字加 %）。順序固定為 ①②③④（`:186`）。
