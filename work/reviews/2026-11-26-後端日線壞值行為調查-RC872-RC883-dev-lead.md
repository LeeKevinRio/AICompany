## 本次結論

1. **RC-872**：後端不會回「status ok、HTTP 200、0 筆」。`/api/bars` 只有在有日線時才回 ok，0 筆一律是 HTTP 200 加 `insufficient_data`。前端只在 ok 時才呼叫 `evaluateDailyBarsUsability`，所以「空陣列視為 usable」那條路在目前的後端下走不到。真正的問題在**壞值**，不在 0 筆。
2. **RC-883**：「命中 0 條、資料完整度 100.00%」確實會出現，而且已實際重現。這兩個數字的計算完全不看日線品質，只看規則的輸入欄位是不是 `None`。只要最新一筆收盤價可用，其他日線是 0、負數、high<low 都照樣算。實測中，一筆 30 根前的收盤價 = 0，就讓一張乾淨資料下是「減碼參考／信心 high」的持有卡，變成「續抱參考／信心 medium／12/12/0/100%」。
3. **「續抱參考」**：結論來自後端（`advice.action == "hold"`），前端只把它翻成文字。後端只檢查最新一筆收盤價，前端的操作摘要和決策卡標題都不讀日線可用性判定。

說明：實際 HEAD 是 `efd1cc41`，不是 `7fa51002`。`git diff 7fa51002 efd1cc41` 只改了一份 md（2 行），程式碼相同。

## 發現

### 1. RC-872：0 筆日線

**Route 與 service（讀程式碼推得）**
- Route：`apps/stock-desk/backend/app/api/bars.py:82-106`，`GET /api/bars/{symbol}`。
- Service：`app/services/market.py:147-215` 的 `load_bars`，底下是 `app/data/service.py` 的 `MarketDataService.get_daily_bars`。
- `bars.py:101`：`status="ok" if ordered else "insufficient_data"`。ok 與「有日線」是綁死的，跟 `data.status` 無關。
- `/api/advice` 也一樣：`api/advice.py:203-207,234-258` 沒有可用的最新收盤價就回 `insufficient_data` 且 `advice=None`，所以 0 筆也不可能是 ok。

**什麼條件下會出現 HTTP 200、0 筆、`insufficient_data`（讀程式碼推得）**
- 該市場沒有行情來源：`market.py:169-170`，訊息用 `NO_ADAPTER_REASON`。
- 主來源、備援都失敗，快取也沒資料：`market.py:189-198`。
- 資料閘門拒絕（admission 或幣別不符）：`market.py:172-187`，原因字句原樣帶出。
- 冷卻期內且快取是空的：`market.py:188`。
- 只抓到尚未收盤的那一天，被濾掉後變空：`data/service.py:936-955`。
- 快取裡每一列都損壞：`data/cache.py:599-601` 會跳過損壞列，全部跳過時回 `None`（`cache.py:607-608`）。
- 回看區間內沒有任何日線（請求的是 `[today-540, today]`）。
- `data.status`：0 筆時 `load_bars` 照抄 service 回傳的 status（`market.py:191`）。依目前 `MarketDataService` 各分支，0 筆只會配 `unavailable`（`service.py:931`；`cache.get` 空的時候回 `None`，`cache.py:564`）。只有不守規則的 PriceService 才可能出現 `data.status="fresh"` 配 0 筆，此時信封 status 仍是 `insufficient_data`。

**前端怎麼呈現 0 筆（讀程式碼推得）**
- 目前實際會看到的：
  - 技術分析區顯示 `InsufficientPanel`（`page.tsx:396-398`）。
  - `dailyBarsUsability` 是 `null`（`page.tsx:146-149`），不會當成 usable。
  - 決策卡收到 `bars=null`（`page.tsx:245`）；`/api/advice` 也是 `insufficient_data`，所以走 `no_price` 分支（`operationSummary.ts:364-371`）。
- 假設將來後端回「ok 加空陣列」（目前走不到）：
  - 技術分析不會收合（`page.tsx:150-151`），會畫一張空圖。
  - 一句結論會是「近 0 根日線，收盤 —。」（`page.tsx:424-427`，`formatNumber(NaN)` 會得到「—」，見 `format.ts:281`）。
  - 詳細區會印「共 0 根日線（— ~ —）。」（`page.tsx:482-486`）。
  - 決策卡因為有長度檢查，不顯示不可用提示（`DecisionCard.tsx:410-415`）；`computeKeyLevels` 遇到空陣列回 `null`，三格顯示「—」（`keyLevels.ts:103`）。

**壞值能進到哪裡**
- **NaN 和 Infinity 進不來（實際執行驗證）**：正常建立 `PriceBar` 時，pydantic 會用 `finite_number` 擋掉 NaN、sNaN、±Infinity。0 和 -1 則可以通過。
  - 只有用 `model_copy(update=...)` 繞過驗證才能塞進 NaN；那種情況下 `/api/bars` 會在 `bars.py:70` 丟出 ValidationError（等同 500）。正式程式碼裡沒有對價格欄位做這種繞過（已 grep `app/` 確認）。
  - 快取裡的 NaN 列會被靜默略過（`cache.py:599-601`），結果是序列少一根，前端仍判定為 usable（讀程式碼推得）。
- **0、負數、high<low 都進得來，而且後端完全不擋（實際執行驗證）**：`quality._check_ohlc_consistency` 有寫（`data/quality.py:167`），但沒有接到任何地方。
- 前端判準本身也不檢查 high<low 和 open（`dailyBarsUsability.ts:31-34,41-47`），所以 high<low 的資料兩邊都視為正常。

### 2. RC-883：`evaluation` 與 `data_completeness`

**定義（讀程式碼推得）**，見 `app/advice/engine.py`。
- `total_rules`：規則檔裡的規則數，目前 `rules/default.yaml` 有 12 條（`engine.py:442`）。
- `evaluated_rules`：沒被跳過的規則數（`engine.py:361`）。
  - 規則用到的任何欄位只要是 `None`，就算跳過（`engine.py:166-167, 179-185, 197-209`）。
- `matched_rules`：可評估且條件成立的規則數（`engine.py:362`）。
- `data_completeness = evaluated / total`，四捨五入到 4 位（`engine.py:364, 445`）。
  - 分母是 12 條規則，分子是可評估的規則數。
  - 它衡量的是「規則輸入欄位是否存在」，不是日線品質，也不是筆數。
- 欄位值來自 `advice/context.py:117-166`。
  - `_as_float`（`context.py:97-101`）不過濾 NaN 或 Infinity，所以 NaN 會被算成「可評估」，而且比較一定是 False，也就是「沒命中」。這和該檔 `:10-12` 的註解不一致。
  - 指標取值用 `last_defined`（`signals/frame.py:97-102`），只丟掉 NaN、不丟 Infinity，而且會往回拿較舊的有效值。
- 信心等級：0 條命中且完整度 ≥ 0.8 時是 `medium`（`engine.py:292-294`）。
- 動作：0 條命中且完整度 ≥ 0.5 時是 `hold`（`engine.py:366-375`）。

**壞值或 0 筆時的實際數值**

以下實測環境：`api_harness`（tmp_path）、fake price service、120 根、量有變化、經過驗證建立的 PriceBar。四個數字依序是 total/evaluated/matched/completeness。

| 情境 | `/api/bars` | `/api/advice` 結果 |
|---|---|---|
| 0 筆 | 200 `insufficient_data` | 200 `insufficient_data`，沒有 evaluation |
| 最新一筆收盤價 = 0 | 200 ok（前端判 unusable） | 200 `insufficient_data` |
| 舊 bar 收盤價 = 0 或 -1、候選（趨勢序列） | ok | ok，action `add`（支持進場），信心 medium，12/11/1/0.9167 |
| 舊 bar 收盤價 = 0 或 -1、持有（趨勢序列） | ok | ok，action `hold`（續抱參考），12/12/2/**1.0** |
| 舊 bar 或最新 bar 的 high/low 為 0、負數、high<low | ok | ok，完整度 0.9167（候選）或 **1.0**（持有），照常產生動作 |
| 持有、非集中持股、sine 序列，乾淨資料 | ok | `reduce`，信心 high，12/12/2/1.0 |
| 同上，但第 -30 根收盤價 = 0 | ok（前端判 unusable） | **`hold`，信心 medium，12/12/0/1.0，`aggregated_action=null`** |

- 第一筆收盤價 = 0、或多筆為 0 時，context 裡的 `volatility.annualized` 和 `drawdown.max_drawdown` 會是 NaN，但仍被算成可評估。目前預設規則沒有用到這兩個欄位，所以暫時不影響計數。
- 也看到垃圾但有限的值，例如 `kd.k = -730`、年化波動 231、最大回撤 -1.006，都被當成可評估的正常值。
- 在 1,440 組 sine 序列的搜尋中，「12/12/0/1.0」組合：乾淨資料 12 組，壞值情況下最多 98 組（第 -30 根收盤價 = 0）。
- 結論：前端第 254-259 行會印出「規則共 12 條，可評估 12 條，命中 0 條，資料完整度 100.00%。」（`formatPercent`，`format.ts:271-276`），摘要列印「命中 0 條」（`page.tsx:580` → `oneLinerWording.ts:36-38`）。這正是偏放心的組合，而且可以由壞日線直接觸發。
- 補充：候選卡因為 `position.weight` 是 `None`，完整度最高只到 11/12 = 91.67%；成交量固定不變時 `volume_z` 是 None，會再少一條。

### 3. 「續抱參考」從哪來（讀程式碼推得，數值已實測）

- 後端產生 `advice.action="hold"`，有五種來源：

  - 只檢查最新一筆收盤價（`api/advice.py:207`，`price_guard.usable_price`）。
  - 指標用全部日線計算（`api/advice.py:208`）。

## 下一步：PR-γ 建議的 pytest 案例（只列案例，全部用 tmp_path 和 fake service）

**RC-872**
1. 每個回傳日線的 endpoint 都要成立「`status=="ok"` ⇔ `len(bars)>0`」：`/api/bars`、`/api/advice`，以及 `/api/signals`（建議一起涵蓋）。
2. fake service 回傳 `FRESH` 加空陣列時，`/api/bars` 仍是 `insufficient_data`、`data.bar_count==0`；並決定 `data.status` 應不應該照抄 `fresh`。
3. 沒有行情來源的市場（預設 harness 的 US）、rejection 路徑、所有日線都在回看區間外，三種情況各自回 `insufficient_data` 和對應的 reason。
4. 最新一筆收盤價為 0 或負數時，`/api/bars` 是 ok、`/api/advice` 是 `insufficient_data` 且 `reason is None`（`api/advice.py:244`）；把這個不對稱釘住。
5. `PriceBar` 拒絕 NaN、sNaN、±Infinity，接受 0 和 -1（釘住 pydantic 的 finite 行為）。
6. 在 tmp_path 建 `PriceBarCache`，直接用 SQL 寫入一列 `"NaN"`：`get` 會跳過該列、回傳其餘日線；全部損壞時回 `None`。

**RC-883**
7. `data_completeness == evaluated/total`；只有 `None` 欄位會讓規則被跳過（用自訂 `ruleset` 的單元測試）。
8. context 出現 NaN 或 Infinity 時（例如第一筆收盤價 = 0 讓 `volatility.annualized`、`drawdown.max_drawdown` 變 NaN），引用這些欄位的規則目前算「可評估、沒命中」。先寫特性測試，再依修法改成預期值。
9. 持有、非集中持股：乾淨資料是 `reduce`/high/12/12/2/1.0；第 -30 根收盤價 = 0 變成 `hold`/medium/12/12/0/1.0（重現案例在 `test_probe5_pair.py`）。修法要先定案預期結果（例如改成 `insufficient_data`，或完整度不得為 1.0）。
10. 壞值位置參數化（第 0 根、第 -30 根、第 -5 根、第 -2 根）乘上欄位（close/high/low 的 0 或負數、high<low），candidate 和 held 都要跑：釘住目前「卡片仍為 ok 並給出動作」的行為，以及修法後的目標行為。
11. 候選卡完整度最高 11/12（concentration_watch 被跳過）、成交量固定時 volume_spike_watch 被跳過、1 根或 2 根日線時的完整度（held 為 1/12 和 3/12；候選為 `insufficient_data`）。

**「續抱參考」**
12. `/api/advice` 只檢查最新收盤價：用同一份含壞值的 fake 資料呼叫 `/api/bars` 和 `/api/advice`，斷言兩者對「日線可不可用」的判定一致（目前不一致，這個測試會失敗，可作為 PR-γ 的目標測試）。
13. 持有卡在 `aggregated_action is None` 且 `matched_rules==0` 時，action 是 `hold`、confidence 是 `medium`：釘住「沒命中就是續抱」的來源。前端標籤對應屬於 vitest 範圍，不在 pytest 裡。
