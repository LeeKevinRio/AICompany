#### 1. 逐項理由

**(1) `TAIL_GAP_DAYS` 取 3。**
- C1 只有一個誤判來源：除息日前最後一批回應漏列（我 2026-10-24 的 R-Q2）。尾段正好是要驗證的區間。取 7 等於把除息日前將近一週沒看到的事件也算進證據，會高估證據。
- 腳本沒有交易日曆，遇到連假的事件會被排除在 M 之外。這是 fail-closed，我接受，跟 quant 的看法一致。
- 範圍要擴大：尾段間隔不只算 `persistent`，三個可檢驗類別都要算。M 只計間隔 ≤ 3 的事件。

**(2) 樣本下限都取 60，旺季涵蓋列為必要，但要改寫成機械條件。**
- 同意 quant 的論點：同一個 run 裡的事件高度相關，有效樣本大致等於 run 數。
- 只寫「6～9 月要有一部分 session」，我不接受。原因是 rule of three 的上界（3/n）只在「每一對都有機會揭露不完整的批次」時才成立。淡季時前一個 run 只有寥寥幾個未到期事件，就算回應被截斷，也幾乎測不出來。把這些對算進分母，會讓「≤ 5%」這個說法不實。
- 所以改成：分母只計「前一個 run 中未到期 key ≥ 30」的相鄰對（N_pair），而且要 ≥ 60。
  - 30 的理由：未到期數 ≥ 30 時，「≥ 3」和「≥ 0.10」這兩個整批掉出條件恰好重合，10% 以上的截斷一定會被抓到。
  - 它直接量的是「月份」想代表的東西（敏感度），不會因為某年旺季提前或延後而失準，CEO 也不用自己數月份。
- 「不同 session ≥ 60」保留為 quant 的登記值。N_pair ≥ 60 已經隱含這一條，兩條並列只是方便閱讀。
- 上界要印出來：3/N_pair（run 層級）和 3/M（事件層級），並標明只在零反例時有意義。

**(3) 整批掉出：採 quant 的量法，但要更正兩點事實。**
- 【事實】現行腳本的 (c) Run-to-run drops 段（`n118_dividend_persistence_probe.py:362-372`）量的已經是「提前消失」：前一個 run 有、本 run 沒有、而且 ex_date 晚於本 run `session_date` 的 key。原始 `row_count` 跌幅是另一段（`:257-283`）。所以 quant 說「現行比較的是原始 `row_count` 跌幅」只說對一半。真正要改的是兩件事：判讀規則指向哪個數字，以及原始段的標示。
- 判讀要看「同時滿足 ≥ 3 和 ≥ 0.10 的相鄰對數」（`drop_pairs_over_both`），不看「最大掉出那一對」。後者會漏掉 qa 指出的情形：某一對掉 5 筆占 0.25，另一對掉 38 筆占 0.076，印出來的只會是後者。
- 計入範圍是所有相鄰對，不限可檢驗對，方向較嚴。
- 改期造成的舊 key 消失也算進提前消失，不扣除。誤報的代價是 TA 改成更保守的撤銷規則，不會傷到使用者，屬 fail-closed。
- 原始 `row_count` 段的 3 和 0.10 要拿掉 PROPOSED 標示，改標 descriptive，避免被看成判讀門檻。

**(4) 反例收緊為「任何 `vanished_returned`」，closed 和 open 都算。**
- 【事實，讀碼 `:320-334`】對 open 事件來說，所有 session 都早於除息日。所以「某個 run 漏列、之後的 run 又列出」這件事已經完整發生在除息日前，不會因為之後的資料改變。這是確定的反證，跟事件有沒有結束無關。
- 只計 closed，會白白丟掉已經觀察到的反例。

**(5) 新增「未解釋的消失」條件。**
- 【推論】最後一批漏列單一事件，在 DB 裡看起來就是一筆 closed 的 `vanished_gone`，跟真撤銷分不出來。這正好是 C1 的誤判型態。

**(6) 新增輸入完整性條件。** 下列任一大於 0，就代表 DB 內容和正式寫入路徑的假設不一致，持續性分析的輸入本身不可信：
