## 本次結論

1. **14% 是對的，docstring 的 9.8% 算錯了。** 算錯的地方是把 `deploy_ratio` 乘了兩次。TOTAL_DEPLOY/5 是部署資金的 **20%**，不是 14%；20% × 70% 才是總資產的 14%。企劃當初也寫「每檔 14%、每批約 4.67%」（`work/stock-desk-快市排程-企劃.md:122`）。所以這個測試在 15% 時代只是剛好過關。
2. **測試的分母也和第 1 條實際用的不一樣，這點比算錯更嚴重。** 測試用的是排程台總資產，含 30% 現金。第 1 條用的是庫存「已估值市值」，不含現金（`app/advice/limits.py:18-25`、`app/advice/book.py:14-17`、`limits.py:856-862`）。換成第 1 條的分母，5 檔均分每檔是 **20%**，15% 時代就已經超限。所以衝突早就在，#61 只是讓它露出來。
3. **只要 CEO 真的在用排程台，他的部位一定是每檔 14%。** 規則集只有確認後才會產生指令；確認時，當時的預設值會原樣寫進 DB，之後改程式預設值對他完全沒影響。目前也沒有任何 API 能改參數。
4. **建議採 (d)：先請 CEO 裁定「第 1 條管不管排程台」，再做靜態告知並重新定義這個測試；不建議 (a) 或 (b)。** 你的初判我**部分推翻**：(a) 是 CEO 事項，這點確認；但 (b) 夾值不只是風控審就好。它同樣會改 CEO 實際的下單股數，還踩到既有的模組邊界，所以也是 CEO 事項，並且要出 ADR。(c) 告知的文案由風控審即可，但它的前提（排程台不受第 1 條約束）要 CEO 拍板。
5. **我要自揭一個漏判。** quant 的第 1 條下修提案只把 `test_playbook_rebalance.py` 列成「佔比在 10%～15% 之間、狀態可能翻轉的 fixture」（`work/reviews/2026-10-26-第1條上限下修提案-quant-researcher.md:93`），沒看出這是排程台規則集本身和第 1 條的衝突。風控那份審查也沒涵蓋排程台。也就是說，CEO 做 #61 時沒有拿到這項資訊，這本身就是回 CEO 的理由。

## 1. 為什麼是 14%：算式與行號

**參數預設值**（`app/playbook/models.py:85-89`）：`cash_floor_ratio=0.30`、`deploy_ratio=0.70`、`n_targets=5`、`batches_per_target=3`。

**每批股數**（`app/playbook/engine.py:149-178`，`planned_batch_shares`）：
- `:167` 每檔金額 = `total_deploy / n_targets`
- `:168` 每批金額 = 每檔金額 / `batches_per_target`
- `:171-172` 前兩批：`max(1, floor(每批金額 / close))`
- `:173-178` 末批：`floor(每檔金額 / close)` 減去前兩批股數（吸收零股差額）

**套進測試**（`tests/test_playbook_rebalance.py:172-194`），總資產 1,000,000、close 100：

| 項目 | 算式 | 結果 |
|---|---|---|
| TOTAL_DEPLOY（`:175`） | 1,000,000 × 0.70 | 700,000 |
| 每檔金額 | 700,000 / 5 | 140,000 |
| 每批金額 | 140,000 / 3 | 46,666.67 |
| 第 1、2 批 | floor(46,666.67 / 100) | 各 466 股 |
| 第 3 批 | 1,400 − 932 | 468 股 |
| 合計 | 1,400 股 × 100 | 140,000 |
| 佔比（`:193`） | 140,000 / 1,000,000（總資產） | **14%** |

- **分母是總資產，不是部署資金**（`:193`：`shares × close / total_assets`）。
- **docstring 錯在哪**（`:165-167`）：「TOTAL_DEPLOY / 5 = 14% of the deployed capital」不對，應為 20%。14% 本來就已經是佔總資產的比例，再乘 70% 就變成 9.8%，等於把 `deploy_ratio` 扣了兩次。

**另外三個測試沒抓到的落差：**
- **比較方向不一致。** 測試用 `<=`（`:194`），第 1 條卻是「達到即違反」（`limits.py:14-16`、`:1043-1045`）。如果把 `n_targets` 改成 7，佔比剛好 10.0%：測試會綠，第 1 條卻判定違反。
- **14% 不是成本上的硬上限。** 末批按當天收盤價重算股數。例如前兩批在 100 買、第 3 批在 91 買（還沒觸發 S1 的 0.90）：合計 1,538 股，成本 148,346，約佔 14.8%。
- **市值會漂移。** 部位在 P1（成本 × 1.20）賣出前，14% 成本可以漲到約 16.3% 市值。所以不論參數怎麼調，都只能保證「進場時的股數」，保證不了「隨時 ≤ 10%」。

## 2. 實際使用時會不會發生

- **排程台就是 CEO 自己的操作規則。** CEO 原始規則集原文：「TOTAL_DEPLOY=可用資金70%(現金30%鐵律)、5檔標的、每檔3批輪動」（`work/stock-desk-快市排程-企劃.md:271`）。CEO 裁決二：「均分，不做信心加權」、`BATCH_AMOUNT = TOTAL_DEPLOY / N_TARGETS / 3`（同檔 `:278`）。PM 的產品審視也寫「排程台對應 CEO 自己的週二四規則集」（`work/reviews/2026-10-26-產品審視-product-manager.md:44`）。`models.py:19-20` 也明寫：每個門檻都是在重述使用者自己的規則。
- **參數不是從 yaml 讀，是存在 DB。**
  - 存在 DB 的 `playbook_rule_params` 表，每列一個 JSON payload，含 version、effective_date（`app/playbook/store.py:98-104`）。
  - 讀取時取「生效日 ≤ 當天」的最新一列；沒有任何列才用程式預設值 `system_default_params`（`store.py:569-586`、`:268-276`）。
  - advice 端的 `rules/default.yaml` 和它的 `rules_version` 是另一套（`app/advice/loader.py:47`），和排程台無關。
  - 排程台指令上記的 `rules_version`，其實就是 `RuleParams.version`（`engine.py:1298`、`store.py:132`）。
- **只有兩種狀態，沒有中間值：**
  - **未確認規則集：** 不產生任何指令（`app/playbook/service.py:541` 起的 `_unauthored_evaluation`），14% 不會發生。
  - **已確認：** `confirm_rules` 會把當時的預設值複製一份寫進 DB（`service.py:523-532` → `store.py:640-665`），之後就固定讀這份。現在只有 `POST /confirm-rules` 這個入口（`app/api/playbook.py:411-429`）。改參數的函式 `request_rule_change`（`service.py:864`）雖然存在，但**沒有接任何 API**，路由只有 `/today`、`/settle`、`/rule-set`、`/confirm-rules`、`/rebalance`、`/emergency-exit`。所以只要 CEO 確認過，他的參數必定是 0.70 / 5 / 3，**每檔進場就是排程台總資產的 14%**。
- **CEO 是否已確認，要讀 DB 才知道，我沒有讀。** 產品審視時前端在 demo.db 確認過一次、資本 1,000,000（`work/reviews/2026-10-26-產品審視-frontend-engineer.md:16`），但那是 demo，不是 CEO 的資料。
- **排程台和庫存是兩套獨立帳冊**（同檔 `:67`、`:109`），第 1 條只看庫存。所以 14% 只有在 CEO 也把這些持股記進庫存時，才會在建議卡上顯示成第 1 條違反。那時是「20% 對 10%」，而且排程台同時在叫他買。ADR-0025 已經預告會有這種情況：「同一個標的會同時有三種聲音……只能靠來源標示與衝突揭露處理，不會自動調和」（`docs/adr/0025-stock-desk-產品定位改為提供投資建議.md:515`）。

## 3. 解法選項

**先講三條既有限制**，它們決定了 (b)、(c) 能怎麼做：
- 排程台不得 import `app.advice` 任何模組，`RiskBudget` 也包含在內（`tests/test_playbook_boundary.py:30`、`:33-52`，風控 R4：「違反即豁免自始不成立」）。
- ADR-0025 AV-11：系統輸出不得寫入任何 playbook 表（`docs/adr/0025-…:550`）。
- ADR-0025 AV-13：前端不得計算門檻或狀態（同檔約 `:552`）。

**(a) 改劇本預設參數**
- 要讓佔比 < 10%：按測試的分母，`n_targets` 至少要 8（8.75%）；按第 1 條真正的分母，至少要 **11**（9.09%）；或者把 `deploy_ratio` 降到 0.50 以下，但這會破壞「現金 30% 鐵律」，也和 `tests/test_playbook_rebalance.py:196` 的斷言衝突。
- **對 CEO：完全沒影響。** 他已確認的那份存在 DB，結果是測試變綠、實際部位仍是 14%。這等於換個方式把衝突藏起來。
- **對未確認的使用者：** 系統預設值不再等於 CEO 寫的規則，違反 `models.py:19-20` 那條不變式，也動搖排程台用語的豁免前提——歸屬語「你自行設定的規則之機械執行結果」（風控 VETO-2）。
- 要改的檔：`models.py:88`、`tests/test_playbook_rebalance.py`、`tests/test_playbook_acceptance.py:350` 一帶、前端規則集參數的測試。
- 版本與 ADR：系統預設不帶版本（固定是 v1）。CEO 真要改自己的規則，得新增一個規則版本，照鐵律④次日生效，而這要先把改參數的 API 做出來。實質上是推翻「5檔標的」和裁決二，**屬 CEO 事項**。
- 風控要審：規則條文文案、歸屬語是否仍然成立。

**(b) 計算股數時以第 1 條上限夾值，並在畫面告知**
- 直接讀 `RiskBudget` 會違反 R4 的匯入邊界與 AV-11，而且等於讓系統判斷混進指令股數，歸屬語的豁免就不成立了。結構上走不通。
- 唯一能走的變形：在 `RuleParams` 加一個**使用者自訂**的單檔上限欄位，比照現金鐵律縮批的做法（`engine.py:981`，`_apply_cash_floor`）。但要注意，新欄位如果帶非空預設值，`store.py:586` 讀舊資料時會把預設值套進 CEO 已確認的規則集，等於冒用他的名義加規則。所以預設必須是「關閉」，只能由 CEO 用新版本自己開啟。
- 對行為的影響：維持 5 檔、上限 10% 的話，部署資金最多只能用掉一半，現金實質變成 50%，TOTAL_DEPLOY 的意義跟著改變。即使這樣，分母仍然對不上第 1 條。
- 要改的檔：`models.py`、`engine.py`、`wording.py`，前端參數表、規則集確認面板，以及新的 API。
- **需要 ADR**（修訂排程台邊界或新增規則）、CEO 核可、新的規則版本。
- 風控要審：縮批告知文案、歸屬語、R4 豁免是否仍成立。

**(c) 不改劇本，只在排程台告知**
- 對行為的影響：股數不變，使用者知情。
- 不建議逐批寫「本批會使第 1 條超限」。排程台看不到庫存，分母也不同，這句話可能根本不成立，屬於假精度。比較誠實的是在規則集層級放一段靜態算式，例如：每檔滿倉約佔排程台總資產 14%（70% ÷ 5）；第 1 條上限 10%，以庫存市值為分母；兩者是不同帳冊，排程台不會因此調整股數。
- 實作限制：受 R4（排程台不得讀 advice）和 AV-13（前端不得算狀態）限制，需要一個中立的後端組合點，由 tech-architect 決定位置。
- 不需要升規則版本。ADR 上，這正是 ADR-0025 的風控待辦第 6 項「engine、plan、playbook 三種聲音並存時的衝突揭露規格」（`docs/adr/0025-…:611`）。
- 風控要審：揭露規格與逐字文案（排程台禁用建議語、R18/R19、H-1 禁誇大、歸屬語不得弱化）。

**(d) 我的建議：先確認適用範圍，再告知並重新定義測試**
1. 這個測試是風控前置意見 D-2 的附帶要求：「playbook 指令不得產生違反 limits.py 上限的部位」（`work/reviews/快市排程-風控前置意見.md:49-50`），而且列在「缺一裁定不成立」的清單裡（同檔 `:41`）。它現在的寫法分母錯、比較方向也錯，本來就沒有真正驗到什麼。
2. 改法：修正 docstring 的算式；把 `<= 第1條` 改成兩個斷言。一是釘住算式（每檔佔比 = `deploy_ratio / n_targets`）；二是「佔比 ≥ 第 1 條時，告知一定會出現」，這部分配合 (c)。
3. CEO 裁決前不要讓這個測試靜默變綠。要嘛維持紅燈擋合併；要嘛用 `xfail(strict=True)` 並在 reason 寫明衝突和待裁編號，之後若被意外修好會立刻轉紅。用哪一種、要不要讓 #61 的 PR 先合，由 qa-reviewer 和風控同意；動 D-2 這項必要條件需要風控簽核。

## 4. 建議、理由，以及是否須 CEO 裁決

**必須由 CEO 裁決。** 這是兩個 CEO 決策正面衝突：#61（第 1 條 10%）對上原始規則集與裁決二（5 檔均分 70%）。加上風控 D-2 是 CEO 七題核可時的必要條件，D-2 做不到時，裁決二的核可是否仍然成立，要風控表態、CEO 拍板。

建議請 CEO 答一題：**第 1 條要不要約束排程台？**
- **要約束：** 由 CEO 用新的規則版本改自己的規則，例如 `n_targets ≥ 11`，或開啟自訂單檔上限。要先把改參數的 API 做出來，照鐵律④次日生效，並出 ADR。
- **不約束**（我傾向這個）：排程台是使用者自訂規則的機械執行，ADR-0025 已定調不自動調和、靠衝突揭露。照 (c) 加 (d) 做，風控審揭露規格和文案，風控簽核修訂 D-2。理由是 (a) 對已確認的 CEO 無效、只會讓測試假綠；(b) 會破壞排程台用語豁免所依賴的「使用者是規則作者」這個前提，而且分母仍然對不上。

我對初判的修正：
- (a) 是 CEO 事項：**確認**。
- (b) 只需風控審：**推翻**。它會改 CEO 的下單股數，又踩到 R4 和 AV-11，所以是 CEO 事項加 ADR。
- (c) 由風控審：**確認**。但它的前提「排程台不受第 1 條約束」要 CEO 先裁定。

**這份報告的限制：** 沒讀 DB，所以不知道 CEO 是否已確認、確認的是哪一版、庫存裡還有沒有其他持股（會稀釋 20% 這個數字）。全部檔案都只用 Read、Grep 與唯讀 shell 指令（`sed`、`grep`、`git log`）讀取，沒有改任何檔案、沒有跑測試，也沒有碰 `.env` 或 `data/*.db`。
