**[TA 補] 讀碼事實的判定**（我只讀程式，沒有執行）：

1. **評估之前先結算，結算失敗時沒有新的指令列：成立。**
   - `evaluate_today` 在 service.py:2153 呼叫 `_settle_pending`，比 `read_in_flight`（:2157）和 `commit_evaluation`（:2222）都早。
   - 例外往外拋，評估與 commit 都不會執行。
2. **`/settle` 同樣會失敗：成立，但只限已確認規則集的情況。**
   - `settle_on_request`（:1524-1551）只有在 authored 時才走到 `settle_pending`，然後進 `_settle_pending`（:1516-1522）。
   - 未確認規則集時直接回傳空結果，本來就不結算。這一點只要求精確化（suggested S6）。
3. **id 排在失敗列後面的到期列都不會結算，包括「全部出清」寫入的出清列：在「失敗發生在逐列迴圈內」的前提下成立。**
   - `pending_directives` 以 `ORDER BY id ASC` 取出到期列（store.py:1528）；`_settle_pending` 的迴圈（service.py:1611-1665）沒有 try/except。
   - `playbook_directives.id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT`（store.py:135），id 嚴格遞增，所以「出清列的 id 一定比較大」成立。
   - 出清列的執行日是下一個交易日（service.py:2329），到期後就排在失敗列後面。
   - **範圍缺口，屬於 R9 (a)：** 失敗也可能發生在逐列迴圈之前，例如 `pending_directives` 解析某一列時（`_row_to_pending`，:1529）。ADR 舉的例子「資料格式錯誤」正可能發生在這裡。這種情況下，本次**沒有任何列**會結算，連 id 較小的列也不會。ADR 目前寫「id 比失敗列小的列，各自 commit 之後保留」，在這種情況下會說多了。
4. **「全部出清」不經過 `_settle_pending`：成立，但「仍然可以送出、回應照常」要附條件（R9 (b)）。**
   - `emergency_exit`（:2288 起）的路徑是 `list_batches` → `_load_symbol_bars` → `commit_emergency_exit`，確實不經過結算。
   - 前端也確認過：今日頁面讀取失敗時，畫面顯示「無法載入排程台資料」（page.tsx:143-147），出清按鈕移到 h1 那一列（:116），對話框掛在 `today.isSuccess` 的條件之外（:228 起），所以按鈕可以按、請求也送得出。
   - 但如果造成確定性失敗的資料問題，也出現在出清要讀的資料裡（例如批次列），出清同樣會失敗。所以只能寫「不因結算失敗而無法送出」，不能寫成出清一定成功、回應一定照常。

**N198-C9 (b) 舉證方式：方向接受，附 R10。**
- 用 PR 頁面的建立時間（由伺服器記錄）當主要時間點、commit 時間只當旁證：正確。
- 但「最終由風控在 risk-gate 確認自己的收件時間」做不到。我是無狀態的 agent，不保有收件記憶，能核對的只有書面紀錄。而且送審紀錄與審查紀錄都是 repo 裡的檔案，日期只記到「日」，同一天內無法排出先後。

### 審查結論、逐條意見、否決理由（輸出契約）

**審查結論：** CONDITIONAL APPROVE。

**逐條意見（required 由 qa 列為 BLOCKING；文字項由 TA 修改後回我確認）：**

- **[ADR-0042 Consequences「失敗分兩種」[TA 補]] R9：**
  - (a) 「id 比失敗列小的列，各自 commit 之後保留」要限定為「失敗發生在逐列處理中時」。並補一句：失敗若發生在逐列處理之前（例如讀取到期列時某一列無法解析），本次沒有任何列結算。Decision 5 第 2 小點也要同步改。
  - (b) 「全部出清仍然可以送出，回應也照常列出出清指令」要改為：不經過結算，所以不會因為結算失敗而無法送出；但若確定性失敗的原因也在出清讀取的資料中，出清同樣會失敗。
  - 用語由 TA 擬，事實範圍以本點為準。
- **[ADR-0042 N198-C9 (b)] R10：** 舉證方式改為下列各項，全部要成立：
  - (1) 我對該補充的審查紀錄，必須在 N-198 的 PR 建立之前已經存在於 `work/reviews/`，並已 push 到 remote。也就是說，(c) 的「審查紀錄存在」提前到 PR 建立之前。
  - (2) PR 說明在**建立當下**就要列出三個路徑：補充、coordinator 送審紀錄、我的審查紀錄。qa 讀 PR 說明的編輯歷史，若這些引用是建立之後才補上的，就判 BLOCKING。
  - (3) 送審紀錄要記到分鐘並註明時區（Asia/Taipei）。
  - (4) 先後無法確立就判 BLOCKING，例如只有日期、時區不明、紀錄缺漏。
  - (5) 「風控確認自己的收件時間」改為「風控在 risk-gate 核對 (1)～(3) 的紀錄」。
- **[ADR-0042 先後與相依、待決] R11：** 加上第二節第 3 點的 CEO 通知義務與送達時點，並移除對應的待決項。
- **[N-199 第 5 節 R7 的範圍] R12：** 限縮的範圍改寫為「預設禁止，例外要能證明」：
  - 豁免只限於同一次測試執行中，由測試程式在暫存目錄自行建構的合成 DB 所產生、並由測試讀取的報告。
  - 無法證明輸入屬於這種情況的報告，一律視同 production 複本，任何 agent 都不得讀。
  - agent 不得對任何非測試自建的 DB 手動執行工具。
- **[修訂七第 2 節 S2] R13：** head SHA 的讀取方式不得依賴 commits 分頁的時間排序，要改成讀能反映分支 tip 的位置。由 TA 指定讀哪裡，限唯讀方式，不得因此新增 Bash。不同來源讀到的值不一致時，判 BLOCKING。這一項不擋 ADR-0042 落檔。

**suggested（不擋）：**
- **S6：** ADR 中「`/settle` 同樣每一次都失敗」補上「已確認規則集時」。
- **S7：** N-200 落地之前，若出現傳入 `at` 的呼叫點，N-200 要先行。修訂七第 4 節的「編號由 coordinator 給」可以改成 N-200。
- **S8：** 規格檔 :2710 的附記補一句「索引第 1 列依 TA 授權改為替換句，與回報原文不同」，讓稽核時能看出差異。之後不要再把這類修改稱為「只刪字」。
- **S9：** 「出清列的 id 一定比較大」可以引用 store.py:135 的 `AUTOINCREMENT` 作為依據。
