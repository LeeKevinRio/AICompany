### [RC-650] RC-594 的無法讀取列揭露缺口：升為 high（required，內部紀錄）

**事實**
- 〔我讀過〕`alerts/snapshot.py:130` 的 `build_summary(store, valuator)` 不分規則類型，一律呼叫。日線讀得到的標的，它的價格、訊號、風險上限規則共用同一份快照。
- 〔我讀過〕`engine.py:501-511` 的 `_load_isolated` 用 `except Exception` 接住例外，只記 WARNING，然後回傳空快照。所以價格規則的理由是「沒有可用的最新收盤價。」（`:526-527`），訊號規則是「沒有可用的訊號輸出。」（`:548-554`）。
- 〔我讀過〕`scheduler.py:412-425`：只有 log。有事件才推播，`outcomes` 被丟掉。
- 〔我讀過〕`AlertStatusStrip.tsx:103-107`：狀態 B 顯示「{n} 條規則已設定，目前沒有待處理警示」加「查詢時間」。同一個元件 `:41-48` 的註解，以及 `oneLinerWording.ts:95-99`，都記下了風控 09-19 R-A3 的理由：「總開關關閉時排程整個 tick 跳過，此時狀態 B……會被誤讀成『剛查過、沒事』，須另立一態」。
- 〔事實，dev-lead，我沒有自己讀〕下面這幾點採用 dev-lead 的說法：
  - 警示 DB 沒有任何每一輪的紀錄；
  - 規則和事件兩個 API 都不讀帳本；
  - 「手動檢查一次」只顯示筆數，不顯示原因；
  - 暫存 DB 的實測結果：`evaluated 3 events 0 load_failures 1`。

**判定**
1. RC-594 第 3 點的升級條件實質成立。手動檢查的「略過 N 條」確實是一個痕跡，但不能據此說「有痕跡」，理由是：
   - 它要使用者主動去設定頁按；
   - 它不說原因；
   - 被動的畫面（首頁）反而顯示「沒事」。
   條件原本要防的是「沒有推播被讀成沒有違規」，這個讀法在現況下完全成立。
2. 比我原本的設想更嚴重的有兩點：
   - 停掉的範圍包括價格規則和訊號規則（dev-lead I-4）；
   - 狀態 B 是「主動顯示放心訊息」，不只是「沒有痕跡」。這和 R-A3 處理的是同一類誤讀，R-A3 只承接了「總開關關閉」，沒有承接「這一輪失敗」。
3. 首頁同時會出現「無法載入投資組合摘要」（dev-lead I-2）。這句可以減輕一些，但不足以抵銷，原因是：
   - 它沒有說警示也停了；
   - 它和狀態 B 並排時，彼此矛盾；
   - 只靠推播的使用者根本不會看到它。
4. **等級 high。失效條件**：RC-652 和 RC-653 都合併進 product 之後，送我重新判定。不得因為 (B) 單獨合併就降級，因為 (B) 對警示的行為零改善（(B) 約束 4 是讓警示快照走明確失敗）。
5. 本機有沒有這種列，照舊記為未知，不得記為零（RC-594 第 4 點）。

### [RC-652] (B) 約束 9 的補強：警示一輪沒有完成時，使用者要看得到（required；給 tech-architect 寫進新 ADR 與規格）

**判定**：只記 WARNING 不夠。(B) 的 Consequences 寫的「警示停止期間，CEO 只有在開啟畫面時才會知道」本身也不成立：現在連開了畫面都看不到，因為狀態 B 會說沒事。依賴推播的使用者，正是不開畫面的人。

**對規格的約束**
1. **觸發範圍**：凡是一輪裡有任何規則因快照載入失敗而被略過（`load_failures > 0`），都適用。不限 `UnreadablePositionsError`。理由：`_load_isolated` 接住的是所有 `Exception`，其他成因一樣沒有痕跡。
2. **每一輪的紀錄**：
   - 後端要把「最近一輪」持久化，至少要有：
     - 完成時間；
     - 本輪啟用的規則數；
     - 因載入失敗而略過的規則數；
     - 其他原因略過的規則數；
     - 失敗類別，用固定代號，至少分出 `positions_unreadable` 和「其他」兩類。
   - 沒有事件的一輪也要寫。
   - 不得只存在 log 或記憶體裡，重啟之後也要能回答「最近一次檢查是什麼時候、結果如何」。
   - 不得帶例外訊息原文、數量、成本、備註。
   - 要透過 API 提供給前端，放在哪個回應由 tech-architect 定。
3. **首頁警示狀態列新增一態**（暫名 E「警示檢查未完成」）：
   - 最近一輪有載入失敗時，**不得顯示狀態 B**。
   - 字面要說出三件事：
     - 有幾條規則這一輪沒有檢查（有 RC-653 之後，改為說明是哪一類規則）；
     - 這些規則在這段期間不會發出推播；
     - 最近一次檢查的時間。
   - 優先序：
     - D（總開關關閉）照舊最優先；
     - C（有事件）照舊顯示事件，但同一個容器裡要加一行 E 的說明，不得被 C 蓋掉；
     - E 優先於 B。
   - 這是 R-A3 同一個邏輯的延伸。
4. **視覺**：E 不得和 B 用相同的中性樣式。版面交 art-lead，送我核。
5. **推播通道**（使用者自己的 Discord 或 Telegram）：
   - 失敗開始時送一則，恢復時送一則，不得每一輪重送。
   - 「開始」可以設門檻，例如連續 2 輪。門檻值由 tech-architect 定，寫進 ADR。
   - 只在 `notify_webhooks` 已設定時送。沒有設定時只能靠畫面，這個殘留要照實寫進 ADR 的 Consequences。
   - 送出失敗時，照現行 `notify_all` 的規則處理。
6. **ADR-0029 維運告警通道**：可以另外送，但不得當作對使用者揭露的替代。要不要接、什麼時候接，由 devops-sre 決定（suggested）。
7. **手動檢查一次**：結果句要分出「因資料讀取失敗而略過 N 條」，不得只有一個總略過數。
8. **其他原因的略過**：例如 ADR-0021 W-2 的永久略過，或上限無法評估造成的略過。
   - 第 2 點的紀錄裡要有這個數字；
   - 狀態 B 要不要附「其中 M 條這一輪無法判定」，等級 medium，required。可以晚於載入失敗那部分，另開 PR，規格由 tech-architect 出。
9. **字面**：
   - 由 creative-lead 起草，我逐字審。
   - 不得叫 CEO 改資料庫或檔案、執行工具或看 log（RC-595 R-c）。
   - 不得承諾什麼時候恢復。
   - 恢復通知不得寫「恢復正常」「沒有問題」，只能陳述「最近一次檢查已完成」這類事實。

    - 推播在開始與恢復時各送一次，連續失敗時不重送；

11. **時點與和 (B) 的關係**：
    - 本條適用所有成因，所以**可以先於 (B) 落地**；
    - 不得和 (A) 放在同一個 PR；

### [RC-654]「查詢時間」：另一個揭露缺口，medium（required；和 RC-650 分開判定）

**事實**
- 〔我讀過〕`oneLinerWording.ts:78-85` 的註解寫「刻意用『查詢時間』而非『最近評估』……誠實標示避免暗示排程剛評估過」。
- 〔我讀過〕`work/reviews/2026-09-19-一眼一句簡化-審查紀錄.md:65` 把這件列為殘留：「『查詢時間』非排程實際評估時間：後端無欄位；data-engineer 另案評估在 `AlertEventListResponse` 加 `last_evaluated_at`」。
- 〔我 Grep 過〕`work/` 裡的 `last_evaluated_at` 只命中 09-19 那一行。`apps/stock-desk` 裡的 `last_evaluated` 和 `lastEvaluated` 都是 0 筆。

**判定**
1. **這是揭露缺口，等級 medium。** 理由：
   - 「查詢」在台灣用語裡，可以讀成「系統去查了」。和「目前沒有待處理警示」放在一起，整句很容易被讀成「這個時間查過了，沒事」。
   - 這和成因無關。帳本、資料來源、其他例外造成的載入失敗，或排程根本沒有在跑，都會讓這個時間和實際檢查脫鉤。
2. **單獨不升 high。** 理由（推論）：排程正常時，實際檢查和查詢時間的差距不會超過一個排程間隔。會造成實質誤導的情形，主要就是 RC-652 承接的那幾種。
3. **修正方向**：
   - RC-652 第 2 點的紀錄存在之後，狀態 B 要顯示從紀錄來的「最近一次檢查時間」，可以取代或並列查詢時間。
   - 還沒有任何一輪紀錄時（例如剛啟動），要照實說出來，不得悄悄退回用查詢時間。
   - suggested：最近一次完成的時間超過排程間隔的 2 倍時，不得顯示狀態 B。
   - 過渡期的改字列為 suggested，避免和正式修正重工。
4. **內部紀錄**：
   - 09-19 的「data-engineer 另案評估」沒有後續，補進 RC-587 第 1 點的落空清單。
   - 自我紀錄：09-19 我逐字核可了「查詢時間」。字面本身沒有說錯，但「誠實標示就足以避免暗示」這個前提不完整。當時只把總開關關閉另立一態，沒有涵蓋「這一輪失敗」。

### [RC-655] F1b-R13 第 2 點在新知悉包 F-1b 那一項的使用（required，給 creative-lead）

**可以用，只能用「現況」那一半**（依 dev-lead RC-601 在 HEAD `6e6ac35` 的確認，以及 `test_unusable_fx_f1b.py` 的 `4 passed`）。字面約束如下：
1. **只寫現況，不寫「從通過改為」。** 「修正前是通過」那一半沒有查證。過去的部分已經由第三項「過去可能怎樣」承接（RC-592，讀碼推定），不得重複，也不得加強。
2. **適用條件必須寫在句子裡**，意思要等同「您已填寫淨值，而且淨值沒有過期時」。
   - 「過期」要用 app 畫面上自己的說法。
   - 不得省略這個條件，也不得寫成所有情形都如此。
   - 不得描述沒填或已過期時的情形。那兩種情形原因不同，寫出來會讓人以為是同一件事。
3. **範圍是整本帳本**（dev-lead RC-601 事實 2：`_fully_valued` 是全帳本的旗標）。
   - 要寫成各標的的決策卡（包括那一筆所屬的標的）和上限總覽都會如此；
   - 不得照 F1b-R13 原文只寫「其他標的」。
4. **用語**：寫「無法評估」，並帶出「不代表已通過」的意思。不得寫「未通過」「違反」。
5. **不得描述卡上的理由句或它的位置。** 理由：
   - 理由句沒有被測試釘住（dev-lead 推論）；
