### 一、三點逐一

**(1) 有沒有「決定 T 之後不寫 `forecast_run`」的正常返回路徑：照字面無**
- **字面依據**：
  - attempt end 的 `outcome` 是封閉集合 {`run_written`, `inputs_not_ready`, `error_before_run`}（D-3 L285-288）。
  - `run_written` 與 A-25 的 run 和範圍快照同一交易，而且在處理任何範圍之前寫入（L286、L1689）。
  - 唯一明文的「正常返回」是 `inputs_not_ready`（L1049），而 Q4 把它定為「本次執行沒有 T」（L956）。所以它不算「決定 T 之後」。
- **決定 T 之後只有兩種出口**：
  - A-25 commit 之前拋例外：寫 `error_before_run`，再 raise（L288、L1047）。
  - A-25 commit 之後進範圍迴圈：正常返回 `ok`／`partial`／`timeout`，或寫 `error` 後 raise（L1028-1044）。
- **連帶**：`RecordStepResult`（L1040）中「t 非 None、`run_id` 為 None」的組合，在現行字面下是死組合。
- **字面沒涵蓋、實作會被迫處理的情形**：
  - (a) 重試或補跑時，T 的範圍已全部寫入。見第 (2) 點，這是最常見的情形。
  - (b) D-14 執行期閘門 G-3、G-4 不成立（L2354；FL-38 L3009）。字面只說「拒絕寫入排程紀錄」，沒說檢查放在記錄一步的哪個位置。三種放法各有問題：
    - 放在開始列之前就返回：違反 D-3 L284「每一次排程記錄一步恰好一列」開始列。
    - 在前置段拋例外：D_v 之前每天一則 `error_before_run` 加 E-3d。
    - 決定 T 之後正常返回：就是本題的路徑，要新增 outcome 值。
    - 若改成逐範圍拒寫：閘門例外不在 `RECORD_SCOPE_REFUSAL_TYPES` 內，會整步 `error`。
  - (c) 決定 T 之前，順帶一提：市場 DB 沒有任何 ok bars run（新安裝或還原後）時沒有候選 T。`inputs_not_ready` 要求 `candidate_t` 非 null（L290），`error_before_run` 又必須先有例外，所以字面上沒有正常出口。
- **實作注意**：
  - **T 怎麼交回編排函式**：前置段與範圍迴圈都以不帶參數的 `raise` 結束（L1047、L1033），編排函式拿不到 T。但 Q4（L956）要求「決定 T 之後才失敗時，T 照樣存在」，而編排函式又不得讀 attempt 表（L291）。實作上只能用編排函式傳入的可變進度物件，或在例外物件上掛屬性。建議 ADR 明定用哪一種。
  - **兩個「T」不同指**：D-3 L288 的「已判定的候選 T」（`candidate_t`）與 Q4 的「決定 T」不是同一件事。例如 (ii) 強制重抓時拋例外：`candidate_t = S`，但 S 還沒通過 (ii)。若此時視為 T 已存在，快照與 plan 會用一個大盤 bar 未定案的 T。建議定為：Q4 的 T 必須四項都通過，`candidate_t` 只是稽核值。

**(2) 重試遇到已寫入範圍：ADR 未定義**
FL-76 L2527 明示排除這個情形，TA 原稿第 360 行也自列為未查證。
- **頻率高**：
  - D-7.1 L909 的啟動補跑在每次程序啟動都會跑。現有 job 的啟動跑法是 `next_run_time`（`scheduler.py:672`、`:686`），週末或盤中重啟時，候選 T 仍是已寫完的上一個 session。
  - 22:10 成功之後，23:10 重試也必然遇到。
- **照字面的後果**：
  - M-6 部分唯一索引（L197）會讓第二次寫入拋 `sqlite3.IntegrityError`。它不在封閉清單內，於是整步中止、`outcome = error`、發 E-3d（L1030-1033）。
  - 中止若發生在第一個已寫範圍，後面真正要重試的範圍（22:10 被拒寫或逾時的）就不會跑。N-64 第 3 項取 `run_id` 最大的 run 判定，這些範圍會被記成 `record_error`。
  - 若改成「跳過、但仍列入快照」：D-3 L276-278 規定 `scopes_done + scopes_missed` ＝ 快照數、`ok ⇒ scopes_missed = 0`、`partial ⇒` 拒寫項數 ＝ `scopes_missed`。跳過的範圍只能算 missed，`ok` 和 `partial` 都過不了寫入驗證。
- **候選做法**（三者都要改字面）：
  - **甲：範圍快照只含尚未寫入的範圍**。在 A-25 交易內依 R_s 判定；全部已寫時快照為空，run 照寫（`ok`，0/0）。
    - 好處：D-3 的 run_end 驗證、D-8 的 N-64 聯集、D-11.4 `not_in_schedule`（L1680；已寫的範圍有 R_s，會先被判定）都不用改。FL-76 (d)（L2531）「補跑快照只有 C」正好就是這個行為。第 (1) 點也不必加 outcome 值。
    - 衝突：D-3 `plan_coverage_log` L837 規定「`targets_json` 與**同一 run** 的範圍快照不一致的標的數，在 §4.2 另列」。採甲之後，每次重試都會出現假的不一致，L837 要改成與 S 全部 run 的快照聯集比對。另外，快照的語意從「當下的排程範圍」變成「本 run 要寫的範圍」，要寫明。
  - **乙：快照照列全部範圍，run_end 加一個計數欄**（例如 `scopes_preexisting`）並改驗證。
    - 衝突：D-8 第 3 項會把「只跳過、沒有寫」的範圍納入判定。例如 C 只有 `late=1` 紀錄，之後又一次補跑跳過 C、end 為 `ok`。依 L764「非決定 run 也適用帳目矛盾」，會拋 `GapAuditRunInconsistencyError`，缺日稽核停擺。採乙必須連帶改 D-8 與 `basis_json` 的定義。
  - **丙：全部已寫時不寫 run，正常返回**。attempt end 新增一個值（例如 `already_recorded`）。D-8 的 S 嘗試定義 (a)(b)（L1239）本來就不會收進它。但部分已寫的情形仍需要甲或乙，所以丙只能搭配使用。
  - **我的建議：單用甲**，路徑最少。
- **不論選哪一個都要定的細節**：
  - 「已寫入」以範圍為單位，還是以（範圍, claim）為單位？若兩次 run 之間新登記了 claim（N-84），範圍內部分 horizon 已有紀錄，一個範圍一個交易會撞 UNIQUE。
  - 已有 `late=1` 紀錄的範圍是否算已寫入。依 L764「含 `late=1`」與 FL-76 (d)，應該算。
  - 「已寫入」的判定要放在 A-25 寫入交易內。

**(3) 前置段的 `except Exception` 放在另一個函式：可行**
- **結構**：
  - 入口函式本身沒有 `except Exception`。開始列寫入不包在任何 try 內（符合 D-3 L284、FL-76 (i)）。
  - 入口依序呼叫 `_record_prelude`（恰好一個 `except Exception`：寫 `error_before_run` 的 end，再不帶參數 `raise`），再呼叫範圍迴圈函式（即 FL-74 (b) 所指的那個函式）。
  - `error_before_run` 的 end 寫入函式另成一個函式，只有一個 `except Exception`，區塊內只記 WARNING、不 `raise`。
  - 這樣同時滿足 FL-74 (b)（L2517）、FL-76 (p)（L2543）與 D-7.7 N-66（L1046-1049）。
- **注意**：
  - a. FL-74 (b)「記錄一步的單一函式內」要讀成「範圍迴圈所在的那個函式」，不是「記錄一步只有一個函式」。建議 TA 加一句澄清。
  - b. AST 測試要認得出哪個是前置段函式。建議 ADR 給暫定名稱，或比照 FL-74 (b) 補上條件：區塊內只呼叫 end 寫入函式並以不帶參數的 `raise` 結束；end 寫入函式只有一個 `except Exception`，而且不呼叫 `str(exc)`／`repr(exc)`。FL-76 (p) 目前只要求「不在同一函式」。
  - c. A-25 commit 之後、範圍迴圈的 try 之前，不能有任何會拋例外的程式碼，否則兩個 except 都接不到（結果是 `job_error`，行為仍正確，但 run 沒有 end）。
  - d. `inputs_not_ready` 的 end 寫入落在前置段的時窗內。它寫入失敗時，依 L1047 會被前置段的 except 接住，再補寫一列 `error_before_run`；依 D-3 L287 的「例外往外拋」則不補寫。兩種讀法稽核結果都是 `record_start_failed`，但 end 列有沒有不同。需要 TA 定。
  - e. `candidate_t` 要在可能拋例外的步驟之前先指派到區域變數，except 區塊才填得出來。
  - f. 開始列寫入必須放在前置段的 try 之外。

### 三、FL-76 各格的可測性
**共同 fixture**：
- 可設定、可前進、微秒精度的假 store 時鐘。clock 注入已有先例：`app/data/market_panel.py:430`、`app/dividends/store.py:159`、`scheduler.py:329`／`:544`。

- 前置段的注入點：假 `MarketPanelReader` 能在判定候選 T 之前拋例外；假 `app.services.index` 能控制 (ii) 重抓的結果。

**需要特別處理的格**：
