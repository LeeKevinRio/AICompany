## 一、本次結論

**審查結論：APPROVE（修改後核可），沒有否決。** 但下面 R-1～R-12 這幾項 required 修改沒有全部套用之前，整批不得落檔，(b) 身分比對也不得實作。

我採用的兩個 suggested（身分三欄、gap_audit 候選），設計方向都對。不過照現在的字面落檔，會出現兩個讓守衛「自己解除」的洞，另外還有一個把相同身分誤判成不符的機械錯誤。

1. **R-1【最重要】gap_audit 候選會讓守衛自己解除（負面那一側放行）。**
   - 依據【事實】：(1b) 規定「守衛成立時本列照常寫入」，N20-2 的 (iii) 取「`market_run_current` 最大的一列（同值時取 `audit_id` 最大者）」。
   - 推論出的情境：結算連日失敗（這正是採用 (iii) 的理由）時，參考值只靠 gap_audit 的歷史最大值 v 撐著。市場 DB 被單獨還原到 v 之前後，新時間線把 run 寫回 v。這時守衛期間的稽核寫下 `market_run_current = v`，身分是新時間線的身分；同值時取 `audit_id` 最大者，候選就換成這一列，身分相符，**守衛自行解除**。
   - 修法：只有守衛不成立時寫入的稽核列，才能當參考候選。
2. **R-2 更正作業的候選 (ii) 在 (b) 狀態下會前進。**
   - 依據【事實】：第 8 點「還原保護」的觸發條件仍是字面上的「W 大於目前市場 DB 的 `MAX(run_id)`」，ADR-0029 L216 也寫明第二批之前「更正作業照常啟動」。
   - 推論：r_now ≥ W、只有身分不符時，第 8 點不成立。作業會掃描新時間線，再把 `market_scan_to` 與它的身分推進到新時間線。
   - 修法：第 8 點改為「共同守衛成立時」。這一項不依賴 CEO #42。
3. **R-3 manifest 只檢查最大的候選，和守衛「任一候選不符就成立」不一致。**
   - 照現稿，manifest 判為可用的組，整組還原後仍可能因為值較小的候選不符，讓守衛永久成立。
   - 修法：值大於 0 的每一個候選都要檢查。
4. **R-4 `session_date` 可以是 null（data-engineer 查證：TEXT，可為 null）。**
   - ADR-0026 寫「比對只用 SQL 的 `=`」，TA 約束第 8 點也允許 SQL `=`。但 `NULL = NULL` 不為真，相同的身分會被判成不符，守衛會永久誤報，逼出繞過的壓力。
   - 修法：SQL 端用 `IS`，`*_identity_json` 解碼後逐欄比對。
5. **N20-1 的但書不接受原字面，修改後核可。**
   - 原字面等於在條文裡預寫一條放寬路徑。它也和 ADR-0026「有參考 run 但沒有存身分就算未通過」互相矛盾：守衛放行，manifest 卻判失敗。
   - 修法：把「本點在 D-9 程式前落檔」從事實陳述改成有約束力的順序規定；晚落檔時怎麼遷移，不在本次核可範圍內。
6. **devops-sre 起草的各點：** 舊組處理、無參考 run、沒存身分算未通過、兩處一致性改字，都核可。「同值時各候選都要通過」被 R-3 取代。另外要補三件事：
   - 災難時改用未通過的組，屬於放寬；
   - F-8 的「沒有成功產出」要定義；
   - 「規定落地」指哪一天要定義。
7. **ADR-0029 E-2：知悉，確認。** 但 render 的三個新標籤，我這次**沒有拿到字面**，無法確認，要逐字送我。

## 二、各部門回報（risk-compliance-officer）

### 審查結論
APPROVE（修改後核可）。R-1～R-12 是 required，全部套用後才可落檔；R-12 的標籤字面要另送。

### 逐條意見

**R-1【required；N20-2「參考值一句」(iii)、4-A、ADR-0026 2-1 (iii)】守衛期間寫入的稽核列不當參考候選**

N20-2 第 (iii) 項改為：
> (iii) `forecast_gap_audit` 中 `market_run_regression_json` 為 null 的列裡，`market_run_current` 最大的一列（同值時取 `audit_id` 最大者）的 `market_run_current` 與 `market_run_current_identity_json`。守衛成立時寫入的稽核列（`market_run_regression_json` 非 null）不是參考候選：否則市場 DB 單獨還原後，新時間線的同號 run 會經由守衛期間的稽核列成為參考，使守衛自行解除。

- ADR-0026 2-1 的 (iii) 要同步，改為「`forecast_gap_audit` 中 `market_run_regression_json` 為 null 的列裡，`market_run_current` 最大的一列（同值時取 `audit_id` 最大者）的…」。
- 方向：補漏洞（收緊）。
- 說明：(i) 本來就安全。D-9.2 規定守衛成立時「本次結算評估不寫入任何列」，所以 settle_eval 的列都是守衛不成立時寫入的。

**R-2【required；ADR-0027 D-3「晚到資料的觸發」第 8 點，與 N-20 同批，不依賴 #42】**
- 定位字串（唯一，L432）：`8. **還原保護**：W 大於目前市場 DB 的 `MAX(run_id)` 時`
- 把「W 大於目前市場 DB 的 `MAX(run_id)` 時」改為：
  > W 大於目前市場 DB 的 `MAX(run_id)`，或 D-7 第 2 點共同守衛成立（含 `regression_kind = reference_identity_mismatch`）時
- 附〔N-20 取代：原寫「W 大於目前市場 DB 的 `MAX(run_id)` 時」〕。
- 這樣 N20-4「還原保護成立、`market_scan_to` ＝ W 時照抄」在 (b) 狀態下也適用，候選 (ii) 不會前進到新時間線。
- 方向：收緊。CEO 同意 #42（守衛成立時不啟動作業）時，這一句是它的子集，兩者不衝突。

**R-3【required；ADR-0026 2-1，L360～L362、L367～L370】每一個值大於 0 的候選都要檢查**

L360～L362 三個子點換成：
> - 沒有列的一方不計。值大於 0 的每一個候選都要通過 (c)：manifest 逐候選記下候選種類、值、存下的身分與檢查結果。三方取值最大者（同值時依 settle_eval → correction_job → gap_audit 取第一個）另記為「參考 run」，只供對照 ADR-0029 E-2，不影響判定。
> - 理由：ADR-0027 D-7 第 2 點的守衛只要任一候選不符就成立。只檢查最大值的組，整組還原後仍可能因為較小的候選身分不符而使守衛成立。每一個值大於 0 的候選都在市場 DB 備份中存在、而且身分相符時，還原後的 `MAX(run_id)` 不小於任何候選，(a)、(b) 都不成立，所以本檢查不另比 r_now〔推論：完整還原程序（含 WAL）未驗證，N-40〕。
> - 沒有任何值大於 0 的候選時，沒有參考 run：manifest 記「無參考 run」，(c) 不適用，不算未通過（與 ADR-0027 同一處理：沒有參考值就不檢查）。

L367 的「下列情形都算沒通過」改為「任一個值大於 0 的候選有下列情形，就算沒通過」，三個子項不變。

**R-4【required；ADR-0026 L365、N20-1 身分子點、約束第 8 點】null 的比對與 JSON 的比對**
- ADR-0026 L365 整句換成：
  > 比對逐欄比原值：以 `run_id` 查市場 DB 備份的 `pit_snapshot_runs`，三欄都要相等。`session_date` 兩邊都是 null 時算相等，一邊是 null、另一邊不是時不相等。在 Python 比對時用 `==`；在 SQL 比對時用 `IS`，不得用 `=`（`NULL = NULL` 的結果不為真，會把相同的身分判成不符）。主 DB 的 `*_identity_json` 先解碼再逐欄比對，不比對 JSON 字串本身。
- N20-1 身分子點，在「`session_date` 兩邊都是 null 時算相等」之後接：
  > ，一邊是 null 時不相等；逐欄比對，`*_identity_json` 先解碼再比，不比對 JSON 字串本身；在 SQL 端比對時用 `IS`，不得用 `=`
- 約束第 8 點整點換成：
  > 8. 身分比對（`market_run_regression`、`read_run_head` 與 ADR-0026 D-9 第 2-1 點的 manifest 檢查）逐欄比原值：Python 用 `==`，SQL 用 `IS`（不得用 `=`；`session_date` 可為 null）；`*_identity_json` 解碼後比對，不比對 JSON 字串。上列函式內，`recorded_at` 不出現在 `ORDER BY`、`<`、`>`、`<=`、`>=`、`datetime.fromisoformat`、`strptime` 的呼叫裡（AST／grep）。本條範圍限於上列函式。
- 理由：要限定範圍，是因為 ADR-0027 L293、L1888 的 PIT 證明本來就用 `inputs_max_recorded_at > cutoff(T)`。不限定的話，這條全域 grep 會打到它，結果不是過不了，就是被臨時放寬。

**R-5【required；N20-1 但書整句換掉】**

把「本點在 D-9 程式實作前落檔，所以不存在身分為 null 的候選列。若晚於…屆時另送風控。」換成：
> - 本點與 D-3 的三個 `*_identity_json` 欄，必須在 D-9 程式（`forecast_settle_eval`、`forecast_correction_job`、`forecast_gap_audit` 的寫入）實作之前落檔，所以不存在值大於 0、身分卻為 null 的候選列；D-3 各欄的寫入驗證拒絕這種列。本點若晚於 D-9 程式落地，既有列如何遷移不在本點的核可範圍：不得預設以 null 遷移、只適用 (a)。遷移方式要先送風控（屬於放寬時，另需 CEO 明示同意）；核可之前，(b) 與該遷移都不得上線。

- 裁定理由：
  1. 原句把一條放寬路徑先寫進條文。「屆時另送風控」擋不住實作者照條文去做。
  2. 原句和 ADR-0026「有參考 run 但沒存身分就算未通過」矛盾。
  3. 「在 D-9 前落檔」是對未來的陳述，要改成有約束力的順序規定，coordinator 才能機械核對。
- 方向：收緊。CEO：否。

**R-6【required；N20-2「處理終點」第一子點、N20-8 (1e)】把絕對句限定範圍，和殘餘一致**
- 處理終點第一子點換成：
  > - 市場 DB 單獨被還原到早於某個參考 run 的時點時，該 run 在還原後不是不存在，就是與重號的新 run 身分不同，所以本判定持續成立，結算評估持續不寫入（fail-closed）。還原點不早於任何參考 run 時，本判定不成立（D-7 第 2 點殘餘）。
- 第二子點句末加：〔推論：完整還原程序（含 WAL）未驗證，N-40〕。
- N20-8 新句裡的「市場 DB 單獨被還原時，稽核列持續非 null」改為：
  > 市場 DB 單獨被還原到早於某個參考 run 的時點時，稽核列持續非 null（還原點不早於任何參考 run 時偵測不到，D-7 第 2 點殘餘）

**R-7【required；N20-5 (1a)】** 現行 (1a)「各鍵與 D-9.2「R 倒退」的例外屬性同義」改為：
> `regression_kind`、`reference_kind`、`reference_value`、`reference_id`、`reference_started_at` 與 D-9.2「R 倒退」的例外屬性同義；`reference_identity`、`current_identity` 是完整身分，其中的 `recorded_at` 分別等於例外屬性 `reference_recorded_at`、`current_recorded_at`

不改的話，七個鍵裡有兩個「同義」不屬實。

**R-8【required；N20-7 FL-67 (n) 身分格加四格；FL-64 (g) 加一格】**
- 在 (ix) 之後接：
  > (x) 結算連日失敗、`forecast_gap_audit` 的歷史最大值是唯一高於還原點的候選：市場 DB 單獨換回備份，再寫 run 使 r_now 等於、再大於該值 → 守衛期間寫入的稽核列（含與參考值同值、`audit_id` 較大者）不成為候選，守衛持續成立；
  > (xi) 兩邊 `session_date` 都是 null、其餘兩欄相同 → 相符，不成立；一邊是 null → 不符，成立；以 SQL 比對的實作用 `=` 時本格失敗（反例格）；
  > (xii) 值最大的候選相符、值較小的候選身分不符 → 成立，回報該較小候選；
  > (xiii) `*_identity_json` 的鍵順序或空白不同、三欄原值相同 → 相符。
- FL-64 (g) 句末接：
  > （N-20）r_now ≥ W，而共同守衛以 `reference_identity_mismatch` 成立 → 比照第 8 點：不產生 `source_revision` 觸發，W 不前進；有其他觸發時作業的 `market_scan_to` ＝ W，`market_scan_to_identity_json` 與前一個已完成作業逐位相同。

**R-9【required；N20-7 FL-71 (e) 接句】** TA 接句的第二句「`forecast_settle_eval.market_run_max_identity_json` 等於同一次讀取的身分。」換成：
> `forecast_settle_eval` 沒有新列（spy）。另一格：守衛不成立時寫入的 `forecast_settle_eval` 列，`market_run_max_identity_json` 等於同一次 `market_run_regression()` 讀到的 R 的身分。

理由：守衛成立時本來就不寫 settle_eval 列。原句會讓人以為守衛成立時有一列可以比對。

**R-10【required；約束第 10 點、ADR-0026 舊組子點】部署順序與「落地」的定義**
- 約束第 10 點句末接：
  > (b) 的部署上線，也不得早於 ADR-0026 D-9 第 2-1 點的備份實作（順序與 manifest 檢查）上線，而且上線時已有至少一組 manifest 檢查通過的備份組（devops-sre 確認）。
- ADR-0026 L380「**規定落地之前已存在的備份組**」那一子點，括號之後加：
  > 「規定落地」指依本點順序與 manifest 檢查的備份實作上線之日，不是本 ADR 文字落檔之日。
- suggested：括號中的「以及落地後、ADR-0027 N-20 欄位存在之前產生的組」改為「以及主 DB 備份中已有值大於 0 的候選、卻沒有 `*_identity_json` 欄的組」。依 R-5 的順序規定，N-20 欄位存在之前不會有候選列；這類組其實是「無參考 run」，照現字會被判為不可用，空窗不必要地變長。

**R-11【required；ADR-0026 L384 與 F-8】**
- L384 整句換成：
  > - 災難發生時若沒有任何通過的組，不得自行改用舊組或未通過的組：升級 CEO 與 devops-sre 決定，決定前不得改動 DB。改用未通過或未檢查的組屬於放寬，要 CEO 書面明示同意，事後送風控審查。不論決定為何，都不得以手動改寫 DB、刪除參考列或關閉守衛代替；整組還原後守衛若成立，依 ADR-0027 D-9.2「處理終點」處理，不另設解除工具。
- F-8 在「備份組連續 3 天沒有成功產出」之後接：
