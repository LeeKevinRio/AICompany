#### 2. C8 的執行與判斷分離（第 5′ 項）：接受

**理由：**
- CLAUDE.md §4 明文規定：「工具缺席不得以放寬唯讀邊界解決：改走執行/判斷分離」。TA 沒有提出把 `git merge-base` 加進 `READONLY_ALLOWED_BASH`，這樣處理正確。
- `git diff` 旁證讓 qa 有一項自己親手取得的內容證據，不只是讀別人的輸出。

**缺口：** 現在的寫法只要求兩份輸出的 SHA 和 exit code 一致，但沒有要求兩份輸出、以及 qa 審的 tree，是對同一個 PR head、同一個 product tip 算出來的。另外 `--is-ancestor` 成功時沒有 stdout，exit code 一定要明確印出來。

**required（qa 列為 BLOCKING；N197a-C8 一併適用）：**
1. **(ii) 要獨立計算。** coordinator（或 devops-sre）要在自己的 checkout 上，fetch 之後自己執行 `git merge-base`，求出 `<base>`，不得抄 PR 說明裡的值。紀錄要列出所用的 PR head SHA 與 product tip SHA（完整 40 碼）。
2. **exit code 要明確印出。** 兩份輸出都要逐條附上指令原文，並在每條指令之後明確印出 exit code（例如 `; echo "exit=$?"`）。只寫「通過」不算數。
3. **執行者要獨立。** (ii) 的執行者不得是 (i) 的執行者，也不得是該 PR 的作者或共同作者。
4. **要綁定 qa 審的 commit。** qa 要以 `git diff <紀錄中的 PR head SHA> <qa 實際審查的 commit>` 確認結果為空。結果不為空，或兩份紀錄的 PR head SHA 不同，都判 BLOCKING。
5. **PR head 變動就重做。** PR head 只要有任何新 push（包括 C9 的 merge product），(i)、(ii)、旁證全部重做，舊紀錄作廢。

**揭露：**
- qa 對 (i)、(ii) 的真實性，只能靠「兩個獨立來源一致」加上「旁證」來判斷，沒辦法親自重現 ancestry。這是執行與判斷分離本來就有的殘留，我接受。
- 這個做法不改變 ADR-0007 所揭露的現況：唯讀邊界目前只靠自律維持。

#### 5. ADR-0041 R-5′、R-6′ 定稿（交 tech-writer，放在 Consequences 的 R-4′ 之後；補完不用回我）

「R-5′：REBALANCE 讀取 snapshot 之後、寫入 TOTAL_DEPLOY 之前，若 `confirm_rules` 寫入資金，結果不等於任何一種先後執行的結果。N-195 之前，新填的資金會被 REBALANCE 蓋回舊值，等同這次資金確認沒有發生，但資金確認的回應可能已顯示新值；N-195 之後，現金是新填的資金，TOTAL_DEPLOY 卻依舊現金算出，使用者調降資金時，會比兩種先後執行結果中較高者再高出（舊現金 − 新資金）× deploy_ratio，方向不保守，並沿用到下一次 REBALANCE 或下一次資金確認。事後無法從帳冊辨識。目前前端沒有 REBALANCE 的入口，規則集確認之後也沒有改資金的入口，不保守的分支只在確認之後以 API 調降資金、同時以 API 執行 REBALANCE 時出現。處理：N-197a 在同一個寫鎖交易內比對 snapshot 讀到的三個 TOTAL_DEPLOY 鍵，不一致就不寫入，並以 `REBALANCE_SUPERSEDED` 揭露，不自動重試；期限最遲與第三包同一個 release；修好之前，這個交錯仍在，以風控 2026-11-07 更正版 CEO 通知揭露。N-197a 上線前，若前端新增 REBALANCE 或確認之後改資金的入口，須先回風控（[TA-177S] 修訂四第 3 節）。」

#### 6. CEO 通知補充句的名稱問題：要重送

**判斷：**
- 已送出的句子，每一句單看都算成立：
  - 現行 production（N-195 之前）首次確認時撞上，資金確實會被蓋回舊值（0），買單會依 `SHRINK_TO_ZERO_NOTE` 全部剔除，使用者看得到；

  - (1) 句中要避免的是那顆按鈕，但按鈕只在尚未確認時出現，這時 C0 = 0，所以「調降資金」在按鈕路徑上根本不可能發生。

**更正版全文（取代已送出的補充句，請重送並確認 CEO 收到）：**

「補充（風控，2026-11-07 更正版，取代同日稍早送出的補充句）：REBALANCE 目前沒有畫面入口，只能直接呼叫 `POST /api/playbook/rebalance`；排程台頁面的『確認規則集並設定資本額』按鈕只在尚未確認規則集時出現，確認之後要改資金，只能直接呼叫 `POST /api/playbook/confirm-rules`。請不要讓 REBALANCE 與資金確認（包括這顆按鈕與直接呼叫 confirm-rules）同時執行。兩者要落在毫秒級的同一個窗口內才會互相干擾，頻率極低，但發生時事後無法從帳冊察覺。N-195 上線前，你新填的資金可能被 REBALANCE 蓋回舊值，等同這次資金確認沒有發生，但資金確認的回應可能已顯示新值。N-195 上線後，資金會保留新值，TOTAL_DEPLOY 卻可能依舊的現金算出：你在確認之後以 API 調降資金時，TOTAL_DEPLOY 會高於任何一種先後執行的結果，並沿用到下一次 REBALANCE 或下一次資金確認；若在首次確認時撞上，TOTAL_DEPLOY 會停在 0，之後每批買進最多只出 1 股，直到下一次 REBALANCE。若你懷疑兩者曾同時執行，請等兩者都完成後，依你原本要的先後，再執行一次較後的那一項。本補充在 N-197a 上線前有效。」
