## 二、逐項裁定

**第 3 點｜RC″-1 同步 A-62 R2 第 1 點：可。**

**第 4 點｜RC″-2 擇 (b)：有條件可（required，RC‴-1）。**

不採 (a) 的四點理由都成立：
- 理由一：store 時鐘若在 Python 端取值，就早於取得寫入鎖的時刻。
- 理由二：牆鐘可能倒退。
- 理由三：持鎖會涵蓋 bootstrap，第二個寫入者（L768）會卡在 `busy_timeout`。
- 理由四：(b) 符合 ADR-0012 D-2 的 `run_id` 與 C-50 L849 的既有做法。

只靠理由二、三就足以不採 (a)。「單一寫入者 ⇒ 配號順序＝commit 順序」的依據也正確。

漏判路徑逐條檢查：
- **序號缺漏一律為真：已寫。** 但缺 fixture；另外「不是整數」要排除 bool 和負數。
- **還原整個備份檔：安全。** snapshot 與事件同在主 DB（D-2 第 1 點），會一起回退；還原後寫入的 `db_restored` 序號一定大於回退後的所有讀取序號。
  - 前提一：沒有 DB 檔以外的 snapshot 或序號快取。還原後，失落時間線的序號會被重新配發，「永不重用」對還原並不字面成立。
  - 前提二：還原以整個檔案為單位。
  - 兩個前提都沒寫，要補。
- **局部還原或遷移重建表：未涵蓋。** 會出現 snapshot 序號大於目前最大值，原文沒有判為真。
- **讀取順序：未涵蓋。** 「同一個明確 read transaction」寫了，但沒有規定先讀序號。萬一隔離失效，「先讀 E、後讀序號」會漏判；「先讀序號」則不論隔離成不成立都安全，因為只會多判為真。
- **呼叫端指定 ID：未涵蓋。** 指定一個比最大值小的 ID，會繞過判定。
- **判定式用 `kind ∈ E_CHANGING_EVENTS`：要改。** 這和 r3″ 保留的「歸不了類就算會改變 E」在執行期不等價，要改為 `kind ∉ E_NEUTRAL_EVENTS`。
- **指定檔漏掉的兩處：要補。** 一是 D-11.4 第 2 點登記兩個序號欄位，二是 `sqlite_master` 的 AUTOINCREMENT 斷言。舊檔都有。

### RC‴ 逐字條文（給 tech-writer，照寫不必回送）

**RC‴-1（掛 A-63 RC′-2，收緊）**
- 「若且唯若」第一項改為：存在 `kind ∉ E_NEUTRAL_EVENTS`、而且 `event_id > e_read_event_seq` 的事件（含未歸類的值）。
- 加入下列子點：
> - 讀取順序：在同一個明確開啟（明確 `BEGIN`）的 read transaction 內，**先讀 `e_read_event_seq`、`e_read_outcome_seq`，再讀 E**。
> - 下列任一情形，`e_changed_since` 為真，並記 WARNING：序號欄位缺漏；不是非負整數（bool 不算）；大於目前看得到的對應最大值。
> - `e_changed_since` 比對的 snapshot 與事件最大值，要在同一個 read transaction 內、從同一個主 DB 檔讀出；不得跨請求或跨程序快取 snapshot 或序號。
> - 備份還原後，失落時間線的序號可能被重新配發，所以 DB 檔以外保存的 snapshot 或序號，不得用於任何判定。還原以整個主 DB 檔為單位。
> - 寫入函式與 SQL 不得指定 `event_id`、`outcome_id`，由 SQLite 配號（比照 D-2 第 3 點）。
- D-11.4 第 2 點：登記 `stats_json.e_read_event_seq`、`stats_json.e_read_outcome_seq`；`e_read_at` 標「稽核用，不作比較基準」。
- FL-58 (e6) 加六格：
  1. 序號缺漏或不是整數 → 為真；
  2. 序號大於目前最大值 → 為真，而且有 WARNING；
  3. 讀序號與讀 E 之間注入一筆 commit → 為真；
  4. 寫入時指定 `event_id` → 拒絕寫入；
  5. snapshot 之後還原，並寫入 `db_restored` → 為真；
  6. `sqlite_master` 斷言兩欄都是 `INTEGER PRIMARY KEY AUTOINCREMENT`。
