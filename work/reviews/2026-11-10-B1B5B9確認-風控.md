### risk-compliance-officer（本人，唯讀）

#### RC-104：B-1「(1′) 不在名單內」（附條件接受）

**(a) 順序變更：接受，屬加嚴。**

RC-91 第 2 點原本沒有這一步。我逐一比對插入前後的結果，(1′) 只會新增拒絕，沒有任何原本被拒的操作因此變成允許，也沒有任何拒絕因此換成資訊比較少的訊息：
- **不在名單內，不凍結，標記**：原本沒有規定，可能寫入一列非名單標的的歷程，違反 FR-29。現在回 W-05l，零寫入。屬加嚴。
- **不在名單內，取消，T = 0**：原本會走到 (3)，回「冪等成功」，對不存在的標的說成功，這句不實。現在拒絕。屬加嚴，而且移除了一條不實的成功路徑。
- **不在名單內，凍結，標記**：仍在 (1) 回 W-05c′，結果不變。W-05c′（RC-93）在這個情境為真：它只陳述凍結期間允許哪幾類操作，沒有說這一檔可以做什麼。RC-90 條件 4 也已經禁止它暗示「可以改做取消」。
- **不在名單內，歷程又不可讀**：只可能來自 app 外的寫入。改判後，標記回 W-05l（為真，資訊比原本多），取消仍走一般失敗分支。兩者都是零寫入，沒有變寬。
- 停止新進場的標的、或只剩 closed／skipped 批次的標的，依 ADR-0043 D1 第 1 點仍在名單內，不會被 (1′) 擋下。這與既有行為一致。

**(b) 取消側只顯示「請求失敗（HTTP 409）」：接受。**
- 這句為真：請求確實失敗了。它沒有承諾，也沒有暗示已取消。
- **不能沿用 W-05l**。W-05l 寫「不能標記高波動」，套在取消上不實。TA 的判斷正確。
- 依 TA 的說法，這條路只會因為直接呼叫 API 而出現。在「名單頁不會送出這種請求」的前提下，不另擬字面可以接受。這個前提目前無法查證，因為 N-207 的前端還沒實作，所以列為下面的條件 4。

**(c) W-05l 用在標記側：仍為真。**
- 定稿字面：「未寫入任何資料。{symbol} 不在名單內，不能標記高波動。」
- 「未寫入任何資料」為真，因為 (1′) 排在 (3)、(4) 之前，沒有任何寫入，也沒有稽核列。
- 「不在名單內」的判定來源，是 RosterFacts 中該檔的批次清單為空，也就是 D1 第 1 點的名單定義，所以為真。
- 「不能標記高波動」為真，因為標記確實被拒絕。
- 這句沒有寫「加入名單後即可標記」之類的承諾。草稿「情境」欄寫「標記不在名單內的標的」，仍然正確，字面不必改。

**條件（required，qa 核對，不必回送我）：**
1. **W-05l 只用在標記側，取消側不得出現。** API 層依 `new_value` 映射：標記對應 W-05l，取消對應 409 加 `{"reason_code":"not_in_roster"}`。後端測試要釘住兩件事：取消的回應不含 W-05l 的任何片段；標記的回應等於 W-05l 定稿全文。
2. **判定不得誤判「不在名單內」。** RosterFacts 在高波動操作時，範圍必須包含目標標的，不能因為範圍沒有收進該檔、清單是空的，就判為不在名單內，否則 W-05l 會變成不實。要加測試：某檔 `entry_stopped = 1`，而且只剩 closed／skipped 批次，此時標記與取消都不得回 `not_in_roster`。
3. **`{symbol}` 是查詢時用的原始字串，不做任何正規化**（比照 RC-50）。若 API 層日後對高波動操作加了「快速名單判定」，必須排在快速凍結判定之後，與 (1)→(1′) 的順序一致，凍結期間的標記才不會先回 W-05l。
4. **名單頁不得送出不在名單內標的的取消請求**：高波動勾選只出現在名單列上。qa-e2e 驗收時要確認這一點。只要有任何 UI 路徑能觸發這個請求，就回送我擬專用字面，不得沿用「請求失敗（HTTP 409）」作為定案。
5. PM 加入 AC-38 的取消 Given 時，要同時寫上「不顯示 W-05l」。

#### RC-105：B-5 一般失敗分支（附條件接受，對形狀無異議）

- **形狀**：`HTTPException(409, detail={"reason_code": ...})`，我接受。
- **前端顯示**：我親自核對了 `frontend/app/lib/api.ts:183-195`。`detail` 不是字串時，`message` 取 `請求失敗（HTTP ${res.status}）`，所以畫面只會出現「請求失敗（HTTP 409）」，不會出現英文的 `Conflict`。這與 TA 的推論一致。
- **其他方案都不能用**：不給 `detail` 會顯示英文；落到 500 不是拒絕的語意；200 加拒絕 body 可能被渲染成成功。TA 的採用正確。
- **原因碼放在 body**：不是使用者可見字面，可以接受。
- **`hv_history_unreadable` 在名單頁真的會出現**：它沿用 C-D7-3／RC-75 的暫行規定，專用字面不是合併閘。這次不變。

**條件（required）：**
1. **前端不得讀原因碼。** 前端對 `not_in_roster` 的 grep 計數為 0，與 C-D7-3 對 `hv_history_unreadable` 的要求同型。
2. **Vitest 要多斷言畫面狀態。** 收到 409 後，該列的高波動勾選與標籤必須維持請求前的伺服器狀態（或重新讀取），不得停在使用者點擊後的樣子。這是「不得渲染成已取消／已標記」在畫面狀態上的具體化。只檢查 ErrorPanel 的文字不夠。
3. **原因碼集合是封閉的**，只有 `hv_history_unreadable` 與 `not_in_roster` 兩個。要新增任何原因碼走這條「沒有字面」的路徑，都要回送我，因為那等於新增一種沒有說明的拒絕。

#### RC-106：B-9 AC-98 改字（接受；不是語意變更，也不是放寬）

- **判斷理由**：
  - AC-98 的同一句已經寫「訊息為 W-05c′ 的 RC-90 重擬定稿字面」。
  - 依 B-5 與 §6 新的名詞界定，「一般失敗分支」只顯示「請求失敗（HTTP 409）」，沒有 W-05c′。原字面在新定義下會自相矛盾；照字面實作反而會讓凍結拒絕看不到截止日句，那才是弱化。
  - 改成「凍結拒絕分支（`portfolio_frozen`）」，是唯一同時符合 RC-90／RC-93「所有凍結拒絕共用 W-05c′」與該句訊息要求的讀法。
  - 我 RC-91 第 5 點寫的是「訊息依 RC-90」，從來沒有要求凍結標記走沒有字面的分支。所以這次改字是回到原意，不是改變原意。
- **條件**：只改這幾個字。AC-98 其餘內容逐字不動，包括四張表逐列不變、不是 `ROSTER_RESULT_*`、不寫成或渲染成「已標記」、W-05c′ 引用、合併閘，以及「不依操作種類分支」。變更紀錄要註明「依 TA B-9，用語精確化，非放寬」。
- **其他文件的用語**：ADR-0043 :423、:672（W8），以及我在 RC-89 寫的「一般失敗分支」，都指 `hv_history_unreadable` 的路徑，與 B-5 的定義一致，不必改。
