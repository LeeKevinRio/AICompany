#### 逐條意見

**RC-96：N10-01，(iii-c) 下的事實落差 → 改寫為統一句（required）**

- **落差成立。** 依 ADR-0044 Context 第 7 點與 (iii-c) 評估中的 R-a 說明，recorded 判定的 yes 列可能這樣產生：
  1. 評估在 `service.py:2200` 讀到舊戳記；
  2. REBALANCE 接著 commit；
  3. `created_at` 之後才在 `store.py:1372` 取值。

  這時 `created_at` 晚於 set_at，「本列在…之前產生」就不為真。原稿第二件事實「股數依產生當時的值計算」也不精確：產生當時，值已經是新的。
- **不能用 N10-01C 分版。** 依 `td_flag_basis` 切換句子，會違反三處：
  - RC-53 條件 1；
  - ADR-0044 Decision 5「不依 td_flag_basis、td_change 分版」；
  - C-N210-15 的 render 測試：recorded 與 time_order 必須渲染出逐字相同的字串。

  而且前端依 Decision 8 不得讀 `td_flag_basis`。所以只能用一句在兩種依據下都為真的句子。
- **新句為什麼兩種依據都成立。** 「最近一次重新設定之前取得的值」，就是評估讀取 TD 的時點早於最近一次 TD 寫入的 commit。
  - time_order 的 yes：讀取早於 `created_at`，`created_at` 早於 set_at，set_at 早於 commit。成立。
  - recorded 的 yes：評估所記的戳記與現行戳記不同，表示評估讀取之後至少 commit 過一次寫入。成立。
  - 用「取得」而不寫「之前的值」，是因為讀取之後若有兩次以上重設，「之前的值」容易被讀成「緊接在最近一次之前的那個值」。
- **與 ADR 的關係。** Decision 5 列的三件事實是上限（「只限」）。定稿句沒有增加事實：它把第 1、2 件改成兩種依據下都為真的同一件，第 3 件帳冊子句與 N9-05 同一套限定，逐字不變。所以不與 accepted ADR 衝突。但 Decision 5 第一點的字面在寫法 A 下已不精確，要加註記（見 RC-103）。
- 句中沒有方向、建議、時機或安撫詞。td_change 為 same_value 時也為真：句子沒有說值不同。

**RC-97：N10-02 → 採 B 的結構（required）**

- 第一句隨 RC-96 改為「本列股數是否依…取得的值計算」。原稿問的是「是否在之前產生」，在 recorded 依據的 unknown 下（decode 失敗、現行戳記讀取失敗）問錯了對象。
- **加帳冊子句的理由。** unknown 正是「可能受影響」。使用者最需要知道的是：即使 TD 已重設，這一列仍以列上的股數入帳。不加，使用者可能以為系統會自動校正。
  - creative-lead 擔心讀者把後半句讀成「這一列受影響」。這種誤讀的方向是保守的。有害的誤讀是「沒受影響」，B 不會造成。
  - 帳冊子句是條件句（「若所指的批次仍待進場」）。即使 `/today` 的額外讀取失敗、全部列都標為 unknown，這句仍為真。

**RC-98：N10-03a → 改寫（required）**

- 原稿「已產生、尚未結算的買進指令中，下列指令…」帶有「其餘的不是」的完整性暗示。這與 C-3 的精神相衝突：清單是快照，R-a 的列不在清單內。改成只對列出的指令做正面陳述。
- 原稿寫「買進指令」，改為「R 系列買進指令」，與 N9-05、N9-06 同詞。`_PENDING_ENTRY_WHERE` 是 C-B1 的 R 買單（`store.py:285-288`）。
- 後半句加「都」，與 N9-06 定稿逐字同構。
- R-a 的揭露由緊接在上方的 N9-06 第三句負責（「重算完成前已開始的評估，可能仍依原值計算」），所以這句不另寫。「重算」在 ok 分支可以用（RC-41）。

**RC-99：N10-03b → 「至多」，主詞改為「計入帳冊」；附生效條件（required）**

- 「只會有一筆成交」會被讀成「恰好一筆」。被跳過、或 missed 時，會是零筆：missed 不改變批次狀態，只加 `missed_count`（`store.py:1607-1612`）。
- 「至多一筆成交」也不採：「成交」是券商端的事。使用者在券商對兩張指令都下單時，兩張都可能成交，系統管不到（R10）。系統能保證、使用者也必須知道的是：**至多一張計入帳冊**，其餘的被 G1 擋下、不動帳。這句同時揭露了「兩張都下單會造成帳冊與券商不一致」，但沒有寫成建議。
- **事實更正（我自己的 RC-47）**：
  - 「同一批次最多只有一張成交入帳」在現行程式上**不無條件成立**。
  - ADR-0042 Context 第 3 點（追蹤清單 :382）指出：claim（`store.py:1548-1555`）與 `settle`（`:1616-1635`）分屬不同交易。兩個結算並發時，同一批次的兩張 buy 都可能在任一邊把批次改成 open 之前通過 G1，結果兩張都動帳。
  - 這要等 N-198（`claim_and_settle`，ADR-0042 Decision 2）合入才消除。我 grep backend，`claim_and_settle` 零筆，表示還沒合入。
  - **生效條件**：N-210b 的 base 必須已含 N-198。不成立時 N10-03b 不為真；而 C-5 要求這一句必須存在，所以 **N-210b 不得在 N-198 之前合併**。若排程做不到，回送我，不得改用其他字面。
  - 同一個並發缺陷也會讓 N9-05、N10-01、N10-02 的帳冊子句，在 N-198 部署前的並發情境下不完全成立。這屬於 N-198 部署通知已涵蓋的既有揭露缺陷，不擋這三句。

**RC-100：N10-04 → 兩版都不採，另定（required）**

- A「清單無法取得。」：清單區塊整段被取代，標題也不顯示，讀者不知道是哪份清單。
- B「已產生、尚未結算的指令清單無法取得。」：範圍說大了，會被讀成「所有未結算指令的清單」。實際的清單只含所指批次仍待進場的 R 系列買進列。
- 定稿句與 N10-03a 用同一組限定，只陳述「無法取得」。沒有「沒有／無」，沒有動作建議，也不指向其他畫面。

**RC-101：td_basis 逐值顯示對照（required，dev-lead 與 qa 照表實作與測試）**

- `td_basis` 本身不是顯示用的列舉。它是 NULL，或 `TotalDeployStamp` 的 JSON（ADR-0044 :79-81）。前端不得讀它（C-N210-2）。顯示只看後端旗標 yes／no／unknown。
- 草稿第四節寫的 `td_flag_basis == "recorded"/"time_order"`，與 ADR :97 的名稱一致。它不影響字面。

| td_basis 與判定情況 | 旗標 | td_flag_basis | 顯示 |
|---|---|---|---|
| NULL（N-210a 部署前已落檔的列、回退期間寫入的列），依 (iii-a)：set_at 晚於 created_at | yes | time_order | N10-01 |
| NULL，依 (iii-a)：時間相等、naive、解析失敗、任一缺值 | unknown | time_order | N10-02 |
| NULL，依 (iii-a)：set_at 早於 created_at | no | time_order | 不顯示任何文字（C-4） |
| 非 NULL，decode 成功，與現行戳記逐字相同 | no | recorded | 不顯示任何文字（C-4） |
| 非 NULL，與現行戳記不同（含任一方有鍵為 null）；td_change 不論是 lower、higher、same_value 或 unknown | yes | recorded | N10-01（逐字同上，不依 td_change 分版） |
| 非 NULL，decode 失敗 | unknown | 不論 | N10-02 |
| 現行戳記讀取失敗（不論 td_basis） | 全部 unknown | 不論 | N10-02；`/today` 照常 200（C-6） |
| 不屬 Decision 2 範圍的列（批次不存在或已非 planned） | 不給旗標 | — | 不顯示 |

**RC-102：顯示條件表的修改（required）**

1. **N10-01、N10-02 的條件改寫**：只依單一後端旗標，兩種判定依據共用同一欄位。旗標為 "yes" 時顯示 N10-01；為 "unknown" 時顯示 N10-02。不論 `td_flag_basis`、`td_change` 為何。前端不得讀這兩個欄位（C-N210-15）。
2. **失效保護**：範圍內的列，旗標值若不是 yes、no、unknown 三者之一，一律顯示 N10-02，不得落到「不顯示」。「範圍外不給旗標」與「範圍內值異常」要能區分，編碼方式由 TA／dev-lead 定。
3. **位置**：N10-01、N10-02 在今日指令表與 in-flight 清單中，都緊鄰該列常駐顯示，不得摺疊，不得用 tooltip 或 hover（比照 RC-40 條件 3）。
4. **N10-03a**：在 status 為 ok 而且清單非空時顯示，位置在 N9-06 之後。N9-06 在同一畫面必須同時顯示。清單由前端從結構化欄位渲染，`message` 不改（RC-40）。
5. **N10-03b**：只依後端的 `multiple_entries == true` 顯示，前端不得用 entries 長度自行判斷。每個批次顯示一次，緊鄰該批次，不是每張指令都顯示。後端測試要釘住 `multiple_entries == (len(entries) > 1)`。
6. **N10-04**：在 status 為 ok 而且 `kept_pending_entries` 為 None 時，取代整個清單區塊，與 N10-03a 互斥，不得同時出現。
7. **不擬句子的三種情況照草稿**：旗標為 no、清單為空、非 ok 分支。
8. **清單項目的標籤**：欄名、批號呈現等，只能用已定稿的既有用詞（批號依 W-19）。有新的標籤文字，送 creative-lead 擬稿、我定稿。每句只能有一個前端常數定義，以 grep 計數釘住（比照 RC-40 條件 1）。
