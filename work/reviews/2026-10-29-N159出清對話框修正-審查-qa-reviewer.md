## 五項重點查核
1. **SSR／hydration：無 mismatch 風險。**
   - `useSyncExternalStore(subscribeNoop, () => true, () => false)` 的 server snapshot 為 false，client snapshot 為 true。
   - hydration 階段 React 用 server snapshot，hydrate 完成後再切成 true，這是標準的 mounted 偵測寫法。
   - 此外 `step` 初值是 `"idle"`，SSR 與首次 client render 本來就不會產生 portal，`document.body` 在 render 期不會被存取。
   - `subscribeNoop` 是模組層級的穩定參考，不會造成重複訂閱。
   - `document.body` 在 render 期被讀取，但只會出現在 `isClientMounted && …` 之後，是安全的。
2. **流程與字面：未動。**
   - diff 的 hunk 只動 import、hook、portal 包裝、外層 `<div>` 的 class，以及面板 class。
   - Step 2／Step 3 的標題、`checkTexts` 渲染、核取方塊的 `checked`／`onChange`、兩個按鈕的 `disabled`、`submit()` 與 `mutation.mutate`、`ErrorPanel`、`role`／`aria-modal`／`aria-label` 都不在 hunk 內。
   - 狀態（`step`、`checks`、`mutation`）仍在 `EmergencyExitControl` 本體，portal 只改 DOM 掛載位置，React 元件樹位置不變，所以狀態不會被重置。
   - React 合成事件會沿元件樹冒泡。我查了 `playbook/` 的 `ModeStatusBar` 與頁面層，沒有 `onClick`、`onKey`、`onSubmit` 或 `<form>`，沒有被意外觸發的風險。
   - portal 目標是 `body`，而 `layout.tsx` 的 `body` 已帶 `bg-black text-neutral-100`，`html` 帶 `dark`。字色與字體繼承不受影響。
3. **z-50：與專案一致，不會蓋到不該蓋的東西。**
   - 專案內 `EditAlertRuleModal`、`KellyImportDialog`、`KellyDeleteDialog`、`EditPositionModal` 都是 `fixed inset-0 z-50`。
   - 其餘 z-index 只有 z-10：`ModeStatusBar`、NavBar 下拉、SymbolCombobox 下拉、圖表 tooltip。
   - 我找不到 toast 元件（grep `toast`／`Toaster` 沒有對應元件，只有 `role="status"`／`role="alert"` 的行內元素）。
   - 對話框蓋過 z-10 的元素是預期行為，因為它是 modal。
4. **測試有效性：「套回舊版 5 則失敗」可信，但這個訊號比字面弱。** 我用舊版原始碼逐則推演（未執行）：
   - 舊版沒有 `createPortal`，所以 #1、#2、#3、#5 都會在 `portalCall()` 的 `expect(start).toBeGreaterThan(-1)` 失敗。
   - #4 因為沒有 `useSyncExternalStore` 而失敗。
   - #6 對舊版本來就會過。
   - 所以確實是 5 失敗、1 通過。但 4 則失敗的原因是同一個，都是「找不到 `createPortal(`」。它們擋得住「整段 portal 被拿掉」的回歸，細節回歸擋不住。
   - 這類原始碼掃描無法取代實機驗證，交件者也已明說要由 qa-e2e 複驗。
   - 括號配對在目前原始碼上成立：JSX 文字內沒有 ASCII 括號，`calc(100vh-2rem)` 是平衡的，中文全形括號不會被計入。
5. **範圍：未超出 N-159。** 只有 `EmergencyExitControl.tsx` 與新增測試。`ModeStatusBar.tsx` 沒動。z-20→z-50 與 `max-h`／`overflow-y-auto` 在交件報告中已明講，屬同一缺陷的必要配套。

## NON-BLOCKING
1. [可維護性／a11y][medium] `EmergencyExitControl.tsx` 約 :111–:200：portal 到 `body` 之後，對話框在 DOM 順序上排到頁尾（footer 之後）。
   - 修正前對話框緊接在「全部出清」按鈕之後，Tab 一下就到；現在鍵盤使用者按 Tab 會先走完整個頁面才碰到對話框內的按鈕。
   - 螢幕閱讀器的閱讀順序也一樣。這是此流程的 a11y 倒退。
   - 原本沒有焦點管理、沒有 Esc、沒有焦點限制，所以不算違反既有承諾，也不阻擋本次合併。
   - 建議另開追蹤項：開啟時把焦點移入面板（第一個核取方塊或標題）、關閉時還給觸發按鈕，並補 Esc。可比照 `EditPositionModal`。
   - 這是 N-159 修法的副作用，建議 CEO 或 product-manager 決定是否在上線前處理。
2. [Edge case][low] `EmergencyExitControl.tsx` 面板 class `max-h-[calc(100vh-2rem)]`：行動瀏覽器（iOS Safari）的 `100vh` 大於可視高度，網址列顯示時面板上下緣可能被裁掉，與修掉的缺陷同類。
   - 建議改用 `max-h-[calc(100dvh-2rem)]`，或同時保留 `100vh` 作為舊瀏覽器退路。
   - 請 qa-e2e 在 375px 實機一併確認，以實測結果決定。
3. [可維護性][low] `EmergencyExitPortal.test.ts` 的 #4 只檢查字串 `useSyncExternalStore` 與 `isClientMounted && createPortal(` 存在，沒有檢查 server snapshot 為 `false`。
   - 若有人把 server snapshot 改成 `() => true`，目前測試不會失敗。
   - 實際影響有限，因為 `step` 初值是 `idle`，首次 render 不會出現 portal。
   - 可加一則 regex 斷言，例如 `/useSyncExternalStore\(\s*subscribeNoop,\s*\(\)\s*=>\s*true,\s*\(\)\s*=>\s*false/`。
4. [可維護性][low] `EmergencyExitPortal.test.ts` 的 #3 與 #6 用 `/\bfixed\b/`，會誤中 `table-fixed` 這類 Tailwind class（`-` 與 `f` 之間算詞界）。
   - 目前 `ModeStatusBar.tsx` 與 `EmergencyExitControl.tsx` 沒有此類 class，所以通過，但日後加了會誤報。
   - 建議改用 `/(?<![\w-])fixed(?![\w-])/`。
5. [可維護性][low] `EmergencyExitControl.tsx` 的 `createPortal(` 之後 JSX 沒有縮排（`<div role="dialog"` 與 `createPortal` 同一縮排層），這是為了讓 diff 保持最小。
   - repo 的 `package.json` 沒有 prettier 或 eslint，所以不會被 CI 擋。
   - 單純是觀感問題；若日後引入格式化工具，會產生一次整檔重排，屆時留意即可。
6. [測試][low] 沒有測試鎖定 `z-50`。
   - 脫離條帶之後，若有人把 z-index 改回 z-10 以下，對話框會被其他固定層蓋住。
   - 可在 #3 加一則 `expect(portal).toMatch(/\bz-50\b/)`。
