**另請回答**
- A. R-1 以 `HEAD:app` tree id 取代「與 CG-2 合併 commit 無 diff」：對「已提交的 `app/` 內容」是嚴格等價（git tree id 即內容雜湊）。漏洞如下。
  - 工作樹與 `HEAD` 不一致：靠 `status` 補，已追蹤檔被改會抓到；但 `assume-unchanged`／`skip-worktree` 抓不到（問題 1）。
  - 未追蹤檔：`--untracked-files=all` 會抓到；被忽略的檔案不會，實務上不會被 import，除非有人新建同名子模組，風險低。
  - `app/` 以外：`pyproject.toml`、`uv.lock`、`scripts/`、venv 內第三方套件（`uv run --no-sync`，venv 可能與 lock 不符）都不在檢查內。claims 與 `app` 依賴的第三方版本沒釘。若原 R-1 的「無 diff」涵蓋整個 backend，這是範圍縮小，請 tech-architect 與風控確認 ADR 語意是否只指 `app/`。
- B. 探針與正式子行程用同一個 `sys.executable`、同樣的 `-I -X utf8`、同一個 `cwd`，差別只在 `-c` 與 `-m`；`-I` 下兩者的 `sys.path` 相同。探針回傳 `claims.BACKEND_DIR`（`APP_ROOT.parent`，由 `__file__` 推得），因此同一個 `app` 套件根，能保證 import 到同一份 `app`。限制：兩個行程之間有極小的 TOCTOU；`sitecustomize` 與 `.pth` 不受 `-I` 影響；也不保證第三方套件相同。另外，父行程是用 `sys.path.insert` 載入 `app`，子行程靠 editable install，兩邊是不同的載入機制，只靠探針這一項把關，這點請記下。
- C. Windows 未實測部分，我認為 CEO 執行前需要額外說明或保護。
  1. 先跑 preflight 當乾跑。它會對真 DB 驗證 `main_db_uri` 與 R-4 的 file URI（含空格、CJK 使用者名稱）。但備份路徑（`xb`、backup API、immutable 讀回）只有 register 才會走，建議在說明文件寫明「備份失敗是 STOP、備份檔保留，不要手動刪或重跑，回報 coordinator」。
  2. 防毒或同步軟體（OneDrive、Defender）鎖住新備份檔，可能造成 `backup_failed`。建議說明「若 `~` 在 OneDrive 下，可能失敗」，並建議關閉同步。
  3. 視窗被關閉或 Ctrl+C 時沒有訊息可看。說明要寫：若在鍵入 0 或 1 之後視窗消失，**不要手動重跑**，先告知 coordinator；實際上 R-4 會擋第二次，但 CEO 不該依賴這一點。
  4. `core.autocrlf=true` 加上 `text eol=lf`：若工作樹被轉成 CRLF，會安全地 STOP。說明要寫「不要自己改 git 設定」（已有 `_TELL`）。
  5. `uv` 解析出的 python 與 `.bat` 使用的 venv：`--no-sync` 不會修 venv。venv 缺或壞時，探針失敗會是 `claims_unreachable`（安全）。
