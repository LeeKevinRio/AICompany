## 一、本次結論

**(a) 確認可行，附一項字面疑義請風控判斷，不構成否決。** 寫入函式在 ⑤ 的 `BEGIN IMMEDIATE` 交易內自行讀取本作業的判定視圖，再做 (甲)、(乙) 重算比對與 T-4，在 SQLite 上可行：沒有隔離問題，也沒有鎖的問題，持鎖時間可以接受。
- 疑義：休市日表無法從 DB 重建（ADR 只存 meta）。「自行讀取」若照字面解成在 ⑤ 再讀一次，會和 D-9 第 5 點 ② 的「之後本作業不再讀……休市日表」、FL-68 (b) 的「`official_holiday_table_meta` 恰好讀一次（spy）」衝突。理由與我的讀法見第二節。

**(b) 確認一致，沒有異議。** quant V19-02 把「已有更大 id、而且已有 end 列」界定為中斷，其餘列為「尚未判定」。這和 ADR-0027 D-3「晚到資料的觸發」第 5 點一致：寫入 job_end 時要驗證「沒有 `correction_job_id` 大於本作業、已有 end 列的作業」，不成立就拒絕。加上 N-32 之後，這項驗證和 job_end 的寫入在同一個 `BEGIN IMMEDIATE` 交易內，SQLite 會把寫入者排成一個一個來，所以不會有「先查再寫」之間的空檔（TOCTOU）。

**順帶檢查 T32-1～T32-7：** 沒有和 ADR 現行條文直接矛盾的地方；引用的名稱、檔案、定位字串都查得到。有 4 處字面張力或模糊，只回報，見第二節 C。

## 二、各部門回報（tech-architect）

### A. 第 (a) 點的理由

1. **鎖與隔離：沒有問題。**
   - 依 ADR-0002，SQLite 用 WAL；依 ADR-0012，市場 DB 是另一個檔案，所有 store 都經 `enable_wal`。
   - 主 DB 在 `BEGIN IMMEDIATE` 之下，其他寫入者不能 commit。所以同一連線讀到的是「已 commit 的資料加上自己這筆交易的寫入」，而且在交易期間不會變。
   - 判定視圖的每個部分都有序號上界，或在 ⑤ 之前已 commit：`event_id ≤ ledger_event_max`、`check_id ≤ index_check_max`、`settle_eval_id ≤ settle_eval_max`、`index_series_sha256` 指向的快照、`observed_sessions_json`。
   - ⑤ 寫入的三張表（`forecast_outcome`、`forecast_void_late_diag`、`forecast_correction_job_end`）都不屬於判定視圖，所以本交易自己的寫入不會改變重算的輸入。
   - 市場 DB 經 `MarketPanelReader` 用另一條唯讀連線讀，只取 `run_id ≤ market_scan_to`。WAL 下讀者和寫者互不阻擋，也不碰主 DB 的鎖。
   - D-9 第 5 點「以存下的視圖重算，結果必須逐位相同」，加上 FL-68 (a)，保證 ⑤ 的重算結果與 ④ 相同。不同只會出在程式錯誤，或 ④ 到 ⑤ 之間市場 DB 被還原；兩者都會落到「該列被拒絕」，屬於 fail-closed。
2. **單一連線：寫入函式在 ⑤ 讀主 DB 時，必須用開啟該交易的同一條連線。**
   - 計數一致、`pending_json` 的鏈尾比對、N32-4 新增子點，都要看到本交易還沒 commit 的寫入。
   - 寫入函式也不得自己 `BEGIN`／commit（SQLite 不支援巢狀交易）。
   - 只增不改的 trigger 是 `RAISE(ABORT)`（L260），只中止該句，交易仍然有效，所以「單列被拒、交易繼續」做得到。
3. **持鎖時間：可以接受。**
   - 有前例：D-9.2 的結算評估把整個評估集合的判定都放在一個寫入交易內（⑥，「不切分」）。⑤ 多出的只有 (甲)/(乙) 作廢 supersede 列的重算，這類列很少。T-4 只從 `observed_sessions_json` 導出 T+h，成本可忽略。
   - 另一面：API 的 on-demand 寫入者最多等到 `busy_timeout`。主 DB 的 `busy_timeout` 實際值我沒有查證，不下數字。
4. **疑義：休市日表（請風控決定要不要補字）。**
   - ② 只把 `official_holiday_table_meta` 存進 `holiday_table_json`，`official_holidays` 的內容沒有存。
   - (乙) 五值重算會呼叫 `span_sessions`，要用到休市日表。
   - 我的讀法：對休市日表這一部分，「自行讀取本作業的判定視圖」應解為「用 ② 讀到的同一份（程序內）」，比照 A-77 第 10 項「一律取……同一份輸入，不另行讀值」。這是輸入，不是判定結果，不違反「不得改由呼叫端傳入判定結果」。
   - 依 ADR 字面，休市日表未接入時為 null，目前沒有實際影響，但接入後就會生效。
5. **實作順序（給 dev-lead／qa，不涉改字）：每一列都要先驗證、再 insert。**
   - ④「已結算數值所用的大盤 bar」要讀 `forecast_outcome` 的更正鏈。若先插入新列再重算，新的 T+h 會變成「已被鏈中某列涵蓋」，`shift_index_bar_unverified` 的比對就被跳過，結果會和 ④ 不同（推論，依條文字面）。

### B. 第 (b) 點的理由

- `correction_job_id` 由 AUTOINCREMENT 配號，SQL 不得指定（L1388），所以大小順序明確，id 也不會重用。
- 依 D-3 第 5 點，較大 id 的作業一旦有 end 列，任何較小 id 的作業寫入 job_end 都會被拒；依 ⑤，被拒或中斷的作業不留下任何 outcome 列與 diag 列。
- 涵蓋了交錯完成的情形（修訂紀錄 L3651 風控舉的並行例）：較小 id 的作業先完成時，較大 id 的作業在 job_end 的 from／W 再驗證會失敗，之後就依 V19-02 歸為中斷。
- 「尚未判定」可能其實已經中斷；V19-02 只寫「可能仍在執行」、不計入中斷，方向保守。
- 「中斷與被拒在資料表中無法區分」屬實：兩者都只有 WARNING，沒有 end 列。
- 主 DB 整檔還原後（L1387），在還原後那份 DB 上判定，結論仍然自洽。
