## 1. 接下補充十三的讀法

我（devops-sre）接下補充十三第 1 點的讀法，作為 D-10 心跳的責任人：

- 核心期間的「心跳」讀為四件事合起來：狀態報告一鍵檔、coordinator 每週比對、比對紀錄、升級。
- 執行每週比對的是 coordinator，不是我。我負責的是收到補充十三第 4 點 (a)、(c)、(d) 的通知之後的技術處置（第 2 節）。

照實寫出這套做法的限制。**這不是自動偵測。** 以下限制我全部知悉，並以此為前提處置：

1. 只能事後發現。主機關機時本機什麼都不會跑，沒有任何東西會在當下通知任何人。
2. 最多晚一個回報週期。CEO 貼回中斷時更晚；那時偵測到的是「無法判斷」，不是停機本身。
3. 完全依賴 CEO 每週執行並貼回。沒有貼回，就沒有任何資料。
4. 被跳過的執行不留 `forecast_run`，與停機無法區分。依 `scheduler.py` 的 `run_forecast_record`，下列情形都是「跳過、不留列」（都在 `record_forecasts` 呼叫、也就是 `begin_run` 之前結束）：
   - `STOCK_DESK_DB_PATH` 存在於 process 環境，或主資料庫不是預設的正式檔案（四種 refusal，各記一行固定 WARNING）。這是**持續性**的，不會自己恢復；
   - 當晚向資料來源強制重抓指數失敗、或讀回的最新 bar 早於本次執行的開始（各記一行固定 WARNING）。這是單次性的；
   - `get_index_resolver()` 拋例外（它在 `scheduler.py` 788 行，不在任何 try 之內），或卡在強制重抓：同樣不留列；
   - 帳本 schema 不完整時，`begin_run` 本身拋例外，由 scheduler 的 job 錯誤 log（ERROR）記錄；這是持續性的。
   - 另有一種不是「跳過」、而是「根本沒被觸發」：主機在排程時刻睡眠或休眠（見第 2 節原因 G，推論）。
5. 這些 WARNING 與 log 只出現在 scheduler 視窗。`dev-up.bat` 用 `cmd /k` 開視窗，`app/logging_setup.py` 只有 `StreamHandler(sys.stderr)`，沒有檔案 log；視窗一關，log 就沒了。（部署手冊的 `logs\scheduler.log` 是手冊流程自己導向的，不是 `dev-up.bat` 的行為。）所以即使 CEO 的機器當晚開著，事後我與 coordinator 也沒有任何管道看到跳過的原因。
6. 貼回不含報告的執行時刻；報告不列漏記的日期；完整視窗之後的單日漏記，可能沒有任何一項比對看得出來（補充十三第 1 點 (c) 的其餘各項，原樣接受）。
7. `report status` 只印每次執行的 `outcome`，**不印 `error_class`**（`report.py` 的 `render_execution_status` 只輸出 `outcome` 計數與最近一次的 `outcome`）。`gate_closed` 與 `error` 各自的細分原因，不在貼回裡。
8. 我碰不到 CEO 的電腦，也不得讀主 DB、不得自己執行 `report`。我能依據的只有：coordinator 存檔的貼回原文、心跳比對紀錄、程式碼、git 紀錄，以及（僅在 RC-361 的四個條件都成立時）CEO 對 L2 的回答。

另有兩種帶有 outcome 的情形，貼回上可以區分，不屬於上面的「區分不了」：

- 最近一次執行的結果是 `gate_closed` 或 `error`：依下面各自的小節處理。

**漏記（尚未開始記錄）**：帳內還沒有任何執行，接線 PR 合併日以後已有平日。上表 A～G 都可能；其中 D（舊程式還在跑，或合併後沒有重新執行 `dev-up.bat`）與 C2（持續型 refusal，尤其是 `STOCK_DESK_DB_PATH`）在這個情形特別需要先排除，因為兩者都是持續性的、不會自己恢復。

**漏記（格點遺失）、F-2 成立、格點遺失達門檻**：見下面「F-2 與格點」。

**中斷的執行（「沒有 end 列=」比 P 大）**

這一次執行有 `forecast_run` 列、沒有 `forecast_run_end` 列。依 `recorder.py` 的 `record_forecasts`：`_run` 內的 `Exception` 會在 except 區塊寫 `error` 的 end 列；但 `end_run` 寫在這個 except 區塊裡，**`end_run` 本身失敗**（例如資料庫被鎖、磁碟滿）時不會再被接住，那一次同樣沒有 end 列。所以「沒有 end 列」的來源有：

- `BaseException`（中斷、`SystemExit`）或程序被直接結束；
- `end_run` 本身失敗（`Exception` 之後寫 end 列又失敗；正常結束路徑的 `end_run` 失敗也一樣）。

**`begin_run` 之前**的例外或卡住（含 `get_index_resolver()` 拋例外、卡在強制重抓）**不留任何列**，不屬於「中斷的執行」，歸入上面漏記表。

「沒有 end 列」可能原因，貼回上區分不了：

- 程序被強制結束：`dev-up.bat` 在 CEO 同意停舊 scheduler 時用 `taskkill /F /T`；
- 視窗被關閉、主機斷電或睡眠；
- 一次執行卡住（`begin_run` 之後）後被人結束；
- `end_run` 本身失敗（資料庫被鎖、磁碟滿等）。

SIGINT／SIGTERM 的處理會讓進行中的 tick 做完（`shutdown(wait=True)`）；視窗直接關閉時 Windows 的行為，我沒有實機驗證。

**中斷後沒有後續執行（第 2 點 (f)）**：最近一次執行仍是同一筆沒有 end 列。代表那次之後 scheduler 沒有再成功開始過新的執行；原因包括上表 A、B、G、卡在 `begin_run` 之後的執行（E 的另一半），以及上表 C2 的持續型 refusal（`begin_run` 之前就被拒絕，也不會再開新的一筆）；貼回區分不了。

**心跳中斷**：D＋8 個日曆日後仍無有效貼回。**沒有任何技術資料可查**。可能是 CEO 沒執行、沒貼、貼的內容不是有效貼回、或 coordinator 沒收到；與主機是否開著無關。我不從這個代號推論任何技術原因。

**無法比對**：貼回缺「最近一次留下執行紀錄的執行：」那一行，或只有 STOP、ERROR 句。依 `forecast_status.py`，STOP 的來源有四種：`STOCK_DESK_DB_PATH` 存在於環境、在預設位置找不到 `stock-desk.db`、讀不到執行狀態、工作資料夾落在 git work tree 內；ERROR 是未預期失敗或被中斷。缺那一行有兩種可能：接線前版本的 `report`（CEO 的 checkout 還沒更新），或**貼回不完整**（只貼到一部分）；貼回上區分不了這兩種。貼回上可以分到「STOP 的哪一種」，分不到為什麼。

**第二段的 STOP 不算無法比對**：第二段（重算核對）的 STOP（`STOP_VERIFY`，`forecast_status.py` 130～134、249～251 行）出現在第一段**之後**時，第一段已完整，那份貼回仍是有效貼回，照第一段比對，不屬於「無法比對」。

**`STOCK_DESK_DB_PATH` 的三種情形**（tech-architect 審查更正；機制：`dev-up.bat` 在 `apps/stock-desk/.env` 存在時設 `UV_ENV_FILE`〔`dev-up.bat` 92～101 行〕，把 `.env` 的內容帶進 scheduler 的程序環境；`forecast-status.bat` 第 11 行清空 `UV_ENV_FILE`，`forecast_status.py` 只看程序環境、不讀 `.env`）：

| (i) Windows 的使用者或系統環境變數 | STOP | 每次拒絕 |
| (ii) 只在 `apps/stock-desk/.env` | **照常印出** | **每次拒絕** |

**最近一次結果為 `gate_closed`**：`recorder._run` 兩種來源，貼回上區分不了（`error_class` 不在貼回裡）：

1. CG-2 執行期檢查不過：recording claim 不是恰好兩個、替代鏈違規、claim 的 scope／kind 不符，或規則檔／定義的雜湊與登記不符、版本未發佈。
2. D-5 第 6 點的跨 commit 檢查：本次的 `code_digest` 或 `runtime_json` 與前一次、或與最近一次通過的執行不同，而全部紀錄重算後有任何一筆不逐位相同（`SemanticsChanged`）；或目前程式無法重算某筆紀錄。

會讓 `code_digest` 或 `runtime_json` 改變、而且我的部門可能經手的事件：

- `dev-up.bat` 每次啟動都做 `git pull --ff-only`，若拉進 `code_digest` 涵蓋檔案的異動，下一次執行就會走第 6 點的重算；
- `uv.lock` 異動（`runtime_json` 含 `lockfile_sha256`）；
- Python 版本或平台字串改變（`runtime_info` 含 `platform.platform()`、`python_build`）。Windows 的版本更新會不會改變這個字串，我沒有實機驗證，只是依 `platform.platform()` 的一般行為推論，**未驗證**。

這與 ADR 後果段「devops-sre 須固定執行環境」直接相關：我能查的是 origin 上的 commit 與 lockfile 是否在兩份貼回之間動過，不能查 CEO 機器上實際的環境。

**最近一次結果為 `error`**：`_run` 內任何 `Exception`。可能包括：第 6 點重算時帳本端讀取或解析失敗、取資料例外、寫入 transaction 失敗（資料庫被鎖、磁碟滿、權限）、計算失敗。貼回上只看得到 `error`，區分不了。單次 `error` 不會讓後續排程停止（`_guarded` 讓 job 繼續排程；下一個排程時刻會重新執行）。

**F-2 與格點（第 4 點 (c)）**

- 第一句：分子是「沒有 `late = 0` 紀錄的定案 session 數 a」加「`inputs_not_ready` 日數 b」。我**不**由兩個整數導出「以哪一項為主」；只轉引 coordinator 比對紀錄對 a、b 各自「增加／相同」的結論，並說明每一項各自可能的原因：
  - a 增加：該區間有定案 session 沒有在當晚（截止前）被記錄，原因同「漏記」A～G，區分不了；
  - b 增加：該區間有晚上資料來源未就緒，記為 `inputs_not_ready`；
  - 分母 0：範圍內沒有任何定案 session，可能是整段停機、資料來源整段缺席或執行沒有存下快照（報告句本身就這樣寫）。
- 第二句：格點遺失 L 增加。依 ADR 後果段，第 0 相位格點會連續落在同一個星期幾，若該星期幾的晚上主機常不運行就會累積；貼回只有 G 與 L 兩個數字，不列日期，**區分不了是哪幾天、為什麼**。
- 補跑 `late = 1` 的紀錄不算 `late = 0`，所以啟動補跑不會讓 a 下降（補充五第 1 點 (d)）。

**計數減少（第 2 點 (d)、(e)）**

任何具名 outcome 的值、合計、全期 `inputs_not_ready` 日數、F-2 的起點、G 或 L 比 P 小，或「曾否成立」由「是」變成不是「是」。依 append-only 的帳本設計，計數正常不會減少。可能原因，貼回上區分不了：

- 比對的 P 選錯，或貼回混到另一台機器、另一個檔案；
- 主 DB 整檔還原、更換或重建，或備份以外的原因使核心表列數減少（F-8）；
- 帳本被改動（D-4 的唯讀邊界被破壞，F-4）；
- recording claim 被取代，視窗起點改變。

### (三) 各通知的處置步驟

### (五) 恢復時需要重啟的程序

先說明：我不能直接指示 CEO，也不自己擬對 CEO 的句子。下面只是技術判斷，任何需要 CEO 做的事，都經 coordinator、以風控定稿的字面提出。

1. 依程式碼，**多數情形不需要任何重啟**：
   - 主機沒開／stock-desk 沒啟動：CEO 日後依自己的習慣再啟動 `dev-up.bat` 時，scheduler 會在啟動後 3 分鐘補跑一次（週一至週五 13:30～22:10 之間啟動不設補跑，等 22:10）。我不要求改變開機習慣（RC-360）。
   - 單次 `inputs_not_ready`、`error`：下一個排程時刻（22:10／23:10）自己會重跑，不需要重啟。
2. **技術上確實需要重新執行 `dev-up.bat` 的情形**（它先 `git pull`，再停掉舊程序、重新啟動）：
   - D（舊 scheduler 還在跑），包括三種來路：接線 PR 合併後沒有重新執行；`git pull` 失敗或工作樹有 tracked 變更而在停舊程序之前就停止；對停止舊 scheduler 的提示回答 N。只有成功執行完 `dev-up.bat` 才會載入 `forecast_record` job；
   - E（一次執行卡住，`max_instances=1` 擋住後續）：需要先結束再啟動；重新執行會以 `taskkill /F /T` 結束卡住的那一次，那一筆會留下沒有 end 列；
   - checkout 未更新（貼回缺「最近一次…」那一行、且確定是接線前的 `report`）：`forecast-status.bat` 不會更新程式，只有 `dev-up.bat` 會。
3. **重啟無效的情形**：
   - `gate_closed`：記錄停止的原因在 claim 登記或程式／環境與紀錄的一致性，重啟不改變它；
   - 任何 refusal（C2）：**`STOCK_DESK_DB_PATH` 的 refusal 不是重啟能解決的**，要改的是設定，不是重啟。拿掉變數若會讓 backend 改用另一顆主 DB，那是**資料位置的決定**，須經 tech-architect 與風控、必要時由 CEO 決定；我不提議、不指示。
4. **請求字面**：coordinator 已請風控在接線 PR 合併**之前**預先定稿一則請求（涵蓋 D、E、checkout 未更新），定稿後本文件引用該定稿，不另寫字面。**定稿前**，照補充十三第 4 點 (f) 辦（尚未定稿的情形，只能重送既有的每週請求，並當天把字面送風控）。既有的 H1、H1b、H2、L1、L2、U1～U4 含有「請 CEO 不要自己重新啟動任何程式」的意旨，所以我不自己擬任何對 CEO 的句子；重啟的需求只記在處置紀錄中，向 coordinator 提出「需要重新執行」「是哪一種情形」「前提」。
5. 預測記錄期間，任何會改動環境的動作（含重啟、重裝工具、更新 `uv.lock`）之前，先通知 tech-architect（`work/dispatch/2026-11-21-缺工具時的安裝引導-內部-devops-sre.md` 第 4 節步驟 2 的同一原則；我沒有查證安裝或升級會不會改變 `runtime_json`，所以不得說「不影響紀錄」）。
