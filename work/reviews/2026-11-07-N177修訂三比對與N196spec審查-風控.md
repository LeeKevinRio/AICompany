#### 3. 3.9 第 3 點裁示：不另開單，接受為有紀錄的殘留

**事實（已讀碼）：**
- service.py:1901 讀 `list_batches()`，:1902 讀 `portfolio_state()`，各開一個連線。兩者之間沒有網路，窗口是毫秒級。
- engine 用到的 portfolio 欄位有：
  - `cash`：只用在 `_apply_cash_floor`（engine.py:1021-1027），`budget = 0.7·cash − 0.3·deployed`；
  - `total_deploy`：:1283，不受結算影響；
  - freeze、emergency、defense：由 `apply_effects` 或 EMERGENCY 寫入，結算不碰。

**推導（q：股數，p：結算價，c：收盤價，都大於 0）：**
- **sell 結算落在窗口內：**
  - 混合值 = 結算前 + 0.7qp；
  - 結算後 = 結算前 + 0.7qp + 0.3qc；
  - 所以「結算前 < 混合值 < 結算後」。
- **buy 結算落在窗口內：**
  - 混合值 = 結算前 − 0.7qp；
  - 結算後 = 結算前 − 0.7qp − 0.3qc；
  - 所以「結算後 < 混合值 < 結算前」。
- 兩種情況下，混合值都落在兩個合法循序結果之間，不會比任何循序結果更寬鬆。
- 這和 REBALANCE 不同。REBALANCE 的總資產是 cash + deployed，係數同號，所以混合值會超出兩端；這裡是異號。
- 評估本身不寫 TOTAL_DEPLOY，也不寫現金。

**條件：**
1. **（required）** tech-writer 在 ADR-0041 Consequences 的 R-3′ 之後新增一點，補完不用回我，逐字如下：「R-4′：`evaluate_today` 先讀批次、再讀現金，分屬兩個連線；兩者之間若有結算 commit，鐵律①的 budget 會落在『結算前』與『結算後』兩個循序結果之間，不比任何循序結果寬鬆，評估也不寫入現金或 TOTAL_DEPLOY，因此接受為已知殘留，不另開單（風控 2026-11-07 裁示 3.9 第 3 點）。若 budget 公式改變、或評估改為寫入由現金與持股共同算出的值，本判定失效，須改用單一讀交易並回風控審。」
2. **（required）** 上面條款裡寫的任何一種變動，都要回 TA 與我。N196-C7 已規定其他呼叫者要改用新 API 時回 TA，兩者一致。

#### 4. `confirm_rules` 與 REBALANCE 並發：要請 TA 分析（required）
