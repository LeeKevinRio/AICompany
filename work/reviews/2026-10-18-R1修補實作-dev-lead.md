## 各部門回報（dev-lead）

**實作摘要**
- 推播失敗的 log 與 `detail` 一律改成固定格式，只帶 channel、例外類別名、HTTP 狀態碼。例：`alert webhook delivery failed: channel=telegram error_class=HTTPStatusError status=404`，detail 是 `error_class=HTTPStatusError status=404` 或 `error_class=ConnectError`。detail 仍非空，失敗仍不拋出。
- 新增共用的 `configure_logging()`，API 與 scheduler 都呼叫，可重複呼叫：
  - **每次呼叫都做**：把 `httpx`、`httpcore` 壓到 WARNING（擋掉 httpx 在成功路徑記完整 URL 的那條洩漏，報告裡的 F-1）。
  - **只在 root 還沒有任何 handler 時才做**：裝 stderr handler 並掛遮蔽 filter；root 設 WARNING，`app`／`scheduler` 設 INFO；格式 `%(asctime)s %(levelname)s %(name)s: %(message)s`。正式環境（uvicorn、`python -m app.scheduler`）一定走這條。在 pytest 等已有 handler 的環境只做第一項，不會改到既有測試的 caplog 行為。
- `redact_url()` 遮四種：Telegram 的 `api.telegram.org/bot<…>`，以及任何主機上 `/bot<數字>:<…>` 形狀的 token；Discord 的 `/webhooks/<id>/***`；query 裡 `token`／`apikey`／`api_key` 的值（不分大小寫）。已遮過的字串再遮一次結果不變，沒有祕密的 URL 不會被改。
- 縱深防禦用 `SecretRedactionFilter`：輸出前先把訊息算好再遮，連 traceback（`exc_text`）與 `stack_info` 一起遮；log 呼叫格式寫錯也不會把原始參數吐出來。
- `describe_failure(exc)` 是唯一可以把例外放進 log 或 detail 的函式，N-23 告警應沿用它（報告 C-5）。

## 下一步（請 qa-reviewer 特別看）
1. **scheduler 少了 APScheduler 自己的 INFO**：原本 scheduler 是 root=INFO，所以 APScheduler 的 INFO 看得到（例如 "Running job"／"executed successfully"）。照定案 root 改為 WARNING 後這些不再輸出，scheduler 自己的 `scheduler` logger 與 `app.*` 不受影響。要不要把 `apscheduler` 加進 INFO 名單，請 CEO 或 devops-sre 決定；我沒有自己加。
2. **scheduler 輸出格式改了**：多了 `%(name)s:`。發版檢查表 grep 的是訊息本文（`failed_symbols=[1-9]` 等），不受影響。請 devops-sre 實機確認，也就是報告 D-10。
3. **「root 已有 handler 就只壓 httpx」是我自己的判斷**：理由是 lifespan 在既有十幾個 `with TestClient(app)` 測試裡都會觸發；若無條件把 `app` 設成 INFO，或把 filter 掛到 pytest 的 handler 上，會改變其他測試的 caplog 結果、造成測試順序相依。代價是：如果將來有別的程式先設定了 root，filter 不會掛上，只剩 httpx 被壓住那一層保護。
