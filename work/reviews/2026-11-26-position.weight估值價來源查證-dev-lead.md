- 日期：2026-11-26
- 轉存：coordinator，逐字轉存 subagent 最終回報

## 本次結論

以下全部是**讀程式碼推得**，沒有實際執行任何程式。

1. **`position.weight` 用的不是 `/api/advice` 自己 `load_bars` 得到的那批日線。** 它來自 portfolio summary 另外做的一次**純快取讀取**：cache-only valuator 呼叫 `get_cached_bars`，回看 10 個日曆日，取最新一根的 `close`。分子、分母都從這次讀取算出：
   - 分子：本標的已估值持倉的市值。
   - 分母：全部持倉中已估值部分的市值合計。

   兩次讀取指向同一個 SQLite 快取。`load_bars` 先執行，live 結果會 upsert 寫回快取，所以一般情況下兩邊讀到的最新一根是同一列。但這是**兩次獨立讀取，程式沒有保證兩者一致**。
2. 估值只讀最新一根的 `close`，不讀 open、high、low、volume，也不讀較早的 bar。所以：
   - **歷史日線有壞值、最新一根正常**：`position.weight` 不受影響。
   - **最新一根 low = 0 但 close 正常**：也不受影響。
   - **最新一根的 close 本身是壞值**，分兩種：
     - close 為 0、負數或非有限值：會被丟棄。這個持倉變成未估值，但 `position.weight` 會變成 **0.0，不是 None**（見發現 C）。
     - close 是正的有限值、但數值錯誤（例如單位錯、跳十倍）：**會直接汙染** `position.weight`。
   - 其他持倉的最新 close 有錯，會經由分母 `total_equity_twd` 影響本標的的比重。
3. **有守門，但只有 `usable_price` 這一道**（`portfolio/valuation.py:496-505`，判斷有限且 > 0）。外幣持倉另有 `usable_rate`（`:585`）。沒有 OHLC 一致性檢查，也沒有跳空或合理範圍檢查。

## 發現

**A. 證據鏈：分子 `position_market_value_twd`**
- `advice/limits.py:873-879`：`position_weight = position_market_value_twd / total_equity_twd`。只有在分子為 None 或分母 ≤ 0 時才回 None。
- `advice/book.py:1304`：`market_value, ... = _position_rollup(matched)`，結果在 `:1403` 填進 `position_market_value_twd`。`:1304` 到 `:1403` 之間沒有重新指派。
- `book.py:639-648`：rollup 只加總 `valuation.status == "ok"` 且 `market_value_twd` 不為 None 的持倉；其他的計入 `skipped`。
- `api/advice.py:193`：`summary = build_summary(store, valuator)`。`valuator` 依 `:67` 注入 `get_cached_valuator`。
- `api/deps.py:352-354` → `:224-237`：`PositionValuator(..., price_mode="cache_only")`，docstring 寫明依據 ADR-0010 D-1。
- `portfolio/summary.py:248-290`：`valuator.value_all(positions)`，逐筆對應到 `valuation.py:374` 的 `value_position`。
- `valuation.py:103`：`PRICE_LOOKBACK_DAYS = 10`。`:484-486`：cache_only 時呼叫 `service.get_cached_bars(symbol, market, today-10d, today)`。
- `valuation.py:495`：`latest = max(result.bars, key=date)`。`:510-517`：`price_now = latest.close`。
- `valuation.py:456`：`market_value_twd = quantity * price_now * fx_now`。
- `data/service.py:438-467`：`get_cached_bars` 只讀快取，不問任何來源。它會套用 `_cache_refuses` 的單位閘門，只回 `CACHED_STALE` 或 `UNAVAILABLE`。

**B. 證據鏈：分母 `total_equity_twd`，以及和 `load_bars` 的關係**
- `book.py:1299`：`equity, _, _ = _book_equity(summary)`，結果在 `:1402` 填入。
- `book.py:575-585` → `summary.py:160-175`：`valued_market_value_twd` 加總**全部** `ok` 持倉。所以任何一檔持倉的最新快取 close，都會進到本標的比重的分母。
- `api/advice.py:183-207`：`load_bars` 的結果只用在兩處：
  - `newest`／`latest` → `compute_signals`；
  - `close=float(latest.close)`（`:220`）→ `PortfolioContext.close`，以及 `book.py:1293` 的 `priced` 判斷。
  它**不進** `position_market_value_twd`。
- 為什麼兩次讀取一般會讀到同一列：
  - 執行順序：`load_bars`（`:183`）在 `build_summary`（`:193`）之前。
  - live 結果會寫回快取：`data/service.py:353` 呼叫 `self._cache.put(...)`，而 `data/cache.py:215-219` 是 `INSERT ... ON CONFLICT(symbol, market, trade_date) DO UPDATE`。
  - 同一程序共用同一個 cache 物件：`deps.py:58-65`。
- 為什麼不保證一致：
  - 兩次讀取的回看範圍不同（`DEFAULT_LOOKBACK_DAYS` 對 10 天）。
  - 快取那條路徑另有 `_cache_refuses` 閘門。
  - `load_bars` 的 live 回應如果沒被寫回（例如被單位閘門拒收），兩邊就可能不同。
  - 這些邊界的實際觸發頻率，這次沒有查。

**C. 對 ADR-δ S2 有影響的副作用：已持有但無法估值時，比重是 0.0 而不是 None**
- 本標的全部持倉都被 skip 時（例如最新 close 未通過 `usable_price`），`_position_rollup` 回傳 `market_value = 0.0`（`book.py:639-655`），`:1403` 原樣填入。
- 結果是 `position_weight()` = 0 / equity = **0.0**。`concentration_watch` 會被**評估成「沒命中」，而不是 skipped**。
- 唯一的揭露是 `SYMBOL_UNVALUED_NOTE`（`book.py:327`、`:1306`）。
- 上一份報告說 S2 `unusable` 時「第 12 條可評估」，這句要修正：在這種情況下，第 12 條評估出的值是假的 0，不是真的比重。
- 不過只要 `/api/advice` 自己讀到的最新 close 也不可用，就會先走 `api/advice.py:207` 和 `:230-258` 的 `insufficient_data`，卡片不會進引擎。只有兩次讀取的最新一根不一致時，這個 0.0 才會進到規則評估。

**D. 守門的實際範圍**
- `data/price_guard.py:31-48`：`usable_price` 只判斷「不是 None、有限、> 0」。docstring 第 21-22 行寫明「只判斷，不修補」。
- valuator 只判斷最新一根，不會退回用較早的 bar（`valuation.py:37-43`、`:469-471`、`:496-505`）。
- `PriceBar` 本身不驗 OHLC（上一份報告已指出：`data/interface.py:46-89` 只驗 volume、時區和空白字串）。所以 close 是正數但錯誤的值，會一路通過，進到估值。
- 外幣持倉的 `fx_now` 由 cache-only valuator 用的同一個 FX adapter 取得（`deps.py:227-235`），守門是 `usable_rate`（`valuation.py:585`）。
