## 定錨(六題共用)

- **目標**:消除文案閘門標記的「凍結範圍失真」與「資料缺漏靜默」兩類不實/不揭露風險,讓每句話
  可被獨立驗證為真;不是重新設計語氣。
- **受眾**:自用規則的使用者本人——他讀到「凍結」二字必須能準確推斷「新倉不會進,但停損停利
  照常保護我」,不能誤讀成「整個系統停擺」。
- **限制**:R13(中性事實、零評價字眼)、H-1(禁「阻止/鎖住」誇大控制語彙)、R6/S-2(資料缺漏不得
  靜默)、既有 house style(最小事實陳述、逐句附 provenance)。這六題創意自由度低——多數是「把
  失真動詞換成準確動詞」的收斂題,故以 Ogilvy(精確不誇大)+ Young(既有元素重組而非另造新詞彙)+
  Rubin(能拿掉的贅字都拿掉)三個視角做收斂判斷,不做發散式腦力激盪(對應 skill 邊界條款:任務越
  接近「取代一個字」,流程應越輕)。

## 1. VETO-1:「所有排程凍結」四處改寫 + VETO-4 併案

統一原則:凍結範圍一律寫「R 系列(新倉進場)暫停」,S/P 系列動詞固定用「照常評估」(與既有
`FROZEN_NOTE` 用字一致,不另造新動詞)。

### 1.1 `RULE_TEXT["EMERGENCY"]`

現況(不實):
```
EMERGENCY_EXIT：使用者提交全部出清，執行後所有排程凍結 20 交易日。
```

**候選 A(推薦)**
```
EMERGENCY_EXIT：使用者提交全部出清，執行後 R 系列（新倉進場）暫停 20 交易日，
S／P 系列停損停利仍照常評估。
```
**候選 B(更短)**
```
EMERGENCY_EXIT：使用者提交全部出清，R 系列（新倉進場）暫停 20 交易日；S／P 照常評估。
```
推薦 A:這一句在畫面上是「規則一覽」的其中一列,讀者可能沒有上下文,S/P 全稱寫出比縮寫更不會被
誤讀成另一個代號。— 待風控覆審

### 1.2 `EMERGENCY_EXIT_RESULT`(併 VETO-4)

現況(不實 + 缺 VETO-4 要求的進度資訊):
```
EMERGENCY_EXIT 已執行：出清 {batches} 批、共 {shares} 股；所有排程凍結至 {until}。
```

**候選 A(推薦,新增欄位 `{frozen_day}`,凍結進度與迄日並列)**
```
EMERGENCY_EXIT 已執行：出清 {batches} 批、共 {shares} 股；
R 系列（新倉進場）暫停中（第 {frozen_day}/20 交易日，依交易日曆），預計 {until} 恢復；
S／P 系列停損停利仍照常評估。
```
**候選 B(迄日提到前段,句序貼近舊句習慣)**
```
EMERGENCY_EXIT 已執行：出清 {batches} 批、共 {shares} 股；
R 系列（新倉進場）暫停至 {until}（第 {frozen_day}/20 交易日，依交易日曆計算）；
S／P 系列停損停利仍照常評估。
```
推薦 A:VETO-4 原文要求「第 N/20 交易日」與「凍結迄日」並列(兩者同時可見,不是其中一個取代另一
個),A 版把「暫停中(第.../20)」與「預計{until}恢復」拆成兩個並列子句,比 B 版把交易日數塞進
括號裡更符合「並列」而非「附註」的字面要求。`{frozen_day}` 為新欄位,實作口徑(以資料日或執行日
計算第幾個交易日)請 backend-engineer 依 `TradingCalendar` 對齊,並與規則版本一覽表的紀錄一致。
— 待風控覆審

### 1.3 `EMERGENCY_EXIT_EMPTY`

現況:
```
EMERGENCY_EXIT 已執行：目前無持有批次；所有排程凍結至 {until}。
```

**候選 A(推薦,與 1.2 同句型)**
```
EMERGENCY_EXIT 已執行：目前無持有批次；
R 系列（新倉進場）暫停中（第 {frozen_day}/20 交易日，依交易日曆），預計 {until} 恢復；
S／P 系列停損停利仍照常評估。
```
**候選 B(去除 S/P 子句,因本次出清後已無部位可評估)**
```
EMERGENCY_EXIT 已執行：目前無持有批次；
R 系列（新倉進場）暫停中（第 {frozen_day}/20 交易日，依交易日曆），預計 {until} 恢復。
```
推薦 A,但附一則邊界提醒供風控裁決:「目前無持有批次」指本次出清當下的持股狀態,不代表整個
凍結 20 交易日期間都不會有 S/P 可評估的部位(例如若使用者之後另以書面規則修改新增其他標的的
既有部位認列,或帳戶原本就有其他未被本次 EMERGENCY_EXIT 觸及的持倉子集——依 EX-6 EMERGENCY_EXIT
是全組合出清,理論上執行當下應無殘留部位,若引擎保證這點,B 版更準確;若引擎不保證(例如 MISSED
未成交殘留),A 版才是真話)。**這句該用 A 或 B,取決於 EMERGENCY_EXIT 是否保證同日全數出清無殘留
——此為事實查核題,非文案裁量題,交 backend-engineer 依引擎行為回答後風控再定版本。**

### 1.4 `MODE_REASON_EMERGENCY`

現況:
```
緊急出清後凍結：所有排程凍結至 {until}。
```

**候選 A(推薦)**
```
緊急出清後凍結：R 系列（新倉進場）暫停至 {until}；S／P 系列停損停利仍照常評估。
```
**候選 B(不含日期以外資訊,供風控認為此欄位應與 1.1~1.3 分層、只需極簡狀態標籤時使用)**
```
緊急出清後凍結：R 系列（新倉進場）暫停至 {until}。
```
推薦 A,與 `FROZEN_NOTE`("全凍結"模式的既有句)採同一句型「範圍暫停 + S/P 照常評估」對齊,避免
使用者看到 `MODE_REASON_FROZEN` 與 `MODE_REASON_EMERGENCY` 兩種凍結狀態下,一個講清楚 S/P 範圍、
另一個不講,產生「這兩種凍結是不是不一樣」的誤讀。— 待風控覆審

## 2. EXIT 確認核取句 2、3 修正版

背景:`work/stock-desk-快市排程-文案起草.md` 版本 1 的 Step 2 核取句 2 現況(VETO-1 點名的「四處」
之外,另計的第五處失真):
```
□ 執行後，所有排程動作將凍結 20 個交易日（預計恢復日：{FREEZE_UNTIL}，依交易日曆計算）。
```
核取句 3 現況(範圍已對,但動詞未對齊 VETO-1 指定的「照常評估」):
```
□ 凍結期間內，S／P 系列規則（停損／停利）仍正常運作；僅 R 系列（新倉進場）暫停，
   且凍結期間仍可再次執行全部出清。
```

**候選 A(推薦——維持兩句分工,各自修正,改動最小)**
```
□ 執行後，R 系列（新倉進場）暫停 20 個交易日（預計恢復日：{FREEZE_UNTIL}，依交易日曆計算）。

□ 凍結期間內，S／P 系列（停損／停利）仍照常評估；凍結期間仍可再次送出全部出清。
```
候選 A 把「僅 R 系列暫停」這件事一次講清楚就放在句 2(講時長的同一句),句 3 不再重複「僅 R 系列
暫停」,只承接「S/P 照常評估」+「可再次 EXIT」兩件事,避免同一畫面連續兩句都出現「僅 R 系列」
造成閱讀疲乏(Rubin 減法)。

**候選 B(合併成一句,供風控認為四句核取太密、應再收斂成三句時使用)**
```
□ 執行後，R 系列（新倉進場）暫停 20 個交易日（預計恢復日：{FREEZE_UNTIL}，依交易日曆計算）；
   凍結期間內 S／P 系列（停損／停利）仍照常評估，且可再次送出全部出清。
```
推薦 A。理由:視覺規範 §4.3 既定版式是「一核取句一事實」,B 版把時長、範圍、S/P 狀態、可再 EXIT
四件事塞進一句,雖然總字數較省,但違反視覺規範既定的「一句一事實」骨架,若要採 B 需先回 art-lead
確認版式跟著改;A 版不動版式只改字面,交接成本較低。兩版動詞皆已對齊 VETO-1 的「照常評估」。
— 待風控覆審(含是否需要 art-lead 同步覆核版面)

## 3. `RULE_TEXT["S2"]` 補句(黑名單期間 S/P 仍評估)

依 S-3「黑名單只封買進,殘留持倉 S/P 活躍明文」。S2 本身是「出清整檔」,但出清指令若當日
MISSED(跌停/無量)未成交,殘留批次會落入 60 交易日黑名單期間,此時不能讓使用者誤以為黑名單期間
連殘留批次的停損停利都停了。

現況:
```
S2 整檔停損：收盤 < 該檔均成本 ×0.85 出清整檔，並列入黑名單 60 交易日。
```

**候選 A(推薦,原句加半句,不拆兩句)**
```
S2 整檔停損：收盤 < 該檔均成本 ×0.85 出清整檔，並列入黑名單 60 交易日；
黑名單期間僅停止新增買進（R 系列），若有未出清批次殘留，S／P 系列仍照常評估。
```
**候選 B(拆成獨立第二句,強調範圍是「規則本身」而非「事後附註」)**
```
S2 整檔停損：收盤 < 該檔均成本 ×0.85 出清整檔，並列入黑名單 60 交易日。
黑名單期間僅停止新增買進（R 系列）；若有未出清批次殘留，S／P 系列停損停利仍照常評估。
```
推薦 A,與其他 `RULE_TEXT` 條目(單句陳述完整規則)格式一致,B 版拆兩句在這個欄位(規則一覽表的
一格)會破版,除非確認呈現位置允許多行。「若有未出清批次殘留」為誠實限定語,不是弱化——沒有殘留
時這句自然不成立,不构成過度承諾。— 待風控覆審

## 4. `DATA_GAP_NOTE` 附加句(持倉時停損無法評估,顯著揭露)

依 S-2「資料缺漏致停損無法評估須主動顯著揭露不得靜默」。現況:
```
{symbol} 資料狀態為 {status}（來源 {source}），依鐵律⑤當日不產生指令。
```
此句只講「沒有指令」,沒講「如果你剛好持有這檔,你的停損保護今天沒被檢查」——這正是最需要被看見
的風險,不能被「不產生指令」這種中性措辭蓋過去。

**候選 A(推薦,沿用 `REBALANCE_OVERSHOOT_WARNING` 已有的【標記】前綴慣例做顯著揭露,僅在有持倉
時渲染)**
```
【停損今日無法評估】{symbol} 資料狀態為 {status}（來源 {source}），依鐵律⑤當日不產生指令；
本檔目前持有部位，停損（S 系列）今日無法依規則評估。
```
**候選 B(不用前綴標記,純句尾附加,供風控認為【】標記在此欄位過重時使用)**
```
{symbol} 資料狀態為 {status}（來源 {source}），依鐵律⑤當日不產生指令；
本檔目前持有部位，停損（S 系列）今日無法依規則評估。
```
推薦 A。理由:R6/S-2 的「顯著揭露」在既有程式碼裡已有先例(`REBALANCE_OVERSHOOT_WARNING` 用
【超額】做視覺標記),沿用既有標記語彙比另創新樣式風險低,且與 H-1(禁誇大控制語彙)不衝突——
【停損今日無法評估】是陳述「評估這件事沒發生」,不是「危險/警告」這種評價字眼。兩版都刻意不寫
「請留意」「請注意」之類提示詞,避免落入 R13 禁止的勸阻/催促語氣。渲染條件(僅該 symbol 當下有
未出清部位時附加)為實作邏輯,交 backend-engineer。— 待風控覆審

## 5. `{RULE_SET_DATE}` 缺值時的替代句(歸屬語 A 版 fallback)

VETO-2 已裁定歸屬語逐字採 A 版:
```
此指令是你於 {RULE_SET_DATE} 自行設定的規則之機械執行結果，非本系統的判斷或建議。
```
邊界情境:帳戶剛啟用、規則沿用系統預設值、尚無使用者本人明確設定/修改紀錄時,`{RULE_SET_DATE}`
沒有值可填——不能留空、不能省略,也不能編一個假日期。依 house style「資料缺漏不得靜默」的既有
慣例(`DATA_GAP_NOTE`/`SETTLEMENT_NO_OPEN_PRICE` 皆是「講出狀態,不是留白」),替代句同樣要把
「沒有這個日期」講成一個可查證的事實,而不是悄悄把整句改寫成「聽起來一樣但少了一個要素」。

**候選 A(推薦,明講缺值狀態,三要素中「日期」換成「缺值揭露」而非省略)**
```
此指令是你設定的規則之機械執行結果，非本系統的判斷或建議
（規則設定日期缺漏：{RULE_SET_DATE_STATUS}）。
```
**候選 B(改錨定「版本」而非「日期」,不揭露缺值原因,句型更貼近 A 版原句節奏)**
```
此指令是你設定的規則（目前生效版本）之機械執行結果，非本系統的判斷或建議。
```
推薦 A。理由:B 版把「沒有日期」這件事悄悄消音,讀者無從分辨這是「本來就沒有日期欄位設計」還是
「日期資料出了問題」,與 R6/S-2「缺漏不得靜默」的精神不一致,即使 R2 本身管的是歸屬語而非資料
缺漏規則,但**同一份文件的兩類 required 不該互相矛盾**——A 版把缺值狀態本身變成可見事實,呼應
`DATA_GAP_NOTE` 既有寫法(「資料狀態為 {status}」)。`{RULE_SET_DATE_STATUS}` 建議值域限定為受控
字串集(呼應 `MODE_REASON_FROZEN` 的 `{reason}` 限受控字串集要求),例如「尚無使用者設定紀錄，
沿用系統預設規則」,不得自由文字。此為 R2 覆審範圍外的新邊界情境,**是否要在 R2 的三要素框架內
另立第四類（缺值型）,還是判定此情境下歸屬語整句不得顯示、改顯示其他中性說明,屬於覆審裁量,
本節僅供裁量時的候選文字。**— 待風控覆審(建議與 VETO-2 本題一併覆審,非獨立小題)

## 6. 拒絕模板 vol 不可得時的替代句(不得「—%」)

現況(`service.py` 呼叫端把 `vol=None` 轉成 `"—"`,組出 `20 日年化波動率 —%`,違反閘門「vol 不可得
時禁『—%』」):
```
目前符合快市條件（20 日年化波動率 {vol}%、近 {lookback} 交易日有 {moves} 日 |漲跌幅| ≥2%）；
快市期間規則不放寬。
```
背景:快市判定本身是「波動率門檻」或「異動天數門檻」任一成立即觸發(`service.py` 的
`fast_market_vol > threshold or fast_market_moves >= count`),所以 vol 缺值時,句子仍可能是因為
異動天數門檻成立而觸發,不能因為 vol 沒有值就整句不顯示或硬填「—%」。

**候選 A(推薦,vol 缺值時整句改用「異動天數」單一門檻陳述,不假裝有波動率數字)**
```
目前符合快市條件（近 {lookback} 交易日有 {moves} 日 |漲跌幅| ≥2%；
20 日年化波動率資料暫缺，本次未採用波動率門檻）；快市期間規則不放寬。
```
**候選 B(保留兩個子句並列,但把「缺值」寫成一個可查證的狀態詞而非數字)**
```
目前符合快市條件（20 日年化波動率：資料暫缺；近 {lookback} 交易日有 {moves} 日
|漲跌幅| ≥2%）；快市期間規則不放寬。
```
推薦 A。理由:B 版仍把「資料暫缺」塞進原本放百分比數字的位置,版面上容易被一眼掃過當成「有填東西
就好」,失去揭露的作用;A 版把「本次到底是靠哪個門檻觸發」講清楚(異動天數門檻成立、波動率門檻
未採用),資訊量更貼近判定邏輯本身,也讓「快市期間規則不放寬」這個結論有明確依據可查,不是純粹的
